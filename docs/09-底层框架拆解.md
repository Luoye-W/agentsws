## 0. 四条硬要求怎么落成设计原则

| 要求 | 原则 | 具体做法 |
|---|---|---|
| 符合 DSH 规范 | **我们的内核用 dsh 同一套插件模型** | 协同服务本身跑在 Cordis 容器里（dsh vendored 的就是它）：每个模块是插件，`inject` 声明依赖、`provide` 提供服务、Schemastery 校验配置、`ctx.effect()` 管回收、类型化事件。"Plugins, not loop changes"、"Model-visible ⟺ logged"、数据格式"并排发新版永不就地改写"、每文件 100% 覆盖，四条原样采用 |
| API 化 | **只有一个入口，所有客户端平等** | 协同服务对外只有一个 API 网关（HTTP + JSON-RPC + 事件流 WebSocket，OpenAPI 自动生成）。桌面 App、工作台、飞书卡片、CLI、dsh-adapter、付费插件、Claude Code 都是它的客户端；没有任何"UI 特权路径"。内部模块之间也只经服务契约调用，不共享数据库表 |
| 全流程模拟 | **外部边界全部可替身，内核一行不改** | 四类外部依赖（provider、模型、人、时钟）各有一个替身实现，与真实实现遵守同一契约；模拟 = 用替身配置启动同一套内核，喂合成公司数据与场景脚本，跑完出报告 |
| 插拔 | **契约 + 一致性套件 + 版本化清单** | 每个模块 = 一份契约（TypeScript 接口 + 事件 + 错误码，semver）+ 一套一致性测试（任何实现都要过）+ 至少两个实现（默认 + 替身）。换实现 = 换插件；升级 = 过一致性套件 + 过模拟 |

## 3. 模拟测试回路（对应画布第二张）

### 3.1 组成

| 件 | 内容 |
|---|---|
| 场景 DSL | 沿用 Commerce Agents 的 case 形状：`state + events[] + expected`，扩展 `clock`（时间推进）、`actors`（合成人的策略）、`invariants`（全程不变量）。一条场景 = 一段公司生活："周一 9 点客户来信 → 草稿 → 客服 10:05 批准 → 发出 → 客户 14:00 回信 → …" |
| 合成公司数据集 | 一家 3 人跨境公司的完整数字孪生：工作区、人、职责分配、店铺、商品、客户、订单、邮件线程、红人、知识库、策略层额度。生成器可参数化（规模、语言、行业），带固定 seed 可复现。**这份数据集同时是 demo 数据、上手引导数据和回归基线** |
| 四个替身 | **合成 provider**：mock OpenConnector，Shopify / Gmail / Meta / Klaviyo 的假 executor 维护内存状态，写操作真的改状态（退款后订单状态变），可注入故障（限流、超时、429）；**合成模型**：三档——确定性 stub（按规则出草稿，秒级）、录制回放（真模型的响应缓存）、真模型 pin seed（eval 用）；**合成人**：审批策略机器人——总是批准 / 30% 编辑 / 按规则驳回 / 慢响应，用来驱动采纳率、升级、L1→L3 晋级；**合成时钟**：可快进，一天的公司生活几秒跑完，调度器与升级时长都吃它 |
| 真实内核 | **同一份代码、同一份二进制**，只换配置把外部边界指向替身。模拟里跑的就是生产内核，这是"不只是 CI 全绿"的前提 |
| 观测与断言 | 不变量：没有 stage 就没有写、写只在 apply、apply 前必有 approved、provenance 命中、fencing 覆盖所有外部文本、**每一条进模型的输入都能从事件日志重建**（Model-visible ⟺ logged 的自动校验：回放事件日志重组 prompt，与实际发送的逐字节比对）。指标：采纳率、干预率、guardrail 命中、队列时延、token 成本、知识缺口数、L 等级变化 |
| 报告与门禁 | 三档运行：**fast**（stub 模型 + 内存存储，每次提交跑，分钟级）、**realistic**（回放模型 + SQLite，每日跑）、**soak**（合成时钟快进 30 天，看晋级、衰减、健康度，每周跑）。产出一份模拟报告；合并门禁 = fast 全过 + 指标不劣化 |

### 3.2 它替我们回答的问题

- "L1→L3 的晋级规则设对了吗" → soak 跑 30 天看有没有误晋级
- "这版 skill 比上版好吗" → 同一场景集、同一合成人，比采纳率
- "换了 OpenConnector 版本内核还对吗" → 一致性套件 + realistic 全过
- "3 人公司 Join 进 15 人部门数据对不对" → Join 场景：两份合成数据集合并，断言去重与权限
- "断网 / 模型挂了会不会乱发" → 故障注入场景：断言队列冻结、无自动发送

## 5. 又发现的没考虑到的（框架层）

1. **数据格式的版本策略**：事件、审批项、变更、职责定义都要像 dsh 会话那样"并排发新版、永不就地改写"，读旧版靠迁移器；第一阶段就定，否则模拟数据集一改格式全废
2. **可观测性贯穿**：一次运行 → 工具调用 → OpenConnector `executionId` → apply → 投递，要一条 trace 串起来（OpenTelemetry）；没有它，模拟报告里"为什么这条没发出去"答不了
3. **托管档的租户模型**：一个 runtime 一个工作区（简单、隔离好、每租户三个 sidecar）还是一个 runtime 多工作区（省资源、数据层要全带 workspace_id）。共享数据层的 scope 字段已经要求带，所以两者都能走，但**进程模型第一阶段要定**：倾向一工作区一 runtime，托管档用容器编排
4. **预算与熔断在内核层**：每次运行的 token / 工具调用 / 时长预算，每工作区的日预算，超了停；急停开关一个变量全关。模拟回路要有"预算耗尽"场景
5. **时间与时区**：跨境公司客户在多个时区，升级时长按谁的工作时间算、调度按哪个时区——共享数据层每条记录带时区，工作区有默认时区
6. **删除与遗忘**：事件日志 append-only 与 GDPR 删除请求冲突——用加密分片（crypto-shredding）：个人数据加密存，删除 = 销毁密钥。第一阶段定下，晚了改不动
7. **降级规则**：模型挂 / provider 挂 / OpenConnector 挂时，队列冻结、L2/L3 自动降回 L1、通知 owner；这是不变量之一，进模拟
8. **插件签名与来源**：teamai 的教训——拉取永不自动执行代码；第一阶段把"插件清单 + 签名校验 + 允许源"做进内核装载器，哪怕第一阶段只有我们自己的签名
9. **桌面壳的进程模型**：三个 sidecar（协同服务、dsh、OpenConnector）的端口、健康、重启、日志、更新顺序，是真实的工程量，之前只写了"打包成桌面 App"
10. **合成人的真实性**：审批机器人太理想会让晋级规则看起来都对；要从 KefuAgents 现有用户的真实审批行为里抽分布（编辑率、响应时长）做参数

## 7. dsh-channels 与 OpenConnector 不是同一个角色（09-08 补）

§1 总图脚注把两者并列写在"上游位置"里，读起来像同一件事。它们对应的是**两份不同的契约**：

| | dsh-channels | OpenConnector |
|---|---|---|
| 抽象的是什么 | **对话渠道**：一个人在某个平台上和 Agent 一来一回的消息流 | **系统动作**：对某个业务系统的一次请求 / 响应调用 |
| 契约形状 | `ctx.channels`：能力协商（文本 / 图片 / 文件 / 卡片 / 线程 / 流式）、`start / stop / send / createReply / beginAuth / getHealth`、平台原始消息映射为结构化 `MessagePart` | `execute_action(actionId, input, connection)`：类型化输入输出 schema、scope、幂等键、run log |
| 方向 | 入站 + 出站，且出站是"在这段对话里回复" | 只有出站调用（读到的文档里没有 webhook 接收、轮询、事件流） |
| 状态 | 有会话概念：每渠道账号一个工作区，扫码登录态 | 无会话，无流式，无卡片 |
| 住在哪 | dsh 进程内的插件 | dsh 进程外的独立 runtime |
| 覆盖 | 微信 / QQ / 钉钉 / 飞书 / Telegram 这类 IM | 1000+ SaaS API：Shopify、Klaviyo、Google Ads、Zoom、Recall.ai…… |
| 对应我们的契约 | #9 入站、#14 投递（对话类） | #8 Connect |

**为什么不能把工具连接塞进 dsh-channels**：它的契约表达不了"查订单""建折扣码""拉分析数据"——那不是消息，是带 schema 的动作；而且它住在 dsh 进程里，我们的执行器在审批通过后 apply 时**没有 dsh**（03 §1.3），必须能在进程外调用。反过来也不能把对话塞进 OpenConnector：它没有入站、没有会话、没有流式、没有卡片。

### 7.1 分工规则

| 这件事是…… | 走哪条 | 例子 |
|---|---|---|
| 一个人发来的消息，要变成 Agent 的一轮 | **渠道**（dsh-channels 契约的适配器 + 我们的入站层做去重 / 队列 / 重试） | 客户邮件、WhatsApp 会话、飞书群里 @Agent、个人微信 |
| 在这段对话里回复 | **渠道 `send`**（线程、回复引用、24h 窗口这些语义在渠道层才对） | 回客户邮件、回 WhatsApp |
| 对业务系统的读或写 | **OpenConnector Action** | 读订单、stage 退款、建 Klaviyo 分群、发 Instagram 帖子、查 GA |
| 非对话式的批量 / 定时发送 | **OpenConnector Action** | Klaviyo campaign、WhatsApp 模板首触序列 |

### 7.2 重叠区怎么不重复：邮件、WhatsApp、飞书

三者既是渠道又有 API。规则：**渠道适配器拥有"收"和"回复语义"，凭据与原始 HTTP 调用尽量委托给 OpenConnector**。

```
邮件渠道适配器（dsh-channels 契约）
  ├─ 入站：IMAP 轮询 / Gmail push → MessagePart → 我们的入站层 → 事件
  └─ send()：组装回复（In-Reply-To、线程）→ 调 OpenConnector 的 gmail.send_message / smtp
                                              ↑ 凭据只在 OpenConnector 里，一次授权两边用
```

这样一个邮箱只授权一次；渠道层不碰 token；OpenConnector 没有的 provider（通用 IMAP / SMTP）由渠道适配器自带实现，同时作为 provider 贡献回 OpenConnector。

### 7.3 与"无状态运行"的关系（重要）

dsh-channels 的原生模型是"渠道消息 → dsh 自己开会话"。在**公司实例**里我们不让它这么做：入站层收消息 → 事件 → RunRequest → dsh-adapter 起 headless run，路由权在协同服务（03 §1.2 已定）。所以公司实例采用的是 dsh-channels 的**契约与适配器代码**，不采用它的会话路由。

在**个人实例**里它可以按原生方式跑：个人微信 / WhatsApp 扫码登录态、每账号一个工作区、原生 dsh UI——这正是 03 §7.4 里"个人身份渠道留本机"的技术形态。

### 7.4 上游贡献因此分两条线

| 上游 | 我们贡献什么 | 为的是哪份契约 |

| dsh-channels | WhatsApp Business、邮件（IMAP / SMTP）两个渠道适配器；审批卡片回调 | #9 入站、#14 投递 |
