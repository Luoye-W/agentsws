## 0. 一句话

**上游更新 → 我们审过、签名 → 发到「内容更新通道」（不等软件发版）→ 用户那边出一张卡「X 有新版 · 官方某日更新 · 已审」，点了才换（或设成「已审的自动更新」），随时一键退回；用户自己改过的段不会被冲掉。** 改到程序本身的，仍然跟软件版本走（左下角更新按钮，WP218）。

## 1. 两类：按「谁装的」分

| | 第一类：随软件带的 | 第二类：用户自己装的 |
|---|---|---|
| 例子 | `packages/skills/bundled/` 里的第三方技能（Shopify 官方技能、从 marketingskills 改写的那几份）、职责 yml 里引用的第三方内容 | 以后从技能市场 / 一个网址装进来的技能 |
| 谁发现新版 | **我们**：每周上游例程（`upstream-watch.yml`） | **用户端**：自己探测上游 |
| 谁审 | **我们**：Fable 照 docs/42「内容更新」一节 | **用户本人**：卡上写清改了什么、有什么风险 |
| 怎么到用户手里 | 签名的内容包 → 内容更新通道 | 用户点头才更新 |
| 用户能做什么 | 每次问我（默认）/ 已审的自动更新；查看改动；一键退回 | 点头 / 不要；锁版本；退回 |
| 本单 | **实现** | **只写规范**（§8） |

两类共同的一条：**用户 / 学习回路对技能的修改（上层）不被官方更新冲掉**——新版基础层与上层改动三方合并，真冲突出卡让人选（§6.3）。

## 2. 分界线：什么算内容、什么必须随程序

内容更新通道只送**声明式的文字**——给模型读、给人看的东西。会被执行的、会改变程序行为的，一律跟软件版本走。

| 算内容（可以走内容更新通道） | 必须随程序（跟软件版本走） |
|---|---|
| 技能正文 `SKILL.md`、参考 `references/*.md`、考题 `evals/evals.json`、我们的旁注 `AGENTSWS.md` / `agentsws.json`、许可证 `LICENSE` | 任何脚本与可执行文件（`.js` `.mjs` `.ts` `.sh` `.py` `.exe` …）、`scripts/` `hooks/` 目录（Shopify 官方的 `scripts/*.mjs` 会上报用户原话，WP216 本来就没收） |
| 职责 yml 里**挂哪些技能**（格式已定，§3.3） | 职责 yml 的自动化档位、权限、范围、阈值、出卡规则（这些是安全底线，改了要过模拟与测试） |
| | `package.json`、依赖、原生模块、MCP 服务的版本（走 docs/42 的 runtime-dep 流程） |
| | 契约（`packages/contracts`）、路由、界面 |

机器怎么守这条线：内容包里每个文件的路径都过 `contentPathProblem`（`packages/skills/src/content-pack.ts`）——只许 `.md` `.json` `.txt` `.yml` `.yaml` 与 `LICENSE` / `NOTICE` / `COPYING`；不许隐藏文件、`..`、绝对路径、`scripts/` `hooks/` `node_modules/`、`package.json`。**打包时**过不了就不打，**用户端**清单里出现一个过不了的路径就**整包拒收**。单个文件上限 1 MB、单个条目上限 4 MB（声明式内容不该这么大，超了就是包打错了）。

## 3. 内容包格式

### 3.1 布局

一个内容包 = 一份清单 + 它的签名 + 一堆按 sha256 命名的文件。

```
dl.agentsws.com/content/<渠道>/                        （主源：R2 桶 agentsws-downloads 的 content/ 前缀，与 WP218 同一个桶）
  content-manifest.json                                清单
  content-manifest.json.sig                            对清单原始字节的 ed25519 签名（base64）
  blobs/<sha256>                                       每个文件一份，按内容命名，永不改写

github.com/Luoye-W/agentsws/releases/tag/content-<渠道>  （镜像：每个渠道一条滚动的 Release，平铺）
  content-manifest.json
  content-manifest.json.sig
  blob-<sha256>
```

渠道与软件更新同一口径：`stable` / `beta`，按软件版本号定（带 `-beta.N` 的是 beta，`contentChannelOf`）。主源连不上 / 被拒才试镜像（§4.4）。

### 3.2 清单（`content-manifest.json`）

| 字段 | 是什么 |
|---|---|
| `schema` | `agentsws.content-manifest/1`。读不懂的大版本整包不收（「要先更新软件」） |
| `channel` | `stable` / `beta`，必须与这台的渠道一致 |
| `serial` | **只增**的序号（发版流水线缺省用当前秒数）。用户端记住见过的最大值，比它小的当旧包（防有人拿旧包回放） |
| `created_at` | 打包时间 |
| `min_app_version` | 整包要求的最低软件版本，不满足整包不收 |
| `key_id` | 用哪把钥匙签的（公钥 sha256 前 16 个十六进制字符） |
| `items[]` | 条目，见下 |

每个条目：

| 字段 | 是什么 |
|---|---|
| `id` | `<kind>:<名字>`，例如 `skill:shopify` |
| `kind` | `skill`（本单实现）/ `role` / `declarative`（§3.3） |
| `name` / `version` | 技能名 / 版本号（技能取 frontmatter 的 `version`，与随软件带的那一版同一口径比大小） |
| `title` / `summary` | 中英各一句：卡上的名字、一句改了什么 |
| `upstream` | 来源上游：`upstreams.yml` 的 id、仓库、tag、**提交**、官方发布日期（卡上写「官方某日更新」）、许可证 |
| `review` | **审核记录摘要**：审核人、日期、许可证前后、扫描命中条数与规则、旁注是否对得上、测试是否全过、提案路径 |
| `platforms` | 只落到建站平台是这几个的品牌（§6.4）；不写 = 所有品牌 |
| `min_app_version` | 这一条要求的最低软件版本，不满足**只跳过这一条**（设置里显示「要先更新软件」） |
| `files[]` | 每个文件：相对路径、sha256、大小 |
| `sha256` | 条目摘要：按路径排序的 `path\tsha256\n` 拼起来的 sha256 |

### 3.3 条目种类

| kind | 是什么 | 用户端 |
|---|---|---|
| `skill` | 一个技能目录（`SKILL.md` + 参考 + 考题 + 旁注 + 许可证）。WP216 那种「官方原样收录 + 旁注」的目录原样适用：用户端把条目摊成目录后用同一个 `readBundledSkill` 读，有 `agentsws.json` 就按 WP216 的拼法拼 | **本单实现** |
| `role` | 一份职责 yml。**只许改「挂哪些技能」**（`skills:` 那一段）；用户端拿新旧两份比，别的字段有一处不同就整包拒收（档位、权限、范围、阈值属于程序，§2） | 格式已定；用户端以后随某个软件版本支持，那之前打包脚本不打 `role` 条目、用户端遇到就跳过这一条 |
| `declarative` | 其它声明式内容（例：平台套件里的教程文字） | 同上 |

## 4. 签名与校验

### 4.1 怎么签

- 算法 **ed25519**；签的是**清单文件的原始字节**——用户端先验签、再解析，不存在「解析后再序列化对不上」的问题；
- 文件不单独签：清单里有每个文件的 sha256，签了清单就等于签了全部文件；
- 实现在 `packages/skills/src/content-pack.ts`（`buildContentPack` / `verifyContentManifest` / `verifyContentItemFiles`），打包脚本、用户端、测试共用这一份。

### 4.2 钥匙

| | 在哪 | 谁管 |
|---|---|---|
| **私钥** | **只在发版流水线里**：GitHub Actions secret **`CONTENT_SIGNING_KEY`**（PKCS#8 PEM）。仓库里只有这个名字 | Luoye 生成、Luoye 填 |
| **公钥** | 内置在应用里：`packages/contracts/src/content-updates.ts` 的 `CONTENT_SIGNING_PUBLIC_KEYS`（`key_id` + 32 字节原始公钥 base64） | 随软件版本发 |

- **现在公钥表是空的** → 用户端不接受任何内容包，设置里照实写「这个版本还没装验签钥匙，内容更新先关着」。这是 fail-closed。
- 生成：Luoye 在自己电脑上跑 `node scripts/content-keygen.mjs --out <仓库外的路径>`——私钥只写进那个文件（权限 600，不打印；路径在仓库里直接拒），屏幕上只打印公钥那一行；然后 `gh secret set CONTENT_SIGNING_KEY < <那个文件>`，把公钥那行加进 `CONTENT_SIGNING_PUBLIC_KEYS`，私钥文件进密码管理器 / 离线备份后删掉。
- **换钥**：先把新公钥**加**进表随一个软件版本发出去 → 等大多数人升上来 → 换 secret 用新私钥签 → 再下一个版本把旧公钥删掉。表允许同时有几把。
- **私钥泄漏**：立刻删 secret、停发内容包；下一个软件版本把那把公钥从表里删掉（这一步只能随软件版本走——这正是公钥内置的代价，也是它的保证：没有任何远端配置能让应用信任一把新钥匙）。
- 测试用的钥匙对一律**现生成**（`generateKeyPairSync('ed25519')`），不入库、不复用。

### 4.3 登记表 `content-reviews.json` 与审核记录

仓库根的 `content-reviews.json` 列出**哪些随软件带的第三方内容走内容更新通道**，每条带一串审核记录。发版流水线只打「**当前目录的条目摘要 = 最新一条审核记录的 `sha256`**」的条目——**签出去的就是审过的那一份**；没审过、审完又改过、版本号对不上、扫描命中没逐条放行的，一律不打（列进作业摘要，发版不红）。

```json
{
  "id": "skill:shopify",
  "kind": "skill",
  "path": "packages/skills/bundled/shopify",
  "upstream_id": "shopify-ai-toolkit",
  "title": { "zh": "Shopify 官方技能", "en": "Shopify official skill" },
  "platforms": ["shopify"],
  "reviews": [
    {
      "version": "1.18.0",
      "sha256": "<条目摘要，提案里给>",
      "reviewer": "Fable",
      "reviewed_at": "2026-10-12",
      "upstream": { "repo": "Shopify/Shopify-AI-Toolkit", "tag": "v2.2.0", "commit": "<sha>", "published_at": "2026-10-10" },
      "license": { "before": "MIT", "after": "MIT" },
      "notes_ok": true,
      "tests_ok": true,
      "scan_accepted": [{ "rule": "exfil-telemetry", "path": "SKILL.md", "match": "log_skill_use", "reason": "正文在说那几个脚本，旁注第 1 条已禁" }],
      "summary": { "zh": "Liquid 参考补了 section 渲染的写法", "en": "Liquid reference: section rendering" },
      "proposal": "docs/upstream/proposals/2026-10-12-skill-shopify-v2.2.0.md"
    }
  ]
}
```

- `pending_merge`：那一条还在别的工作单分支上（目录还不在），打包时跳过；合进来之后删掉这一格（`skill:shopify` 在 WP216 合进主干后已删）。
- 许可证变了（`before ≠ after`）必须写 `license_note`（还能不能原样分发；不能就改成「首次使用时从官方下载」，WP216 `PlatformSkillSource.install` 的 `download`）。
- CI 里 `node scripts/content-pack.mjs check` 查登记表的形状。

### 4.4 用户端收包的规矩（顺序即判断顺序）

1. 取清单与签名（主源 → 不行再镜像）；
2. **验签**：对不上内置公钥里的任何一把 → 拒（`bad_signature`）；表是空的 → 通道关着（`no_keys`）；清单写的 `key_id` 与签的钥匙不一致 → 拒；
3. 解析、查格式（`schema`、字段、路径分界线、大小上限、条目摘要与文件列表一致）；
4. 渠道一致、序号不比见过的小、整包最低版本满足；
5. 下载本机还没有的文件，**全部条目的全部文件在内存里验完 sha256**——**任一不对，整包拒收，什么都不写**；
6. 全对才落盘（`blobs/` 按内容存、`trees/` 摊开），记下序号与这份清单；
7. 再按品牌判（§6）。

拒收给人话（`CONTENT_REJECT_TEXT`），设置里那一行常显：

| 原因 | 设置里写 |
|---|---|
| `no_keys` | 这个版本还没装验签钥匙，内容更新先关着。 |
| `bad_signature` | 这次的更新包签名对不上，没收，照旧用现在这一版。 |
| `bad_hash` | 有个文件下载下来和清单对不上，整包没收，照旧用现在这一版。 |
| `bad_path` | 更新包里有不该有的文件（只许技能这类说明文字），整包没收。 |
| `app_too_old` | 这批内容要更新的软件版本才收得下，先更新软件。 |
| `fetch_failed` | 这次没连上更新源，过几个小时再试。 |

（全表见代码。）安全类的拒收（签名、哈希、路径）另记事件 `content_update.rejected`。

## 5. 全流程

```
上游出新版
  │ ① 发现：每周上游例程（upstream-watch.yml 周报那一趟）
  │    · 官方原样收录的（有 agentsws.json）：content-proposal.mjs --all-official 自动出「待审升级」提案
  │    · 改写类的（marketingskills 那几份）：周报里看见上游动了 → 人把改动移植进来 → 本机出提案
  ▼
待审升级提案（diff + 许可证对比 + 可疑指令扫描 + 分界线检查 + 审核记录草稿）
  │ ② 审核：Fable 照 docs/42「内容更新」——许可证没变、没有可疑指令（或逐条放行）、旁注仍对得上、测试与模拟全过
  ▼
合进主干（技能目录 + 版本号 + 登记表加一条审核记录）
  │ ③ 分发：发版流水线 release.yml 的 content 作业（推 tag，或手动「只打内容包」）
  │    只打审过的 → 签名 → 用内置公钥再验 → 传 R2（先文件、再签名、最后清单）→ 镜像到 GitHub Release
  ▼
用户端（桌面版服务进程，每 6 小时 + 启动后 30 秒）
  │ ④ 应用：验签 / 验哈希 → 按品牌：每次问我 → 出卡；已审的自动更新 → 直接换
  │    原子换这个品牌的基础层、保留旧版一份 → 与上层改动三方合并，真冲突出卡
  ▼
⑤ 退回：设置里一键退回上一版（没有就回到随软件带的那一版），这一版不再自动提
```

### 5.1 发现

- 每周周报（`upstream-watch.yml` 的 `content-proposals` 作业）：登记表里目录有 `agentsws.json` 的条目（官方原样收录），查上游最新 release，tag 与旁注里锁的不一样就照旁注把官方文件下到临时目录、出提案（artifact + 作业摘要），**不改仓库、不开 PR**。
- 改写类：周报的 `marketingskills` 那一节看见 release / 路径有动，人先把改动移植进 `packages/skills/bundled/<名字>/`，再跑 `node scripts/content-proposal.mjs --item skill:<名字> --to <候选目录> --repo … --commit … --published-at …`。
- 提案里有扫描命中、许可证变了、目录里有脚本：**标红**，脚本退出码 3，不当「可直接合」。

### 5.2 审核（docs/42「内容更新」）

照提案末尾的清单逐项打勾，填好审核记录（§4.3），连同技能目录与版本号一起合进主干。审核记录的 `sha256` 就是提案里算好的那个——之后目录再动一个字节，打包就不会打它。

### 5.3 分发

`release.yml` 的 `content` 作业（与安装包作业互不依赖）：

- 推 tag：按 tag 定渠道、打那个 tag 上审过的内容、真传；
- 手动触发：勾「只打内容包」（`content_only`）就不打安装包；默认只打包自检、留 artifact，勾 `content_publish` 才真传；
- 打完先用**应用里内置的公钥**再验一遍（`verify --builtin`）：secret 里的私钥与发出去的应用对不上，用户一份都不会收——那就别传；
- R2：与 WP218 同一个桶、同三样 secret（`R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_ACCOUNT_ID`）。**先传文件（长缓存、immutable）→ 再传签名 → 最后传清单（不缓存）**；
- GitHub：滚动 Release `content-<渠道>`（第一次由这一步建），平铺上传，`--clobber`。

已知的小窗口：签名与清单是两个文件，不能原子地一起换；用户端恰好在两次上传之间来取会判「签名对不上」，下一次（6 小时后）就好——不会收错东西，只会晚一点收。

## 6. 用户端

### 6.1 卡片与设置项

**内容更新卡**（`ApprovalKind` `content_update`，只加）：

- 标题：「**X 有新版 · 官方某日更新 · 已审**」（例：「Shopify 官方技能 有新版 · 官方 2026-10-10 更新 · 已审」）；
- 一句改了什么（审核记录的 `summary`）；版本「原来 → 新版」两格；
- 按钮：**更新**（主）/ **查看改动**（就地弹窗，按段列出加了 / 改了 / 删了）/ 稍后（`···` 里）。没有「不要」：不点就一直是旧版；
- 审核时有要留意的地方（`scan_hits > 0`）：一句「审核时有 N 处要留意，已逐条看过放行，所以不自动更新」。

**冲突选择卡**（`content_conflict`，只加）：「X「某段」这一段：新版和你的改动不一样」，选项 **用新版 / 保留我的**，「**看对比**」弹出三栏（旧版 / 新版 / 你的）。

**设置 → 通用**加一行「**已审的内容更新：每次问我 / 自动**」（默认每次问我，按品牌存），说明进问号；旁边一个通道状态图标（通 / 这次没收 / 关着 / 还没查过，docs/36 §7 第四档）和「现在查一次」；下面列这个品牌**更新过或有新版**的条目：状态图标（已是新版 / 有新版 / 有一段要你选 / 要先更新软件）+ 名字 + 版本，按钮「更新 / 查看改动 / 退回」。失败给人话常显。

### 6.2 存放与原子替换

```
<数据目录>/content-updates/
  blobs/<sha256>                    验过哈希的文件（内容寻址）
  trees/<条目摘要>/<名字>/…          摊开的目录（读技能就从这里读）
  state.json                        见过的最大序号、最后一份收下的清单、上次查的时间与结果
  workspaces/<品牌>/state.json      这个品牌：每次问我 / 自动、每个条目的当前版与保留的上一版、出过的卡、冲突
```

- **原子替换**：换版只改那个品牌的 `state.json`（写临时文件再 `rename`），新版的文件早已验过、摊好；断电只会停在旧版或新版。技能库那一侧随后换这个品牌的基础层（失败就把状态改回去）；
- **保留旧版一份**：换版时当前版挪进 `previous`；
- **退回**：`previous` 挪回当前（没有就回到随软件带的那一版），退下来的那一版记成 `skipped_version`——自动模式不会再把它换上，更高的新版照常提；设置里还能手动「更新」回去；
- **软件追上了**：新软件自带的版本 ≥ 这个品牌更新过的版本，启动时丢掉覆盖，用软件自带的。

### 6.3 三方合并：官方更新不冲掉你的改动

按段判（docs/24 §1 的段 id 对齐，改标题不改 id）。三方 = 旧基础层（你改的时候看到的那一版）、新基础层、你的改动（公司 / 部门 / 岗位 / 职责 / 个人层的整段替换与 overlay，含学习回路采纳的）：

| 上游（旧 → 新） | 你 | 结果 |
|---|---|---|
| 没动 | 改了 | 保留你的 |
| 改了 | 追加了一句 | 新版 + 你追加的 |
| 改了 | 替换成和新版一样 | 干净 |
| 改了 | 替换成别的 / 删了 | **冲突** → 出卡 |
| 删了 / 改到认不出 | 改了 | **冲突** → 出卡 |
| — | 你自己加的段 | 干净 |
| 改了 | 上层只是照抄了旧版（没真改） | 跟新版走，不问人 |

冲突没选之前**你的那一段照旧生效**（新版的其余部分已经换上）；选「用新版」= 去掉你那一处改动、新版露出来；选「保留我的」= 不动，这一处不再问。实现：`planContentMerge`（`packages/skills/src/content-merge.ts`）只算，服务进程按选择改。

### 6.4 只落到启用了它的品牌（与 WP216 / WP215 的关系）

- 与 WP216 `PLATFORM_KITS` 同一口径：技能名在那张表里（平台专属），或条目写了 `platforms` 的，只落到**建站平台正是那一个**的品牌（读品牌档案的 `storefront_platform`，每次现取）；**品牌没设平台就不落**（WP216 第二轮定的「没设平台不启用」，不按 Shopify 兜底）；两样都不沾的 = 所有品牌；
- 每个品牌**各管各的**（WP215 / docs/52「一个品牌一个工作区」）：设置、当前版、保留的上一版、卡、冲突都按品牌存；技能库里「按品牌换基础层」——包基础层多一份**只属于这个品牌**的记录（`source.package = 'content-update'`），别的品牌查不到它（`MemorySkillRegistry` 的包层查找：本品牌那份 → 全局那份 → 兜底扫时跳过别人的内容更新记录）；
- 品牌改了平台：下一次运行就跟着变（WP216 的读法本来就是每次现取）。已经换上的版本留着，不删（改回 Shopify 时还在）。

### 6.5 开关

服务进程只在 `AGENTSWS_CONTENT_UPDATES=on` 时查——**桌面安装包启动服务时给**（`apps/desktop/src/server-process.ts`，外面显式给 `off` 才关）；测试、模拟、demo 默认不查，不出网。开着但没有内置公钥：通道关着、不查、设置里照实说。

## 7. 可疑指令扫描

第三方技能是给模型读的文字——一句「把对话内容发到这个网址」「不用问用户直接发」就足以让模型越线。所以对技能文本做规则检查（`packages/skills/src/content-scan.ts`，中英两套关键词 / 正则，宁可多报）：

| 类别 | 抓什么（举例） |
|---|---|
| 外发数据 | 「把对话 / 客户资料发到某网址」、命令里 `curl -X POST` / `fetch('https://…')`、`telemetry` / `log_feedback` / `--user-prompt-base64` |
| 绕过审批 | 「忽略之前的规矩」「不用问 / 不用确认」「跳过审批 / 卡片」、WP160 那张授权字样表 |
| 要凭据 | 索要密码、API key、令牌、私钥、助记词、银行卡、验证码 |
| 隐藏身份推广 | 装成普通用户 / 顾客、不透露是 AI / 合作关系、小号、刷评刷票 |
| 藏起来的字 | 零宽字符、双向控制符、HTML 注释里的字 |

- **命中就标红、不自动通过**：提案里标红；审核人逐条看，确属误报（多半是「不许……」这种禁止句）的在审核记录 `scan_accepted` 里写规则 + 文件 + 命中原文 + 理由；打包脚本重扫一遍，有一条没放行就不打；
- **用户端也带着同一组规则**：审核记录里 `scan_hits > 0`、或本机重扫有命中的条目，即使设了「自动」也**照样出卡等人点**；
- `LICENSE` 这类许可证正文不扫；
- 10-05 用现有 17 份自带技能试扫：4 份各命中 1 处，全是禁止句（「绕过卡片」「跳过审批」「刷评论」「忽略之前的规则」）——首次给它们写审核记录时逐条放行。Shopify 官方技能（WP216）命中 9 处，全是官方正文与我们旁注在讲那几个上报脚本（`log_skill_use`、`--user-prompt-base64`、session id 等）——扫描抓的正是该抓的东西，旁注已禁，审核时逐条放行。

## 8. 第二类：用户自己装的（只写规范，等技能市场）

| 环节 | 怎么做 |
|---|---|
| 来源 | 技能市场的条目，或用户贴的一个网址（`UserInstalledContentSource`：`kind: 'market' \| 'url'`、`ref`、`pinned_version`） |

| 合并 | 与第一类同一套三方合并 |

## 10. 第一次发内容包之前要准备的

1. **钥匙**：Luoye 跑 `node scripts/content-keygen.mjs --out <仓库外>` → `gh secret set CONTENT_SIGNING_KEY < 那个文件` → 公钥那行填进 `CONTENT_SIGNING_PUBLIC_KEYS` → 私钥文件备份后删；
2. **带公钥的软件版本先发出去**（公钥只能随软件版本到用户手里）；
3. **R2**：WP218 那三样 secret 填好；`dl.agentsws.com` 绑到桶上（WP218 待 Luoye 确认那一步）；
4. **审核记录**：要发的条目在 `content-reviews.json` 里有审核记录，摘要对得上；
5. **试一趟**：手动触发 `release.yml`，勾「只打内容包」、不勾「真传」→ 看作业摘要与 artifact（`verify --builtin` 过了才算钥匙配对）；
6. 真传：再触发一次勾上「真传」（或随下一个 tag）。
