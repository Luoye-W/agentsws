## 1. Connect（#8）：connect-adapter 的契约

```ts
interface Connect {
  // 发现
  providers(): Provider[]                                   // service, auth kind, executable / catalogOnly
  actions(service): ActionMeta[]                            // id, input/output schema, requiredScopes, side_effect: 'read'|'write'
  // 连接
  connections(workspace): Connection[]                      // id, service, alias, ownership: 'workspace'|'person', identity{accountId, displayName}, status
  beginConnect(service, { ownership, alias, mode: 'own_app' | 'agentsws_connect' }): { authorizationUrl | secureFormSpec, requestId }
  pollConnect(requestId): 'initiated' | 'connected' | 'failed' | 'expired'
  transferConnection(id, toWorkspace)                        // Join 时公司资产类转移
  // token
  issueToken({ assignment_id, kind: 'role-read' | 'role-apply' }): { token, expires_at }   // 由 05 scopes 编译 allowedActions / allowedConnections / requestedScopes
  revokeTokens(assignment_id)
  // 执行
  execute(actionId, input, { token, connection?, idempotencyKey? }): { data, executionId, meta }
  proxy(service, req, { token, connection? })
}
```

规则：`role-read` token 的 allowedActions 只含 `side_effect: read` 的 Action，**allowedProxies 为空（禁 proxy）**，**allowedConnections 必须非空**（空范围的 Assignment 拒签，因为上游空列表 = 不限制，09-08 改）；`role-apply` 只有执行器拿得到；所有 `execute` 的 executionId 记进事件日志并与 run / change 关联；`idempotencyKey` 在 apply 路径 = change_id。凭据从不出现在任何返回值里。

Action 的 `side_effect` 由目录元数据 + 我们的覆盖表决定（OpenConnector 目录没有这个字段，我们维护 `action-side-effects.yml`，未标的按 write）。

## 2. 入站（#9）

### 2.1 InboundEvent

```ts
type InboundEvent = {
  id: string; schema_version: 1; workspace_id: string
  channel: 'email' | 'whatsapp' | 'meta_dm' | 'feishu' | 'wecom' | 'shopify_webhook' | 'meta_webhook' | 'tiktok_webhook' | 'form' | 'api'
  kind: 'message' | 'system_event'          // 人发来的消息 vs 系统事件（订单创建、物流更新）
  received_at: string; occurred_at: string
  dedupe_key: string                        // 平台 message id / webhook id / IMAP Message-ID
  actor?: { external_id: string; display?: string; resolved?: ObjectRef }   // 解析到客户 / 联系人（provenance 起点）
  thread?: { external_id: string; resolved?: ObjectRef }
  parts: MessagePart[]                      // dsh-channels 的结构化类型：text / image / file / card / …；text 已 fencing
  raw_ref: string                           // 原始载荷在**受控原始材料区**（加密、保留期、随主体删除；秘密在入站脱敏后才落此处）的引用，不进模型
  routing: { role_id?: string; work_item_id?: string; confidence: number }   // 落到哪个职责车道
  secrets_scrubbed: boolean                 // 13 §4.3 入站秘密检测
}
```

### 2.2 管线

```
接收（webhook / IMAP 轮询 / 渠道适配器）
 → 去重（dedupe_key，24h 窗口）
 → 围栏 + 秘密检测（命中即脱敏并记 secrets_scrubbed）
 → 解析（客户 / 线程 / 订单引用）
 → 路由（职责分类，06 §2.4 同一路由器）
 → 排队（持久队列，按 workspace × role 车道；重试指数退避 ≤ 5 次；死信进 owner 车道）
 → 触发（生成 RunRequest 或 app_event 注入进行中的工作项）
```

### 2.3 渠道适配器（dsh-channels 契约）

采用其 `ChannelService`：`start / stop / send / createReply / beginAuth / getHealth` + 能力协商。我们的扩展：

| 扩展 | 说明 |
|---|---|
| `send` 的凭据委托 | 适配器不持有 token；`send` 内部调 Connect.execute（gmail.send / whatsapp.send…）；OpenConnector 没有的（通用 IMAP / SMTP）适配器自带，并作为 provider 贡献回去 |
| 入站落我们的管线 | 适配器把平台消息映射成 InboundEvent，不直接开 dsh 会话（公司端）；个人端可按原生方式 |
| 24h 窗口 / 模板首触 | WhatsApp 适配器暴露 `window_expires_at`；窗口外 `send` 自动改走模板 Action 并标 `template_used` |
| 账号健康 | `getHealth` 汇总到连接器就绪检查（doctor）与 Agent 健康看板 |

首批适配器：email（IMAP / SMTP + Gmail / Outlook 推送）、WhatsApp Business、飞书 bot、Shopify webhook（系统事件）。

## 3. 投递（#14）

```ts
interface Delivery {
  deliver(item: ApprovalItem | Notification, to: person_id, channel, view: 'full' | 'redacted'): DeliveryRecord   // 14 §7
  refresh(delivery_id, state)                      // 已由他人处理 → 卡片刷新
  onCallback(channel, payload): { item_id, decision_token, action }   // 只解析 token 与动作，不解析业务参数
  reply(conversation_ref, parts)                   // 对话回复（渠道 send 的投递侧入口）
  providers: ('workstation' | 'feishu_card' | 'wecom_card' | 'dingtalk_card' | 'email')[]
}
```

规则：工作台队列永远投递；卡片 = 脱敏视图 + 通过 / 编辑 / 驳回三个按钮（编辑跳工作台）；回调幂等（token 一次性）；投递失败退避重试并回落到邮件；`digest` 模式按工作区 tz 定时合并。

## 4. 连接器就绪与迁移

- 职责的 `connectors[].required` 未连 → 职责"未就绪"：积木灰、车道不产工作项（05 §4）
- Join：`ownership: workspace` 的连接经 `transferConnection` 到共享 runtime；`person` 的留本地
- 换机：导出包只含连接的元数据；导入后 Connect 列出"需重新授权项"

---

## 5. 一致性用例

1. 同一 webhook 重放三次 → 一条 InboundEvent
2. 客户邮件正文含 `ignore previous instructions` → parts.text 被围栏，模型看到的是围栏内文本
3. 入站含 16 位卡号 → 脱敏，`secrets_scrubbed=true`，原文只在 raw_ref
4. role-read token 调 write Action → 网关 403，事件 `tool.result{blocked}`
5. WhatsApp 窗口外 send → 走模板并标记
6. 飞书卡片回调重放同 token → 幂等
7. 合成 provider 注入 429 → 入站重试 5 次后死信进 owner 车道
8. Join 后 Shopify 连接在共享 runtime，个人 runtime 上不再存在
