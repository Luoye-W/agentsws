## 0. 一句话

付费分三块（数据接口 / AI 使用 / 增值服务），充值四档（US$20 / 50 / 100 / 200），
第一个增值服务是**红人营销增值服务**——30 积分 / 月，本地一份、云端一份，双向同步。

**它买的不是云端备份。** Luoye 09-19 的原话：它是为「红人营销以后**不依赖本地
Agents 工坊也能跑起来**」做的地基，像 KOLAgents 那样数据在云端，区别只是本地也有
一份。备份是"出事了能捞回来"，这是"我不在这台电脑前面，活也照跑"——两件完全不同
的事，卖点、定价、技术选型全都不同。

## 1. 付费三块

见 49 §3.1。一句话：`pricing.json` 每条能力加一列 `block`，三块是
`data`（数据接口）/ `ai`（AI 使用）/ `kol_service`（增值服务）。

**块的名字叫「增值服务」不叫「红人营销增值服务」**，尽管 Luoye 那天说的是后者：
因为同一块里马上会有第二个服务（客服，WP124），而把第一个实例的名字刻在块上，
第二个进来的那天就只能改数据或者认下一个读不通的标签。块的 id 保持 `kol_service`
不动（契约只加不删），只是界面上的中文标签是「增值服务」。

老的价目表（用户断网时本地内置的那一份）没有 `block` 这一列。**读的时候一律经
`pricingBlockOf` 兜底**：`ai.*` → AI，`kol.service.*` / `support.service.*` → 增值服务，
其余 → 数据接口。这条兜底与 json 里那一列是同一件事写两遍——一遍给数据，一遍给旧数据。

## 3. 红人营销增值服务

### 3.1 订阅：一份引擎，红人是第一个实例

**引擎是通用的**（Luoye 09-19 后续：客服增值服务同价同机制）。一个服务在引擎眼里
只有两样东西：一个 `service_id`（同时就是计费能力名）和每月多少积分，两样都在
`packages/metering/src/subscriptions.json` 里。

五个状态，一个不多：

| 状态 | 什么意思 | 能同步吗 | 界面上长什么样 |
|---|---|---|---|
| `none` | 没开通过，或者已经彻底结束 | 否 | 一张"开通"的卡 |
| `active` | 正常 | 是 | 一行状态 |
| `grace` | 这一期扣不上（余额不足），在 30 天宽限里 | **否** | 一句提醒 |
| `suspended` | 宽限期过了还是没充上 | **否** | 一张要人拍板的卡（充值 / 导出 / 删除）|
| `cancelling` | 点了取消，当期用完为止 | 是 | 一行"到 X 月 X 日为止" |

为什么 `grace` 与 `suspended` 要分开：前者在界面上是一句提醒，后者是一张卡。合成
一态就没法区分这两句话。

三条纪律，每一条都对着一类事故：

1. **幂等键里没有时间戳**：`sub:<service_id>:<org_id>:<cycle 起始那一天>`。KefuAgent
   曾经用 `Date.now()` 当 key，定时任务每跑一次就发一次积分，白送了一整个月。
   反过来（扣钱）犯这个错更贵：用户一个月被扣 N 次 30 积分。`service_id` 必须进键，
   否则一个组织同时订了两个服务时，这两笔在同一个月算出同一串——于是只扣一次。
   库那一层还有第二道：`kol_cloud_charges` 的主键就是这个键。
2. **余额不足不删数据**：进宽限 30 天，同步暂停，数据一条不动；过了宽限期仍然只是
   暂停。删数据的按钮只在用户自己手里。
3. **取消当期用完为止**：用户这个月的 30 积分已经扣了，立刻断等于我们收了钱不给服务。
   界线是当期的末尾——从那一刻起的每一期都属于"已经取消掉的将来"，一期都不扣。

**扣不上的那一期不记进账。** 没扣成就不算扣过，否则用户充值回来之后这一期被永远
跳过——他白付一个月。

赠送（运营后台）走的是同一条流程，只是那几期 0 积分。

### 3.2 云端红人库：每个组织一个对象

| | 公共红人库（48 §5.3 / WP61、WP116）| 云端红人库（这里）|
|---|---|---|
| 数据是谁的 | 跨租户共享的一层事实 | **一个组织自己的**（私有）|
| 对象怎么落 | 全局一个 `KolPublicDO` | **每个 org 一个** `KolTenantDO` |
| 怎么收钱 | 按次（reveal / 体检）| **按月订阅** |
| 主键 | `(channel, handle)` 自足键 | `(kind, id)`——本地那份数据的 id |
| 代码 | `packages/kol-public` | `packages/kol-cloud`（两个包零 import）|

**为什么一个组织一个对象**：对象边界就是隔离边界。堆在一张表里靠一列 `org_id` 和
"别忘了加 where"来隔离，是这类系统最常见的串数据方式。Compose 形态里落成"一个组织
一个库文件"，隔离边界与 Workers 形态一致。

表里**没有 `org_id` 这一列**——一个库就是一个组织。

九种对象（`KolObjectKind`）：`creator` / `platform_account` / `creator_contact` /
`collaboration` / `deliverable` / `tracked_link` 六种与本地 `KolStore` 一一对应；
`campaign` / `candidate` / `note` 三种是 Luoye 点名要的、本地那一头还没实现的部分——
契约先到位，本地补上就直接能同步。**同步协议对"种类"不关心**：它只认 `(kind, id)`
与版本号，加一种就是往表里加一行，不改任何一条路由。

### 3.3 双向同步

变更日志 + 每对象版本号 + 最后写入者胜。四件事是这一块的全部：

1. **版本号每对象自己数**，从 1 起，每写一次 +1。**它不是时间戳**：两台机器的钟差
   几秒是常事，用时间当版本号会让"谁更新"变成"谁的钟快"。
2. **判是不是冲突靠版本号**，不靠时间：`candidate.version > current.version` 说明本地
   是在看过云端当前值之后改的（干净覆盖）；`<=` 说明两头各改各的（真冲突）。
   用时间判的话，钟差几秒就会把一次正常更新当成冲突，界面上天天挂标记。
3. **最后写入者胜**定谁是当前值：先比 `updated_at`，同一刻比 `version`，都一样比
   `writer` 的字典序。第三级不是为了公平，是**为了确定性**——两头各算一次必须算出
   同一个结果，否则同步永远收敛不了。
4. **输的那一份留着**（`kol_cloud_conflicts`），界面上标出来，导出时一起带走。
   静默丢掉用户在另一台机器上写的半句话，是这类功能最常见也最伤的事故。

删除**留墓碑**（`deleted=1`，没有 body）。不留的话，一台机器删掉的东西会被另一台
还没同步的机器当成"新对象"推回来，删不掉。

游标是一个**单调自增的 seq**，不是时间戳：两条在同一毫秒写进来的对象会有一条被永远
跳过，而那一条是用户的数据。

接口（scope `kol`，只加）：

| 路径 | 干什么 |
|---|---|
| `GET /v1/kol/sync/status` | 订阅状态 + 云端多少条 + 最近同步 + 冲突数 |
| `POST /v1/kol/sync/push` | 上行（一次最多 500 条，超了回一句人话让本地分批）|
| `GET /v1/kol/sync/pull` | 下行（游标翻页；自己推上来的不回给自己）|
| `POST /v1/kol/subscription` | 开通（当场扣第一期）|
| `DELETE /v1/kol/subscription` | 取消（当期用完为止）|
| `GET /v1/kol/cloud/export` | 导出云端这一份（**欠费也给导**）|
| `DELETE /v1/kol/cloud` | 删掉云端这一份（本地一条不动）|

`kol` 动作集**进默认签发**。理由反过来说：这把动作集本身不解锁任何东西——没订阅的
组织调同步接口一律 402。不进默认的后果是"订阅完了还要回云上重签一把令牌"，而那一步
用户不知道要做，也不该知道（18 §1 最小动作集管的是**能做什么**，不是**付过钱没有**）。

### 3.4 钱在哪一侧动

钱**不在租户对象里**。月费由租户对象打一条内部路由去 `WalletDO(org_id)`，那一侧
同步做完预扣 + 结算再回一个"成了 / 没钱"。所以租户对象上没有一行碰余额的代码。

与 WP116 公共红人库那套**两段式**的差别只有一处，但它是全部理由：**月费不需要
两段式**。公共库要先预扣再打上游，是因为"要花多少"在打之前不知道；月费是一个定数
（30 积分），所以预扣与结算在同一次调用里做完——钱那一侧全程同步，中间一个 await
都没有。

为什么是 DO 打 DO 而不是绕回入口 Worker：月费也会由**定时器**触发（租户对象每天醒
一次补扣），那一刻根本没有请求，也就没有入口可以绕。

**归属（org / workspace）落库，不落内存**：Durable Object 会被驱逐，而闹钟可能在一个
刚醒过来、内存空空的对象上响——那一刻要扣费就得知道扣谁的。只记内存的后果是"机器
闲了一阵子之后，这个月的月费再也不扣了"。

### 3.5 加密

**不做端到端加密、不做恢复口令**（Luoye 09-19 定，见 21 §4.1）：那一套的前提是"云上
存的是一坨我们看不懂的字节"，而看不懂就替用户跑不了任务。

实际做的是三层：传输 TLS；静态加密沿用平台能力；**联系方式那一格再包一层**服务密钥
（`AGENTSWS_KOL_EMAIL_KEY`，与公共库同一把）。没配那把密钥就**不存邮箱**——不降级成
明文。

### 3.6 用户的数据权利

- **导出云端这一份**：一个可读的 json（`format: 1`），含全部对象、墓碑、订阅状态，
  以及**留着的那些冲突版本**（不然"输的那一份"就真丢了）。**欠费也给导**——这时候
  拦着等于拿数据当人质。
- **删掉云端这一份**：本地一条不动（那是两份数据，不是一份）。删数据**不等于退订**
  （用户可能只是想清空重来），所以订阅、扣费记录与审计都留着。
- 两个动作都写审计（`kol_cloud_audit`）。

## 4. 运营后台

组织抽屉加一块「红人营销增值服务」：订阅状态、当期到期、云端对象数、待处理冲突数、
最近同步、赠送剩余月份、最近几笔扣费（**含扣不上的那些**——用户来问"你们是不是把我
停了"的时候要答得出"2 月 3 日那一期扣不上，余额 4 积分、要 30"）。

后台那一口只有两件事，刻意没有第三件：**看**与**赠送 N 个月**。
**没有"替用户取消"，也没有"替用户删数据"**——后台能做这两件事，就迟早有一天有人
替用户做了。赠送走 CSRF + 审计（`kol_service.grant`）：一个月 30 积分，送十个月就是
300，这种事必须留一行谁在什么时候做的。

## 5. 下一步：云端跑起来要什么（本轮**不实现**执行器）

本轮只保证数据与契约到位。往下走三件事，各自缺什么，列在这里免得下一个人重新想一遍：

### 5.1 云端跟进节奏

**够了。** 合作（`collaboration`）与交付物（`deliverable`）已经在云端，状态机与阶段
判定是纯函数（`packages/kol-core` 的 `stages.ts`），搬到云上不需要新数据。
要加的只有一个**定时器**：租户对象已经有 alarm（每天扣费那一次），跟进节奏搭在同一拍上。

### 5.2 云端收发信

**不够，缺两样。**

1. **发件身份**。本地那一头用的是商家自己的邮箱（IMAP / SMTP 或 OAuth）。云端要代发，
   要么拿到那份凭据（那是一道单独的授权，且会把"云端读得懂数据"的边界从业务数据扩到
   **通信凭据**，得 Luoye 单独定），要么用我们自己的域名代发（送达率与"这封信看起来
   不是商家发的"两个问题）。
2. **收件那一半的存储**。`collaboration` 上现在只有**线程摘要**，没有正文。云端要回信
   就要读得到上一封信的正文——那是一类新对象（`message`），同步协议本身不用改
   （加一种 kind 而已），但"要不要把商家的邮件正文放到云上"是一个要 Luoye 拍板的问题。

### 5.3 云端长程任务

**不够，缺一样**：任务的**运行记录**（run / step / 审批点）现在完全在本地（docs/17）。
云端跑长程任务要有一份能续的运行态，那是另一个对象族，不该塞进红人库的同步协议里——
它的生命周期（几分钟到几天）、读写频率（每步一写）与红人数据完全不同。
建议单开一个 WP，用同一套租户对象、不同的表。
