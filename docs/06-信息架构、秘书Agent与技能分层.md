## 1. 一人多职责时首页不会乱：首页的形状不随职责数量变化

### 1.1 问题的根源

KOLAgents 的后台面板多，是因为它是一个**你去操作的工具**：红人池、campaign 看板、建联队列、归因……每个面板对应一个你要主动去看的地方。十个职责 × 每个职责六个面板 = 六十个面板，怎么排都乱。

中台的首页不是工具面板的合集，是**你回答的队列**。工作找你，不是你找工作。所以设计规则只有一条：

> **首页的形状固定，与职责数量无关。** 职责变多，变的是队列里工作项的种类，不是首页上的区块数。

### 1.2 首页固定四区

| 区 | 内容 | 与职责的关系 |
|---|---|---|
| 队列 | 一条，所有职责的审批项、认领项、待办合并；按职责打标签，按紧急度 × 等待时长排序 | 职责越多队列越长，但仍是一条 |
| 告警条 | 所有职责的 `immediate` 通知合并成一条横向的告警条，处理完即消失 | 合并，不分职责 |
| 今日关注 | 自适应区，**最多 6 张卡**；从所有职责的候选卡里按"今天值得看"挑；个人钉住 / 隐藏永远优先 | 候选来自各职责，但只露 6 张 |
| 日报 | Agent 每日生成的一份，跨职责 | 一份，不是每职责一份 |

四区之外没有别的。3 个职责和 10 个职责的人打开首页看到的是同一个形状。

### 1.3 职责的面板去哪了：职责工作面，按需进入

04 文档里每个职责列的"首页积木"要重新分类。05 schema 的 `HomeBlock` 增加 `placement` 字段：

| placement | 含义 | 出现在哪 |
|---|---|---|
| `queue` | 产生工作项的车道 | 合并进首页队列，不单独显示 |
| `alert` | 即时告警 | 合并进告警条 |
| `focus` | 值得"今日关注"的卡片候选 | 自适应区，竞争 6 个位置 |
| `digest` | 只进日报的统计 | 日报 |
| `role_view` | 职责工作面的面板（红人池、campaign 看板、归因、店铺健康……） | **只在该职责的工作面里**，永不进首页 |

KOLAgents 那些面板全是 `role_view`。进入职责工作面有三条路，都是"被带过去"而不是"去找"：

1. **从工作项进入**：队列里点开"给红人 A 的报价草稿"，右侧抽屉直接是红人 A 的卡片、往来记录、campaign 上下文。你没有去红人池翻他。
2. **侧栏职责切换器**：侧栏按岗位分组、默认折叠，点进某个职责才展开它的 `role_view` 面板。这是"我今天要专门做红人"的深度模式。
3. **命令面板（⌘K）**：搜"红人 A"、"上周退款率"直接跳到数据视图。SaaS 里大多数面板在中台里退化为可搜索的数据视图。

付费插件可以往 `role_view` 注册面板（积木注册表），但**插件不能往首页四区之外加任何东西**。这条写进插件契约。

### 1.4 注意力预算的量化

BtoB 讨论稿写过"每天早上 6 分钟处理完队列"。把它做成产品指标：首页每天显示"今天队列预计 X 分钟"，自适应层的优化目标就是这个数，不是停留时长。职责越多这个数越大，那是真实工作量，不是界面问题；界面问题才是我们要消灭的。

## 2. 秘书 Agent：会议与群聊的产出怎么落库、怎么被认领

### 2.1 角色定位

每个人的秘书 Agent = 那个人 `common.member` 职责下的个人 Agent，以本人权限运行。它和公司级的会议 bot 分工：

| | 秘书 Agent（个人） | 会议 bot / 群聊连接器（公司） |
|---|---|---|
| 看什么 | 本人参加的会议、本人所在的群、本人的邮件 | 公司公共会议、公司群、公共渠道 |
| 权限 | 本人的 | 服务账号 |
| 产出去哪 | 先在本人工作区生成提议，再上交公司 | 直接进公司事件流 |
| 隐私 | 私人会议的内容不上交，只上交提议 | 无私人内容 |

两者产出的东西形状完全相同，走同一条管道。

### 2.2 管道：事件 → 提议 → 路由 → 认领 → 落库

```
会议转写 / 群聊 / 邮件（事件流，知识原料）
        │
        ▼ 抽取运行（Agent，只读）
   Proposal（提议，带出处）
        │  类型：knowledge / action_item / decision / question / data_request
        ▼ 路由（按职责分类，不按人）
   落到某个职责的车道 → 该职责的持有人的队列里出现"认领项"
        │
        ▼ 人处理：接受 / 转给别人 / 不是我的 / 不是事
   接受 → 进知识库审批（knowledge）或变成工作项（action_item）
   转给别人 → 路由器记一笔（学习）
```

### 2.3 Proposal 的形状

```ts
type Proposal = {
  id: string
  kind: 'knowledge' | 'action_item' | 'decision' | 'question' | 'data_request'
  text: string                       // 抽取出的内容，一句到一段
  provenance: { source: 'meeting' | 'group' | 'email'; source_id: string; at: string; speaker?: string; quote: string }
  route: { role_id: string; range?: RangeRef; confidence: number; reason: string }   // 路由结果
  explicit_assignee?: string         // 原文点名的人（"小王去跟进"），优先于分类
  knowledge_target?: { domain: DataDomain; layer: 'fact' | 'phrasing' | 'policy' }  // knowledge 类专用
  due?: string                       // action_item 专用
  status: 'proposed' | 'claimed' | 'redirected' | 'rejected' | 'accepted'
}
```

### 2.4 路由规则：职责分类表就是路由词典

这是 04 文档那张职责表的第二个用途。路由器不问"这条给谁"，问"这条属于哪个职责"，然后查分配表：

| 情况 | 处理 |
|---|---|
| 原文点名了人 | 直接给那个人，职责按他持有的职责里最匹配的 |
| 分类到的职责在该范围只有一个持有人 | 自动进他的队列，标"Agent 认为这条属于你" |
| 多个持有人 | 给范围管理者分派；或给会议里的发言人（如果他持有该职责） |
| 没有持有人 | 进 owner 的"未认领"车道；这也是一个信号：公司有事没人负责 |
| 置信度 < 阈值 | 进抽取者本人的队列让他手动路由，而不是猜 |

"转给别人"是路由器的训练数据：每次转派记录 `(文本特征, 原路由, 实际接收)`，作为下次分类的 few-shot 记忆，按公司隔离。

### 2.5 各类提议的归宿

| kind | 接受后 | 谁批 |
|---|---|---|
| `knowledge` | 进目标职责知识库的审批车道；按三层（事实 / 话术 / 策略）走对应权限：事实层人审、话术层自动生效可回滚、策略层只有 owner | 该知识域的负责人（见 §3 的负责人机制） |
| `action_item` | 变成该职责车道里的工作项，链接回会议；无人认领超过 N 小时按 `escalate_after_hours` 升级 | 认领即批 |
| `decision` | 进决策账本（公司级只读记录），关联到受影响的职责 | owner 确认 |
| `question` | 进缺口队列（BtoB 讨论稿 §9），有人答了自动变 knowledge 提议 | 被问到的职责持有人 |
| `data_request` | **Agent 先干**：如果该职责的 Agent 有读权限，直接跑分析把数据附上，人只确认；没权限才变成给人的 action_item | 持有人 |

`data_request` 那条回答了"怎么自动获取数据"：会上说"客服把上周退货率发一下"，散会时客服的队列里已经是"退货率 3.2%，附表，发到群里？"而不是一条待办。

### 2.6 不做的事

- 不直接写任何知识库。会议里说的话是原料不是知识；没有人接受的提议 7 天后归档，不删（出处要留）
- 不给会议 bot 写权限。抽取运行只读，产出只有 Proposal
- 不做"所有人都收到全部纪要"。纪要作为文档投影到飞书供阅读，但可执行的东西只到对应的人

## 3. 技能分层：个人 / 部门 / 公司，同名叠加，向上晋升，自动学习

### 3.1 三层 + 叠加解析

```
公司库  company/customer-care@1.4    ← 负责人：客服主管
部门库  dept:ops/customer-care@1.4+2 ← 负责人：运营组长（基于公司 1.4，两处修改）
个人库  me/customer-care             ← 我自己（基于部门版，一处修改）
```

**同名解析：最近的一层赢，但不是整体替换，是叠加。** skill 正文拆成带稳定 id 的段（规则 / 示例 / 禁忌 / 模板 / 工具用法 ……），上层的修改是**按段的 replace / append / remove**，不是整文件 diff。这样公司版升到 1.5 时，我的个人修改还能自动叠上去；只有同一段两边都改了才报冲突让人看。

这比 git 的行级 diff 粗，但对 SKILL.md 这种以自然语言写的东西，段级合并成功率高得多，而且非开发者看得懂"你改了'退货窗口计算'这一段，公司版也改了这一段"。

### 3.2 每个共享 skill 有一个负责人

| 层 | 负责人 | 权力 |
|---|---|---|
| 公司库 | 指定的人（默认该职责的范围管理者） | 批准晋升到公司库的修改；决定版本；配 eval |
| 部门库 | 部门内指定的人 | 批准晋升到部门库的修改 |
| 个人库 | 本人 | 随便改，随时回滚 |

没有负责人的共享 skill 不能存在——晋升请求路由不到人就会卡在 owner 那里，这和 §2.4"未认领车道"是同一个信号。

### 3.3 三种操作

| 操作 | 含义 | 走什么 |
|---|---|---|
| 个人化修改 | 在个人层对某段 replace / append | 直接生效，自动记版本，可回滚 |
| 晋升（向上提交） | 把个人层的某几段修改提交到部门或公司层 | 审批队列 `skill_promotion`；负责人看到的是**段级 diff + 触发这次修改的证据**（哪些运行、哪些人工纠正）；通过 → 该层版本 +1；被合并的段从个人层移除（已经在上游了） |
| 下沉（跟随上游） | 上游出新版，个人层与部门层自动 rebase | 无冲突静默；有冲突 → 本人队列里一条"公司版改了你也改过的那段"，二选一或手合 |

晋升的门槛：目标层的 eval 不回归。evals 目录里每个共享 skill 一组用例（03 文档已定形状），晋升时自动跑，红了不给合。

### 3.4 自动学习：像 Hermes 一样从经验里更新 skill，但分层落地

你说的对：人不会主动说"把这个总结成经验"。所以学习必须是**外围机制**，挂在运行之外，不靠人触发。分三级信号、三个时机：

**信号来源**

| 信号 | 例子 | 强度 |
|---|---|---|
| 人工纠正 | 编辑了 Agent 的草稿（修改即学习的 diff）、驳回并给了理由、转派 | 强 |
| 运行内摩擦 | 同一 skill 下工具反复失败、模型反复追问同一件事、guardrail 命中 | 中 |
| 运行后反思 | 每次运行结束一个廉价的反思步骤："这次 skill 里有没有哪条不适用 / 缺什么"；产出 `skill_lesson` 候选，带 run id | 弱，但量大 |

**三个时机**

1. **即时（每次运行后）**：反思步骤产出 lesson，只写进本人的 lesson 池，不动 skill。零打扰。
2. **每日整理（夜间）**：把当天的 lesson 聚类，去重，和已有段落比对，生成**第二天的审批项**："Agent 建议给你的 customer-care 改一段"，附证据。**不自动改任何一层**（09-08 Luoye 定：话术层也不例外）。人接受才写进个人层；忽略即负样本。
3. **每周巩固（Co-Engram 的 REM 阶段）**：跨人聚类——如果客服组三个人的个人层都给同一段加了相似的修改，自动生成一条晋升提议给部门负责人，证据是这三个人的修改和相关运行。这就是"重复模式固化为 skill"（dsh-memory-evolve 已有参考）。

**纪律**

- 每条自动修改带出处（run id、纠正者、时间），可追溯、可整体回滚到某天
- lesson 有置信度：被重复确认升、被忽略衰减、被驳回记负样本；只有置信度过线才进每日整理
- 策略层永不自动改，连提议都只给 owner
- 自动修改的段落在界面上有标记（"Agent 于 9-7 根据 3 次纠正修改"），人随时能看到 skill 里哪些是自己写的、哪些是学来的

### 3.5 与现有设计的对应

| 已有 | 在本节里 |
|---|---|
| 架构总览 "两级技能库 + 统一审批" | 变成三级（加部门），晋升仍走同一条审批队列 |
| 架构总览 "修改即学习" | §3.4 的强信号 |
| BtoB 讨论稿知识三层权限 | 直接决定自动修改能落到哪一层 |
| Co-Engram 的 REM 与置信度 / 衰减 | §3.4 每周巩固与 lesson 置信度 |
| dsh-memory-evolve "重复模式固化为 skill" | §3.4 跨人聚类 |
| 03 文档 §7.4 Join | 个人库随人；Join 时个人层保留，想共享走晋升 |
| evals/ | 晋升门槛 |

## 5. 第二轮（09-08）：对 §4 待定项的解释与定案

### 5.1 skill 的"段"是什么，怎么定（解释）

一个 skill 就是一份写给 Agent 的说明书（SKILL.md），比如 `customer-care` 大致长这样：

```
## 回答顺序
先说记录显示什么，再说条款怎么说，最后说下一步……
## 事实来源
日期和物流只来自本会话取到的记录……
## 退换货判定
按记录状态 + 送达日 + 今天 vs 条款窗口算……
## 愤怒客户
短句，只说现状和下一步……
## 禁止事项
不发明补偿，不写道歉段，不回显卡号……
```

每个标题下面就是一"段"。我做个人化修改时，改的通常是其中一段（比如给"退换货判定"加一句"德国站按 14 天算"）。问题在于：公司版下个月更新了，系统要知道**我改的是哪一段**，才能把公司的新版和我的修改叠在一起。这需要每段有一个不变的身份。

三种办法：

| 办法 | 做法 | 问题 |
|---|---|---|
| 作者手工标 id | 写标题时加 `{#returns}` 这种标记 | 非开发者不会做，忘了标就合不了 |
| 按标题文字识别 | 系统按 `##` 自动切段，标题文字就是身份 | 公司版把"退换货判定"改名为"退换货规则"，我的修改就找不到家了 |
| **系统自动发隐藏 id**（推荐） | 系统按标题自动切段，第一次保存时给每段发一个隐藏编号存在旁边的索引文件里；改标题、挪位置编号都不变 | 作者零负担；只有把一段拆成两段这种结构变化才需要人确认一次 |

**定案建议**：第三种。用户在界面上看到的仍是普通的标题和正文，"段"这个概念对他不可见，只在合并时起作用。

### 5.2 自动修改的"试用期"是什么（解释）—— **已被 09-08 决定取代：不自动改，改为第二天审批项**

§3.4 说夜间整理会把**话术层**的经验直接写进个人 skill，不问人。例子：Agent 发现你连续五次把开头的 "Dear customer" 改成 "Hi there"，第二天晚上它就自动在你个人版的 `customer-care` 里加一句"开头用 Hi there"。

这有个风险：它学歪了你也不知道，比如那五次其实都是同一个特殊客户。两种对策：

| 对策 | 体验 | 问题 |
|---|---|---|
| 改之前先问 | 每晚一批"要不要加这条"让你点 | 打扰；正是你说的"人不会主动去做这件事" |
| **试用期**（推荐） | 直接生效，但 7 天内标"试用中"；受它影响的草稿在界面上有一个小标记"用了新学的规则"；你看不顺眼一键撤销，撤销即负样本；7 天没撤销就转正 | 需要在草稿上做出标记 |

~~**定案建议**：试用期 7 天。~~ **09-08 定案**：不采用试用期。Agent 学到的东西一律在第二天以审批项出现（"建议改一段"+ 证据 + 一键接受 / 忽略），接受后才写进个人 skill。理由：默认直接改的收益不足以抵消"学歪了没发现"的风险；一天一批、一次点完的打扰是可接受的。

### 5.3 路由置信度与未认领升级（详细）

**置信度是什么。** 路由器读一条提议（"下周之前把德国站的退货说明改成 14 天"），输出两样东西：它认为属于哪个职责（`dtc.store-config`）和有多确定（0 到 1 的一个数，比如 0.82）。这个数来自分类模型本身，再加上公司历史（过去类似的话被转派过几次）。

**阈值决定三种处理**，不是一刀切：

| 置信度 | 处理 | 用户看到什么 |
|---|---|---|
| ≥ 0.7 | 自动进该职责持有人的队列 | "Agent 认为这条属于你" |
| 0.4 – 0.7 | 仍进该持有人队列，但标"不确定" | "可能是你的，不是请转走"，转走一次只需一步 |
| < 0.4 | 不猜，回到抽取者（会议发起人或秘书 Agent 的主人）队列 | "这条不知道给谁，你指一下" |

**为什么不能只定一个数。** 阈值太低，错派多，被派错的人烦；太高，什么都回到发起人手上，等于没有自动路由。所以默认值要**随公司自己调**：新工作区从 0.8 起（宁可多问，别一开始就派错让人失去信任）；每周看转派率，转派率低于 5% 就把阈值往下调 0.05，高于 15% 往上调。用户不用碰这个数，但设置页里能看到它现在是多少、为什么。

**未认领升级是什么。** 一条行动项进了小王的队列，小王两天没点。它不能一直躺着，也不能自动换人（换人等于替老板做决定）。升级的做法是**加人不换人**：

```
0 小时   进小王队列
24 小时  仍未认领 → 小王的范围管理者也收到（"小王有一条 24 小时没认领"），小王队列里的这条变红
48 小时  仍未认领 → owner 收到
```

时长按**工作时间**算（周末和非工作时段不计），默认 24 小时；`immediate` 类（客户投诉）默认 4 小时。每个职责可以在 05 schema 的 `NotificationRule.escalate_after_hours` 里单独设，公司可在策略层统一改。

**两个默认值汇总**：路由阈值 0.8 起步自适应到 0.7 左右；升级 24 工作小时、紧急 4 小时。

### 5.4 不抽取清单：默认 + 用户可加（定案）

抽取运行在生成提议**之前**先过这张清单，命中的内容连提议都不产生，也不进事件流的可检索部分（原始转写照常保留在会议记录里，只是不抽）。

**默认清单**（工作区创建时自带，owner 可增删；个人秘书 Agent 另有本人可加的个人清单）：

| 类别 | 例子 |
|---|---|
| 薪酬 | 工资、奖金、提成、期权 |
| 人事评价 | 绩效、晋升、辞退、试用期评估、对某人的负面评价 |
| 健康与家庭 | 病假原因、家庭事务 |
| 私人财务与法律 | 个人借贷、私人纠纷 |
| 凭据 | 密码、验证码、卡号、API key（这条不可删除） |
| 未公开的公司重大事项 | 融资、并购、裁员计划（默认开，owner 可关） |

用户加规则的方式就是对话："以后会议里提到供应商报价的部分不要抽"，秘书 Agent 把它写进清单并复述确认。

### 5.5 首页"今日关注"：默认 6 张，对话定制（定案 + 机制）

**定案**：上限是个人设置，默认 6，用户可改；更重要的是用户能**通过和 AI 对话**定制自己的卡片，不用在设置页拖拽。

**对话定制怎么落地**。用户对自己的 Agent 说："首页给我加一张卡，每天早上显示昨天的退款率和最差的三条评价。" Agent 做的事：

1. 把这句话变成一张**自定义卡**的定义：`{ 标题, 组件（从注册表选：统计卡 / 表格 / 列表 / 图）, 查询（服务端命名查询，以本人身份执行）, 刷新时间 }`
2. 先渲染一张预览给用户看，用户说"好"或者"把评价换成差评数就行"，再改
3. 确认后钉在"今日关注"区（用户自建的卡默认钉住，自适应层永不动它）

**三条硬约束**，都是为了它不变成 dsh-genui 那种"模型想画什么画什么"：

| 约束 | 原因 |
|---|---|
| 组件只能从注册表选 | 不注入任意 HTML；样式统一；数字不经模型手（查询结果直接进组件） |
| 查询以本人身份执行 | 看不到的数据卡片上也不会出现；权限压在数据层 |
| 卡片定义是数据不是代码 | 可以分享：用户说"把这张卡给客服组都加上"→ 走审批进职责模板的 `focus` 候选；也能随 Join 带走 |

同一机制也用于职责工作面（`role_view`）的定制："红人工作面加一个按国家分的红人数量图"。

用户也能用对话做排序和隐藏："把退款卡放最上面""日报我不想在首页看"，这些落成个人钉住 / 隐藏，与 05 schema 的规则一致。

**默认值**：每个职责模板自带 1–3 张 `focus` 候选卡（04 文档里的"首页积木"经 §1.3 重新分类后属于 `focus` 的那些），加上"今天队列预计 X 分钟"这一张常驻卡。
