## ① 一句话结论

**本周要动的只有一件，而且是「先别动」：BrowserSkill（「我正在用的浏览器」那条腿）的 0.3.2 给一个我们当成「只读」的工具加了一个能改线上数据的新动作，升级之前必须先把门禁改好 —— 请派一个半个工作包的单子，范围见 ④ 第 1 条。** 其余 51 个上游本周都不用动：dsh 本体我们已经在最新的那一版上（WP293 刚升完），电脑操控驱动按我们自己的规矩照旧不跟，其他的要么没动静、要么动的地方碰不到我们。

## ② 逐个上游

### 2.1 BrowserSkill —— 本周唯一要处理的一件（`runtime-dep`）

这是「我正在用的浏览器」那条腿：腾讯开源的一套东西，由一个 dsh 插件（给 Agent 六个浏览器工具）加一个叫 `bsk` 的命令行程序组成。两样我们都锁死版本。

**更新了什么。**

| 东西 | 我们锁的 | 上游最新 | 最新那版的日期 |
|---|---|---|---|
| dsh 插件（npm） | 0.3.0 | **0.3.2** | 2026-09-30 |
| `bsk` 命令行 | cli-v0.3.0（2026-09-17） | **cli-v0.3.2** | 2026-09-30 |
| 浏览器扩展 | 用户自己装 | ext-v0.3.2 | — |

两版都是 09-30 发的，严格说不在本周区间里 —— 但 W40 / W41 没出报告，所以第一次记在这里。本周上游仓库还在动（26 次提交，10-10 合进了一个「录视频」的功能），**那个还没发版**。

**碰不碰我们：碰，而且碰的是门禁。** 把 0.3.0 和 0.3.2 两个包拆开逐字比过，结论是三条：

| 比什么 | 结果 |
|---|---|
| 六个工具的名字 | **一个没变**（`browser_assist` / `browser_inspect` / `browser_interact` / `browser_page` / `browser_session` / `browser_tabs`） |
| 工具下面的动作 | **`browser_inspect` 多了第 7 个动作 `debug`**（0.3.0 有 6 个，全是读） |
| `lazyTools` 这个开关的缺省值 | 还是 `true` —— 我们必须继续显式写 `false`，否则工具面整个是空的（没变化） |

关键就在那个 `debug`。**0.3.0 里 `browser_inspect` 的说明第一句是「读页面状态，不执行任意脚本」**；0.3.2 的说明变成了「读页面状态，并显式控制任务级调试」，并且上游自己在说明里写明了两件事：

- `rule_add` / `rule_enable` 可以**拦截、改写或伪造线上请求**；
- `replay` 会**发出一个新请求，可能改变服务器上的数据**。

也就是说，一个我们一直当「只看不动」的工具，现在挂上了能改线上数据的能力。

**我们这一侧现在是什么状态（好消息）。** 门禁的兜底是对的：我们按「动作名在不在白名单里」判读写，白名单里只有那 6 个老动作，**表外一律按写**（`packages/dsh-adapter/src/browserskill.ts`）。所以万一哪天被动升上去，`debug` 会落进「写」，要人点同意才跑 —— **没有漏**。

**不漏，但有两个真问题：**

| # | 问题 | 为什么要紧 |
|---|---|---|
| 1 | **粗细不对。** `debug` 底下还有十来个子动作，从「开始录流量」到「重放一个请求改掉服务器数据」全挤在同一个「写」里 | 审批卡上只能写「它要调试浏览器」，用户看不出自己批的是哪一种。读类的子动作（看活动、等一下）也要走审批，吵 |
| 2 | **域名白名单看不见它。** 我们只在三处检查「要去哪个网址」（开页 / 开会话 / 开标签）。`replay` 自己发请求、`rule_add` 能改写请求的目标，**两条都绕过了域名白名单** | 今天靠「写要审批」挡着，但少了一层。品牌只授权了自己的店，不该能往别处发请求 |

**还有一件顺带的：上游把我们等的那个东西做了一半。** 我们登记表里的愿望是「插件的 peer 范围放宽到能和预发布版相交」（它写死 `^0.1.0-rc.6`，每次有一个新包第一次进我们的树，安装就红一次，只能一条条往 overrides 里钉）。0.3.2 把范围改成了 `^0.1.5-rc.3 || ^0.2.0-rc.1`，**还顺手去掉了一个 peer**（`dsh-client-ui-attachment`，我们一直盯着的两个「没进树」之一）。但按 semver 的预发布规则，`^0.2.0-rc.1` 仍然**对不上**我们树里的 `0.2.1-alpha.2` —— **overrides 还是免不了，只是以后少撞一次**。这条愿望算部分达成，不要销号。

**另外一个新动作：插件开始注册自己的技能。** 0.3.2 的包里多了一份 `skill/SKILL.md` 加 5 篇参考，代码里会去拿官方的「技能」服务（`ctx.get("skills")`）把自己注册进技能目录。我们的组合里**没有**这个服务，所以今天它直接空转、什么都不做 —— **但这是插件碰的一个新 seam，登记表的 `we_depend_on` 里现在只写了「注册六个工具」，要补一行**。

**和我们已有功能重不重复。** 不重复。这是我们唯一的「用用户自己浏览器」的腿，没有替代品。那个新的 `debug` 能力（抓流量、改请求）我们自己也没有 —— 但那不是我们要给跨境电商运营的东西。

**值不值得融合。**

| | |
|---|---|
| 收益 | 中。跟上两个小版本（含若干录制与重载的修复），顺带少一次 overrides 的碰撞 |
| 风险 | **门禁粒度不够 + 域名白名单有一个口子**，不先补就升 = 自己给自己开洞 |
| 工作量 | **半个工作包**（扩动作表 + 子动作分级 + 给 `replay` / `rule_*` 加网址检查 + `we_depend_on` 补技能 seam + 测试） |

**建议：现在不升，派一个半个工作包的单子先把门禁改好，改完再按 docs/42 升到 0.3.2。** 范围见 ④ 第 1 条。顺序不能反。

| 0.2.1-alpha.1 | 10-03 | 跳过了 |
| **0.2.1-alpha.2** | **10-09** | **我们锁的就是它** |

> 说明一句：npm 上的「latest」还是 0.2.0-rc.2，我们锁的 alpha 版比它新。这是 Luoye 10-10 定的「要采用 alpha 的」。

**不只看依赖树里已有的包（本周的重点发现）。** 按要求把上游 `packages/` 目录在三个 tag 上各列了一遍，这一周出现了一个**反方向**的动作 —— 有包从正式区**降级**进了 experimental（试验区）：

| 口径 | 0.2.0-rc.2（09-29） | 0.2.1-alpha.1（10-03） | 0.2.1-alpha.2（10-09，我们锁的） |
|---|---|---|---|
| `packages/` 正式区 | 61 | 60 | **58** |
| `packages/experimental/` 试验区 | 25 | 28 | **48** |

本周（alpha.1 → alpha.2）具体动了：

| 动作 | 包 | 对我们什么意思 |
|---|---|---|
| **降级**（正式区 → 试验区） | `hooks` → 拆成 `hook-protocol` / `hooks-claude-code` / `hooks-codex` | 我们没取用。**降级是个信号**：上游自己对这块还没定 |
| **降级** | `webhook` → `webhook` / `webhook-github` | **我们等的「渠道 seam」就是它**，见 2.3 |
| 试验区新增 20 个 | 见 2.3 | WP293 已经逐个过了一遍、Luoye 10-10 全部定过 |

（再往前一版，`runtime-diagnostics` 也从正式区消失、在试验区变成了 `session-inspector` / `inspector-profile`。我们也没取用。）

**和我们已有功能重不重复。** 本体无变化。降级的那三类我们一个都没用上，删不删都不碰我们。

**建议：不动**（已在最新）。但把「上游把包从正式区降回试验区」记成一条新的观察口径 —— 我们的登记表现在只盯「转正」，不盯「降级」，而降级同样是「别急着依赖」的信号。

### 2.3 dsh-experimental（盯转正信号，`reference`）

**更新了什么。** 试验区本周从 28 个长到 48 个。WP293 已经逐个评过、Luoye 10-10 全部拍过板（思考翻译、调试工具、徽章那几项），所以这里**不重复那一轮**，只挑出两个和我们登记的愿望直接对上的。

**① 我们等了很久的「渠道 seam」出现了 —— 但形态不对、而且刚被降级。**

登记表里 dsh 的愿望写着「出现渠道 seam（现在入站只能靠 `agent.followup()`）」，dsh-experimental 的愿望写着「experimental 下出现渠道 / IM 相关的包」。本周两条**同时命中**：

- `dsh-webhook`：给宿主一个 `ctx.webhookRuntime`，是「可信的程序化 webhook 规则」的注册表，接口只有 `register(rule)` 和 `dispatch(delivery)`。它**自带的唯一动作**是「在官方 Web 工作区里开一个普通根会话」。
- `dsh-webhook-github`：在 `ctx.webServer` 上注册一条确切路由，验 GitHub 签名、限流、投给上面那个运行时，然后不等结果直接回 202。

| 判断 | 结论 |
|---|---|
| 和我们已有功能重不重复 | **可借一部分。** 我们自己写的四条渠道（微信 / 企微 / 飞书 / 钉钉）做的事更多 —— **按提问人身份路由**。`dsh-webhook` 自带的那个动作只会「开一个会话」，没有发送人身份、没有审批去向 |
| 三条底线对不对 | 数据不默认上报：**对**（纯入站，不传出去）。一次运行一棵树：**要看**（一个 webhook 能不断开会话）。门禁 fail-closed：**不对** —— 它自带的动作是在**官方**工作区开会话，那条路不经我们的门禁。真要用，只能用它的注册表、换掉自带动作 |
| 值不值得融合 | **现在不值得。** 它 10-09 刚从正式区**降回**试验区，上游自己还在改 |

**建议：不动。把登记表里那条愿望改细一点** —— 从「出现渠道 seam」改成「渠道 seam 从 experimental 转正，**且入站后要做什么可以由宿主替换**（不是写死开官方会话）」。那一天才是我们能把四条自写渠道收到同一个口上的时候。

**② 「让 Agent 回头查自己过去的会话」现在有两个包了。** W39 提过 `tool-session-query`（判了「可替代性不明，本周不建议动」）。本周旁边又多了一个 `session-search`（五个只读全局工具，默认关、在插件页里选才开）。两者的差别值得记：

| 包 | 隔离做法 | 对我们的意思 |
|---|---|---|
| `tool-session-query` | 只有目标会话的工作目录**和调用方完全一样**才许跨会话读 | 我们按品牌分工作目录，这个隔离口径**和我们对得上** |
| `session-search` | 内容索引**所有 Agent 共享** | **和我们的品牌 / 岗位隔离冲突** —— 一个品牌的 Agent 不该搜到另一个品牌的会话 |

**建议：都不动。** 维持 W39 的判断。如果以后真要做「会话历史回看」，只考虑 `tool-session-query` 那一种口径，`session-search` 的共享索引对我们是反向的。

**③ 其余新增的，逐条归类（不重复 WP293 已拍过的）。**

| 包 | 它做什么 | 判断 |
|---|---|---|
| `hook-protocol` / `hooks-claude-code` / `hooks-codex` | 把 Claude Code / Codex 的 `hooks.json` 接进来跑；**只有 command 类的钩子会真跑** | **不取。** 等于让一份配置文件在本机跑任意命令，绕过我们的门禁 |
| `tool-terminal` / `terminal-bundle` | 六个「常驻终端」工具（跨调用保留状态、可交互输入） | **重复。** 我们已有命令行那条路且有门禁；常驻终端会多出一批门禁不认识的工具名 |
| `tool-ralph` / `ralph-bundle` | 对一个不变的目标反复派全新子 Agent 迭代 | **无关。** 我们自己的 Agent 层已经定了组织方式 |
| `tool-worktree` / `worktree` | git 工作树 | **无关**（我们的用户不写代码） |
| `translator` / `cot-translation-bundle` / `client-ui-cot-translation` | 思考过程翻译 | WP293 已评、**Luoye 10-10 已拍板**，不重复 |
| `badge-skill-bundle` / `skill-badge` | 「powered by dsh」徽章 | 已在 `plugin-allowlist.yml` 里标明不启用 |
| `session-titles-bundle` / `session-title-all-prompts-llm` | 会话自动起标题 | **可替代。** 我们自己有对话命名，不动 |

**更新了什么。** 我们锁 **1.30.0**，1.x 线已经走到 **1.32.1**（10-05，在本周区间内）。

**一条更要紧的背景：1.x 开始让位了。** 1.32.1 的改动里有一条是「README 指向 v2，并说明 1.x 还支持什么」—— 上游的 **2.x 线已经在发**（发布页上能看到 2.3.x）。也就是说我们锁的 1.30.0 所在的这条线，正在变成维护线。

**和我们已有功能重不重复。** 不重复，它是接缝本身。

**值不值得融合。** 收益小（两个新开关我们都不需要）、风险小、工作量小。但 **2.x 迁移是另一回事**：那是一个工作包的量级，而且要和 dsh 自己用的版本对齐（它也依赖这个 SDK）。

**建议：**
- 1.x 内部的小版本：**不动**（没有我们要的东西，被动跟就行）。
- **记一条新的待办**：2.x 已经在发、1.x 变维护线 —— 不用现在迁，但要先去看一眼 dsh 自己打算怎么走（见 ④ 第 4 条）。

### 2.6 cua-driver（电脑操控的驱动本体，`runtime-dep`）

**更新了什么。** 上游本周发了三版，而且差距已经拉得很大：
