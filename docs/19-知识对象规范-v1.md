## 1. 对象

### 1.1 FactCard（事实卡）

```ts
type FactCard = {
  id: string; schema_version: 1; workspace_id: string
  layer: 'fact' | 'phrasing' | 'policy' | 'historical_case'   // 事实 / 话术 / 策略 / 历史案例（47 J2）
  domain: DataDomain | 'company'                  // 属于哪个数据域（决定 ACL）
  scope: RangeRef[]                               // 店铺 / 部门 / 全公司
  sensitivity: Sensitivity
  subject: { type: string; id?: string; key: string }   // 关于什么：产品 SKU / 客户 / 政策名
  statement: string                               // 一句话事实（≤ 500 字）
  structured?: Record<string, unknown>            // 可选结构化值（退货天数=14）
  provenance: { source: 'document' | 'meeting' | 'email' | 'web' | 'human' | 'agent_inference'; ref: string; locator?: string /* 文件+页码 / 会议时间点 */; quote?: string; at: string }[]
  confidence: { value: number; state: 'unverified' | 'plausible' | 'probable' | 'verified' | 'refuted' }   // Co-Engram 状态机
  conflicts?: { with: string; note: string }[]    // 双值并存
  valid: { from?: string; until?: string }        // 有效期（价格、活动）
  as_of?: string                                  // 47 J2：这句话说的是**什么时候**的状态（只有 historical_case 有）
  downgraded_from?: FactCard['layer']             // 47 J2：进入管道把它从哪一层降下来的（误伤可人工改回）
  // ── WP56（48 §3 L2 与 §4 #6 #9）：只加不删，全部可选，不写这几格的实现与 WP56 之前逐字段一致 ──
  stage?: 'both' | 'presales' | 'postsales'       // 适用范围。售前 / 售后不是两套模式、不是两个知识库，是每条知识的一格；缺省 both
  fact_fingerprint?: Record<string, string | number>  // 受管辖数值的类型化快照（期限 / 金额 / 比例 / 币种 / 责任方）
  verification_state?: 'fresh' | 'stale' | 'quarantined'  // 缺省等价 fresh
  source_content_hash?: string                    // 这条卡是从源的哪一版派生的（sha256 前 16 位）
  source_changed_at?: string                      // 源最后一次变内容的时间（数值没变时也记：源动过但口径没动）
  media?: string[]                                // 外部链接。没有上传、没有图床、没有富文本
  last_verified_at?: string                       // 最后一次有人确认过这条口径；**为空就是没记录，禁止拿 created_at 冒充**
  usage: { recalled: number; cited: number; last_recalled_at?: string; drafts_edited_after_cite: number }   // 沉默 / 过期信号
  status: 'proposed' | 'active' | 'retired'
  owner: person_id                                // 该知识域负责人
  created_by: { kind: 'agent' | 'person'; id }; created_at; updated_at
}
```

**事实指纹是什么（WP56，48 §4 #6）**：源页一改，"要不要惊动人"这个判断不能交给模型——
它每次跑出来的答案都可能不一样，而这条链的另一头是"改不改客户看到的口径"。
所以指纹是**纯函数 + 冻结词表**（`packages/knowledge/src/fact-fingerprint.ts`）：
只从正文里抽五类受管辖数值（期限 / 金额 / 比例 / 币种 / 责任方），
键是 `<类别>:<归一化后的值>`（`duration:day:30`、`money:USD:15`、`responsibility:payer_customer`），
值留原始出现形态。**措辞、排版、链接、SEO 文案、日期戳一律不产生指纹项**；
`¥` 没有上下文时只记币种不记金额——宁可漏判，不误判。
同输入同输出，所以这条链可复算、可回放、可在 code review 里逐行读懂。

**三种时效状态的分工**：`stale` 不是"不能用"，是"排在后面"。
检索**只排除 `quarantined`** 这一种，而 `quarantined` 只能由人显式产生。
理由是召回损失看不见——没被检索到的那条知识不会报错，只会让回信少一句该说的话；
把一条只是"源页动过"的知识直接从候选里拿掉，代价比让它排在最后大得多。

### 1.2 MemoryFact（运行记忆，Commerce Agents A7）

```ts
type MemoryFact = { key: string /* ≤64 */; value: string /* ≤200 */; category: 'constraint' | 'preference' | 'context'; subject: ObjectRef; source_run_hash: string /* SHA-256 前 12 位 */; expires_at: string }
```
写过滤：拒 ≥ 9 位数字、IBAN、邮箱、卡号；每轮 ≤ 3 条；Jaccard 去重；`constraint` 每轮必注入，其余按新近度到 cap=8；"忘记"= 覆写式撤销并如实说明。

## 2. 三层与权限

| 层 | 内容 | 谁能改 | 自动更新 |
|---|---|---|---|
| fact 事实 | 参数、认证、交期、政策条款 | 人审（负责人） | Agent 只能提议 |
| phrasing 话术 | 语气、结构、称呼、节奏 | 负责人审；个人层可自改 | 次日审批项（不自动） |
| policy 策略 | 折扣底线、账期、额度、优先市场 | **只有 owner** | 永不；Agent 只引用不推断 |
| historical_case 历史案例 | "当时那一单是这么处理的" | 人审（负责人） | Agent 只能提议 |

### 2.1 边界：知识层不存状态（47 J2，WP52）

**事实卡可以说"退款政策是 30 天"，不能说"订单 #1001 已退款"。**

后者是操作层的实时状态：它写进 Wiki 的那一刻就开始过期，而 Wiki 没有人会回去更新它。
半年后模型检索到它，会理直气壮地告诉客户一件半年前为真的事。真源不在这儿——
订单在平台 API 上，变更在 15 的账本上，本体登记表（47 J1）逐条登记着它们都归谁管。

所以 §4 的进入管道加一道拦（实现在 `packages/knowledge/src/state-words.ts`）：

- 带**状态词**的句子（订单号 / 履约状态 / 库存数 / 带货币的金额 / 退款流水，中英都认）
  降级为 `historical_case`，打上 `as_of`（"当时"，取出处里最早的时间），并记
  `downgraded_from`；
- 降完它仍然查得到、仍然有用（"上次这种情况我们怎么办的"），只是不再冒充"现在是什么样"；
- **判据故意窄**：政策里的天数（"14 天内可退"）、话术层里的金额占位都不算；
- **误伤可人工改回**（`restoreLayer`）：改回原来那层，`as_of` 一并清掉。

检索命中一条 `historical_case` 而问的是"现在怎么样"时，Agent 以**操作层**为准回答，
并发一条 `knowledge.card.stale` + 一张 `knowledge_update` 卡把矛盾报出来（24 的学习回路吃它）。
界面上两种引用长得不一样：对象引用是实框可点的 `ObjectChip`，知识引用是虚线带引号的
`FactChip`（历史案例还会把"当时"写在芯片上）。

## 3. 检索接口（带身份，过滤下推）

```ts
interface Retrieval {
  search(q: { text: string; actor: { person_id; assignment_id; role_id }; domains?: DataDomain[]; scope?: RangeRef[]; layers?: Layer[]; k?: number; precheck?: boolean
    stage?: 'both' | 'presales' | 'postsales'    // WP56：这次问的是售前还是售后；不给就不按适用范围过滤
    mode?: 'auto' | 'context' | 'lexical' | 'hybrid'  // WP56：检索档，缺省 auto（按库的大小自己定）
    budget_chars?: number                        // WP56：长上下文档的字符预算，缺省 16000
  }): { hits: Hit[]; relevant: boolean; matched: string[]; missing: string[]; tier?: 'context' | 'lexical' | 'hybrid' }
  cite(fact_card_id, run_id)                     // 记 usage.cited
}
type Hit = { fact_card_id; score; layer; statement_redacted; provenance_summary; sensitivity
  provenance_grade?: 'tracked' | 'cited' | 'unverified'   // WP56：读取时派生，不占一格
  verification?: 'fresh' | 'stale'; last_verified_at?: string; stage?: ...   // WP56 溯源四件套
}
```

规则：先按 actor 可见集合（Casbin）过滤候选，再算相似度（sqlite-vec + FTS5 混合，RRF 融合，可选重排）；`precheck=true` 只回 `relevant` 与 matched / missing，不读正文不计 usage（teamai）；命中即 `usage.recalled+1`；返回的 statement 已按 actor 脱敏。

### 3.1 长上下文档（WP56，48 §4 #7）

检索本身是有损的，而这个损失**看不见**：没被检索到的那条知识不会报错，
只会让回信少一句该说的话。中小卖家的知识库通常只有几千字——
这种规模下，整个给模型比任何排序都准。所以加一档 `context`：

- **`context`**：全库（**按身份过滤之后**）字符数 ≤ `budget_chars`（缺省 16000，
  工作区 / 单次可覆盖）就按 `updated_at` 倒序整库注入，**不检索、不打分**。
  这一档 `matched` / `missing` 不作数（没有"没匹配上"这回事）；
- **`lexical`**：超预算才退回现有的关键词检索，过滤下推一个字没改；
- **`hybrid`**：BM25 + 向量 RRF 的接口留着，本期**不实现**，选到它按 `lexical` 跑。

**两档都在最后叠一层溯源分层装箱**：`tracked+fresh > cited+fresh > unverified+fresh > stale`，
层内保持原来的顺序。装得下时它只影响顺序；装不下时 `stale` 与 `unverified` 最先被挤出预算——
"排在后面"这句话只有在预算真的不够时才有代价，这是故意的。

**`stage` 过滤下推**：只排除**只属于另一头**的条目。问售后时 `presales` 的不进候选，
`both` 与没标 stage 的两头都进；不传 `stage` 就完全不过滤——邮件是混合渠道，硬过滤会答错。

**不做的一件事**：命中 < 4 条时回落到"行业模板库"。那是多租户 SaaS 的平台标准库，
本地档没有这样一个库，凭空造一个等于替用户编口径。

## 4. 进入与更新管道

```
文档 / 会议 / 邮件 / 网页 → 解析（anydoc / html 清洗 / 转写）→ 分块（按标题层级，≤ 800 token）→ 抽取候选事实（Agent，只读）
  → knowledge_update 审批项（14）→ 通过 → FactCard.active（层由审批决定）
缺口：Agent 答不了 → question 提议（缺口队列）→ 有人答 → 自动变 knowledge_update
冲突：新事实与旧事实矛盾 → 不覆盖，写 conflicts，双值并存，生成 resolve_conflict 审批项；置信度按来源方向（规模类第三方可信、需求类客户自述可信）
过期：valid.until 到期 / 高召回低认可（drafts_edited_after_cite / cited ≥ 0.5）→ 生成 update 提议（附 Agent 草稿）
沉默：90 天 recalled=0 → 健康看板"沉默条目"，建议归档
晋升：置信度 ≥ 0.9、≥ 5 次 cited 未被改、≥ 2 个不同来源、≥ 14 天 → 建议 verified
```

### 4.1 源页复核（WP56，48 §4 #6）

一条从网页 / 文档派生出来的知识，源改了之后口径要不要跟着改，**人说了算**。
链路（实现在 `packages/knowledge/src/recheck.ts`）：

```
源同步一次新正文
  → 算内容 hash：与 KnowledgeSource.last_content_hash 一样 → 什么都不做，收工
  → 不一样 → 对每条派生卡比事实指纹（§1.1，纯函数）
      → 受管辖数值没变（改的是措辞 / 排版 / 营销文案）
          → 自动回鲜：只记 source_changed_at 与新的 source_content_hash，
            发 knowledge.card.refreshed。**不惊动任何人**
      → 数值真的变了
          → 卡标 verification_state=stale（**口径一个字都不改**），
            发 knowledge.card.stale + knowledge.recheck.opened，
            开一张 knowledge_update 复核卡送给知识的 owner，三选一：
              · 确认没变（unchanged）→ 卡回鲜，记一次 last_verified_at
              · 按新值更新（adopt_new）→ 换成新口径、卡回鲜，
                **旧值归档成一条 historical_case**（它当时是真的，将来还查得到）
              · 忽略（ignore）→ 留在 stale，继续排在后面
          → 人答完发 knowledge.recheck.resolved
```

三条边界：

1. **第一次同步只记 hash，不产生复核**——没有"上一版"就没有"变没变"这回事；
2. **裸 approve 不等于"按新值更新"**。选项 id 是冻结的；没选具体哪一个时按"确认没变"处理——
   改口径这件事必须是显式的，不猜；
3. **承诺类永不自动激活**（定价 / 政策 / 边界，按层或来源文件名判定）。
   这类知识哪怕指纹比下来"没变"，也不会自己走到 `active`。

事件：`knowledge.card.stale`（复用 47 J2 那条）、`knowledge.card.refreshed`、
`knowledge.recheck.opened`、`knowledge.recheck.resolved`。
API：`GET /v1/knowledge/rechecks`、`POST /v1/knowledge/rechecks/:id/resolve`。
端到端由模拟题 `packs/dtc-3c-3p/scenarios/knowledge/source-changed-recheck.yml` 钉住。

## 5. 与飞书 / 内容仓的关系

- 飞书文档是 KnowledgeSource（只读，ACL 继承）；中台产出的知识**投影**回飞书只读页

## 7. 一致性用例

1. 售后客服检索"成本价"→ 无命中（过滤下推），非"命中后被脱敏"
2. 同一 subject 两条矛盾事实 → 双值并存 + resolve_conflict 审批项，无覆盖
3. MemoryFact 写入含邮箱 → 被写过滤拒绝
4. precheck 不改 usage 计数
5. 90 天未召回 → 出现在健康报告沉默条目
6. 政策层卡片由非 owner 提交修改 → 审批项路由到 owner，其他人不可决
7. 引用该卡的草稿连续被改 → 生成 update 提议
8. 导出 markdown 再导入 → 卡片 id 与出处不变
9. （47 J2）"订单 #1002 已全额退款 $89" 进 Wiki → 层变成 `historical_case`、带 `as_of`、
   记 `downgraded_from`；"德国站退货窗口 14 天"照旧是 fact
10. （47 J2）检索命中历史案例 → `knowledge.card.stale` + 一张 `knowledge_update` 卡；
    回答以操作层的当前状态为准
