## 0. teamai 是什么，和我们的关系

一句话：**给开发团队的 AI 工具"团队层"**——把 skills、rules、docs、MCP、hooks、env、packages 放在一个 git 仓里，成员 `push` 开 MR、评审合并、每次 AI 会话启动时自动 `pull`；再加一层学习闭环：按摩擦信号（打断、拒绝工具、纠正、重试）给会话评分 → 提示分享经验 → learnings 进知识库 → recall 时 upvote → 置信度回写 → 剪枝 / 晋升为正式 skill。它支持十几个 AI 工具，**DeepSeek Harness 也在列**（skills / docs / learnings / codebase / teamwiki）。

它和我们不是竞品：它管的是"开发者的 AI 工具怎么统一"，没有业务职责、没有审批动作、没有渠道、没有权限感知检索，一切以 git 和终端为前提。但它把"团队层"的**分发、治理、学习、健康度**四件事做得很完整，正好是我们三层技能库与学习回路里没写细的部分。

## 1. 可借鉴的范式（按价值排序）

| # | teamai 的做法 | 我们现状 | 动作 |
|---|---|---|---|
| 1 | **HTTP 只读消费模式**：不会 git 的成员 `init --http`，服务端通过 report / sync / ack 三个端点下发 `install_skill` 等命令（带签名下载 URL、host 白名单、120s 超时、客户端可拒绝远程命令） | 我们只说了"公司库按作用域分发到个人端"，没有协议 | 技能 / 职责模板 / 卡片定义的分发**直接采用这个三端点模型**；这就是非 git 用户的分发协议，他们已经踩过坑 |
| 2 | **知识库健康报告（KB Health）**：各类型召回覆盖率、高频召回排行、**沉默条目**（从未被召回）、召回趋势、作者贡献、维护控制台（待晋升 / 建议归档 / 过时待更新） | 我们有学习回路，没有"知识库自己健不健康"的视角 | 新增 owner 视角的**知识与技能健康看板**；"沉默条目"和"高召回低认可"两个信号直接抄 |
| 3 | **量化的晋升判据**：置信度 ≥ 0.90、≥ 5 次 upvote、≥ 2 个不同贡献者、存在 ≥ 14 天 | 06 文档说"置信度过线"，没给数 | 作为事实卡和 lesson 晋升的默认阈值；跨人巩固里的"≥ 2 个贡献者"尤其重要，防一个人的习惯变公司规则 |
| 4 | **摩擦信号的具体定义**：interrupt（中途打断）、toolReject（拒绝工具调用）、correction（stop 后 60s 内含"不对 / 重来 / 错了"的追加）、retry（工具反复失败）；顺利但很长的会话不触发 | 06 §3.4 列了信号但没量化 | 把我们的信号对齐成可计数的四类：编辑 diff、驳回、转派、guardrail 命中 + 工具重试；**干预率**成为技能质量与 L1→L3 晋级的共同指标（采纳率是它的反面） |
| 5 | **高召回低认可 → 自动生成更新草稿**（`--update-quality` 产出 `.draft.md`，人改名即应用） | 没有 | 知识条目被频繁检索但基于它的草稿总被人改 → 该条目过期候选 → Agent 出更新草稿进审批队列 |
| 6 | **订阅源（sources）**：订阅其他团队 / 组织公共仓 / HTTP 源的 skills，pull 时自动同步 | 我们只有"公司库" | 技能库加**第四层：外部源**——官方源、付费插件源、行业社区源、服务商源。这是商业化的入口（见 §3） |
| 7 | **标签订阅 + 个人排除**：按 tag 只同步需要的；`skill exclude` 本地排除不影响他人 | 有个人叠加层，没有"排除" | 个人层加 exclude 操作；职责模板的 skill 支持 tag |
| 8 | **两级配置**：团队默认 + 用户覆盖 + 环境变量急停（recall、coAuthor、autoUpdate 都是这个形状） | WorkspacePolicy 有公司层，没有用户覆盖层的通用模式 | 所有功能开关统一为"公司默认 / 个人覆盖 / 紧急关闭"三级；试用期、自动学习、recall 都用它 |
| 9 | **隐私姿态**：上报只有计数和工具名，不落 prompt 原文；prompt 摘要要显式 `--include-prompt` 且脱敏；机器 id 只本地哈希 | 我们会话日志是全量（审计需要），但跨人看板没定纪律 | 跨人的看板与日报**只用计数**；原文只在本人工作区和审计通道 |
| 10 | **分发可执行物的治理**：hooks 可要求只跑团队脚本目录内的命令、`autoApply:false` 只提示不执行、packages 变更只提示成员手动装、不自动跑第三方代码 | dsh 插件无沙箱，我们说"公司库审核 = 安全边界"，没写分发规则 | 写成规则：拉取永不自动执行代码；只装签名源；安装动作是显式确认的审批项 |
| 11 | **tombstone**：删除也是一条要分发的记录（`.removed`），不猜测本地副本是否过期 | 没考虑删除的传播 | 技能 / 模板 / 卡片的删除都走 tombstone |
| 12 | **重复提交更新原 PR**：同一资源未合并时再 push 更新原 MR 而不是开新的 | 审批项规范还没写 | 审批项去重规则：同一对象的待审项只有一条，再提交即更新 |
| 13 | **culture.md**：结构化的公司 / 团队信息 + 正文，编译后注入每个工具的 CLAUDE.md，用标记块管理不碰用户内容 | 我们有 persona 和话术层，没有"公司档案"这个一等对象 | 加 `company.md`：使命、品牌口吻、红线声明（不能说的话）、目标市场；经 `systemPrompt.section` 注入；AgentsWorkshop 的品牌定义就是它的样板 |
| 14 | **从合并的 MR 抽取知识**（CI 评论模式 → reviewer 👎 否决 → 合并后写入） | 有"修改即学习" | 加"从已完成的工作项抽取"：审批通过并发出的邮件、关闭的售后单，事后抽取候选知识，审批人可 👎 |
| 15 | **模板仓起步**（teamai-hub "Use this template"） | 有 3 / 15 / 50 人模板的想法 | 工作区模板做成可浏览的"起步包"：按行业（3C / 家居 / 服饰）× 规模；服务商可发布自己的 |
| 16 | **recall 前的相关性预检**（`--check` 不读文件不 upvote，无关就跳过检索） | 知识 MCP 没设计 | 检索接口加预检，省 token 也省误召回 |
| 17 | **卸载保留用户自建内容**；`doctor` 诊断 | 有 doctor | 卸载 / 退出工作区时明确"哪些是你的、哪些是公司的"——与 Join 的退出条款对应 |

## 2. 我们没考虑到的（不只是细节）

1. **Agent 使用健康度是 owner 的刚需。** teamai 的 digest / dashboard 给团队看：token 用量、对话量、人均干预率、某个 skill 上线后干预率有没有降。我们的日报全是业务数字，没有"Agent 本身干得怎么样"。老板花钱买 Agent，第一个问题就是"它到底省了多少、错了多少"。要有一张 **Agent 健康看板**：按职责 / 按人 / 按技能的干预率、采纳率、token 成本、L 等级分布、知识缺口数。这也是天然的付费项。
2. **公司库要能被员工的其他 AI 工具消费。** 老板或运营可能同时在用 Claude Code、Codex、ChatGPT。我们的公司知识与技能如果只活在中台里，就是又一个孤岛。teamai 已经把 dsh 列为分发目标，反过来说明**公司库导出成 teamai 仓布局是零成本的互通**：`skills/ rules/ docs/ learnings/` 四个目录。做一次，公司的知识就能进员工的所有 AI 工具。
3. **知识的"沉默"比"错误"更常见。** 大多数知识条目写了没人用；teamai 用召回次数发现它们。我们的知识库要从第一天记录每条被检索 / 被引用的次数。
4. **删除与撤回的传播。** 我们设计了怎么加（提议 → 审批 → 分发），没设计怎么删。tombstone + 撤回也是审批项。
5. **急停开关。** 每个自动化行为（自动学习、L2 自动发、recall 注入）都要有一个环境变量 / 设置级的"立刻全关"，不经审批。出事时先关再查。
6. **上报数据与知识资产分开存**（teamai 用孤儿分支放 members / sessions / votes / stats）。我们的事件日志和内容仓已经分开，但"统计数据"（干预计数、召回计数）该归哪边没定——归事件日志的聚合表，不进内容仓。
7. **跨工具的秘密处理**：`${VAR}` 声明、拉取时解析成明文落盘且 0600、明确告知"会落盘请 gitignore"。我们个人端的连接器凭据也会落盘，要写同样清楚的告知。

## 3. 商业化发散：用户不懂 IT、不会 git，钱在哪

### 3.1 一条原则

**免费 = 所有跑在用户自己机器上、用用户自己账号的东西；付费 = 需要我们的基础设施、我们的平台身份、我们的数据、或我们的人的东西。**

这条线的好处：它不是按功能砍免费版（开源社区最反感），而是按"谁承担成本 / 谁持有资质"划分，用户一听就懂。

### 3.2 免费（开源本地版）给什么

全部核心能力：桌面 App、公司实例（跑在一台 Mac / 迷你主机 / NAS）、所有职责与岗位模板、所有开源 skill、所有连接器代码、审批队列、知识库、学习回路、evals、Join、导出导入、Agent 健康看板的本地版。用户自带模型 key、自带存储、自带各平台开发者账号。

一家 3 人公司靠它能把客服和红人完整跑起来（L1）。这是承诺，不是残废版。

### 3.3 付费线（八条，按"非 IT 用户为什么付"排）

| # | 线 | 卖什么 | 非 IT 用户为什么付 | 计费 |
|---|---|---|---|---|
| P1 | **连接服务（Connect）** | 我们持有各平台的**开发者身份**：Meta 应用（Instagram / Facebook / WhatsApp）、TikTok 开发者、Google Ads / Merchant Center、Amazon SP-API 开发者注册、YouTube 配额、WhatsApp BSP。用户在中台点"连接"→ 走我们的 OAuth 应用 → 授权完成 | **这些审核个人根本过不了**（Meta 应用审核、Amazon 开发者注册、WhatsApp BSP 都要公司资质与数周审核），且 API 配额按应用算。开源代码里放不下应用密钥，所以自托管必须自己申请——绝大多数人做不到 | 免费档有限额（渠道数 / 月调用），超出按席位或按量 |
| P2 | **模型网关（Credits）** | 预充值积分，走我们的网关调 DeepSeek / 千问 / OpenAI / Anthropic；按职责记账；prompt 缓存；付费插件的云端大脑也走它 | 不用注册境外账号、不用境外信用卡、不用管多家 key；一个余额看全公司 | 积分（已有体系，1 积分 = $0.01）；网关加价 |
| P3 | **托管（Hosted）** | 我们托管公司实例：常开、备份、换机一键恢复、远程访问（手机也能审批）、自动升级 | 没有常开机器、不会配组网、怕丢数据 | 按工作区 + 席位包月 |
| P4 | **付费职责包（现有产品线）** | KefuAgents / KOLAgents / BtoBAgents：外部数据供给（公共红人库、海关数据、平台买家消息）、领域大脑、高级 skill、L2 / L3 自动化、SLA | 免费版只懂你自己写过的知识；付费版懂行、能自己跑 | 积分按量（数据查询、云端推理） |
| P5 | **渠道基建即服务** | 邮件送达（域名预热、轮换、SPF / DKIM / DMARC 全托管）、WhatsApp 号码质量监控、会议 bot（入会录音转写） | 这几样每一样都是专业活；BtoB 讨论稿已判断"不能指望客户自己懂" | 按发送量 / 按会议时长 |
| P6 | **技能与模板市场** | 第四层"外部源"：官方认证包、行业 playbook（3C / 家居 / 服饰）、服务商发布的模板与连接器、eval 套件；分成 | 想要"别人已经踩平的路" | 一次性 / 订阅；平台抽成 |
| P7 | **团队与治理（Team）** | Agent 健康看板完整版（跨人对比、趋势）、知识库健康、审计导出、SSO、多店铺 / 多品牌、部门层级、高级审批路由、GDPR 数据驻留选项、职责分离 | 15 人以上公司的管理需求 | 席位包月 |
| P8 | **服务与伙伴** | 陪跑上线、知识库整理（把现有 FAQ / SOP / 邮件历史导入）、定制连接器、代运营商的多客户管理 | 就是没人会做 | 项目制；伙伴计划分成 |

**P1 经 09-08 独立评审修正**：平台应用身份确实只能属于法人实体，但（a）Gmail 受限 scope 要安全评估、Amazon 有角色与 PII 条件、WhatsApp 可直接走 Cloud API 不必经 BSP、配额不随客户数增长——所以 Connect 不是可普遍转售的通行证，而是**按平台逐项立项的配套服务**：每个平台一张资格证据表（应用主体、审批状态、scope / role、端点、市场、数据流），拿到生产批准前不承诺销售；v1 只做不需平台审核的路径（Shopify 自建 app、API key 类、邮箱 IMAP）。

**Gmail 核实（09-08，Google 官方）**：Gmail 读写属 restricted scopes，须 scope 验证；"apps accessing restricted data from or through a third-party server" 须每年经 Google 认可的第三方做 CASA 安全评估，流程"potentially several weeks"，且每 12 个月复审；例外含 personal use、组织内部使用、dev/testing。含义：(a) **我们托管的 Connect** 一旦代持 Gmail OAuth 应用 = 第三方服务器 → 必须 CASA，是一项年度成本；(b) 本地 runtime 用**用户自己的** OAuth 应用可能落在"组织内部使用"例外，但要逐案确认；(c) v1 最稳的是 **IMAP + 应用专用密码**（无 OAuth 审核）。Gmail OAuth 应用作为独立立项，拿到验证前不进 Connect 售卖清单。

### 3.4 第三方服务：能引入什么，谁来配

原则：**每一项都要回答"非 IT 用户能不能自己配"**。不能的，就是我们 Connect 或托管的一部分。

| 类别 | 候选 | 用户能自己配？ | 我们的角色 |
|---|---|---|---|
| 模型 | DeepSeek、通义千问、豆包、OpenAI、Anthropic | 国内的能；境外的多数不能（支付） | 网关统一接入（P2） |
| 身份 / IM | 飞书、企业微信、钉钉 | 能（但要在各自后台建应用，中等难度） | 提供向导；托管档我们代建 |
| 存储 / BYOC | Supabase、Neon、Turso、Cloudflare R2、阿里云 OSS、群晖 / QNAP NAS | 半能（注册能，配连接串不能） | 向导 + 自动识别 NAS |
| 邮箱 | Gmail、Outlook、Zoho、阿里企业邮、Cloudflare Email、Resend | 收发能；送达率配置不能 | 收发免费；送达托管付费（P5） |
| WhatsApp | Meta 官方 BSP（360dialog、Twilio、YCloud 等） | 不能（要 BSP 与企业验证） | 我们做 BSP 或转售（P1） |
| 会议 | Zoom、Google Meet、Teams、腾讯会议；**Recall.ai** 这类会议 bot API 一次接四家 | 不能 | 托管会议 bot（P5） |
| 物流追踪 | 17track、AfterShip | 能（注册拿 key） | 连接器 + 向导 |
| 评价 | Judge.me、Loox、Shopify Reviews | 能 | 连接器 |
| 邮件营销 | Klaviyo、Shopify Email | 能 | 连接器 |
| 数据供给 | Apify、Keepa、ImportGenius / Volza（海关）、Modash / Collabstr（红人） | 能但贵且要会用 | 付费职责包内置（P4） |
| 广告平台 | Google Ads、Meta Marketing、TikTok Marketing、Amazon Ads | **不能**（开发者应用审核） | Connect（P1） |
| 社媒平台 | Meta Graph、TikTok、YouTube Data、Pinterest、X | **不能**（同上，且 YouTube 配额按应用） | Connect（P1） |
| 电商平台 | Shopify（能，自建 app）、Amazon SP-API（不能）、TikTok Shop（不能） | 分化 | Shopify 免费直连；Amazon / TikTok Shop 走 Connect |
| 远程访问 | Tailscale、Cloudflare Tunnel | 半能 | 桌面 App 内置组网向导；托管档不需要 |
| 备份 | restic / Kopia 到任意 S3 兼容 | 不能 | 内置加密备份到用户自己的对象存储（免费）或我们的（付费） |
| 支付（我们收款） | Waffo、Creem、Stripe | — | 已有 |

### 3.5 收入结构小结

```
（09-08 独立评审后重排，见 31 §1 I1）
 主收入 ───── P4 业务能力（结果导向）> P3 托管 > P8 服务
 配套收入 ─── P5 渠道基建（按量）、P1 Connect（按平台逐项）、P7 Team
 不作收入预测 ─ P2 模型加价（薄）、P6 市场（不抽成，成本中心）
 定价原则 ─── 覆盖每租户支持成本；"本地免费"含全部自动化等级与治理（待 Luoye 确认，31 §5.1）
```

开源本地版永远免费；它的作用是把 3–10 人公司变成 P1 / P2 的用户，把 10–50 人公司变成 P3 / P7 的用户。

## 4. 明确不借鉴的

- git 作为用户可见的心智模型（他们的用户是开发者；我们隐藏 git，见架构总览 §四）
- 终端 CLI 作为主入口（我们是桌面 App；CLI 只给开发者和部署）
- learnings 全团队可见、无权限过滤（我们的检索必须带身份）
- 代码知识图谱（我们的图谱是客户 ↔ 订单 ↔ 事实卡，不是代码）

## 5. 待拍板（09-08 Luoye：1 定案 Connect 进 v1；2、3、4、5 原则同意，数值到定价阶段定）

1. 是否把 **Connect（平台应用身份代理）** 列为第一条付费线并在 v1 就建（它决定社媒 / 广告 / Amazon 连接器在自托管下能不能用）
2. 公司库是否做 teamai 兼容导出（成本很低，收益是互通与引流）
3. 模型网关的加价幅度与免费额度（P2）
4. Agent 健康看板：本地免费版给到什么粒度，Team 版多什么
5. 是否自己做 WhatsApp BSP 还是转售（前者周期长、后者毛利低）
