## 0. 一句话

agency-agents 是一套**写得很用心的「人设 + 做法」提示词库**：282 个角色、每个一份 Markdown，装进 Claude Code / Cursor / DSH 等十几种工具里当子代理或技能用。它强在**广度**（营销、销售、客服之外还有定价、数据、合规、财务、实验、选品等「后台」角色）和**单个文件的交付物模板**；弱在**没有任何执行与约束**（没有权限、没有额度、没有审批、交接靠人复制粘贴），以及**成功指标几乎全是拍脑袋**（243 个文件写了成功指标，197 个带具体数字目标，**没有一个**写出处）。

对我们最有用的不是「再多开几个岗位」，而是三件事：
1. **按我们「职责按人切」（50 §0）的规矩，它的大多数「角色」该落成我们的技能，不是职责**——它有 7 个付费广告角色，我们是 4 条按平台分的投放职责 + 技能；它的拆法是按专业切，我们按人切。
2. **缺口集中在「后台」五样**：经营数据与周报、合规（产品认证 / 宣称 / 包装与税）、定价与单位经济（毛利、盈亏线）、客户声音汇总、实验与转化率。前四样对跨境电商公司都是天天要的（§2.2）。
3. **写法上我们缺的是「交付物长什么样」「交出去前查什么」「谁把活交给我、我交给谁」**——但 persona 已经贴着 260 字上限，这些**不该塞进 persona**，该补在技能和结构化字段里（§3）。协作上值得借的是它的**交接单**与**跨角色 runbook**：把 persona 里那句「你不负责→转给 X 岗位」从一句话变成一个真能点的动作（§4）。

顺手查到两处我们自己的问题：**14 条职责的英文 persona 里混着中文**（`ads/*` 四条、`design/*` 五条、社媒五条，「Who you are」那一句）；**约 23 条职责没有任何「做法」技能**，只挂了 `brand-voice` 或什么都没挂（§3.3）。

## 1. agency-agents 是怎么组织角色的

### 1.1 部门与数量

部门是顶层目录，`divisions.json` 是唯一真源（CI 里校验目录、转换脚本、lint 三处一致）。18 个部门 282 个角色：

| 部门 | 数 | 和出海营销的关系 |
|---|---|---|
| specialized（杂项） | 59 | 混着放：客服、退货、客户成功、定价、供应链、翻译、编排器、幕僚长……也有医疗、法律、房产、留学 |
| engineering | 65 | 基本无关（两个购物车开发者是 Drupal / WordPress） |
| marketing | 37 | **13 个面向中国国内平台**（抖音、快手、小红书、微博、知乎、B 站、公众号、百度 SEO、私域、直播带货、中国电商、中国本地化、多平台分发）；跨境相关的只有 1 个「跨境电商」通才；其余是 TikTok / IG / X / LinkedIn / Reddit / YouTube / 内容 / SEO / AI 引用 / 邮件 / 增长 / 公关 / 播客 |
| game-development | 21 | 无关 |
| gis / security / spatial-computing / academic / healthcare / research | 41 | 无关 |
| design | 10 | 品牌守护、AI 出图提示词、包容性视觉、UI / UX 若干 |
| sales | 9 | 外拓、需求挖掘、方案书、大客户扩展、管道分析、教练…… |
| testing | 9 | 证据收集、「现实检查」（默认判不合格）等质检角色 |
| paid-media | 7 | 搜索广告、社交广告、素材、搜索词、追踪、账户审计、程序化 |
| project-management | 7 | 实验追踪等 |
| product | 6 | 反馈汇总、趋势研究等 |
| support | 6 | 客服应答、数据报表、高管摘要、财务、合规、基础设施 |
| finance | 5 | 记账、FP&A、财务分析、税务、投研 |

**它是按「专业」切的**：同一件事按工种拆成好几个角色（付费广告拆成 7 个：投搜索的、投社交的、做素材的、看搜索词的、搭追踪的、做审计的、买程序化的）。这和我们 50 §0「一条职责 = 中小公司里同一个人干的一摊活」正好相反——我们的投放是按**平台**切成 4 条（Meta / Google / TikTok / X），每条都包含了它那 7 个工种的活。所以对照时，它的一个「角色」多半对应我们的**一份技能**或**一个动作**，而不是一条职责（§2.1 表里逐条标了）。

### 1.2 一个角色文件长什么样

`CONTRIBUTING.md` 给的模板：YAML 头（`name` / `description` / `color` / `emoji` / `vibe`，可选 `services` 声明依赖的外部服务、`tools`、`author`）+ 九段正文。贡献指南把这九段分成两组——**人设组**（身份与记忆、沟通风格、硬规矩）和**做事组**（核心任务、交付物、工作流、成功指标、进阶能力）；转换脚本按这两组把一个文件拆成不同工具要的格式。

实际覆盖率（282 个文件逐个 grep 小标题，10-05 统计）：

| 段 | 有这一段的文件 | 说明 |
|---|---|---|
| 硬规矩（Critical Rules） | 258 | 写法参差：好的是 10 条具体禁令（退货、记账），差的是 8 条正确的废话（「确保品牌一致性」） |
| 成功指标 | 243 | **197 个带具体数字目标，0 个写出处**（§1.5） |
| 工作流 | 246 | 多是 4 步「调研 → 规划 → 执行 → 复盘」，好的带检查点 |
| 沟通风格 | 244 | 多数带 3–5 句「示范台词」 |
| 交付物 | 225 | **它真正的长处**：报告 / 清单 / 计算表的现成格式，很多带代码块模板 |
| 学习与记忆 | 176 | 写的是「记住哪些模式」，没有机制（机制靠外挂 MCP 记忆，§1.3） |
| 打勾清单（`- [ ]`） | 45 | 退货、方案书、合规、跨境选品等 |
| 写了升级 / 转交给谁 | 51 | 多是一句「超出权限就升级」 |
| 写了上下游协作对象 | 50 | 只有 **4 个**明确写「谁交给我 / 我交给谁」（例：社媒策略师写了「上游：内容、趋势、品牌；下游：数据、增长、销售；敏感话题升级给合规」） |
| 「什么时候用我」 | 36 | 类似我们的 `task_examples` |

文件长度中位数 243 行，最短 32 行、最长 759 行。对比：我们一段 persona 中文 ≤ 260 字。

### 1.3 多角色怎么协作、怎么交接

单个角色文件里几乎不写协作（上表：只有 4 个写清上下游）。协作全在 `strategy/` 这一层，叫 **NEXUS**：

| 机制 | 是什么 | 适用面 |
|---|---|---|
| 七阶段流水线 | 发现 → 策略 → 搭架子 → 开发 ↔ 质检 → 加固 → 上线 → 运营，**每两阶段之间一道闸**，闸有打分表（标准 / 门槛 / 结果 / 证据） | 为软件产品开发写的；营销只出现在「上线」「运营」两段 |
| 指挥结构 | 一个「编排器」角色在顶上，下面制作人 / 项目经理 / 分部负责人 | 同上 |
| 三种规模 | 全量（所有角色，12–24 周）/ 冲刺（15–25 个，2–6 周）/ 微型（5–10 个，1–5 天） | 「内容活动」在微型里：内容 → 社媒策略 → X / IG / Reddit 几个平台角色 |
| 交接模板（7 种） | 标准交接、质检通过、质检不通过、升级报告、阶段闸、冲刺交接、事故交接 | 标准交接 = 从谁到谁、现状、相关文件、依赖、约束、**要什么 + 验收标准**、证据要求、**下一棒是谁、要什么格式** |
| 开发 ↔ 质检回路 | 每个任务交给质检；不过就带「具体问题 + 改法 + 只改这些」退回；**最多 3 次**，第 3 次不过写升级报告（三次各改了什么、根因、建议：换人 / 拆小 / 改方案 / 接受现状 / 延后） | 软件任务；思路可以挪到内容与设计稿的审核上 |
| runbook（4 个） | 创业 MVP、企业功能、事故响应、**多渠道营销活动** | 营销那份：14 个角色名单、按周排的分工树、指标与负责人、**品牌一致性检查点**（每条发布前品牌守护过一遍、每周合规过一遍） |
| 记忆 | 外挂一个 MCP 记忆服务（`remember / recall / rollback / search`），每个角色提示里加一段「开工先回忆、做完存一笔、交接时打上给下一棒的标签」 | 让「人当胶水、复制粘贴上一棒的产出」少一点 |

一句话：**它的协作是「文档约定 + 人来驱动」**。用户说「激活 X 角色」，把上一棒的产出贴进去；编排器角色本身也只是一段提示词。没有路由、没有权限、没有审批，交接对不对全靠模板写得全不全。

### 1.4 怎么分发：它已经能装进 DSH

`scripts/convert.sh` 把同一批文件转成 15 种工具的格式；**其中一种就是 DeepSeek Harness**（`integrations/dsh/`）：每个角色变成一个 `agency-<名字>` 技能，装到 `${DSH_HOME:-~/.dsh}/skills/`，DSH 会热加载。

对我们的影响查过了，**结构上进不来，不用做事**：我们跑岗位用的是 dsh-adapter 自己搭的最小组合（`packages/dsh-adapter/src/harness.ts`），**不挂 `dsh-skill`、不读 `DSH_HOME`**（`browserskill.ts` 的注释写明「我们的组合里没有 dsh-skill」）；工坊里能打开的官方场景用的是我们应用数据目录那份 `DSH_HOME`（79 §2），不是 `~/.dsh`。所以用户自己装了 agency-agents，它的 282 个人设不会混进我们岗位的系统提示——这正是 69 要防的串岗。唯一要记一笔的：DSH 官方的技能扫描还认 `~/.agents/skills`；**哪天我们的组合挂上 `dsh-skill`，要先关掉用户层的扫描根**，否则这条路就通了。

另外它有社区中文译本（`jnMetaCode/agency-agents-zh`，MIT，21,058 星，141 个译本 + 46 个中国市场原创）。**引进只从英文原仓自己改写**：译本的著作权人是另一批人，引它就要另登记一份署名，而它的中国市场原创对出海用处不大。

### 1.5 质量判断：哪些好、哪些拍脑袋、哪些不该学

**好的（值得学）**：
- **交付物模板具体**：退货资格判定单（窗口剩几天、品类限制、例外要谁批）、跨境选品打分表（市场 / 毛利 / 合规三维）、邮件流程设计单（触发 / 分群 / 每封 / **退出条件** / 合规）、AI 引用审计的「丢失问法分析 + 修复包」、账户审计的严重度分级。
- **硬规矩写成禁令而不是口号**：退货「不当面指控客户欺诈」「每个例外都记下理由和批的人」「同一政策对每个客户一样执行」；定价「没有算式不报价」「每个折扣都要有理由和到期日」；AI 引用「永远不保证被引用、先测基线再改」；记账「职责分离：发起的人不批」。
- **「现实检查」质检角色的立场**：默认判「还不行」，前一棒给的满分当成危险信号，每条结论去对证据。

**拍脑袋的（不搬）**：
- 成功指标 197 个带数字、0 个有出处。例：内容创作者「全平台平均互动率 25%」「内容带来的线索 +300%」；增长黑客「月自然增长 20%+」「K 因子 > 1」「7 日留存 40%」；社媒策略师「每月涨粉 8%」；品牌守护「品牌一致性 95%+」。**连贡献指南自己的示范都是「多个账号合计 10,000+ karma」**——这句会把人往小号上引（89 §1.1 已记）。
- 模板里的默认数当成了事实：跨境通才的打分表写死「月搜索量 > 10,000」「首页平均评论 < 500」「售价 $15–50」「平台佣金 15%」「目标 ACOS 25%」，平台对比表写死各平台毛利区间。这些如果引进，**只能进公司层阈值或事实卡**，不能进技能正文（与 69 §5.1「数字与日期不写进 persona」同一条理由）。

**做法本身不该学的**：
1. **规避平台检测**：多平台分发角色要求「同一张图在不同平台改一下裁切 / 亮度，让 MD5 不同」「同平台两帖之间随机等 30–180 秒」——这是绕反垃圾，不是运营。
2. **不经人审直接发**：轮播图增长引擎「生成后直接发到 TikTok / IG 的 feed」。营销 37 个角色里只有 10 个提到草稿或人审，只有 3 个提到 FTC / 广告披露。
3. **客服的「先共情、绝不说不行、这事我来搞定」**：通用客服角色要求「承担问题：『我来帮您搞定』」「永远不说做不到」——和我们客服技能「不写完成式、不承诺、不写道歉段、做不到就说要同事确认」（`customer-care` SKILL.md）正面冲突。我们的写法是对的：跨境客服里一句「我来搞定」就是一个没人批的承诺。
4. **强人设当卖点**：每个角色一个 emoji、一句 vibe、一段性格。对个人开发者是乐趣；对我们，persona 是**公司对外的口径**（69 §4.1 只有公司层、没有个人层），口气要跟品牌档案走，不跟角色性格走。
5. **一个角色包打天下**：跨境电商通才一个文件管 6 个平台运营 + 物流 + 税务合规 + 多语种 listing + 广告 + 收汇 + 选品 + 品牌出海 + 客服——违反它自己「窄而深」的原则。我们按人切，这类内容要拆进好几条职责的技能里。
6. **让模型自己决定记什么**：MCP 记忆那套「由 LLM 判断什么值得记」。我们的记忆写入走「提议 → 批准」（54 §3），手改本层当场写、提上一层要卡——不改。
7. **自动重试回路**：开发 ↔ 质检最多 3 次自动来回。对外发东西的活（帖子、开发信）自动来回改到通过 = 没人看就发了第三版；我们只借它「退回时写清具体问题和改法」的格式（§4.2）。

另有一类「不相关但不是坏」的：13 个中国国内平台角色（抖音、小红书……）、医疗营销合规（只讲中国法规）、所有工程 / 游戏 / GIS 角色。不进对照。

## 2. 覆盖对照

### 2.1 和出海营销 / 跨境电商相关的角色，逐个落到我们这边

判断四档：**覆盖**（我们有、且不比它浅）/ **部分**（有落点，它有一块我们没有）/ **缺** / **不需要**。「落成什么」按 50 §0 判：中小公司里是不是同一个人在干。

| 它的角色（文件） | 一句话 | 我们的落点 | 判断 | 落成什么 |
|---|---|---|---|---|
| `marketing-content-creator`、`-seo-specialist`、`-aeo-foundations` | 内容、SEO、答案引擎 | `dtc.content` + `seo-judgment` | 覆盖 | — |
| `marketing-ai-citation-strategist` | 查品牌在 ChatGPT / Claude / Gemini / Perplexity 里被不被引用 | `dtc.content` 的 `ai_visibility`（WP154 / 155） | 部分 | 技能补「丢失问法 + 修复包」格式 |
| `marketing-email-strategist` | 生命周期邮件、分群、送达 | `dtc.email-marketing` + `email-sms` | 部分 | 技能补三条（§5 #4） |

### 2.2 它有、我们缺、对跨境电商公司有用的——按价值排

都先按 50 §0 过一遍「中小公司里是不是同一个人在干」。结论是**一个都不必新开岗位**：这几样在中小跨境公司里要么是老板自己看（数据、合规、定价），要么是现有某个岗位顺手做（客户声音、实验、本地化）。所以落点是**技能 + 少量动作**，挂到现有职责上。

| # | 缺什么 | 为什么对出海公司要紧 | 它那边的素材 | 建议放哪 |
|---|---|---|---|---|
| 1 | **经营周报**：把各岗位的数（店铺日报、广告两口径、内容按页收入、社媒近 30 天、红人归因、客服量）汇成一页给老板 | 现在每个岗位各说各的数，老板要自己拼；agency 的高管摘要格式（情况 / 发现 / 影响 / 建议 / 下一步，每条发现带一个数、总长 ≤ 500 词）正好是这一页的骨架 | `support-executive-summary-generator`、`support-analytics-reporter`（「先验数据再分析」「每个结论写来源与假设」） | `common.owner` 加一个只读动作「本周经营一页纸」+ 技能 `weekly-review`；秘书每周一推。数字只从各岗位已有的面板取，**取不到就写取不到**，不估 |
| 2 | **合规**：宣称合规（「最便宜」「治愈」「环保」「前后对比」）、产品认证与市场准入（CE / FCC / UKCA、德国包装法、EPR、电池 / 电子垃圾）、广告与红人披露 | 跨境卖家被平台下架、被罚，多半出在这里；我们现在只有四份政策的 `policy-review`，以及散在 `email-sms`（TCPA / GDPR）、`influencer-marketing`（FTC）里的几段 | 跨境通才的「合规红线」段、`support-legal-compliance-checker`（每条合规决定写依据与法规出处、审计留痕）、直播带货的宣称禁令 | 拆两份技能：`claims-check`（宣称合规，挂在所有对外出稿的职责上，和 `brand-voice` 一样 always）；`market-compliance`（产品与市场准入清单，挂 `common.owner` 与将来的 Amazon 运营）。**法规条目进事实卡、带日期，不写死在技能里** |
| 3 | **定价与单位经济**：一件货的落地成本、毛利瀑布（采购 + 头程 + 仓储 + 平台佣金 + 广告 + 尾程 + 退货损耗 + 汇率）、盈亏线 ROAS | 我们改价有额度、投放有止损，但**止损线是固定的 ROAS < 1**（57 §3）——毛利 40% 的货 ROAS 要到 2.5 才不亏，按 1 止损等于一直在亏钱的那段不报警 | 跨境通才的「毛利纪律」（广告费率超过毛利率就关）、`specialized-pricing-analyst`（没有算式不报价、按人群定价不按平均、折扣要理由与到期日、优先用替代折扣的手段） | 技能 `unit-economics`，挂 `dtc.store`、投放四条、将来的 Amazon 运营；毛利率是公司事实卡里的一格。止损线怎么改要 Luoye 定（§7 #2） |
| 4 | **客户声音**：把评价、客服来信、评论区、退货原因汇成「这个月客户在抱怨什么、夸什么」，回给 listing、详情页、广告文案和产品 | 我们客服、社媒、店铺评价各自处理单条，没有人看「同一个问题来了 40 次」；`audience-research` 是去外面挖原话，不看自己家的 | `product-feedback-synthesizer`（收集 → 归类 → 打分 → 交付）、退货角色的原因码表 | 技能 `voice-of-customer` + `dtc.store` 一个每月动作；退货原因码先在 `returns-policy-calc` 里统一，后面才汇得起来 |
| 5 | **实验与转化率**：一次只改一处、改之前算样本量、不中途偷看就停、写清假设与回滚 | 改价、换主图、换邮件主题、换广告素材都是实验，现在没有任何「怎么判这次改得好不好」的规矩，容易一两天的波动就下结论 | `project-management-experiment-tracker`（硬规矩 8 条、实验设计单）、增长黑客的漏斗拆法 | 技能 `experiments`，挂 `dtc.store`、`dtc.content`、`dtc.email-marketing`、投放四条 |
| 6 | **本地化**：listing / 详情页 / 邮件 / 广告的多语种，母语审校，按市场改单位、尺码、节日、禁忌 | 机翻 listing 转化差是行业共识；我们 `brand-voice` 只管「用客户的语言回」 | 跨境通才的「本地化原则」四条、翻译角色的「按意思不按字」「标出正式 / 非正式」「医疗法律不猜」 | 技能 `localization`，挂内容、店铺、邮件、投放、社媒；**出卡时标「机翻未审」**，这条进卡片而不是只进提示 |
| 7 | **广告账户体检**：结构、追踪、出价、素材、商品 feed、落地页逐项打分，按严重度排 | 投放职责现在会止损、会对账，但没有「新接手一个账户先体检一遍」这件事 | `paid-media-auditor`（六大块、严重度四级、每条带影响与改法）、`paid-media-tracking-specialist` | 技能 `ads-audit`，挂投放四条；体检结果是一张只读报告卡 |

排在后面、本轮不建议做的：**短视频成片**（设计岗只做图，§7 #4）、**直播带货**（等 TikTok Shop 排上）、**选品与趋势**（产品范围问题，§7 #3）、**财务对账**（等 Amazon 运营与 SP-API）、**B2B 大客户健康分**（B2B 岗位先把询盘到报价跑通）。

### 2.3 我们有、它没有的（我们的长处，别丢）

| 我们 | 它 |
|---|---|
| **权限、额度、自动化级别**：每条职责有数据域 × 操作 × 范围、每个动作有额度与窗口、L1 / L2 / L3 与硬顶（04 §0、15） | 只有正文里的「硬规矩」，模型守不守全看自觉；只有 6 个文件声明了依赖的外部服务 |
| **对外动作一律出卡**：发帖、发信、改价、退款、投预算都是提议，人批了执行器才做 | 营销 37 个里只有 10 个提到草稿或人审；轮播图引擎直接发 |
| **数字只从记录和事实卡来**（`customer-care`「数字不由你产生」、69 §5.1、guardrail 数字出处） | 197 个文件带数字目标、0 个有出处；模板里的默认数会被当成事实 |
| **防串岗**：persona 第三段「你不负责→转给哪个岗位」+ 串岗测试（69 §5） | 4 个文件写了上下游；角色之间的边界靠用户自己选对角色 |
| **一个入口、岗位内路由、拿不准就问**（54） | 用户自己说「激活 X 角色」；编排器只管软件开发流水线 |
| **记忆分层 + 提升要批**（54 §3、24） | 外挂 MCP 记忆，由模型自己决定记什么 |
| **外部内容当数据不当指令**（`customer-care` 的围栏一段、`core/fencing.ts`） | 282 个里 11 个提到提示注入或不可信输入；通用客服角色没有 |
| **出海执行的深度**：红人五渠道、社媒十二渠道、投放四平台、B2B 询盘 → 报价 → 跟单单证 → 展会、拒付举证、退款计算 | 没有红人经理、没有评价管理、没有展会、没有外贸单证、没有拒付；跨境只有一个通才 |
| **真连接与真动作**：Shopify、Meta、Google、邮箱、各社媒适配器、受控浏览器 | 纯提示词 |
| **冷启动给人看的**：每条职责的 `quick_prompts`（点一下就开干）与 `task_examples`（典型活 + 你会拿到什么） | 36 个文件有「什么时候用我」 |
| **自动化级别靠实测采纳率升降**（`automation.*.promotion.adoption_rate_min`，例：连续 4 周采纳率 ≥ 95% 才升） | 成功指标只写目标、不量 |

最后一行值得单说：它的「成功指标」是写给模型看的愿望；我们真正在量的指标只有一个——**人批不批 Agent 的提议**——而且它直接决定这条活能不能升到自动。这比 243 段目标数字有用。**不建议往职责里加「成功指标」段**；要加，加的是「这条职责看哪几个数」（不写目标），而这些数已经是各职责面板上的数字块（36 §3）。
