## 1. 开发者路径：规范在我们这，代码在他们熟悉的工具里

原则一句话：**我们提供规范、脚手架、测试与发布通道；写代码用 Claude Code / Codex / dsh 随便哪个。** 平台里没有代码编辑器，也不做"在线 IDE"。

### 1.1 开发者工具包（agentsws DevKit）的五样东西

| 件 | 是什么 | 给谁用 |
|---|---|---|
| **规范** | `package.yml` schema（11 §2）、职责 schema（05）、Agent Skills 格式、积木组件注册表与命名查询规范、OpenConnector provider 贡献规范、远程 Backend 契约（HTTP + OpenAPI）、模拟场景 DSL | 人和编码 Agent 都读 |
| **编码 Agent 技能包** | 一组 Agent Skills 格式的 `SKILL.md`：`agentsws-package-dev`（怎么写一个职责包）、`agentsws-connector-dev`（怎么写 provider）、`agentsws-backend-dev`（怎么实现远程 Backend）、`agentsws-block-dev`（积木）。装进 Claude Code / Codex / dsh 后，它们就会按我们的规范干活 | **这是主要的开发者入口**：不是让人学规范，是让他们的编码 Agent 学 |
| **脚手架** | `agentsws create <kind>`：访谈式（Commerce Agents commerce-builder 的做法）：问 8–12 个问题 → 生成包骨架、示例场景、eval 用例、CI 配置 | 起步 |
| **本地测试** | `agentsws test`：schema 校验 + 契约版本兼容 + 一致性套件 + **在本机模拟回路里跑包自带的场景**（fast 档），出与市场审核完全相同的报告 | 提交前自测；本地过 = 市场审核过 |
| **发布** | `agentsws publish`：签名、上传、进审核管线；或从工作台"发布到市场" | 发布 |

**开发者体验的目标**："在 Claude Code 里说一句'给 agentsws 写一个 Etsy 客服职责包'，它读我们的技能包、生成包、跑 `agentsws test`、全绿后 `agentsws publish`。"人全程不用看规范文档。

### 1.2 GitHub 一体化

提供一个 GitHub Action：PR 里自动跑 `agentsws test`，把模拟报告贴成评论；合并到 main 自动发布到 registry 的 `community` 通道（声明类包）。这就是 teamai `ci extract-mr` 的形状，也是 11 §5 审核管线的 CI 端。

### 1.3 远程 Backend 的开发者路径（伙伴做付费能力的方式）

伙伴不需要碰我们的代码：实现一份 OpenAPI 描述的 Backend 契约（读方法 + `stage_*` + `apply_change` + `limitations`），部署在自己的服务器；包里只写地址与鉴权。我们给：契约的 OpenAPI 文件、一致性套件的远程版（对着他们的端点跑）、一个参考实现（我们三个 SaaS 的无头 API 就是参考实现）。

## 2. 新岗位：建站与开发（半刚需）

放进 04 文档的岗位清单，作为第七个岗位。定位：**Agent 负责需求、验收、预览、发布门禁；写代码交给编码 Agent；一切上线走 staged change。** Shopify 主题天然适合这个模式——未发布的主题副本就是 stage，预览链接就是审批材料，"发布"就是 apply。

| 职责 | 一句话 | Agent 做什么 | 编码交给谁 | 连接器 | 自动化上限 |
|---|---|---|---|---|---|
| `dev.shopify-theme` Shopify 主题开发 | 主题定制、section、模板、样式；Liquid / Theme App Extension | 把运营的话变成开发任务书（改哪、验收标准、截图对照）→ 派给编码 Agent → 拿回未发布主题副本 → 生成预览链接与前后截图 → stage `publish_theme` | Claude Code / Codex / dsh，经 §2.1 的交接契约；Shopify CLI 推主题 | Shopify（themes 写）、GitHub | 任务书 L3；预览 L3；**发布 L1 永远** |
| `dev.storefront-pages` 独立站页面开发 | 落地页、活动页、博客模板、页面美化、速度优化 | 同上；加 Lighthouse / PageSpeed 验收 | 同上 | Shopify 页面 / 自建站仓库、GA4 | 同上 |
| `dev.apps-extensions` 插件与扩展开发 | Shopify App、浏览器插件、小工具 | 需求 → 任务书 → 派单 → 验收（测试通过、权限最小）→ stage 提交 | 同上 | GitHub、Shopify Partner | 发布 L1 |
| `dev.agentsws-packages` 平台包开发 | 给公司自己或市场做职责包、积木、连接器 | 用 §1 的 DevKit：访谈 → 派单 → `agentsws test` → 晋升 / 发布审批 | 同上 | GitHub、registry | 发布走市场审核 |
| `dev.site-ops` 站点运维 | 域名、DNS、SSL、CDN、备份、监控 | 诊断、变更 stage、告警 | — | Cloudflare（OpenConnector 有 provider）、域名商 | 诊断 L3；改 DNS **L1** |

岗位默认包：`dev.shopify-theme`、`dev.storefront-pages`、`dev.site-ops`；其余可勾。3 人公司通常由运营兼，15 人以上会有一个"建站 / 技术"的人。

### 2.1 开发任务交接契约（Dev Handoff）

这是这个岗位的核心机制，也是"不在我们平台写代码"的技术落点：

```
DevTask {
  brief          任务书：目标、改动范围、验收标准（含截图对照、Lighthouse 阈值、测试）、禁区（不能碰结账 / 支付 / 税务）
  repo           仓库或主题：GitHub 仓 + 分支，或 Shopify 主题 id
  executor       编码 Agent：dsh（本机 headless）| Claude Code | Codex | 人
  budget         token / 时长上限
  result         PR 链接 / 未发布主题副本 id / 构建产物 + 测试报告 + 预览链接
  staged_change  发布动作：publish_theme | merge_pr | deploy —— 永远 L1
}
```

执行器只是又一个"替身可替换"的外部边界：本机 dsh 跑 headless 是默认（它本来就是编码 harness），Claude Code / Codex 经各自的 CLI / SDK，人工经"待办 + 回传"。**代码从不进我们的进程**，进的是任务书与结果。

## 3. 命名：技术上叫包，对外叫什么

候选与判断：

| 对外名 | 感觉 | 问题 |
|---|---|---|
| **应用（App）** | "应用市场""安装应用"——你自己那句"和安装 App 一样"就是这个词，用户零学习 | 职责包、模板、连接器都叫"应用"略泛，用**类别标签**区分即可 |
| 数字员工 | 对老板最有画面感："请一个客服数字员工" | 只适合职责包，装个连接器不能叫员工；且容易过度承诺 |
| 能力 | 中性 | 太抽象，"安装一个能力"不像话 |
| 岗位包 / 职责包 | 准确 | 就是"包"，没解决问题 |

**定案（09-08 Luoye）：对外统一叫「应用」，市场叫「应用市场」。** 市场里按类别给第二层名字，卡片上显示类别标签：

| 技术 kind | 市场类别名 | 动词 |
|---|---|---|
| role-pack | **职责** | 安装 / 分配给人 |
| position | **岗位** | 安装 |
| starter | **模板**（"15 人 DTC 公司模板"） | 套用 |
| skill | **技能** | 安装 |
| block | **卡片** | 添加到首页 / 工作面 |
| connector | **连接** | 连接 |
| backend（付费） | **升级**（"升级到 KefuAgents"） | 升级 |
| dsh-plugin（官方） | 不在市场露出 | — |

"数字员工"留作**营销话术**，不做产品名词：市场首页可以写"给你的公司装一个客服"，但按钮上是"安装职责"。

## 4. 计费：两种方式的比较（待议）

| | A · 市场钱包：一个余额，调用哪个服务按量扣 | B · 逐服务订阅：用哪个订哪个，各自付费 |
|---|---|---|
| 用户感受 | 一个账单、一个余额；不用为每个服务开卡 | 花费可预期；"我就订了客服" |
| 免费到付费的摩擦 | 最低：充一次值，所有付费能力都能试 | 每个服务一道墙 |
| 与现有三个 SaaS 的关系 | 三家的积分账户要并成一个钱包（改造大） | 各自维持现有订阅（改造小） |
| 伙伴 | 伙伴服务从钱包结算，我们代收代付（要牌照与对账） | 伙伴自己收钱，我们只管授权 |
| 财务 | 预收款、递延收入、退款复杂 | 简单 |
| 用量型服务（云端推理、数据查询） | 天然合适 | 订阅要设配额，超了怎么办又回到按量 |

**我的建议：钱包做结算层，订阅做计价方式，两者不冲突。** 每个付费应用自己选计价：按量（从钱包扣）或订阅（按月从钱包扣或绑卡代扣）；用户永远只有一个账户、一个账单、一个余额页。三个 SaaS 的改造顺序：先让它们接受"agentsws 工作区授权 + 报用量"，各自积分暂时保留；钱包上线后把三家积分并进来，用户看到的是一次"余额合并"。伙伴第一年只做 B 的形态（自己收钱，我们只发授权），等有对账能力再进钱包。

**定案（09-08 Luoye）：按混合方案做。** 落地顺序：① 三个 SaaS 接受工作区授权 + 报用量；② 钱包上线，合并三家积分；③ 付费应用各自声明计价（按量 / 订阅）；④ 伙伴先自收自付，有对账能力后进钱包。
