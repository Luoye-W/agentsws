## 0. 一句话

**先把"现在是什么样"钉成一份可比对的文件，再动版本号；升级的通过条件不是"测试没红"，是"和钉住的那份一样"。**

差别在哪：测试只钉住我们写下来的断言，基线钉住的是**全部可观测行为**。上游改一个提示词、
多发一个事件、少一次工具调用——单元测试可以全绿，基线一比就露出来。

## 1. checklist（照着做，一步不跳）

### ① 基线：先钉住现在的样子

**在还没动任何版本号的分支上**跑：

```bash
pnpm install --frozen-lockfile
pnpm exec tsc -b --force
pnpm exec vitest run --project @agentsws/dsh-adapter        # 记下用例数
node packages/dsh-adapter/test/upgrade-baseline/capture.mjs  # 按当前装的版本命名
```

`capture.mjs` 把**两档 dsh × pack 里的全部场景**跑一遍，记下四样东西：

| 记什么 | 为什么是它 |
|---|---|
| 事件指纹 `type@at`（类型 + 合成时钟时刻） | 17 §2 的事件序列是运行时契约的可观测面；带上 `at` 能抓到"上游让某一步变慢/变快"这种单看类型看不出的漂移 |
| 六条不变量 + 场景断言 | 31 §1 的安全底线，一条都不能因为升级变色 |
| 指标数值（`tokens_per_item` 等） | 提示词、工具集、轮数的任何实质变化都会在这里显形 |
| 运行摘要（给人看的那句话） | 17 §3。它是模型输出经我们的 `describeRun` 出来的，变了说明模型看到的东西变了 |

**红线**：这一步必须在**升级前**做。事后拿 git 历史"补"一份基线，等于拿升级后的代码解释升级前的行为。

**红线（WP70 补）：基线要在"升级前的**当前**代码树"上重采，不许沿用上一次升级留下的那一份。**
WP41 采的 `0.1.5-rc.1.json` 是 WP41 当天的代码树（pack 只有 13 条场景）；到 WP70 时
pack 已经 30 条，WP42–WP69 还加了 `context.injected` / `guardrail.gate_decided` 等事件。
直接拿它当 FROM，diff 出来的全是**我们自己的改动**，把上游的账算错。
文件名带上 WP 号（`<版本>-wp<NN>.json`），`upgrade.test.ts` 里 `FROM_FILE` 与 `FROM`
分开写：前者是文件名、后者是要断言的 `dsh_version`。旧的两份仍然不删。

**要不要连上游包的类型也存一份**：要，但存在 scratchpad 不进仓库——

```bash
# 升级前，把我们 import 的那些包的 *.d.ts 与 README 抄一份出来
cd packages/dsh-adapter/node_modules/@deepseek-ai
for p in *; do rsync -aL --include='*/' --include='*.d.ts' --include='README*' \
  --include='package.json' --exclude='*' "$p/" "$TMP/old/$p/"; done
```

上游没有 CHANGELOG（10 §3.2 就写明了 dsh 这一条），`.d.ts` 的 diff **就是** changelog。

### ② 观察：上游到底有什么

```bash
npm view @deepseek-ai/dsh dist-tags --json
npm view @deepseek-ai/dsh versions --json | tail -20
```

**红线：dist-tags 要如实写进报告，不许把"latest"当成"稳定版"。** WP41 那次：
`latest` = `next` = `0.1.5-rc.1`，`alpha` = `0.1.5-alpha.2`，**没有裸 `0.1.5`**，
`0.1.4` 整个版本号也没发过。上游预发布期的 latest 就是一个 rc——这件事影响两个决定：
锁精确版本（不用 `^`）、`minimumReleaseAgeExclude` 要加。

顺便看一眼**共享的兄弟包**跟没跟着升：`@deepseek-ai/cordis`、`@deepseek-ai/schemastery`。
它们是 dsh vendored 出来独立发的，`packages/kernel` 也在用——**跟着升是"必要时"才做的事**，
不是默认动作（改了就要跑 kernel 全部测试）。

### ③ 升级：改版本号，把依赖树的变化看完

```bash
# 精确版本，不用 ^
sed -i '' 's/"<旧版>"/"<新版>"/g' packages/dsh-adapter/package.json profiles/agentsws/package.json
pnpm install
```

装完**立刻**比依赖树，别急着跑测试：

```bash
git show HEAD:pnpm-lock.yaml > /tmp/lock-old.yaml
awk '/^packages:/{f=1;next} /^snapshots:/{f=0} f && /^  [^ ]/{print}' /tmp/lock-old.yaml | sed 's/^  //;s/:$//' | sort -u > /tmp/old.pkgs
awk '/^packages:/{f=1;next} /^snapshots:/{f=0} f && /^  [^ ]/{print}' pnpm-lock.yaml   | sed 's/^  //;s/:$//' | sort -u > /tmp/new.pkgs
comm -13 <(sed -E 's/@[^@]*$//' /tmp/old.pkgs|sort -u) <(sed -E 's/@[^@]*$//' /tmp/new.pkgs|sort -u)  # 新增
comm -23 <(sed -E 's/@[^@]*$//' /tmp/old.pkgs|sort -u) <(sed -E 's/@[^@]*$//' /tmp/new.pkgs|sort -u)  # 消失
```

然后按 16 §3「最严解释」处理原生依赖：

| 情况 | 做什么 |
|---|---|
| 新出现的原生依赖 | `allowBuilds: <包名>: false`，**并写注释说明它是什么、为什么不构建** |
| 消失的原生依赖 | 从 `allowBuilds` 删掉，并在 UPGRADE.md 里记一笔——**它可能解锁了某个我们以前放弃的选项**（WP41 那次 `fs-ext` 消失就直接改写了官方 SDK 的评估结论，见第 ⑤ 步） |
| 已有的原生依赖还在 | 保持 `false` |

**红线：不给 dsh 的原生依赖开构建。** 唯一的例外是"子进程档必需"，
而且要在 UPGRADE.md 里点名是哪一个、为什么非它不可。

预发布版本还要加静默期例外：

```yaml
minimumReleaseAgeExclude:
  - '@deepseek-ai/dsh@<新版>'   # pnpm 会把整棵传递依赖树展开进来
```

**红线：写死版本，不写包名通配。** 排除的是"这一个版本"，下一版 rc 出来还得再决定一次。

最后 `pnpm install --frozen-lockfile` 必须通过（不通过就说明 lockfile 没提交全）。

### ④ 修 seam：先编译，再逐个 seam 对着 `.d.ts` diff 看

```bash
pnpm exec tsc -b --force        # 第一道：类型层面的破坏性变更
diff -rq $TMP/old $TMP/new      # 第二道：类型没破但语义变了的那些
```

`tsc` 绿**不等于**没事——改了默认值、改了事件名、改了"什么时候调 next()"，类型都不会红。
所以第二道必须做：把 diff 出来的每个文件看一遍，逐条填 UPGRADE.md 的表：

| 包 | 变化 | 出处 | 碰到我们吗 |
|---|---|---|---|

**「出处」这一列不许空。** 上游没 CHANGELOG，出处就是具体哪个 `.d.ts` 的哪一段、
或者 README 的哪一节；日后回看能复核，才叫记录。

#### ④bis 默认值扫描（WP70 加的一步，独立于 seam）

`.d.ts` 的 diff **看不见默认值**：`enabled?: boolean` 前后一模一样，改的是
`z.boolean().default(false)` → `.default(true)`，而那行在 `src/` 里、不在 `lib/types/` 里。
README 也可能只改一个词（"Enable it only when…" → "Disable it only when…"）。
WP70 就是这样差点漏掉一条把整条会话日志上报给模型厂商的开关（见 `docs/39 §3.3 (d)`）。

所以每次升级都要**单独扫一遍默认值**，两个动作：

```bash
# 1) 克隆上游两个 tag 的源码（npm 包里只有编译产物，schema 的 default 看不到）
gh repo clone deepseek-ai/deepseek-harness $TMP/dsh-old -- --depth 1 --branch dsh-v<旧版>
gh repo clone deepseek-ai/deepseek-harness $TMP/dsh-new -- --depth 1 --branch dsh-v<新版>
# 2) 只看 default( 那一行的变化
diff -r $TMP/dsh-old/packages $TMP/dsh-new/packages | grep -nE '^[<>].*\.default\(|^[<>].*default:' 
```

**红线：凡是"默认打开的出网 / 上报 / 遥测"，一律在 `profiles/agentsws` 的 patch 层
显式关掉，并加一条测试钉住；不许靠"我们没装这个插件"当保证。**
默认值是上游可以单方面翻的，而"我们的组合里碰巧没有它"随时可能因为换 bundle 而失效。

我们碰的五个 seam（17 §4）逐个确认：

1. `tools/pre-execute` 的 allow / deny / ask 语义
2. `tools/post-execute` 的 replace / enrich / block
3. `approval/request` answerer waterfall 的四个结果值与 fail-closed
4. `systemPrompt.section({ complete: true })` 的遮蔽、`systemPrompt.context` 的分节
5. `ctx.tools.restrict({ allow })` 在 scoped context 里的过滤

改动只许发生在 `harness.ts` / `gate.ts` / `llm.ts` / `preset.ts` / `headless/*` 里。
**红线：一切 dsh API 调用收在 `packages/dsh-adapter`（34 §「唯一 import dsh 处」）。
如果修 seam 需要改这个包以外的代码，说明薄适配层破了——那是一次设计事故，要单独提出来，不是顺手改掉。**

### ⑤ 重判上次放弃的选项

每次升级都要回头看一眼**上一次因为上游缺东西而放弃的路**。把它写成一张表，一行一条，
逐条给"还成立吗"。WP41 那次重判的是官方 SDK（`dsh --profile sdk` + `dsh-sdk-client`）：

| # | 上次的判断 | 这次实测 | 还成立吗 |
|---|---|---|---|
| 1 | 要开 `fs-ext` 原生构建才能起 | 依赖没了，`allowBuilds` 一个没开也能起 | **已解决** |
| 2 | 官方 server 没有 server→client 请求 | 仍然只有 `onRequest` + `notify` | 成立 |
| 3 | 官方 loop 驱动 turn，事件序列对不上 | 不变 | 成立 |

**换与不换的线要事先说死，不能看完再定。** WP41 定的是"≤ 100 行且两档事件序列仍相等就换"——
第 2 条决定了代码量远超这条线，第 3 条决定了序列不可能相等，所以不换。

**红线：判断要有可复核的实测出处**（跑了什么命令、回了什么），不能只写"看起来还不行"。

### ⑥ 对比：升级后重跑第 ① 步，逐条比

```bash
pnpm exec vitest run --project @agentsws/dsh-adapter        # 用例数应与 ① 一致（除非你加了新用例）
node packages/dsh-adapter/test/upgrade-baseline/capture.mjs # 按新版本命名
pnpm exec vitest run --project @agentsws/dsh-adapter        # 再跑一遍：upgrade.test.ts 现在会做对比
```

`test/upgrade.test.ts` 只读那两份 JSON，断言：

| 断言 | 阈值 |
|---|---|
| 事件**类型**序列 | 完全相同 |
| 事件 `type@at` | 完全相同 |
| 六条不变量 | 全绿且逐条相同 |
| 场景断言 | 全绿且逐条相同 |
| 运行摘要 | 完全相同 |
| `tokens_per_item` | 偏差 ≤ **5%** |
| 两档 dsh 之间 | 仍然逐条相等 |

**`upgrade.test.ts` 不 import `@agentsws/simulation`**——采集器才需要它，而且用相对路径引
`dist`，不进包的依赖图。这条是硬约束：dsh-adapter ↔ simulation 的 devDependency 环（38 §1）
好不容易解掉，别为了一份对比测试又长回来。

**提示词变了怎么办**：允许，但要把**前后 diff 摘要**列进 UPGRADE.md，并说明为什么可以接受
（例：上游给系统提示词加了一段安全说明）。判断办法是把 dsh 的 `systemPrompt.assemble()`
在新旧两版下各导一次——`pnpm install` 回退一次版本、导一份、再装回来，几十秒的事，
比"看着像没变"可靠。

**指标真的变了怎么办**：只有在 §④ 把变化的原因写清楚之后，才可以用
`pnpm -s simulate ... --rewrite-baseline` 重定 `packs/*/baseline.json` 的对应档，
并在 UPGRADE.md 里**逐条说明每一个变的数**。
**红线：`--rewrite-baseline` 不是"让它变绿"的开关。解释不了的数，就是不升级。**

## 2. 七条红线（都在上面出现过，集中放一遍）

1. **基线在升级前采**，不许事后补，而且要在**当前代码树**上重采（不沿用上一次那份）。
2. **不给 dsh 原生依赖开构建**，除非子进程档必需，且点名说明是哪一个、为什么。
3. **锁精确版本**（不用 `^`），`minimumReleaseAgeExclude` 写死版本不写通配。
4. **一切 dsh API 调用收在 `packages/dsh-adapter`**；修 seam 要动这个包以外的代码 = 设计事故。
5. **`--rewrite-baseline` 要逐条解释**，解释不了的数就是不升级（17 §4「任一红 = 不升级」）。
6. **每条判断要有可复核的出处**：`.d.ts` 的哪一段、README 的哪一节、跑了什么命令回了什么。
7. **默认打开的出网 / 上报 / 遥测，一律在 profile 的 patch 层显式关掉并加测试**（④bis）；
   不许靠"我们的组合里碰巧没有它"当保证。

## 3. CI：`upstream-watch.yml`（**已启用，WP91**）

`.github/workflows/upstream-watch.yml` 做这份 checklist 的第 ②、④bis、⑥ 步。
09-17 之前它只有 `workflow_dispatch`；WP91 把 ④bis 的默认值扫描做进去之后
（下面 §3.2 说的那个启用前提），两条 `schedule` 已经打开。

### 3.1 两条 cron 分别是什么意思

| cron（UTC） | 北京时间 | 范围 | 有事没事各出什么 |
|---|---|---|---|
| `0 6 * * 1` | 周一 14:00 | **全量周报**：`upstreams.yml` 里每一个上游 | 一定出一条 issue，标题 `上游周报 <年>-W<周>`；同一周只开一条，再跑就往那条上追评论 |
| `30 18 * * *` | 次日 02:30 | **只查 dsh**：dist-tags 与 GitHub releases | **没新版就零输出**（不开 issue、不评论、不试升级）；有新版才跑试升级 + ④bis，开一条 `上游哨兵：dsh <旧> → <新>` |

为什么这么分：dsh 是唯一一个"它动我们就得动"的上游（全仓唯一 import 处在
`packages/dsh-adapter`），而且它还在预发布期，节奏比 pnpm 的静默期还快，所以每天看一眼；
其余上游一周看一次够了，多了没人看。周报即使"什么都没变"也照出一条——
**"这一周我替你看过了、没事"本身就是信息**；而每日那趟如果没事也发一条，
一个月三十条噪声之后就没人再点开了，所以它零输出。

"有没有新版"**不是**"latest 不等于我们锁的"：dist-tags 要如实看（第 ② 步那条红线）。
现在 `latest` = `0.1.5-rc.1`、`alpha` = `0.1.6-alpha.1`，而我们锁的正是后者——
按"升到 latest"办事就是降级。脚本里的判断是**在 dist-tags 指着的那几个版本里取最高**，
再和我们锁的比，结论分四档：落后 / 就是最新 / 我们比 dist-tags 还新 / 查不到。

### 3.2 ④bis 默认值扫描：启用的那个前提

`scripts/scan-default-flips.sh` 把 §1 ④bis 的两条命令做成一步：克隆上游两个 tag 的
**源码**（npm 包里只有编译产物，schema 的 default 看不到），`diff -r -u -U0` 之后只留
`.default(` 与源码里的 `default:` 那些行，**带文件名**列进 issue 正文（红线 6：出处不许空）。
整个文件的新增 / 消失另列一段——新包里一个默认打开的开关，在 diff 里是 "Only in"，不是 `+`。

它拿 WP70 那一跳（`dsh-v0.1.5-rc.1` → `dsh-v0.1.6-alpha.1`）实跑过，35 行里第一眼就能看见：

```diff
- packages/session/session-log-deepseek/src/index.ts: enabled: z.boolean().default(false),
+ packages/session/session-log-deepseek/src/index.ts: enabled: z.boolean().default(true),
```

这正是 WP70 差点漏掉的那条（docs/39 §3.3 d）：它一不改类型、二不改行为指纹，
只看基线对比的自动报告会整条漏掉。扫不成（私有仓 / tag 命名变了）**不把流程染红**，
但 issue 正文会写明"没扫成，要人工补做"——盲区要说出来，不能装作扫过了。

### 3.3 它做什么、不做什么

| 做 | 不做 |
|---|---|
| 按 `upstreams.yml` 查 npm dist-tags、GitHub releases / README / 指定路径的提交 | **不自动改版本号** |
| wishlist 命中就单独列出来并给出处链接 | **不开 PR、不自动合并** |
| dsh 有新版就在临时工作树里试升级：装 → `tsc -b` → dsh-adapter 全部测试 → **在当前代码树重采基线** → 与升级后那份逐条对比 | **不碰 main、不推分支** |
| ④bis 默认值扫描的结果贴进 issue | **不替人做"纳不纳入"的决定** |
| 报告最后一段"给评估例程的提示"（哪条要走 docs/42、哪条只是"重判"） | **不产出审批项**（还是 §4 第 4 条） |

为什么止步于 issue 而不是 PR：10 §3.3 第 ⑤ 步说得很清楚，**L1 是人看报告点通过**。
自动开 PR 会让"点一下 merge"变成默认动作，而升级的风险恰恰在那些测试全绿、
基线却悄悄变了的地方。等 10 §3.3 说的晋级条件真的到了
（patch 级、不碰 seam、全绿的升级采纳率 ≥ 95% 持续 4 周），再谈 L2。

### 3.4 怎么读这份周报

一条 issue 从上到下四段，按这个顺序看最省时间：

1. **顶上那张小表** —— 看了几个、哪几个有新版、哪几个命中 wishlist、哪几个查不到。
   没事的那一周，这张表四行全是"无"，看完就可以关掉。
2. **每个上游一节** —— 版本与 dist-tags（如实列，不替你解释成"最新"）、
   窗口内的 release / README 变动（都带链接）、折叠着的"我们碰到的 seam"
   （上游动了这些，就要按 §1 ④ 逐条对 `.d.ts` diff 看）。
3. **dsh 那一节后面** —— 默认值扫描与自动试升级的结论，再加一份 docs/42 的 checklist。
4. **末尾"给评估例程的提示"** —— 每条一句话，说明这一条该走哪条路：
   走 docs/42 的全套升级，还是只是一次"重判"（wishlist 命中不是升级），
   还是"这一趟查不到、下一趟仍要看"。**查不到 ≠ 没变**，这一句是故意写死在模板里的。

关键是别把报告当结论：它只摆事实。17 §4「任一红 = 不升级」仍然是人来判。

本机演练（不开 issue、只出报告）：

```bash
pnpm upstream:watch --dry-run                 # 全量，出整份周报
pnpm upstream:watch --dry-run --scope daily   # 只查 dsh，跟每日那趟同一套
pnpm upstreams:check                          # 只校验登记表（CI 里跑的是 --check）
```
