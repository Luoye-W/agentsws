## 0. 一句话

**一个品牌一份 `DESIGN.md`，三条来路填它，四个岗位吃它。**

---

## 1. 格式：用别人的，不自造

文件格式逐字对齐 Google Labs 开源的 **DESIGN.md 规范**
（`github.com/google-labs-code/design.md`，Apache-2.0，版本 `alpha`）：

- 前面一段 **YAML front matter** 放机器可读的令牌（`colors` / `typography` /
  `rounded` / `spacing` / `components`，外加规范的 `version` / `name` /
  `description` / `omitted`）；
- 后面是 **Markdown 正文**，八个 `##` 小节，**名字与顺序都是规范定的**：
  Overview → Colors → Typography → Layout → Elevation & Depth → Shapes →
  Components → Do's and Don'ts。

用通用格式的好处只有一条，但它够大：**用户拿这份文件去 Stitch / Claude Code /
Cursor 也能直接用。** 自造一个更贴合我们的格式，等于给用户的数据加一道只有
我们认得的锁。

**一处记在案的扩展**：`shadows`。规范把阴影放在正文的「Elevation & Depth」里当
散文写，没有对应的令牌组；但 WP89 的主题沙箱与规范自检都要一个能比对的值。
规范对"不认识的内容"的规定是**保留、不报错**，所以这样写出去的文件在它自己的
linter 里仍然读得动。

## 2. 三条来路，可叠加

| 来路 | 怎么来的 | 把握度 |
|---|---|---|
| **官网** | WP121 分析时顺带跑，**同一次抓取**（见 §3） | 变量名里有语义的 `high`，只从规则量出来的 `medium` |
| **上传文件** | 品牌手册 PDF（走 WP99 的上传链路） | `high`——手册是规范，不是我们量的 |
| **手改** | 界面上点一格改 | `high`，且**标 `edited`** |

### 2.1 优先级：手册 > 官网，但输的那个留着

文件里写的是**规范**，官网是**实现**，实现可能没跟上。所以冲突时手册的值当
`value`。

**但"优先"不等于"删掉另一个"。** 输的那个进 `BrandDesignValue.conflict`，
界面上两个色块并排画出来，让用户点一下。我们没资格替用户判他的手册和他的官网
哪个是对的——**我们只有资格让他看见这两个不一样**。

这恰恰是这件事对一个真实品牌最有用的一刻：很多品牌根本不知道自己的官网没照
手册做。

### 2.2 重抓时：用户改过的格子整格不动

与 70 §3.4 一字不差，理由也一字不差：一个按钮只要有一次吃掉过你的手工修改，
它就死了。另外两条也照抄：这一轮没抽到、上一轮有的**留着上一轮的**（抓不到
不等于"这一格现在是空的"）；改成空 = 这一格我不要，删掉而不是留个空值。

## 3. 官网那条路：没有无头浏览器

那几个开源实现（§8）共同的做法是**开一个 Puppeteer / Playwright，对每个元素调
`getComputedStyle`**。我们不这么做，两个理由：

1. 每个都自带一套浏览器运行时（几百兆），而桌面壳里已经有一个工作浏览器；
2. **公司端明令禁止让 AI 在网页里跑脚本**（`packages/dsh-adapter` 的
   `BROWSER_SCRIPT_TOOLS` 那道闸，`policy === 'executor'` 时 `browser_evaluate`
   直接拒），而 `getComputedStyle` 只能靠跑脚本拿。一个只在个人端能用的抽取器，
   等于公司端的用户永远抓不出设计规范。

所以我们读的是**声明后样式**：内联 `<style>`、外链样式表、CSS 变量。
拿不到的（JS 运行时才算出来的、媒体查询里按视口挑的）**如实缺席**。

换来的不只是省依赖：**CSS 变量的名字在计算后样式里是看不见的**
（`getComputedStyle` 给你 `rgb(26,28,30)`，不给你 `--color-ink`）。
而站方自己给这个色起的名字，是判它是不是品牌色最硬的一条证据。

### 3.1 同一次抓取

页面的 HTML 由 WP121 那一轮（`analyzeSite`）原样递过来——`brand-intake` 加了
一个**可选的 `keepHtml`**（只加不改），开着才把 HTML 留下来。WP121 那条路解析
完就不要它了，一路带着是白费内存；要它的只有设计规范抽取。

唯一额外的网络请求是**外链样式表**（它不在 HTML 里）：封顶 6 份、只抓同源与
站自己的 CDN、遵 robots。拿不到页面时（进程重启过、或者用户是从设置页直接点的）
**如实说「还没有抓回来的页面」，不偷偷把用户的站再抓一遍**。

### 3.2 主次判定：面积与位置，不只频次

> 数一数页面上哪个颜色出现得最多，最多的那个就是主色。

按这条规则跑任何一个真实的站，选出来的是**边框灰**——一条 1px 的分隔线在一页上
出现四十次，而铺满整个首屏的那块品牌色只出现一次。频次这个数把"出现"和
"看得见"当成了同一件事。

所以一个候选色的分数是四样相乘：

| 乘数 | 它代表 |
|---|---|
| **属性权重** | `background-color` 铺面积（6），`border-color` 只有一条线（1） |
| **结构权重** | `:root`/`body` 10，英雄区 8，按钮 4，页脚 1 |
| **区域权重** | 首屏 1.5，页头 1.2，正文 1，页脚 0.4 |
| **√次数** | 次数仍然算数，但不线性地压倒前三项 |

外加一个**变量名系数**（`--color-brand` ×3，`--color-border` ×0.5）——
这是整套打分里唯一一条不是估算的证据。

「按钮 4」那一行需要解释：按钮很小，面积上排不进前十，但**站方把强调色放在
按钮上**——它是整页里语义最明确的一处"这是我们的颜色"。给它 4 不是因为它大，
是因为它准。

### 3.3 彩色与中性分两堆挑

混在一起排名的话，前四名会是白、黑、灰、灰，一个品牌色都排不进去。

中性色**用彩度判，不用 HSL 饱和度**：`#f7f5f2` 是一张纸的颜色，人一眼就知道
它是"白"，但它的 HSL 饱和度是 0.24——比很多真正的品牌色还高（分母在 L→1 时
趋近 0）。彩度（三通道极差）只有 0.02。阈值 0.1。

## 4. 手册那条路：零依赖读 PDF

开工时仓库里**一个 PDF 解析器都没有**（`packages/knowledge` 的 `parser` 那一格
留了 `anydoc` 的位置，但明写"本包不安装 anydoc"；`dsh-office-to-pdf` 在 WP93 被
当成 259 MB 的下载型可选依赖挡掉了）。为读一份品牌手册引入第一个 PDF 运行时
依赖，该走 `docs/42` 一整轮上游评估——**那是个单独的决定，不该夹在这张单里
顺手做掉**。

而手册要的东西很浅：**文字层**（颜色值、字体名、留白规则通常就写在那儿）与
**页面用过的填充色**（色卡那几块）。`node:zlib` 加一个内容流扫描器就够
（`packages/brand-design/src/pdf.ts`）。

读不动什么，说清楚：

- **扫描件 / 纯图排版**没有文字层 → 如实回「读不到，可能是扫描件」，**不编**。
  那种手册要逐页转图给视觉模型看，而那条路现在走不通（见 §9 留尾）。
- **子集嵌入字体**取出来可能是乱码 → 非可打印字符过半的整页丢掉。宁可少读
  一页，不往规范里写一页乱码。
- 加密的 PDF：不解密。

### 4.1 Pantone 与 CMYK 原样留着

`BrandDesignPrintColor.raw` 一个字不动：

- **Pantone 不换算**——没有一张不带授权的对照表能给出准确的 HEX。原值留着，
  HEX 那一格空着；界面上画一个带问号的色块，比画一个错的色块好。
- **CMYK 换算了**（最朴素那条公式，不走 ICC），但只是为了在屏幕上画个色块。

把印刷色换算成 HEX 之后就把原值扔掉，等于让这份文件再也回不到印刷那一侧——
而一个做实体产品的品牌，包装、画册、展会物料全在那一侧。

### 4.2 手册的色板按出现顺序排

不按统计：**手册的作者是按重要性排的版**，那个顺序比任何统计都准。官网上我们
只能靠面积猜，才需要 §3.2 那一套打分。

## 5. 正文：只根据证据写

模型把令牌写成人话（用法、禁忌、什么场合用哪种色、logo 最小尺寸与留白……）。

**没证据的节写「未找到，请补充」，不编。** 这条纪律在代码里有形状：证据不够的
小节 `sectionEvidence()` 直接判空，**根本不进提示词**——模型看不见那一节，
也就没机会替它编一段听起来很像品牌手册的话。抓不到的节同时记进 front matter 的
`omitted`（规范的 linter 认这个，用户也能一眼看见缺哪儿）。

八节写出来而不是省掉：一份缺了三节的文件，用户看不出是"这个品牌没有这一项"
还是"我们没抓到"，而那两件事他要做的动作完全不同。

**钱**：一次成文**只发一次模型请求**（八节一起写），封顶
`DEFAULT_BRAND_DESIGN_CAP_CREDITS = 1`——与 WP121 的 2 加起来 3，仍在注册送的
10 以内。开跑前报预估，撞顶就停，**停下来时已经写好的照样交**。

接不上模型 / 模型抛了 / 回的东西读不出小节——三种都**退回按令牌直述的文本**。
读起来干，但每一句都对得上一个真实的值。这是下限，不是目标。

## 6. 让它真的被用上

这是这件事的价值所在。

### 6.1 一处拼，四处用

`brandDesignContext()`（`packages/brand-design/src/context.ts`）是**唯一**拼那段
注入的地方。四个 core 各拼一遍的话，过两周它们就会拼得不一样——而"为什么社媒
出的图和建站出的页不是一套颜色"这种问题，事后没人查得出是哪一行提示词的差别。

| 岗位 | 接口 |
|---|---|
| 设计 | `composePrompt(item, brand, design?)`（`design-core/variants.ts`） |
| 社媒 | `voicePrompt(resolved, design?)`（`social-core/voice.ts`） |
| 建站 | `siteDesignPrompt(design)` + `themeDesignVariables(tokens)`（`site-core/brand-design.ts`） |
| 投放 | `adDesignPrompt(design)` + `designNoteZh(findings)`（`ads-core/brand-design.ts`） |

四个 core **只接 `BrandDesignContext`（契约里的类型）并把 `prompt` 接上去**，
不自己拼，也不依赖 `@agentsws/brand-design`。

`themeDesignVariables()` 是给 WP89 的主题沙箱的：预览里的颜色与规范里的颜色是
**同一个来源**，不是"设计规范说一套、沙箱里又调一套"。

两条克制：**没抓到的项整行不出现**（不写"未指定"——那会被模型当成一条指令去
满足它）；**没有规范时 `present: false`、`prompt` 是空串**，四个岗位照常干活。

### 6.2 规范自检：只提示，不拦人

`checkAgainstDesign()` 查五件事：色板外的颜色、字体表外的字体、logo 最小尺寸、
logo 留白、对比度（WCAG AA，小字 4.5:1 / 大字 3:1；半透明前景**先压到背景上
再算**，否则会得出一个漂亮但假的 21:1）。

出来的每一条都贴在卡片上当一行字，**没有一条会挡住 publish**——
`BrandDesignCheckFinding` 里没有 severity 这一格，`ads-core/brand-design.ts` 里
没有一个函数回 `boolean`。

理由：品牌规范是给人省事的，不是用来管住人的。一张广告图用了色板外的一个橙，
很可能是设计师故意的；而一个会拦住你的检查，人只会想办法关掉它。

再一条克制：**没有规范就一条都不查**。一个刚建的工作区还没抓过设计规范，
这时候每张图都报"不在色板里"，等于把一个还没启用的功能做成了噪声源。

## 7. 界面与边界

**设计规范页**（`/brand-design`）：上半可视化（色板带名字与色值、字样按它自己的
字体与字号排、间距与圆角示意、按钮 / 卡片样例**用这些令牌实时渲染**、logo 深浅底
预览），下半是 `DESIGN.md` 原文编辑器（左改右预览）。**每个值点得开出处**
（网页的哪条变量 / 手册第几页 + 原文片段）。

**右栏面板**（`registerPanelBody('design-md', …)`）：**只读速查表**。没有编辑、
没有抓取按钮——那两件事有后果，后果应该发生在一个用户特地去到的页面上，
而不是他干别的活时顺手划开的抽屉里。

**向导入口**：品牌档案卡上一行「设计规范：已抓到 N 色 · N 字体 · N 个 logo」+
「上传品牌手册」。那一行**自己取数**，查不到就整行不出现（不显示「0 色」——
那会让用户以为出了错）。

**边界**（71 §6）：只抓用户自己填的网址的公开页面，遵 robots 与频率；
**不把别人网站的图片素材存成我们的资产**（只存 logo 与出处展示用的缩略图，
存本机）；用户上传的手册只在本机与用户选定的模型之间流动。

`NOTICE` 里加了 design.md 规范那一条（Apache-2.0）。其余五个只借了算法、
一行代码都没抄，署名写在 `packages/brand-design/src/css.ts` 的文件头与这一节。

## 9. 留尾（下一张单）

1. **视觉档那条路走不通。** 契约里 `ChatMessage.content` 是个纯 `string`，
   没有"图进模型"这一格（`packages/contracts/src/model.ts`）；模型网关只有
   **文生图**（`ImageProvider`），没有图生文。所以「逐页转图给视觉模型」与
   「看截图描述图片风格」这两件事这一版**如实留白**：`composeDesignProse` 留了
   `DesignVisionModel` 这个口子并有测试钉住它的行为，但生产里没人往里传东西。
   要补的是一个契约级的改动（`ChatMessage` 收图），该是单独一张单。
2. **Shopify 主题设置里的配色与字体没读**（有连接时那条路）。契约里
   `BrandDesignOrigin` 留了 `'theme'` 这一档，抽取器还没有。
3. **改一格的界面只做到了展示**：`PATCH /v1/brand-design/tokens/:path` 与
   `setAt()` 都在、有测试，但页面上还没接那个小铅笔（现在改值要走「原文」
   那一半整份替换）。
4. **成文没有接模型**：`apps/server` 装配时 `model` 没传，所以现在出来的正文
   是按令牌直述的那一版。接上 `packages/model-gateway` 的便宜档是一行的事，
   但要先把积分计量那一跳接对（与 WP121 的 `estimateCredits` 同一套）。
5. **docx / pptx 手册**：`extractFileDesign` 留了 `pages` 这个口子（调用方把
   已经拆好的页递进来），但 `apps/server` 那一侧只接了 PDF。
6. **`design.md` 规范的 linter 我们没跑过**：序列化出来的文件按它的 `docs/spec.md`
   手工对过，但没有一条 CI 会在它改了之后提醒我们。`upstreams.yml` 的
   `watch_paths` 是目前唯一的哨兵。
