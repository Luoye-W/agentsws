## 1. 职责骨架（S1）

> **WP76 实现**：五条 yml 在 `packages/roles/roles/design/{dtc,amazon,social,ads,exhibition}.yml`
> （骨架样板写在 `dtc.yml` 的文件头，其余四条只写"这条职责特有的三件事"：规格表、
> 需求来源、grounding 的意图词）。**五条的动作 id 与数据域一模一样**，所以意图词是
> 岗位路由唯一分得开它们的东西（54 §2）。`connectors` 是空的而且是故意的——出图走
> 模型网关的图片槽（22），那不是一条连接，连接页上根本没有一张"图片模型"的卡可以点。
>
> 契约面：`packages/contracts/src/design.ts`（`DESIGN_DUTIES` / `DESIGN_SPECS` /
> `DesignRequest` / `DesignBrief` / `DesignAsset` / `DESIGN_CAPS`），四条 ChangeKind 在
> `changes.ts`。**04 §6 那句纪律钉在三处类型里**：`@agentsws/core` 的 `HARD_L1` 含
> `asset_publish`、`DesignAsset` 没有「Agent 定稿」那一档、`isDesignAssetFinal` 是唯一一份判据；
> 加上职责 yml 里 `stage_asset` 的 `hard_ceiling: true` 与 `picked_by` / `picked_at` 进
> `protected_fields`（Agent 提都不许提）。
>
> guardrail 四道门在 `packages/core/src/guardrail.ts`：`n ≤ max_variants_per_brief`
> （转人审）、每日出图上限**按张数累加**（转人审）、提示词里的品牌禁忌词 **block**、
> 入库没有 `picked_by` 也 **block**。图片槽在 `packages/model-gateway/src/images.ts`：
> 默认挂的是 `unavailableImageProvider`（`available: false` + 一句人话），
> `stubImageProvider` 只给模拟与 demo 用。
>
> **三条 `request_design`** 加在 `dtc/store.yml`、`social/meta.yml`、`kol/youtube.yml`
> 各自末尾（`design_request` L3：不出图、不花钱、不对外发一个字）。
>
> 素材库：`apps/server/src/design.ts` 三张表按品牌落盘，字节进 blob store，
> key 把品牌放最前面；**提示词存哈希不存原文**（里面可能带客户名与未发布的卖点）。

五条骨架相同，差别只在**规格表**与**需求来源**：`design.dtc`（首页 / 产品页 / 落地页 / Banner / 图标；来源：网站运营、建站）、`design.amazon`（主图 / A+ / 旗舰店 / 视频封面；Amazon 规格；来源：Amazon 运营）、`design.social`（帖子 / Reels 封面 / 故事 / 头像；各平台尺寸；来源：社媒运营、红人）、`design.ads`（各平台广告素材与变体；读 `ads-core/spec.ts`；来源：投放）、`design.exhibition`（展位 / 易拉宝 / 画册 / 名片；印刷规格 CMYK / 出血；来源：人手动）。

| 读 | 写（→ ChangeKind） | 额度 | 上限 |
|---|---|---|---|
| 需求单（事项）、品牌系统（公司层技能：色 / 字 / 版式 / 禁忌）、素材库、规格表、参考图 | `draft_brief`（`design_brief`：把需求单变成 brief + 规格 + 变体计划）、`generate_variants`（`design_variant`：调图片模型出初稿变体，N ≤ `max_variants`）、`stage_asset`（`asset_publish`：把选定稿入素材库并回给需求方） | `max_variants_per_brief` 6、`max_generations_per_day` 30、`max_brief_per_day` 10 | brief **L3** 自动；变体 **L2**（出卡给人挑）；入库回给需求方 **L1 永远人定**——人没点"就这张"之前什么都不算定稿 |

- 连接器：图片生成走模型网关（22）的图片能力（DeepSeek 无图片 → 走 OpenAI 兼容口或 agentsws 云按积分），没有就明说"只出 brief 与规格，不出图"；Figma / Canva 登记"待增加"。
- 素材库：blob store（41）按品牌；每张素材带来源（brief id、模型、提示词哈希、人定稿时间）。

## 2. `design-core`（S2）

> **WP76 实现**：`packages/design-core/`，五个模块与 §2 一一对应。两处与方案稿不同，
> 都是故意的：
>
> 1. **广告规格是本地一份形状**（`specs.ts` 里的 `AdCreativeSpec` + 一句 TODO），不是
>    `import '@agentsws/ads-core'`——那个包是 WP75 的，还没合进 main。合了之后改
>    import，`DESIGN_SPECS` 那一侧一个字不用动。
> 2. **`brand.ts` 从头到尾没有一个色值**。品牌系统只从公司层技能取；一张都没有时出
>    「先设品牌系统」卡（`blocking: false`——**不挡路**，但把代价说清楚：
>    没有它，同一个品牌的十张图放在一起会像十个牌子）。
>
> 额度在 `variants.ts` 的 `planGeneration` 里**提前说**，与 guardrail 判的是同一个数；
> 禁忌词自查（`checkPrompt`）**不是门**——Agent 自查不能当门，真拦在 guardrail。
> WP76 ⑤ 补了 `VariantPrompt.positive_prompt`：喂模型的是全量提示词（带禁忌行），
> 提交 `design_variant` 报上去的是**正向那一半**——禁忌行本身就是那几个词的原文，
> 报全量上去等于每次出图都自己撞 `brand_forbidden_term` 那道门。

`brief.ts`（需求单 → brief：目标 / 受众 / 尺寸 / 文案 / 禁忌，纯函数）、`specs.ts`（Amazon / 各社媒 / 印刷规格表；广告规格 import 自 `ads-core/spec.ts`）、`variants.ts`（变体计划与提示词组装，品牌系统注入）、`library.ts`（素材库索引：按品牌 / 用途 / 尺寸 / 定稿状态）、`brand.ts`（从公司层技能取品牌系统，缺就出"先设品牌系统"卡）。

## 3. 面板与卡（S3）

> **WP76 实现**：五块的积木与查询在 `packages/deck/src/{blocks,queries,types}.ts`，
> **五块全走 `design` 这一个源**（我们自己的库，永远算连上）。与社媒那两组最大的不同是
> 这里一个渠道源都没有。两件事写在查询里而不是渲染层：**待挑与待定稿分得开**
> （"等你挑一张" / "你挑好了，等你点入库"——混成一块，面板上就再也看不出球在谁那儿）、
> **本周产出数的是定稿**（出图张数只是分母，把张数当产出的结果是这个数永远好看，
> 而没有一张图真的上线了）。
>
> 四张卡**不是四个新 kind**（36 §2），是既有 kind 的投影，差别在四个新芯片上
> （规格 / 出几张 / **谁挑的** / 没有图片模型）。「谁挑的」给强调色——它是 04 §6
> 在界面上唯一看得见的地方。截图 `docs/assets/workstation/design-position.png`。

分块：需求单队列（按来源岗位）、进行中（brief / 出图 / 待挑）、待定稿、素材库（按用途）、本周产出；卡：brief 卡（L3，看完即用）、变体挑选卡（L2，N 张图 + "就这张 / 都不行再来"）、定稿入库卡（L1）、缺品牌系统卡。

> stub / direct / dsh-subprocess 三运行时各跑一遍。接线在

>
> 四条题的判据一个字都不在模拟层：路由走 `@agentsws/roles` 的 `routeWithinPosition`
> （与服务进程、与秘书同一份）、brief 走 `design-core` 的 `draftBrief`、
> "入库永远人审"走 guardrail 的 `HARD_L1`（场景**故意把等级报成 L3**）。
>
> 两处"不是靠开关演出来的"：
>
> - **品牌系统缺失**是真缺——3 人 pack 的 `skills/brand-system.md` 由 synth 生成，
>   15 人 pack **故意没有**。靠场景开一个开关就什么都没证明。
> - **没有图片模型**是默认状态（生产上挂的就是 `unavailableImageProvider`），
>   demo 里才挂 stub。
>
> 展会那条题的需求单 `from` 写的是 `human`（§1 里 `design.exhibition` 的来源那一栏
> 就是"人手动"）：这时**一条 `design_request` 都不提**——那条 ChangeKind 说的是
> "**Agent** 想向设计岗下一张单"，人自己填的单不需要谁批，提上去队列里只会多出一张
> "请批准：你刚才自己填的那张单"。`human` 是写死的一个词，不是"分配查不到就当手动"：
> 查不到通常是职责 id 写错了，悄悄当手动的后果是那条题从此再也发现不了这个错。

3 人 pack +3：`design/request-routes-from-store`（网站运营下需求单 → 岗位路由到 `design.dtc` → brief 自动出）、`design/variants-then-human-picks`（变体卡 → 人挑一张 → 入库 L1）、`design/no-image-model-says-so`（没图片模型 → 只出 brief 并明说）；15 人 pack +1：`design/brand-system-missing-card`。
