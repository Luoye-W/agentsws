## 0. 拆分规则：什么算一个职责

拆得太粗（"独立站运营"）权限和队列分不开；拆得太细（"回复 Instagram 评论"）管理成本爆炸。一个职责必须同时满足下面四条，缺一条就并回去：

1. **有自己的权限边界**：它碰的数据域和写操作与别的职责不同
2. **有自己的连接器或账号**：通常对应一个外部系统或一个平台账号
3. **有自己的队列车道**：它产生的审批项可以单独路由给一个人
4. **可以单独交接**：把它从 A 转给 B 时，积木、队列、上下文、在办事项能一起转

由此得出两条推论：

- **平台是天然的职责边界**（Facebook 主页管理、Instagram 管理各是一个职责），因为每个平台 = 一个连接器 + 一套账号 + 一种风控。跨平台共用的能力（写文案、回评论、排期）做成 **skill**，被多个职责引用。职责是权限单位，skill 是复用单位，两者不混。
- **只读的分析类工作单独成职责**（独立站数据日报），因为它权限最低、自动化最高、最适合第一批 L3。

每个职责的定义包含"四件套 + 三项约束"：

| 字段 | 含义 |
|---|---|
| 权限作用域 | 数据域 × 操作（读 / stage 写 / 授权 Agent 代做）× 范围 |
| 首页积木 | 这个职责在工作台首页默认出现的卡片 |
| 技能包 | 引用的 skill 列表（开源版 + 付费插件的高级版同名替换） |
| 通知路由 | 哪些事件即时推、哪些进队列批处理、哪些只进日报 |
| 连接器依赖 | 必须接上哪些外部系统这个职责才可用 |
| 写操作与额度 | 允许 stage 哪些变更；每种变更的 guardrail caps（Mandate） |
| 自动化上限 | 每个动作最高能升到 L1 / L2 / L3；标"永不 L3"的是硬约束 |

## 1. 独立站运营（详细）

以 Shopify 为默认平台，自建站同构。十个职责，默认包含八个，两个可选。

### 1.1 独立站售前客服 `dtc.presales`

| 项 | 内容 |
|---|---|
| 干什么 | 回答下单前的问题：产品参数、尺码、兼容性、运费与时效、是否有货、能否优惠 |
| Agent 做什么 | 读知识库与商品数据起草回复；识别"要折扣"意图并 stage 一张折扣码（不直接发码）；识别高意向线索标记给邮件营销 |
| 数据域 | 商品（读）、库存（读）、知识（读）、客户（读 + 新建）、折扣（stage） |
| 连接器 | 客服邮箱 / 网站 live chat / 社媒私信转入；Shopify 商品与库存只读 |
| 写操作与额度 | `stage_discount_code`：折扣 ≤ `max_presales_discount_pct`（默认 10%），单码单客单次 |
| 自动化上限 | FAQ 类回复 L3；涉价格 / 承诺（交期、兼容性保证）L2；发折扣码 L2 且必过额度 |
| 首页积木 | 待审回复（售前车道）、今日高意向线索、未答问题（知识缺口） |
| 通知路由 | 大额询单（购物车 ≥ 阈值）即时；其余进队列；缺口问题进日报 |
| 技能 | `customer-care`（Commerce Agents 三段式）、`product-qa`、`discount-request` |

### 1.2 独立站售后客服 `dtc.aftersales`

| 项 | 内容 |
|---|---|
| 干什么 | 订单状态与物流、退换货、退款、改地址、漏发错发破损、拒付争议 |
| Agent 做什么 | 先读订单与物流记录再回答（grounding 强制）；按条款算退换窗口；把退款 / 补发 / 改地址 stage 成变更；拒付争议整理证据包 |
| 数据域 | 订单（读）、物流（读）、退款 / 补发 / 地址（stage）、客户（读写）、知识（读） |
| 连接器 | 客服邮箱；Shopify 订单；物流追踪（17track / AfterShip 类）；支付网关争议（只读起步） |
| 写操作与额度 | `stage_refund`：≤ `max_auto_refund_amount`（默认 $50）且订单未超退款窗口；`stage_reship`：≤ 1 件 / 单；`stage_address_change`：仅未发货订单。超额一律人审，不可关闭 |
| 自动化上限 | 查单查物流 L3；退换窗口判定 L2；退款 / 补发 L2 且必过额度；拒付争议 L1 |
| 首页积木 | 待审回复（售后车道）、待批退款 / 补发、逾期未送达订单、投诉升级 |
| 通知路由 | 投诉 / 差评威胁 / 拒付即时；退款待批进队列；逾期订单日报 |
| 技能 | `customer-care`、`returns-policy-calc`、`chargeback-evidence` |

### 1.3 独立站店铺设置 `dtc.store-config`

| 项 | 内容 |
|---|---|
| 干什么 | 运费区域与费率、支付方式、税务、域名、结账设置、政策页、App 安装、主题 |
| Agent 做什么 | 解释当前配置、诊断问题（为什么某国不能结账）、起草变更并 stage；不直接改 |
| 数据域 | 店铺配置（读 + stage） |
| 连接器 | Shopify Admin（配置类 scope） |
| 写操作与额度 | 全部 stage；`protected_fields`：支付、税务、域名、货币——**永远 L1** |
| 自动化上限 | 诊断与解释 L3；运费 / 政策页文案 L2；受保护字段永不 L3 |
| 首页积木 | 待批配置变更、店铺健康检查（结账 / 支付 / 域名） |
| 通知路由 | 支付或域名异常即时；其余日报 |

### 1.4 独立站商品管理 `dtc.catalog`

| 项 | 内容 |
|---|---|
| 干什么 | 上新、描述与 SEO 字段、变体、价格、库存同步、集合 / 分类 |
| Agent 做什么 | 从供应商资料生成商品页草稿；批量改描述；价格变更 stage；库存异常提醒 |
| 数据域 | 商品（读 + stage）、库存（读 + stage）、素材（读） |
| 连接器 | Shopify 商品；素材库 |
| 写操作与额度 | `stage_price_change`：`max_price_delta_pct`（默认 20%）、`max_items_per_change`（默认 25）；`stage_listing_edit`；`stage_publish`（新商品上架） |
| 自动化上限 | 描述 / SEO 字段 L2；价格 L2 且必过额度；新品上架 L1；下架 L1 |
| 首页积木 | 待批商品变更、缺图 / 缺描述商品、库存告警 |

### 1.5 独立站内容与博客 `dtc.content`

| 项 | 内容 |
|---|---|
| 干什么 | 博客、落地页、FAQ 页、指南类内容；SEO / GEO 导向 |
| Agent 做什么 | 从选题生成草稿、内链建议、旧文更新提议；发布必经审批 |
| 数据域 | 内容（读 + stage）、素材（读）、分析（读） |
| 连接器 | Shopify 博客 / 页面；GSC（只读） |
| 写操作与额度 | `stage_publish_post`、`stage_update_page` |
| 自动化上限 | 草稿 L3（不发布）；发布 L1 → 更新旧文 L2 |
| 首页积木 | 内容日历、待审草稿、掉排名页面 |

### 1.6 独立站促销与折扣 `dtc.promotions`

| 项 | 内容 |
|---|---|
| 干什么 | 折扣码、自动折扣、捆绑、节日活动、价格规则 |
| Agent 做什么 | 按活动日历起草促销方案与折扣配置；算毛利影响；stage |
| 数据域 | 折扣（stage）、商品价格（读）、成本价（**Agent 可读、按接收方脱敏**） |
| 写操作与额度 | `max_promotion_discount_pct`（默认 50%）、`margin_floor_pct`（默认按公司策略层）；margin_before / after 必填 |
| 自动化上限 | 方案起草 L3；配置上线 L1 → L2 |
| 首页积木 | 活动日历、待批促销、进行中活动表现 |

### 1.7 独立站数据日报 `dtc.analytics`

| 项 | 内容 |
|---|---|
| 干什么 | 销售、转化、流量、退款率的日报周报；异常检测 |
| Agent 做什么 | 只读查询 + 分析子代理（SQL 白名单）；数字不经模型手，直接出卡片 |
| 数据域 | 分析（读）、订单（读）、GA4（读） |
| 连接器 | Shopify Analytics；GA4 |
| 写操作 | 无 |
| 自动化上限 | **L3，第一批全自动候选** |
| 首页积木 | 日报卡、异常告警 |
| 通知路由 | 异常（转化骤降 / 退款率飙升）即时；日报定时 |

### 1.8 独立站邮件营销 `dtc.email-marketing`

| 项 | 内容 |
|---|---|
| 干什么 | Klaviyo / Shopify Email 的 flow 与 campaign、分群、弃购挽回 |
| Agent 做什么 | 起草 campaign、建议分群、A/B 方案；发送 stage |
| 数据域 | 邮件营销（读 + stage）、客户分群（读） |
| 连接器 | Klaviyo / Shopify Email |
| 写操作与额度 | `stage_campaign_send`：受众 ≤ `max_campaign_audience` 内可 L2；flow 结构变更 L1 |
| 自动化上限 | 文案 L3（不发）；发送 L1 → L2 |

### 1.9 独立站评价管理 `dtc.reviews`（可选）

| 项 | 内容 |
|---|---|
| 干什么 | 回复评价、邀评、差评升级到售后 |
| 连接器 | Judge.me / Loox / Shopify Reviews |
| 自动化上限 | 好评回复 L3；差评回复 L2；邀评 L3 |
| 备注 | 小店可并入售后客服；单独列出是因为它有独立连接器与独立的公开面风险 |

### 1.10 独立站订单履约 `dtc.fulfillment`（可选）

| 项 | 内容 |
|---|---|
| 干什么 | 订单处理、3PL / 海外仓对接、发货异常、物流延误主动通知 |
| 连接器 | Shopify 订单履约；3PL / 海外仓 API |
| 写操作与额度 | `stage_fulfill`、`stage_split_shipment`；延误通知草稿 |
| 自动化上限 | 主动通知 L2 → L3；履约标记 L2；异常处理 L1 |
| 备注 | 有自建仓或 3PL 的公司才需要；纯 dropship 并入售后 |

### 1.11 岗位默认包：独立站运营

| 商品管理 | ✅ | 运营 | 运营 | 商品专员 |
| 内容与博客 | ✅ | 运营（低频） | 内容 1 人 | 内容组 |
| 促销与折扣 | ✅ | 运营 | 运营主管 | 运营主管 |
| 数据日报 | ✅ | 老板看 | 运营主管 | 数据分析 |
| 邮件营销 | ✅ | 运营 | 运营 | CRM 专员 |

## 2. Amazon 运营（清单）

| 职责 | 一句话 | 连接器 | 自动化上限 |
|---|---|---|---|
| `amz.buyer-messages` 买家消息 | 站内信与售后，24 小时回复 SLA | SP-API Messaging | FAQ L3；退款类 L2 过额度 |
| `amz.listing` Listing 管理 | 文案、A+、图片、变体、关键词埋词 | SP-API Listings | 文案 L2；上架 L1 |
| `amz.inventory` 库存与 FBA 补货 | 库存预测、补货计划、断货预警 | SP-API FBA | 预警 L3；补货计划 L1 |
| `amz.reviews` 评价与反馈 | 差评监控、合规邀评、卖家反馈移除申请 | SP-API + 页面抓取 | 监控 L3；申请 L1 |
| `amz.promotions` 促销与 Deal | Coupon、LD、Prime Day 报名 | SP-API | 方案 L3；报名 L1 |
| `amz.account-health` 账户健康与合规 | 绩效通知、侵权 / 审核申诉、类目审核 | SP-API Notifications | 监控 L3；申诉 **永不 L3** |
| `amz.market-intel` 关键词与竞品监控 | 排名、竞品价格、BSR 变化 | 第三方数据（Keepa 类） | L3 |
| `amz.finance` 财务对账 | FBA 费用、退款、报销申请 | SP-API Finances | 对账 L3；报销申请 L2 |

Amazon 站内广告不在这里，它是投放岗位的 `ads.amazon`（§5）；Amazon 运营岗位的默认包可以把它勾进来。

Amazon 与独立站的售后客服 **不合并**：平台规则、消息模板、可做的动作完全不同，硬合会让额度和 skill 都变成两套 if。共用的只有 `customer-care` 的说话纪律。

## 5. 投放（清单）

独立岗位（09-07 Luoye 定）。按平台拆职责，理由比社媒更硬：每个广告平台是一个独立的花钱账户、独立的计费与风控，额度必须按账户设。

投放岗位有一条所有职责共用的额度纪律：**减少花钱的动作可以到 L3，增加花钱的动作最高 L2，新开花钱口子永远 L1。** 具体：

| 动作类型 | 例子 | 上限 |
|---|---|---|
| 止损 | 暂停超 CPA 的广告组、异常花费熔断、否词 | L3（保护性动作） |
| 额度内调整 | 出价 ±`max_bid_change_pct`（默认 15%）、预算 ±`max_budget_change_pct`（默认 20%）、素材轮换 | L2 |
| 开口子 | 新 campaign、新受众、提预算超额度、改计费方式 | L1，不可关闭 |

全岗位总闸：`max_daily_spend_total`（所有账户日花费上限，超过即熔断并即时通知 `common.owner`）。

| 职责 | 一句话 | 连接器 | 备注 |
|---|---|---|---|
| `ads.google` Google Ads | Search / Shopping / PMax / YouTube；关键词、否词、出价、预算 | Google Ads API | YouTube 广告归这里，不归 `social.youtube` |
| `ads.merchant-center` Google 商品 Feed | Merchant Center feed、拒登修复、商品数据质量 | Merchant Center API + Shopify 商品（读） | Shopping 广告的前置；拒登修复 L2，feed 结构变更 L1 |
| `ads.meta` Meta Ads | Facebook / Instagram 广告；受众、素材、预算 | Marketing API | 与 `social.facebook` / `social.instagram` 分离：主页管理不花钱 |
| `ads.tiktok` TikTok Ads | 视频广告、Spark Ads、TikTok Shop 广告 | TikTok Marketing API | Spark Ads 要引用有机视频，依赖 `social.tiktok` 的授权 |
| `ads.amazon` Amazon 站内广告 | SP / SB / SD；关键词、竞价、否词、预算 | Amazon Ads API | 从 Amazon 运营岗位挪来；Amazon 运营的默认包可勾选 |
| `ads.pinterest` Pinterest Ads | 推广 Pin、购物广告 | Pinterest Ads API | 家居 / 服饰类目才需要，默认不勾 |
| `ads.microsoft` Microsoft Ads | Bing 搜索广告，通常从 Google 导入 | Microsoft Ads API | 默认不勾 |

## 7. 公司通用职责（人人都有）

不属于任何岗位，加入工作区自动获得：

| 职责 | 内容 |
|---|---|
| `common.member` | 个人任务、个人队列、日报阅读、知识库检索（按权限） |
| `common.approver` | 被路由到的审批项处理（按其他职责的通知路由决定收到什么） |
| `common.owner`（工作区所有者） | 策略层规则、授权额度、职责分配、连接器授权、公司简报 |

个人工作区里一个人同时是 `member` + `owner` + 自己选的所有职责。

## 8. 职责组合的规则

1. **有效权限 = 并集**；同一动作在两个职责里额度不同时，按工作项所属职责的额度算，不取最大
2. **队列合并**：一个人的所有职责进同一条队列，按职责打标、按紧急度排序；不做多 Tab
3. **交接**：撤销职责时，该职责的在办工作项、上下文、积木整体转给接手人；没有接手人时挂到 `common.owner`
4. **岗位模板可改**：公司管理者可改岗位默认包，改的是模板不影响已分配的人；重新应用模板需确认
