## 1. 还缺什么：按契约逐个对照

09 文档 §5 已经列了框架层十个盲区。再往下挖一层，按 16 份契约和内核逐个看"有没有现成轮子"，发现七处**空着的位置**（不是没想到，是还没有实现路径）：

| 缺口 | 属于哪个契约 | 现状 | 建议 |
|---|---|---|---|
| **多步骤长流程编排** | 调度 #13 之上缺一层 | 我们有"持久定时 → 单次运行"，没有跨天、跨多次人审、可补偿的流程状态机：红人合作（寄样 → 发布 → 回款）、订单里程碑、邮件序列、Join 迁移都是这种 | 加第 17 份契约 **流程（Workflow）**：durable 状态机 + 步骤 = RunRequest 或人工审批 + 补偿。候选见 §2 |
| **检索引擎** | 知识 #10 | 契约写了"带身份检索"，没定引擎：向量 + 关键词混合、重排、分块、权限过滤下推 | SQLite 起步用 sqlite-vec + FTS5（dsh 自己也用 FTS5）；Postgres 档用 pgvector；引擎藏在契约后 |
| **文档解析** | 知识 #10 / 入站 #9 | 供应商 PDF、说明书、邮件 HTML、飞书文档 → 事实卡，没有解析管线 | 解析器做成 provider（Docling / MinerU / Unstructured 类），输出统一的"文档块 + 出处（文件 + 页码）" |
| **策略引擎** | 职责与分配 #2 → 数据层 ACL | 角色 × 数据域 × 操作 × 范围 × 字段分级，目前是"自己写判断"；这是最容易写出漏洞的地方 | 用 policy-as-code 引擎（Cerbos / OpenFGA / Casbin 类）承载，职责定义编译成策略；一致性套件里放"越权用例集" |
| **输出侧脱敏** | 执行器 #5 | fencing 管输入侧（移植 Commerce Agents），输出侧"按接收方清权脱敏"只有原则 | PII / 机密字段识别做成 provider（Presidio 类 + 我们的字段分级），在投递前统一过一遍 |
| **计量与计费** | 模型网关 #7 / Connect #8 | 按职责记账写了，没有"计量事件 → 账单 → 积分扣减"的通路；P2 / P1 都靠它 | 计量做成内核事件的一个消费者（OpenMeter 类思路），积分扣减沿用 KefuAgents 已有账本 |
| **Agent 间协议** | 运行协议 #6 | 个人端 Agent ↔ 公司端 Agent、付费插件的云端大脑 ↔ 本地执行器，之间怎么说话没定 | 内部用 RunRequest；跨实例评估 A2A 一类的开放协议，不自造 |

另外两项是**格式采用**，不是缺口，但要定死：

- **skill 格式采用 Agent Skills 开放规范**（`SKILL.md` + frontmatter + 资源目录）：这样我们的技能能被 Claude Code、dsh、teamai 直接消费，公司库导出零成本。06 文档的"段级叠加"在它之上加一层元数据，不改格式。
- **工作台事件流参考 AG-UI 一类的 Agent-UI 事件协议**：我们的十种事件（Commerce Agents 来的）与它对齐，积木注册表就能接第三方前端。

## 2. 值得参考或采用的开源方案（按契约）

| 契约 | 候选 | 拿它干什么 | 建议 |
|---|---|---|---|
| 内核 | Cordis（已定） | 插件容器 | 采用 |
| 流程 #17（新） | Inngest（KOLAgents 已在用）、Temporal、Restate、DBOS、Trigger.dev | durable 流程状态机 | **Inngest 优先评估**：团队已有经验，且有 self-host；Temporal 太重 |
| 运行协议 #6 | dsh SDK / ACP（dsh 已支持）、A2A | 本地起 run；跨实例对话 | dsh SDK 采用；ACP 给工作台聊天面；A2A 只评估 |
| 模型网关 #7 | LiteLLM、Portkey Gateway、Cloudflare AI Gateway、Vercel AI SDK 的 provider 层 | 多模型路由、重试、缓存、记账 | 契约自写；实现可先套 LiteLLM proxy，托管档看 Cloudflare AI Gateway |
| 可观测 | OpenTelemetry + Langfuse（或 Arize Phoenix） | trace 贯穿 run → tool → action → apply；模型调用的成本与质量 | **采用 Langfuse**：开源、self-host、天然记 prompt / cost，和模拟报告一起看 |
| 策略引擎 | Cerbos、OpenFGA、Casbin | 职责编译成策略；越权测试 | Cerbos 或 Casbin（有 TS 库、可嵌入 SQLite 档）；OpenFGA 更强但要独立服务 |
| 知识 #10 | sqlite-vec + FTS5 / pgvector；LanceDB；Co-Engram（数据模型） | 混合检索；记忆置信度与衰减 | 引擎按存储档切换；Co-Engram 只借数据模型 |
| 文档解析 | Docling、MinerU、Unstructured、Marker | PDF / Office / HTML → 结构化块 | 做成 provider，先接一个 |
| 输出脱敏 | Microsoft Presidio；NeMo Guardrails（只看思路） | PII 识别与替换 | Presidio 作 provider（Python，独立进程） |
| 计量 | OpenMeter、Lago | 计量事件 → 用量 → 账单 | 先只做计量事件与聚合，账单沿用现有 |
| 评测与模拟 | Commerce Agents evals（已采）、promptfoo、Inspect AI、DeepEval；**τ-bench / AppWorld**（合成环境 + 合成用户的 benchmark 思路）；**确定性模拟测试（DST，FoundationDB / TigerBeetle / Antithesis 的做法）** | 场景 DSL、LLM judge、合成人的写法；seeded 随机 + 虚拟时钟 + 可回放 | **τ-bench 的"合成用户 + 工具环境"是我们合成人和合成 provider 最直接的样板**；DST 是模拟回路的理论锚点：一切随机与时间都来自 seed，失败可复现 |
| 属性测试 | fast-check | 不变量断言的随机输入 | 采用，跑在一致性套件里 |
| 桌面壳 | Tauri（sidecar、updater、keychain）、Electron；Wanta、dsh-desktop（看结构） | 三个 sidecar 的进程监督与更新 | **Tauri 优先**：包小、sidecar 与更新是一等公民、能接 OS keychain |
| 身份 | better-auth（KefuAgent 已在用） | 本地账号、magic link、SSO provider | 沿用 |
| 内容仓 | isomorphic-git | git 隐藏在 UI 之下 | 采用 |
| 插件签名 | Sigstore / npm provenance | 插件清单签名、允许源 | 采用 Sigstore 思路，第一阶段先自签 |
| 同步（v2） | PowerSync、ElectricSQL、Turso | 按权限部分复制 | 仍推迟 |
| 远程接入 | Tailscale、Cloudflare Tunnel | 手机审批本地实例 | 桌面壳内置向导 |
| 对话渠道 | dsh-channels（已定）；unipile（LinkedIn + WhatsApp 统一消息，OpenConnector 已有 provider） | 渠道契约；LinkedIn 人机协同的消息面 | unipile 值得评估：LinkedIn 消息一直没有好路径 |

不建议再加的：LangGraph / CrewAI 一类 Agent 编排框架（turn loop 是 dsh 的，再套一层是重复）；自建向量数据库；自建 OAuth 服务器（OpenConnector 已管）。

## 3. 上游哨兵：参考过的库更新了，自动判断、自动试升级

答案是**可以**，而且不用另造一套系统——它就是我们自己框架的第一个"客户"：上游变更 → 提议 → 审批队列 → 执行器试升级 → 报告。这既是工程需要，也是最好的 dogfood。

### 3.1 先把上游分类，不同类型不同处理

| 类型 | 例子 | 我们拿了什么 | 变更意味着什么 |
|---|---|---|---|
| **运行依赖** | dsh（`@deepseek-ai/dsh-*`）、OpenConnector runtime、Cordis、Inngest、Langfuse | 版本锁定的包 | 要升级；可能破坏契约 |
| **Vendored 分支** | dsh-channels（我们的适配器在上面）、providers-contrib（贡献 OpenConnector 的 provider，合并前 vendored） | fork + 补丁 | 要 rebase 我们的补丁；我们的 PR 合并后要"从 vendored 转依赖" |
| **移植代码** | Commerce Agents 的 fencing / gates / changes | 抄进来的源码 | 上游修 bug 或加规则时要对照回来 |
| **只参考** | teamai、Co-Engram、dsh-genui、dsh-memory-evolve、Hermes、τ-bench | 数据模型、机制、思路 | 不升级，只看"有没有新想法" |

### 3.2 一份清单文件是一切的起点

```yaml
# upstreams.yml（放仓库根，本身也是契约的一部分）
- id: dsh
  kind: runtime-dep
  repo: deepseek-ai/deepseek-harness
  pinned: dsh-v0.1.3-alpha.1
  we_depend_on:                      # 我们碰到的 seam，变更分类靠它
    - packages/core/tools/src/index.ts      # pre/post-execute, restrict
    - packages/interaction/user-approval    # answerer
    - packages/core/system-prompt           # section / context
    - packages/sdk                          # headless run
    - packages/preset/agent-presets
  changelog: .agents/notes/               # 它没有 CHANGELOG，看这里
  covered_by: packages/adapter/dsh/contract-tests
  wishlist: [多用户, cron 调度, MCP server 模式]   # 命中就单独提醒
- id: open-connector
  kind: runtime-dep
  repo: oomol-lab/open-connector
  pinned: <commit>
  we_depend_on: [docs/runtime-api.md, src/providers/shopify_admin, src/providers/gmail, src/providers/meta, src/providers/whatsapp, src/providers/klaviyo]
  covered_by: packages/adapter/connect/contract-tests
  wishlist: [amazon_sp_api, tiktok_shop, imap, feishu_contacts, merchant_center]
- id: dsh-channels
  kind: vendored
  repo: wsz987/dsh-channels
  our_patches: vendor/dsh-channels/patches/
  our_upstream_prs: [<PR url>]
- id: commerce-agents
  kind: ported
  repo: anthropics/commerce-agents
  ported_files: { commerce_common/fencing.py: packages/core/src/fencing.ts, merchant_agent/changes.py: packages/core/src/changes.ts }
- id: teamai-cli
  kind: reference
  repo: Tencent/teamai-cli
  topics: [分发协议, 知识库健康, 晋升判据]
```

### 3.3 管线：观察 → 分类 → 试升级 → 提议 → 人批 → 施行

```
① 观察      每日：release / tag / 默认分支的提交，只看 we_depend_on 与 changelog 路径
            （GitHub API 或 Firecrawl monitor；dsh 这种无 CHANGELOG 的看 .agents/notes/ 与导出类型的 diff）
② 分类      一次 Agent 运行（只读）：
            · 碰没碰我们的 seam（按 we_depend_on 路径 + TS 声明文件 diff）
            · 破坏性 / 增量 / 安全修复（semver + 声明 diff + 上游说明）
            · 是否命中 wishlist（"OpenConnector 新增 amazon_sp_api provider"）
            · 只参考类：有没有值得看的新机制 → 变成"知识提议"，不是升级
③ 试升级    在隔离 worktree 里自动做：
            · 运行依赖：改 pin → 装 → adapter 契约测试 → 该契约的一致性套件 → 模拟 fast 档；
              碰了 seam 再跑 realistic 档
            · vendored：把上游新版拉进来，rebase 我们的 patches；冲突即失败
            · 移植代码：对上游变更文件与我们的移植文件做语义 diff，列出"上游改了、我们没跟"的规则
④ 提议      产出一条审批项 upstream_upgrade：
            上游说明摘要 · seam 影响 · 测试结果 · 模拟指标前后对比 · 建议（合并 / 观望 / 需人工改 adapter）
            → 进维护者工作区的队列（common.maintainer 职责的车道）
⑤ 人批      L1：人看报告点通过 → 施行 = 合并升级分支、更新 pinned
            将来按同一套晋级规则：patch 级、不碰 seam、全绿的升级采纳率 ≥ 95% 持续 4 周 → L2 自动合并 + 抽检
⑥ 施行后    我们的上游 PR 被合并 → 自动提议"vendored 转依赖"；
            wishlist 命中 → 自动提议"把该 provider 加进 Connect 契约的覆盖表"
```

### 3.4 为什么这样做而不是只用 Renovate / Dependabot

它们能开"版本号 +1"的 PR，不知道我们碰了哪些 seam、不会跑模拟、不认识 vendored 分支和移植代码、更不会读 `.agents/notes/`。所以用法是：**Renovate 负责发现 npm 版本，哨兵负责分类、试升级和提议**；git 固定的、vendored 的、只参考的，全靠哨兵。

### 3.5 它给框架带来的三个额外收益

1. **审批总线与学习回路的第一个真实负载**：升级提议就是审批项，采纳率就是晋级依据——框架还没接一个客户之前，就先服务自己
2. **契约测试与模拟回路有了持续的外部压力**：上游每动一次都在验证"薄适配层是不是真的薄"
3. **wishlist 变成产品路线的一部分**：等的功能上游做了，第二天队列里就有一条

### 3.6 第一阶段范围

把 `upstreams.yml`、观察与分类、运行依赖的自动试升级（dsh、OpenConnector）、审批项产出做进第一阶段的交付 D（模拟回路）旁边；vendored rebase 与移植 diff 第二阶段。
