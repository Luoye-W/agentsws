## 0. 一句话

九条渠道职责骨架相同、各自一个连接器，分两组只是模板里的摆法：**内容账号组**（Meta / TikTok / X / YouTube）写的是发布、排期、回评论，**发布永远人审**；**社群组**（Facebook Group / Reddit / Discord / Telegram Group / WhatsApp）写的是入群审核、群规、群发、私信，接抑制名单与频率上限，**群发永远人审**。共用能力进 `social-core`。群里冒出来的客户问题由岗位路由转给客服的"社群管理"。

- 所有出站文案过 `commitment_scan` + `suppression.ts`（WP64 那份全仓唯一规则）；社群组的私信与回帖还过"是不是客户问题"分类（`social-core/triage`）→ 是 → 出"转客服"卡（54 岗位路由到客服的社群管理），社媒运营不答。
- 面板（36 积木）：内容组：内容日历（本周 / 下周排期）、待发布队列、近 30 天表现（曝光 / 互动 / 涨粉）、待回评论；社群组：待审入群、活跃度、待处理帖子、群发队列、转客服计数。数据源没连就明说。
- 卡：发布卡（L1，带预览与排期时间）、回评论草稿卡、群发卡（L1，带受众数与抑制剔除数）、入群审核卡、转客服卡。

## 3. `social-core`（P2）

> **WP72 实现**：`packages/social-core`，六模块 + 九条适配器。四条有真实现
> （Meta / YouTube / Discord / Telegram），四条说清为什么还没有，

## 4. 客服岗位加一条：`dtc.community-support` 社群管理（P3）

> **WP72 实现**：`packages/roles/roles/dtc/community-support.yml`，动作 id 与
> `mandate` 与 `dtc.support` **逐字相同**（同一个客户换个渠道问，能拿到的补偿必须一样）。
> 与它真正不同的只有三处：读的是社群线程（**读不到成员名册**）、连接器换成八张社媒卡、
> 回复从 L2 起。岗位模板与 `SEED_POSITIONS` 都加了第四条，默认勾。
>
> **一处判断跟着变**：客服岗位里一句不提渠道的"客户问退货"现在**判不准**了——
> 网站客服与社群管理只差一个渠道，那句话本身不带答案（54 §2「拿不准就问一句，不猜」）。
> 带上渠道（"Discord 群里有人问退货"）立刻判得准。15 人 pack 那条路由题照这条改了。

- 干什么：群与私信里的**客户问题**（售前问答、订单、售后）——由社媒运营的 triage 转过来，或直接从这些渠道的私信收件；答法与 `dtc.support` 同一套（知识、事实卡、额度、承诺扫描），只是渠道不同。
- 读：转客服卡、该渠道私信 / 帖子（只读）、订单 / 知识；写：`reply_customer`（`outbound_message` L2 → L3）、`stage_refund` 等沿用 `dtc.support` 的动作与额度（同一份 caps，不另起）。
- 岗位模板"客服"= 网站客服 / 网站在线客服 / Amazon 客服 / **社群管理**，默认全勾。
- 与社媒运营的分界写在两条职责的 description 里（54 路由判据靠它）：社媒运营 = 内容、氛围、活动、群规；社群管理 = 客户的问题。

>
> 1. **四个适配器真实现**在 `packages/social-core/src/channels/{tiktok,x,reddit,whatsapp}.ts`：
>    TikTok 两跳发布（`/post/publish/video/init/` + `tiktokPublishStatus` 轮询，**403 单独判

>    Reddit 每跳带 UA + form-urlencoded + `t3_` 前缀 + 一分钟 60 跳自己先排队 +
>    「群发」= submit + distinguish 置顶、WhatsApp 只发模板（`template.name` 必填）
>    且自由文本只在 24h 窗口里（窗口按最近一条入站时间判，**没记过 = 关着**），
>    `whatsappBroadcastGate` 把 opt-in 也当硬闸。连接目录 `tiktok_content` / `reddit` /
>    `whatsapp_business` 三张从"还没接"改为**可连**，表单与准备说明补齐；
>    `action-side-effects.yml` 补齐 Reddit 四个口与 X 社媒那一侧。
> 2. **Facebook Group 浏览器模式**接上执行器（`BrowserExecutor` 是这个包对 55 §3 那个
>    执行器的形状）：**读走白名单**（职责 yml 的 `browser_scope: ['*.facebook.com',
>    'facebook.com']` 是真闸，`FACEBOOK_GROUP_HOSTS` 是适配器自己那第二道，两处写同一份）、
>    **写先出卡**（五个写口子永远回 `browser_required`，批准之后才走
>    `executeApprovedBrowserAction`，没有卡 id 就不点）、**失效即停**（执行器回
>    `handover` 就说"请你接管"且不重试；`failed` 是另一句话）。没有真 Facebook 账号，
>    用假执行器把这三条钉住。
> 3. **社媒库 `/v1/social/*`**（`packages/api/src/routes/social.ts` +
>    `apps/server/src/social-service.ts`）：账号 / 帖子 / 线程 / 成员四类读写。
>    `triage.ts` 与 `moderation.ts` 从此有调用方——`POST /v1/social/threads` 收一条新入站
>    的帖子，类由 `triageThread` 判（调用方递不进来一个 `triage`），客户问题出**转客服卡**
>    落到真持有 `dtc.community-support` 的人头上，其余按群规出审核卡。
>    **成员名册那把闸**（56 §4）由 `community_member` 这个域兑现：同一条
>    `GET /v1/social/members`，社群组 200、客服 403，路由里一行 if 都不用写。
> 4. **内容日历**：`GET /v1/social/calendar`、`POST /v1/social/posts`、
>    `PATCH /v1/social/posts/:id/schedule`（改时间 = 重新出一张卡，因为换个时间发
>    也是一次发布）；撞车当场算、**写在卡面上**；定时方 `HANDLERS.socialPublish`

>    发失败写回平台原话且不重试。工作台职责页多一块**七列周视图**（拖拽改排期）。
