## 0. 一句话结论

**能做，但做不成「整个 agentsws 装进去」，做得成「一部分装进去 + 连着我们自己的服务」。**

- 官方插件能带进去的：**岗位的人设、做事方法（技能）、工具、侧栏里的一页界面、设置页、接 MCP 服务器**。这些装上就能用，用户在官方桌面端侧栏「插件 → 添加插件」里填一个包名就装好。
- 官方插件带不进去、或者带进去会很难受的：**出卡审批队列与账本、连店铺 / 邮箱的连接器、邮件收发与聊天窗、关了应用也照跑的巡检、学习回路、多人与公司端、云同步**。它们要么官方根本没有对应物，要么需要一个一直开着、有自己数据库的服务——官方插件跑在桌面端进程里，关了应用就停，装原生数据库模块风险很高。
- **推荐**：先做方案 A「岗位包」（只带人设 + 技能，装上即用，约 3–5 天），再视反馈做方案 B「连本机工坊」（插件当遥控器，重活还在 Agents 工坊里，先走 MCP 口）；**不做**方案 C「全部塞进插件」（要重写半个产品，且每次官方升级都可能坏）。

## 1. 官方插件体系到底支持什么（0.2.0-rc.1 查到的事实）

### 1.1 插件是什么、装的单位是什么

| 概念 | 白话 | 事实 |
|---|---|---|
| 插件（plugin） | 一段代码，官方启动时调它的 `apply(ctx)`，它借 `ctx` 往系统里「登记」东西 | 分**宿主半边**（Node，跑在后台进程里）和**界面半边**（浏览器 / 桌面窗口里的 React 组件）；卸载时登记的东西自动撤掉 |
| 组合包（bundle） | **用户装的单位**：一个 npm 包，里面带一份 `cordis.patch.yml`，写着「往系统里插哪几行插件」 | `package.json` 里写 `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`；一个组合包可以插很多行，用户能在插件页里**逐行开关** |
| profile | 一套「装了哪些组合包、按什么顺序」的配置目录 | 官方桌面端用的是 `$DSH_HOME/profiles/desktop`（通常 `~/.dsh/profiles/desktop`），由桌面端独占，命令行改不了它 |
| 只带配置的组合包 | 不写一行代码，只往 patch 里插官方现成插件并配好参数 | 官方「接一个 MCP 服务器」的模板就是这种：两份文件（`package.json` + `cordis.patch.yml`） |
| 官方可选包 | 官方随安装附带、默认关着、在插件页「官方」分组里点开的包 | 0.2.0 起「自动化任务」「团队协作」「语音输入」都是这种（上游 `OPTIONAL_BUNDLES`）；**第三方包进不了这个分组** |

### 1.2 插件能往系统里登记什么

| 能登记的 | 官方怎么叫 | 能不能用在我们身上 |
|---|---|---|
| 给模型用的工具 | `ctx.tools.register`（`defineTool`） | ✅ 我们的读工具、「提议」工具都能这样挂 |
| 工具调用前拦一道 / 问人 | `tools/pre-execute`（可返回 ask）、`ctx.tools.guard`（只能拒） | ✅ 对**所有**工具生效，不分谁装的——我们的门禁就是这一类（16 §2） |
| 系统提示词段落 | `ctx.systemPrompt.section` | ✅ |
| 一个 Agent 的人设 | `dsh-persona`（挂在 preset 里，遮蔽默认人设） | ✅ 岗位 / 职责的 persona 正好对上 |
| 一套 Agent 组合（「模式」） | `dsh-agent-preset`：一行一个 preset，写它挂哪些工具、哪段人设；会话开头选 | ✅ 每个岗位一个 preset；用户在对话首页的选择器里选 |
| 技能（做事方法） | 技能提供方（`ctx.skills`）或技能目录；模型用官方 `skill` 工具按需读 | ✅ 我们 18 份 `SKILL.md` 本来就是这个格式 |
| MCP 服务器 | 插一行 `dsh-mcp-client`（本机子进程 `stdio` 或网址 `streamable-http`，可带请求头） | ✅ 这是「插件连我们服务」最省事的一条路 |
| 界面 | 往「插槽」里挂 React 组件：左侧栏加一个入口 + 主区一整页、右栏一个标签页、对话里的卡片 / 工具结果样式、设置页、插件详情页里的配置表单 | ⚠️ 能挂，但官方明确要求：**用 React 组件画在插槽里，不许用 iframe 嵌网页**；官方界面是 **React 18**，我们工作台是 React 19 + Tailwind + shadcn，**组件搬不过去，要重画** |
| 定时提醒 | 官方可选包「自动化任务」 | ⚠️ 只是「到点把一句话投回原来那次对话」，应用关着不跑（WP181 已查清） |
| 后台长活 | 插件的宿主半边可以开定时器、起子进程、开端口 | ⚠️ 技术上能，但**只在官方桌面端开着时活着**（关窗口只是隐藏，退出应用就停） |
| 自己的数据 | 官方的存储服务，或插件自己写文件 | ⚠️ 要数据库就得带原生模块，见 §1. |

### 1.3 用户在官方桌面端装插件的真实步骤

1. 打开官方桌面端（DeepSeek Harness），左侧栏点**插件**。
2. 点**添加插件**，输入框里填下面任一种：
   - npm 包名（可带版本），例如 `@agentsws/dsh-roles`——**最省事**，装的是我们发布时就构建好的代码；
   - GitHub 地址（`github:xxx/yyy#提交号`）——拉的是源码，需要用户**额外点一次「允许构建脚本」**，官方提示这等于「允许这个包在你电脑上以你的权限执行」；
   - 压缩包（`.tgz`）或本机目录的绝对路径。
3. 安装按钮上方一直挂着官方提示：「来源可信……插件在本机以你的权限运行，来源不明的插件可能损坏 DeepSeek Harness，或读取和泄露你的数据」。
4. 桌面端用**自带的 pnpm** 装（用户不用装 Node / pnpm）；首次会自动在 npm 官方源和国内镜像（npmmirror）之间挑快的那个；连不上 GitHub 时提示「改用国内镜像」。
5. 装好默认就开；插件页里出现一张卡片（名字、说明、图标来自包里的 `locale/zh.json` 与 `icon`），点进去能**逐行开关**、改配置、卸载。
6. 大多数改动**不用重启**即生效（官方叫热重载）；替换已装包的新版本要重启一次。

另外两条路：
- **对话里让模型装**：官方「创造模式」有个 `plugin_manager` 工具，模型可以替用户装 / 开关插件，每一步都要用户批（没开「完全访问」时）。
- **命令行**：`dsh plugin --profile <名> add <包>`——但**改不了桌面端那份 profile**（桌面端独占）。

**官方没有插件市场。** 插件页的「官方」分组只放官方自己随附的可选包；第三方插件只能靠用户自己知道包名。官方 README 的说法是：给插件仓库加 GitHub 话题 `dsh-plugin` 便于被发现。社区有 `dsh-market` 等索引站（53 §1.3），都不是官方的。

### 1.4 权限与审阅、常驻进程、原生模块

| 问题 | 事实 | 对我们意味着什么 |
|---|---|---|
| 插件有没有沙箱 | **没有**。宿主半边和官方代码在同一个进程里，以用户权限运行；官方的沙箱只管「模型生成的命令 / 代码」，不管插件 | 用户装我们的插件 = 完全信任我们；反过来我们的插件也管不住别的插件 |
| 插件工具「要人批」怎么做 | 两种：① 工具自己在执行前调 `ctx.approval.request(...)`，结果只有「这一次允许 / 拒 / 取消 / 没人答」，**没人答就当拒**；② 在 `tools/pre-execute` 里返回 ask，走官方对话框。都是**对话里当场弹窗、批一次管一次** | 官方的「批」是**当场一问一答**，没有「攒成一摞卡、换个时间一起批、批了由执行器幂等地做」这回事——我们的出卡队列与账本在官方里**没有对应物** |
| 模型装插件要不要批 | `plugin_manager` 的每个动作都要批（或用户开了完全访问）；官方默认的普通模式里这个工具是关的，只在创造模式里开 | 与我们 WP180「装插件一律出卡」同一个口径 |
| 能不能起常驻后台进程 | 能（插件里起子进程、开定时器、监听端口都行）。但它**活在桌面端的后台进程里**：关窗口只是隐藏、任务照跑；**退出应用就全停**。桌面端退出前会弹框问「有正在运行的任务 / 定时任务，要退出吗」 | 我们的每日巡检、邮件收件、聊天窗值守要「电脑开着就一直跑」——放进插件就变成「官方桌面端开着才跑」 |
| 能不能带原生模块 | 装的时候：原生模块要跑安装脚本，pnpm 默认拦下，用户要点「允许这些脚本并重试」。跑的时候：插件和桌面端一起跑在 **Electron 自带的 Node** 里，原生模块必须按它的版本编译；而装包用的是桌面端另带的一份 Node。**两者对不上时会加载失败**（本单没法实测，列为高风险） | 我们服务端全靠 `better-sqlite3`（原生模块）。放进插件要么赌它能装上，要么改用 Node 自带的 `node:sqlite` 或官方存储服务——都是大改 |
| 装坏了怎么办 | 桌面端启动失败会弹原生恢复框：退出 / 重启 / **禁用第三方插件** / 备份 profile 补丁后重启 | 我们的插件出错，用户看到的是「DeepSeek Harness 启动失败」，第一反应是禁用我们 |

### 1.5 版本兼容：跟随成本

- 插件在 `package.json` 的 `peerDependencies` 里写它要的 `@deepseek-ai/dsh-*` 版本范围；**每次启动都会对照当前 dsh 版本**，对不上的包直接跳过不加载（不报错崩溃，但功能消失）。不写就不检查。
- 用户可以对某个「插件版本 × dsh 版本」组合手动豁免（`compatibility.json`，要勾「我接受风险」）；插件或 dsh 一升级，豁免就失效。
- 官方桌面端**会自动更新**（有强制更新流程）。我们现在自己的安装包是把 dsh **锁死到精确版本**（`profiles/agentsws/package.json`，WP177），升级走 docs/42 七步；**做成插件后，dsh 什么时候升级由官方和用户决定，不由我们决定**。
- 官方仍是 developer preview，明说会有破坏性改动：0.1.7 时就把「按目录扫 preset」整包下线换成了 registry（WP132）；0.2.0 把自动化任务改成了可选包。**界面插槽**的名字与参数变得最勤——官方创造模式的开发指引也写着：别引用官方界面组件包，「它们会不打招呼就改」。

### 1.6 许可证与分发要求

- dsh 本身 MIT；官方对插件的许可证**没有要求**，npm 上发什么许可证都行。我们仓库是 Apache-2.0，插件包照用即可。
- 发到 npm 公共源 = 公开。只能放本来就在开源仓库里的东西（人设、技能、工具代码）；**私有仓库 `agentsws-extension` 的代码、KOLAgents / KefuAgent 的 MkSaaS 模板代码一个字节都不能进插件包**（_common 许可证红线）。
- npm 需要一个 `@agentsws` 组织账号（Luoye 注册），发布走 CI；国内用户经 npmmirror 同步（一般几分钟到十几分钟延迟）。
- 包里要带 `locale/zh.json` / `en.json`（插件页上的名字与说明）和一个 ≤256 KB 的图标，否则卡片上只显示英文包名。
