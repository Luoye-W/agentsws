## 1. 卡片呈现：照 KefuAgent 的四段式，逐条对照 WP15

KefuAgent 的卡面（`support-inbox-deck.tsx`）是四段式、三条边界线，**一次只看一张**，动作行永远在视口里。WP15 做成了"多张平铺的列表卡"，且违反了三条红线。逐条对照：

| KefuAgent 做法 | WP15 现状 | 改法 |
|---|---|---|
| **一次一张**：780px 居中、min-height 320、内容区 `max-h 420` 卡内滚、动作行不出视口；背后两张歪斜的"景深"假卡；"第 N / M 张" | 平铺列表，一屏三张，各自带"详情 ▾" | 改为单卡 deck；键盘 ←/→/↑ 对应拒绝/批准/稍后；列表只在"记录"Tab |
| **标签行**顺序固定：渠道 → 优先级（P0 红，其余主色）→ 倒计时（琥珀，有 expires 才出）→ 卡型纯文本 → "合并 N 张" | 顺序是 档位 → 卡型 → 客户名 | 按 KefuAgent 顺序；客户名不进标签行 |
| **标题**单行 15px 半粗，服务端截 120 字 | 相近 | 保持 |
| **内容盒**：一次只显示一种语言（中文摘要 / 原文 / English 队列级切换，禁双语堆叠）；`bg-muted/40` 圆角盒 | 英文原文直接露在摘要位 | 加语言切换；默认中文摘要；原文在盒内切换 |
| **证据 chip 永不裸 id**：`labelKey` 走 i18n，形如「订单：已查单」「政策：退货 14 天」，最多 10 条；实体 chip 另起一行 | 露了 `fact_775c…`、`cus_anna`、`run_demo_42` | 服务端 enrichment：ObjectRef → 展示名（订单号 / 客户名 / 事实卡标题）；run id 只进"详情"；上限 10 |
| **动作行** ≤ 3 个快捷决定，approve 主按钮；右侧安静区"需要补素材""稍后 ↑"；**没有"更多"菜单**，多余选项折进"指导" | 有"…"溢出、有"详情 ▾" | 去掉"…"；"详情"改为点卡面展开；补素材 = `ai_question` 的反向入口 |
| **已处理不留队列**：飞出 300ms → 下一张；`done` 只在档案室和"今日战报" | 已决定的卡还留在列表变灰 | 同 KefuAgent |
| **空态 = 今日战报**四格（AI 自主处理 / 你已处理 / 自动发送 / 拦截待确认） | "暂无卡片" | 同 KefuAgent，数字来自事件日志 |
| 折叠区（指导 textarea、拒绝理由、补素材、问 AI）**点开前不在 DOM 里** | 部分常驻 | 同 KefuAgent |
| 手机 deck：右批准 / 左拒绝 / 上稍后 / 下指导；高风险先弹拦截 | 无 | 二阶段（Electron 内不需要；浏览器手机入口时做） |

**筛选**（KefuAgent 只有 全部 / 客户在等 / 无人等待 三枚 chip，无按卡型 / 岗位筛）。我们多岗位，所以加一行：**岗位 chip**（全部 / 各岗位）+ **等待 chip**（客户在等 / 无人等待）+ **卡型下拉**。筛选只改当前 deck 的集合，不跳页；计数按张数；P0 永不被筛掉（永远置顶出现一次提示）。排序沿 KefuAgent：`priority_band → expires_at → priority → created_at`。

## 2. 四种东西，各是什么

先把词定死。之前把"任务"当成万能容器是错的，四样东西性质不同：

| 对象 | 一句话 | 谁产生 | 谁消费 | 有没有时间 |
|---|---|---|---|---|
| **卡片** Card | **AI 助手提交给人的审批 / 拍板请求**，就是 14 的审批项 | Agent（运行中遇到要人定的事）、系统（告警、摘要、计划、复盘） | 人：批 / 驳 / 指导 / 稍后 | 有**期限**（expires_at），没有"日期"；到期升级或过期 |
| **待办** Todo | **人的承诺**：我（或我交给 AI）要做的一件事 | 人手动、会议纪要、复盘建议、卡片里"建个待办跟进"、数据告警 | 人做，或**委托给 Agent 做** | 可有可无：无日期 = 长期；有截止 = 短期；有排期（某天某段）= 上日历 |
| **会议** Meeting | 一段有参与者的时间，加上它的记录、决定、产出 | 日历（外部 / 本地）、会议应用、人手动建 | 人开会；会议助手处理记录 | 一定有时间，一定上日历 |
| **日历** Calendar | **时间索引的视图 + 排期面**，不是对象 | — | 人看今天 / 本周；把待办拖到某天就是排期 | 显示：会议、有排期的待办、定时任务（25）、卡片到期（叠层可关） |

**目标** Goal 在上面（§2.3），**复盘** Review 在后面（§2.4），它们不参与这张表的混淆。

### 2.1 卡片 ↔ 待办：不是父子，是两条线的交点

- 卡片**不是**待办。卡片是 AI 在做事的过程中回头问人的一句话；待办是人答应要做的事。
- 一张卡片总挂在一个**上下文**上：一个 Run（谁在做什么时候问的）+ 一个**主题**（14 `subject`）：某条客户对话、某个变更、某个待办。
- 交点一：**待办委托给 Agent** → Agent 跑 Run → Run 里产生卡片 → 卡片挂在这条待办下（`ApprovalItem.subject.todo_id`）。人看待办能看到"AI 做到哪、卡着几张要我定"。这就是"有机结合"的主形态。
- 交点二：**卡片里"建个待办跟进"** → 从卡片派生一条待办（`Todo.source = card`），卡片决定后待办还在。
- 交点三：**待我决定的卡片本身出现在"今天"里**，但它是**派生**出来的，不是写进待办表的。今天视图 = 今天到期的卡 ∪ 今天到期 / 排期的待办 ∪ 今天的会议。
- 没有任何待办的卡（客户来信触发）挂在对话上，不挂待办；岗位的"日常"不再造一条假待办，改为在岗位页显示"今天来信 N、AI 处理 M、待我定 K"。

### 2.2 待办的长期与短期：一个对象，靠字段区分

```ts
type Todo = {
  id; workspace_id; position_id?: PositionId
  goal_id?: GoalId; parent_id?: TodoId                // 长期待办拆成短期待办：父子
  title; note?
  owner: PersonId                                     // 承诺人永远是人
  delegate?: { assignment_id: AssignmentId; brief: string }   // 交给哪个 Agent 做、怎么做
  horizon: 'backlog' | 'week' | 'today'               // 由 due / scheduled 推出，也可手动
  due?: Iso8601                                       // 截止 → 短期
  scheduled?: { start: Iso8601; end: Iso8601 }        // 排期 → 上日历
  source: 'manual' | 'meeting' | 'review' | 'plan' | 'card' | 'alert'
  status: 'open' | 'doing' | 'blocked' | 'done' | 'dropped'
  cards: ApprovalItemId[]                             // 委托给 Agent 后回来的卡
  runs: RunId[]
  origin?: { meeting_id?; card_id?; review_id?; alert_id? }
}
```

- **长期待办** = 无 due、挂 goal，住在"待办箱"（backlog），例如"Q4 前上线新品页"。它不上日历，只在目标页与待办箱里。
- **短期待办** = 有 due 或从长期拆出来的子项。有 `scheduled` 才进日历格子；只有 due 的显示在那天的"到期"栏，不占时段。
- 长期拆短期是父子，不是两种对象。周计划就是把 backlog 里的挑几条拆成本周的子项。
- **待办委托给 Agent**：`delegate` 一填，系统按 25 起一个 Run（或定时）；Agent 的进度写回 `runs`，问题回来成 `cards`。撤销委托 = 取消 Run。

### 2.3 目标

```ts
type Goal = { id; level: 'company' | 'position' | 'person'; parent_id?; position_id?; owner: PersonId
  metric: { query: string; format }; target: number; period: { kind: 'week' | 'month' | 'quarter'; start; end }
  status: 'active' | 'achieved' | 'missed' | 'archived' }
```

目标挂指标，指标复用 29 的命名查询，所以首页数字块直接多一行"目标 / 进度"。长期待办挂目标；卡片不直接挂目标（经待办或对话间接）。

### 2.4 每日循环怎么走（"看数据 → 排任务 → 执行 → 复盘"）

- **早上**：`daily_plan` 卡（系统卡）：Agent 看目标差距、昨日数据、昨日复盘、今天会议、到期待办，**建议**把哪几条 backlog 拆到今天、哪几条委托给 AI。人采纳 / 调整。它只是**建议**，不替人写待办；采纳后才写。
- **白天**：今天视图（§3）；卡片 deck；待办打勾；会议。
- **晚上 / 次日早**：`review` 卡：目标进度、异常、今天卡片处理结果（战报四格）、待办完成率、会议产出、Agent 学到的（24 lesson）；产物是明天 `daily_plan` 的草案。周五出周复盘，月末出月复审（可提"改目标"）。

## 3. 首页 = 今天（第三稿）

```
① 目标进度        本月 / 各岗位：值 / 目标 / 进度 / 剩余天数
② 今天            左：时间轴（今天的会议、有排期的待办、定时任务）  右：到期清单（今天到期的待办 + 待我定的卡片数）
③ 卡片 deck       一次一张；筛选：岗位 / 等待 / 卡型 / 来源（待办委托 vs 客户对话 vs 系统）
④ 复盘 / 战报     晚上是复盘卡；白天是四格战报
```

日历完整视图（周 / 月）在左栏单独一项"日历"；岗位页"记录"Tab 里是该岗位的月视图。把待办从待办箱拖到日历某天 = 写 `scheduled`。

## 4. 会议：进内核，记录多源，功能分层

Luoye 定：会议在公司里是必需品，**不做成可有可无的应用**。会议对象进内核，功能分三层：内核自带的免费默认会议助手、我们的付费增强、第三方会议应用。

### 4.1 会议对象与记录来源

```ts
type Meeting = {
  id; workspace_id; title; start; end; location?: string | { online: string }
  participants: { person_id?: PersonId; name?: string; email?: string; external?: boolean }[]
  agenda?: string
  records: MeetingRecord[]                            // 一个会议可以有多份记录
  outputs: { decisions: Decision[]; todos: TodoId[]; boundary_answers: string[]; knowledge: FactCardId[] }
  calendar_ref?: { source: 'google' | 'outlook' | 'feishu' | 'ics' | 'local'; event_id }
  sensitivity: Sensitivity                             // 外部参与者在场默认 restricted
}
type MeetingRecord = {
  id; meeting_id
  source:                                              // 记录从哪来
    | 'online_meeting'    // 线上会议平台：飞书 / 腾讯会议 / Zoom / Teams 的录制与转写导出
    | 'in_app_recording'  // 我们自己录：桌面壳录音 → 转写
    | 'device'            // 外出开会：Plaud 等录音设备 / 手机录音
    | 'third_party'       // Plaud / Otter / 妙记 等第三方工具的接入
    | 'handed_over'       // 别人给过来的会议记录（文档、消息粘贴）
    | 'manual_notes'      // 人手写的笔记
  media?: { kind: 'audio' | 'video' | 'transcript' | 'document'; raw_ref: string }   // 进 18 的受控原始材料区
  transcript?: { text; speakers?; language }
  consent: { recorded_by: PersonId; notice_given: boolean }                            // 录外部人要有告知
  status: 'ingested' | 'transcribed' | 'processed' | 'failed'
}
```

- 记录先进**受控原始材料区**（18 §2.1：加密、保留期、随主体删除），再由会议助手处理；不进模型的只有原始音视频，进模型的是转写文本（围栏包裹）。
- 处理产物走已有管道：决定 → `knowledge_update` / 边界答案（`policy_change`）；待办 → `claim` 卡发给对应的人（06 §2 认领管道，本人确认前不形成责任，31 I13）；下次会议 → 日历。

### 4.2 功能分层

| 层 | 内容 | 谁提供 |
|---|---|---|
| **免费默认（内核自带，随安装）** | 会议对象与日历；粘贴 / 上传记录；桌面壳一键录音；转写（经模型网关的 ASR provider，自带账号）；摘要、决定、待办、边界答案抽取；认领卡；会议纪要导出 | 我们，Apache-2.0 |
| **付费增强（我们的）** | 线上会议 bot 自动入会与实时转写；说话人分离与人名匹配；Plaud / Otter 等设备与工具的自动同步；多语会议翻译；会后自动跟进邮件 | 我们，作为应用市场里的付费应用（23） |
| **第三方会议应用** | 其他团队做的：某平台专用 bot、行业模板、自定义抽取 | 第三方，按 23 的应用规范接 `meeting.record_source` / `meeting.processor` 两个扩展点 |

应用扩展点写进 23：`meeting.record_source`（提供记录：轮询 / 推送 / 设备同步）、`meeting.processor`（从转写抽产出，必须走围栏与 provenance）。免费默认版就是用同一套扩展点实现的第一个应用，保证第三方能替换或叠加。

### 4.3 需要的契约与能力

- 新契约 #19「工作模型」：Goal / Todo / Meeting / MeetingRecord / DailyPlan / Review + API（`/v1/goals`、`/v1/todos`、`/v1/meetings`、`/v1/meetings/:id/records`、`/v1/calendar?from&to`、`/v1/plans/today`、`/v1/reviews`）
- 14：`ApprovalKind` 加 `daily_plan`、`review`；`subject` 加 `todo_id`、`meeting_id`；`claim` payload 加 `source: 'meeting' | 'review'`
- 22：模型网关加 `transcribe(audio, meta)`（ASR provider 槽；自带账号；音频不落日志）
- 18 / 21：原始材料区接会议媒体；会议记录默认 `restricted`
- 23：应用扩展点 `meeting.record_source` / `meeting.processor`
- 25：定时任务完成可产待办；日历取数

## 6. 自主决定（待 Luoye 审）

- C1 卡片不是待办：卡片挂在 Run + 主题（对话 / 变更 / 待办）上；"今天"里的卡是派生显示
- C2 待办一个对象，长期 / 短期靠 due / scheduled / 父子区分；承诺人永远是人，可委托 Agent，Agent 的问题回来成卡
- C3 日历既是视图也是排期面（拖到某天 = 排期）；显示会议、有排期的待办、定时任务、卡片到期叠层
- C4 会议进内核；记录六种来源；先进受控原始材料区再处理；外部参与者在场默认 restricted 且要有录音告知
- C5 会议功能三层：免费默认（自带）/ 付费增强 / 第三方应用，同一套扩展点
- C6 每日计划与复盘仍是两张卡，且计划只是建议，采纳才写待办
