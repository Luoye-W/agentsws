## 1. 卡片呈现：照 KefuAgent 的四段式，逐条对照 WP15

KefuAgent 的卡面（`support-inbox-deck.tsx`）是四段式、三条边界线，**一次只看一张**，动作行永远在视口里。WP15 做成了"多张平铺的列表卡"，且违反了三条红线。逐条对照：

| KefuAgent 做法 | WP15 现状 | 改法 |
|---|---|---|
| **一次一张**：780px 居中、min-height 320、内容区 `max-h 420` 卡内滚、动作行不出视口；背后两张歪斜的"景深"假卡；"第 N / M 张" | 平铺列表，一屏三张，各自带"详情 ▾" | 改为单卡 deck；键盘 ←/→/↑ 对应拒绝/批准/稍后；列表只在"记录"Tab |
| **标签行**顺序固定：渠道 → 优先级（P0 红，其余主色）→ 倒计时（琥珀，有 expires 才出）→ 卡型纯文本 → "合并 N 张" | 顺序是 档位 → 卡型 → 客户名 | 按 KefuAgent 顺序；客户名不进标签行 |
| **标题**单行 15px 半粗，服务端截 120 字 | 相近 | 保持 |
| **内容盒**：一次只显示一种语言（中文摘要 / 原文 / English 队列级切换，禁双语堆叠）；`bg-muted/40` 圆角盒 | 英文原文直接露在摘要位 | 加语言切换；默认中文摘要；原文在盒内切换 |
| **证据 chip 永不裸 id**：`labelKey` 走 i18n，形如「订单：已查单」「政策：退货 14 天」，最多 10 条；实体 chip 另起一行 | 露了 `fact_775c…`、`cus_anna`、`run_demo_42` | 服务端 enrichment：ObjectRef → 展示名（订单号 / 客户名 / 事实卡标题）；run id 只进"详情"；上限 10 |
| **动作行** ≤ 3 个快捷决定，approve 主按钮；右侧安静区"需要补素材""稍后 ↑"；**没有"更多"菜单**，多余选项折进"指导" | 有"…"溢出、有"详情 ▾" | 去掉"…"；"详情"改为点卡面展开；补素材 = `ai_question` 的反向入口 |
| **已处理不留队列**：飞出 300ms → 下一张；`done` 只在档案室和"今日战报" | 已决定的卡还留在列表变灰 | 同 KefuAgent |
| **空态 = 今日战报**四格（AI 自主处理 / 你已处理 / 自动发送 / 拦截待确认） | "暂无卡片" | 同 KefuAgent，数字来自事件日志 |
| 折叠区（指导 textarea、拒绝理由、补素材、问 AI）**点开前不在 DOM 里** | 部分常驻 | 同 KefuAgent |
| 手机 deck：右批准 / 左拒绝 / 上稍后 / 下指导；高风险先弹拦截 | 无 | 二阶段（Electron 内不需要；浏览器手机入口时做） |

**筛选**（KefuAgent 只有 全部 / 客户在等 / 无人等待 三枚 chip，无按卡型 / 岗位筛）。我们多岗位，所以加一行：**岗位 chip**（全部 / 各岗位）+ **等待 chip**（客户在等 / 无人等待）+ **卡型下拉**。筛选只改当前 deck 的集合，不跳页；计数按张数；P0 永不被筛掉（永远置顶出现一次提示）。排序沿 KefuAgent：`priority_band → expires_at → priority → created_at`。

## 2. 缺的那块：目标 → 任务 → 卡片 → 复盘，卡片只是第三层

Luoye 描述的循环是：**总目标 → 渠道 / 岗位目标（可再拆到职位）→ 每天：看数据 → 安排 / 调整任务 → 制定方案、执行 → 复盘**。对照我们现有对象：

| 循环里的东西 | 现有对象 | 状态 |
|---|---|---|
| 总目标 / 岗位目标 | 无 | **缺** |
| 看数据 | 首页核心数据条 + 岗位面板（36） | 有，但没有"目标"可比，只能比昨天 |
| 安排 / 调整任务 | `work_item_id` 散在 4 份契约里，没有对象；`claim` 卡型；`scheduled_task` | **缺一个正式的「任务」对象** |
| 制定方案、执行 | Run（17）、变更账本（15）、审批项（14）= 卡片 | 有 |
| 复盘 | `digest` 一张摘要卡；lesson → 次日提案（24） | 有雏形，没闭环 |

所以缺的不是"一个 todo 列表"，而是**两头**：上面缺目标，下面缺复盘把结论喂回明天的任务。中间的"任务"要成为正式对象，卡片挂在任务下面。

### 2.1 四个对象

```ts
/** 目标：公司 → 岗位（渠道）→ 人；指标就是 29 的命名查询，所以数据条能直接显示"值 / 目标 / 进度" */
type Goal = {
  id; workspace_id; level: 'company' | 'position' | 'person'
  parent_id?: GoalId                       // 岗位目标挂在公司目标下，人的目标挂在岗位目标下
  position_id?: PositionId; owner: PersonId
  metric: { query: string; format: 'money' | 'count' | 'percent' | 'ratio' }   // 复用 NamedQuery
  target: number; period: { kind: 'month' | 'quarter' | 'week'; start: Iso8601; end: Iso8601 }
  status: 'active' | 'achieved' | 'missed' | 'archived'
}

/** 任务：一天里要做的一件事；人做或 Agent 做；卡片挂在它下面 */
type Task = {
  id; workspace_id; position_id: PositionId; goal_id?: GoalId
  title: string; note?: string
  owner: { kind: 'person'; id: PersonId } | { kind: 'agent'; assignment_id: AssignmentId }
  source: 'plan' | 'review' | 'alert' | 'meeting' | 'card' | 'manual' | 'scheduled'
  due?: Iso8601; status: 'todo' | 'doing' | 'blocked' | 'done' | 'dropped'
  cards: ApprovalItemId[]                  // 执行过程中需要人拍板的都在这
  runs: RunId[]                            // Agent 做的话，跑了哪些运行
  outcome?: { note: string; metric_delta?: number }
}

/** 每日计划：早上一张卡。Agent 按"目标差距 + 昨日数据 + 昨日复盘"起草今天的任务清单，人采纳 / 调整 */
type DailyPlan = { id; date; position_id; tasks: Task[]; card: ApprovalItemId /* kind: 'daily_plan' */ }

/** 复盘：晚上（或次日早）一张卡。目标进度、异常、今天卡片的处理结果、Agent 学到的、明天建议 */
type Review = {
  id; date; position_id
  goals: { goal_id; value; target; progress }[]
  anomalies: { metric; delta; explanation? }[]
  cards_summary: { approved; rejected; auto; blocked }
  lessons: LessonId[]                      // 24 的 lesson，进次日提案
  next_plan_draft: Task[]                  // 直接变成明天的 DailyPlan 草案
  card: ApprovalItemId                     /* kind: 'review' */
}
```

两个新卡型：`daily_plan`（选择题形态：采纳 / 调整 / 稍后；"调整"打开可勾选、可改的任务清单）、`review`（阅读型：看完 → "按建议排明天" / "我来排"）。都进 14 的审批项体系，所以照样去重、投递、记事件。

### 2.2 每天长什么样（首页第三稿）

```
首页（今天）
① 目标进度条          本月总目标 / 各岗位目标：值 / 目标 / 进度 / 剩余天数   ← 从数据条升级而来，数字块加"目标"一行
② 今日任务            按岗位分组；人的任务打勾，Agent 的任务显示进度与挂着的卡数
③ 卡片（deck）        一次一张；岗位 / 等待 / 卡型筛选；卡面第一行多一条「属于：任务 X · 目标 Y」
④ 复盘 / 今日战报     晚上生成；白天是四格战报（KefuAgent 的空态）
```

- **卡片和任务的结合点只有一个字段**：卡属于哪个任务（`Task.cards` ↔ `ApprovalItem.subject.work_item_id`）。没有任务的卡（客户来信触发的）归到岗位的"日常"任务，日常任务的卡数就是"今天客服处理了多少"。
- **任务从哪来**：早上计划（Agent 起草）、复盘建议、数据告警（`alert` → 一键"建任务"）、会议纪要（§3）、卡片里"指导"时选"建个任务跟进"、手动。
- **周 / 月节奏**：周复盘（周五）与月目标复审（月末）是同一张 `review` 卡的更长周期版本；月目标复审可以提出"改目标"（`goal_change` 走 `policy_change` 形态）。

### 2.3 为什么这样做而不是做一个 todo 应用

非技术用户不缺 todo 工具，缺的是"今天该干什么"这个判断。把任务做成 Agent 起草、人拍板的选择题，和卡片同一套动作矩阵，用户学一次就够。复盘不是给老板看的报表，它的产物是明天的计划草案——这才闭环。

## 3. 日历与会议

- **日历 = 视图，不是新对象**。把 `Task.due`、25 的 `scheduled_task`、外部日历事件（只读）画到同一条周视图上；放在首页 ② 的右侧切换（列表 / 周），岗位页"记录"Tab 里有月视图。外部日历经 Connect 只读接入（Google Calendar / Outlook / 飞书），v1 先支持导入 ICS 订阅链接，OAuth 接入随 Connect 的 Google 配套服务立项。
- **会议 = 应用，不是内核**。不做会议软件（不做音视频、不做转写引擎）。做的是"会议 → 任务与决定"这一跳：会议纪要（粘贴 / 上传 / 飞书妙记与腾讯会议的导出）→ 秘书 Agent 抽出 `任务`、`决定`、`边界答案` → 以 `claim` 卡（06 §2 的认领管道）发给对应的人；本人确认前不形成责任、不进考核（31 I13）。31 把秘书放在第二阶段，这里只定接口：`meeting.notes_imported` 事件 + `claim` 卡 payload 加 `source: 'meeting'`。
- 会议本身的排期、邀请，v1 交给用户已有的日历工具；我们只读它。
