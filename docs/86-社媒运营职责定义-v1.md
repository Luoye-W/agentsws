## 0. 一句话

社媒运营从九条变成**十二条可选、一条老的**：内容账号组拆成 **Facebook 主页 / Instagram / Threads / TikTok / YouTube / X / LinkedIn** 七条，`social.meta` 留作老 id、启动时迁成 FB + IG 两条。每条的「这条渠道特有的部分」按 §3 的调研重写；额度按平台节奏改；LinkedIn 发帖走官方接口、**批不下来就变成「复制文案去 LinkedIn 发」的待办**，永不抓取、永不自动加人私信。开源技能里有三份值得引，**先写评估（§8）交 Fable 定，这一单不引进**。

跨平台的六条规律（上表各行的共同点，写进 persona 与技能时优先用这几条）：

1. **稳定胜过数量**：一周断更就掉到自己的基线以下；一周五条以后收益基本变平。所以额度是"别刷屏"的线，日历上的目标是"做得到的节奏"。
2. **视频拿触达，轮播 / 文档拿互动**（IG、LinkedIn、TikTok 都这样）。
3. **原创被各平台硬执行**：IG（2026-04）、FB（2025-07、2026-03）、YouTube（2025-07）、TikTok 都对搬运、水印、模板量产降推荐或取消变现。**一条内容不能原样搬到另一个平台**——这就是这次把 Meta 拆开的最实际的理由。
4. **对话信号比点赞重**：X 作者回复 75 倍、Threads 回复 +42%、LinkedIn +30%、IG 私信转发。**回评论不是客服的附属品，是内容本身**（仍然：客户的问题转客服）。
5. **满意度与注意力是核心**：观看时长、停留、看完率、问卷、负反馈。
6. **最佳时间只是起点**（Hootsuite 2025 那组时间不带时区），之后看自己的数。

## 3. 按平台整理的职责定义（职责 yml 直接照这一节写）

共同骨架不变（56 §2 内容组）：`stage_post`（发布 / 排期，**永远 L1**）、`reply_comment`（回评论，L2 → L3，过承诺扫描）、`stage_profile_edit`（改资料，L1，handle 受保护）；动作 id 与数据域一个都不改（54：九条同构，所以意图词是唯一分得开它们的东西）。六段 persona 的「你不负责」四句对每条都一样（订单退款物流 → 客服、找红人 → 红人营销、买广告 → 投放、别人的版 → 公共关系），下表只写**各平台自己多出来的那一句**。

### 3.2 各平台特有的坑（写进 yml 头注释与 persona「怎么做」）

**YouTube**
1. 连接卡与红人 `kol.youtube` 共用（不变）。
2. **没过审计的 API 项目上传的视频只能私享**；配额现在是上传每天 100 次单独计、其余共用 10,000 单位，回一条评论 50 单位。
3. 上传不走这条路（resumable upload 在后台做，不变）；Shorts ≤ 3 分钟且竖屏，否则算长视频。
4. 警告 90 天内三次封频道，**删视频不消警告**；AI 模板片、幻灯片合集算「不真实内容」，不能变现。
5. 先定标题与缩略图再剪（开源技能与官方都强调点击率 × 满意度）；**不编数**——点击率、留存拿不到就说拿不到。

**TikTok**
1. Content Posting API 申请制（不变）；**没过审计时发出去的只有自己看得见**、账号还得设成私密——所以"发出去了"不等于"大家看得到"，卡面上要写清。
2. 两种发法：直发（`video.publish`）与进草稿箱（`video.upload`，人在 App 里点发布）。现在的适配器走直发；**没过审计时该走草稿箱**——这一单只在 persona 与连接卡里说清，适配器改发法列进 §9 的后续。
3. 发之前必须查 `creator_info`；**可见范围要人亲手选**、商业内容声明开关默认关——这两格在卡面上，不替人选。
4. 没有开放的评论读写接口（不变）。
5. 搬运、别家水印、极短纯图不进推荐。

**X**
1. 官方已改**按次计费**（发一条 0.015 美元、带链接 0.20 美元）——「付费档」那句人话改成「按条计费」。
2. 回复与发推是同一个接口、同一份额度（不变）；280 字硬上限（Premium 长帖不能排期，所以我们只按 280 排）。
3. **自动化规则是这条渠道最大的坑**：不许按关键词搜到就自动回陌生人、不许发重复或近似的推、不许自动蹭热搜。所以 `reply_comment` 只回**我们帖子下面**与**直接 @ 我们**的，不去搜；同一段话不在一周内发两次。
4. 作者回复的权重是点赞的 150 倍：发完一小时内守着回。

**Facebook 主页**
1. 与 IG **共用 `meta_graph` 一张卡**（连一次、批一次）。
2. 排期两格一起写（`published=false` + `scheduled_publish_time`），时间必须在 10 分钟到 30 天之间——超出这个窗口的由我们自己的调度器到点再发。
3. API 发 Reels 每主页 24 小时 30 条；快拍素材不能是发过的。
4. Messenger 里的对话 24 小时窗口、窗口外不能推销——**私信不归这条**，客户问题转客服。
5. Facebook **群组**是另一条职责（`social.facebook-group`，浏览器模式）：意图词要分得开（主页 vs 群组）。

**Instagram**
1. 与 FB 共用 `meta_graph`（走「Facebook 登录」那条路，IG 账号要关联主页）；只用「Instagram 登录」的用户是另一次授权——这一版**不支持**，连接卡上写清"IG 要关联 FB 主页"。
2. 发布是两跳（建容器 → `media_publish`），**API 没有排期**：排期由我们自己的调度器到点发。
3. 配文 2,200 字、30 个话题标签、20 个 @；轮播最多 10 张、只收 JPEG；Reels 要进推荐得 ≤ 3 分钟；API 发帖 24 小时 100 条。
4. 不原创（加边框、水印、只注明来源）不给非粉丝推荐——**不许把 FB 那条原样搬过来**。
5. 私信与私下回复不归这条（客户问题转客服）。

**Threads**
1. **自己一张卡 `threads_api`**：Threads 的授权与 FB / IG 分开（单独的用例、应用 id、令牌 60 天要续），Meta 那把主页令牌用不上。这不违反「同一件事不连两次」——它本来就是另一次授权。
2. 正文 500 字、最多 5 个链接、一个话题标签；两跳发布；24 小时 250 帖 / 1,000 回复 / 100 次删除。
3. **回复与发帖一样重**：回评论额度给到 100 / 天（接口上限 1,000），仍然 L2 起步。
4. 发原创，不从 IG / FB 搬。

## 5. Meta 拆成三条：Facebook 主页 / Instagram / Threads

| 条 | 连接 | 为什么这么分 |
|---|---|---|
| `social.facebook` | `meta_graph`（原卡，不动） | 同一次 Facebook 登录授权里同时要主页与 IG 的权限（§1.3），**连一次、批一次**；拆职责不拆卡 |
| `social.instagram` | `meta_graph`（同一张） | 同上；连接卡上原来就有 `ig_user_id` 那一格 |
| `social.threads` | **新卡 `threads_api`** | Threads 的授权本来就是另一套（单独用例、单独令牌），Meta 主页令牌调不动 graph.threads.net——一张卡装不下两套令牌 |

拆开的理由不是"平台多了"，是 §2 规律 3：**三个平台都在惩罚搬运**，一条内容在 FB / IG / Threads 上要写三遍；受众、节奏、形式、看的数都不一样（§3.1）。老的「一条管两个号」让 Agent 天然倾向于一条搬两处。

红人（`kol/*`）与投放（`ads/meta.yml`）**不拆**，只核意图词：

| 一句话 | 该落到 | 靠什么分 |
|---|---|---|
| 「IG 帖子下面的评论回一下」「排一条 IG 轮播」 | `social.instagram` | 社媒岗位里：Instagram / IG / Reels 只在 IG 这条的意图词里（FB 那条不写 IG） |
| 「找 20 个 IG 红人」「给 IG 博主发开发信」 | `kol.instagram` | 跨岗位：红人那条的 cue 是「红人 / 博主 / 达人 / 合作 / 开发信 / 寄样」；社媒这边的 persona「你不负责：找红人」 |
| 「IG 广告预算加一点」 | `ads.meta` | 投放那条的 cue 是「广告 / 预算 / 出价 / ROAS」 |
| 「FB 群组里有人发垃圾链接要删帖」 | `social.facebook-group`（排第一；与 Telegram 群组分数接近时出选择卡，这是 WP191 之前就有的样子） | 群组那条的意图词是「群组 / 小组 / group」，FB 主页那条不写这几个词 |

## 6. `social.meta` 的平滑迁移（设计）

**原则**：`social.meta` 不删（老工作区的分配、审批、帖子、事件上写着它），但新建岗位不再出现；已有分配在**进程启动时**迁成 `social.facebook` + `social.instagram` 两条；**可重复跑、不丢数据**。

| 迁什么 | 怎么迁 | 为什么 |
|---|---|---|
| 分配（assignment） | **原分配就地改成 `social.facebook`**（id 不变），再**复制一条** `social.instagram`（范围、额度覆盖、自动化状态照抄；id 按原 id 派生，所以重跑时认得出"已经复制过"） | 待办、审批卡、队列车道、定时任务、交接记录都挂在**分配 id** 上——原 id 留给 FB，这些东西一件都不用搬；复制的 IG 从同一份采纳率起步，不清零 |
| 先后 | **先建 IG、后改 FB**：中途断电重跑时，原分配还是 `social.meta` → 看到 IG 那条已经有了就跳过 → 再改名 | 反过来的话，改完名就认不出它原来是 Meta，IG 那条永远补不上 |
| 已撤销的分配 | 不动 | 历史就是历史（同 WP54 的迁移） |
| 社媒库里的账号 | `channel: 'meta'` 的账号按 URL 判：`instagram.com` → `instagram`，其余 → `facebook`；帖子与线程跟着账号走 | 老数据里一个账号只会是 FB 主页或 IG 号之一，URL 就是答案 |
| 事件 | 每迁一条记一条 `assignment.role_migrated`（原分配那条 `from: social.meta, to: social.facebook`；复制那条 `to: social.instagram`、多一格 `split_from` 指原分配 id） | 15 §1：变更必须留痕 |
| 新建岗位 | 岗位模板与 `SEED_POSITIONS` 里不再有 `social.meta`；契约上它标 `superseded_by: [facebook, instagram]`，向导只读 `ACTIVE_SOCIAL_CHANNELS` | Luoye 09-29「新建岗位的选项里不再单独出现 Meta 社媒运营」 |
| 模拟包 | pack 的 `assignments.yml` **不改**（它们就是"老工作区"），模拟世界装配完照样跑同一段迁移；场景里 `channel: meta` 改成 `facebook` / `instagram` | 这样模拟里跑的就是真迁移那一段代码 |

迁移表写在 `packages/roles/src/load.ts` 的 `ROLE_ID_SPLITS`（与 `ROLE_ID_ALIASES` 同一条纪律：只可加行），并由测试钉住它与契约的 `superseded_by` 一字不差。
