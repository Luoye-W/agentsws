## 1. 流程（#17）与定时任务

### 1.1 白话：为什么"定时触发一次运行"不够

现在的调度契约只能做一件事：到点起一次运行。但公司里很多事是**一串**：

> 红人合作：寄样 → 等物流签收（可能 5 天）→ 提醒红人 → 等内容发布（可能 2 周）→ 检查内容 → 结算 → 45 天后回访

这一串里有等待、有分支、有人审、有失败要补救（样品丢了要重寄）。用"定时 + 单次运行"拼，状态就散落在各处：谁记得这单走到第几步了？重启了怎么办？某一步失败了前面的要不要撤？

**流程引擎**就是专门管"一串"的东西：把这串写成一个流程定义，引擎负责记住每一单走到哪一步、等多久、失败重试几次、重启后从断点继续。它和我们现有件的关系：

| 件 | 管什么 |
|---|---|
| 调度 #13 | "什么时候"——到点发一个事件 |
| 运行协议 #6 | "做一次"——一次 Agent 运行 |
| 审批总线 #3 | "人点头"——一个步骤等人 |
| **流程 #17** | "一串怎么串起来"——步骤顺序、等待、分支、重试、补偿、断点续跑 |

### 1.2 为什么评估 Inngest

Inngest 是"事件驱动的持久函数"：一个流程写成一个函数，里面每一步 `step.run()` 结果会被记住，`step.sleep('5d')` 可以等五天而不占进程，重启后从记住的那一步继续；失败按步骤重试；可以自托管；**KOLAgents 已经在用它**（`INNGEST_EVENT_KEY` 就是它）。相比之下 Temporal 更强但要独立集群，对 3 人公司的本地实例太重。

流程契约不绑 Inngest：契约定义"流程定义、实例、步骤、等待、补偿"的形状，Inngest 是默认实现，模拟替身是"内存流程引擎 + 合成时钟"。

### 1.3 定时任务：用户看得见、管得了、与会话绑定

定时任务是流程契约里最简单的一种流程（一个步骤 + 一个时间条件），单独成一等对象：

```ts
type ScheduledTask = {
  id: string
  workspace_id: string
  owner: person_id                    // 谁的
  role_id: string                     // 属于哪个职责（决定权限与队列车道）
  origin: {                           // 与会话绑定：从哪里来
    conversation_id: string           // 创建它的那次对话 / 工作项
    run_id?: string                   // 创建它的那次运行
    message_ref?: string              // 用户说的那句话 / Agent 的那条提议
  }
  trigger: { kind: 'once', at } | { kind: 'cron', expr, tz } | { kind: 'after_event', event }
  action: RunRequestTemplate          // 到点做什么：以谁的身份、哪个职责、带什么上下文、允许什么工具
  context_policy: 'resume_conversation' | 'fresh_with_summary'
                                      // 到点时回到原对话继续，还是新开一次运行并带上原对话摘要
  state: 'active' | 'paused' | 'done' | 'failed'
  created_by: 'user' | 'agent'
  approval?: approval_item_id         // Agent 创建的定时任务是否经过确认
  next_fire_at, last_fire_at, fire_count, last_result
}
```

**设计要点**

| 要点 | 做法 |
|---|---|
| AI 能设，人能管 | Agent 有 `schedule_task` 工具；创建**低风险**定时（只读、提醒、起草）L2 直接建并在对话里显示一张"已设定时"卡；创建会发出 / 会写的定时 L1 进队列。人在两处都能看到：对话内的"本对话的定时"（与会话绑定的体现），以及职责工作面的"定时"面板（列表、暂停、改时间、删除、看历史） |
| 与会话绑定 | `origin` 指回创建它的对话；到点时按 `context_policy` 要么在原对话里续一轮（用 `agent.followup()` / 新 RunRequest 带原对话 id），要么新开运行并注入原对话摘要。对话被归档时提示"这个对话有 2 个定时任务，一并停掉？" |
| 与职责绑定 | 定时任务继承创建时的职责与权限；职责撤销 → 其定时任务随交接清单转移或暂停（05 schema 的 handover 加 `scheduled_tasks`） |
| 时区 | 每条定时带 tz，默认取工作区时区（09 §5 第 5 条） |
| 可见性规则 | 我的定时我看；范围管理者看范围内的；owner 看全部；Agent 创建的都标"由 Agent 设定，来自 ×× 对话" |
| 模拟 | 合成时钟驱动；场景里可以断言"周一 9 点应触发、触发后队列里有草稿" |

dsh 自带的 `schedule` 包（最小 5 分钟、冷会话不投递）不用；定时对象在协同服务，到点由调度 #13 发事件，流程 #17 或运行协议 #6 消费。

## 2. 检索引擎推荐（知识 #10）

要求：本地免费档零外部进程、SQLite 一致；中文分词要对；向量 + 关键词混合；权限过滤下推；托管档可换更强的。

| 方案 | 形态 | 中文 | 适合 |
|---|---|---|---|
| **sqlite-vec + FTS5 + `simple` 分词扩展** | 全在 SQLite 里，零进程 | FTS5 原生不切中文，装 `simple`（含 jieba）扩展后可以 | **本地免费档默认**。与共享数据层同一个库，权限过滤就是一个 JOIN；dsh 自己也用 FTS5 |
| LanceDB | 嵌入式文件库，TS SDK，向量 + 全文 + 混合 + 重排 | 全文分词器需核实中文支持 | 本地档的备选；数据量大、要重排时 |
| Orama | 纯 JS 嵌入式，向量 + 全文混合 | 有 CJK 分词 | 浏览器端 / 极轻场景 |
| **Meilisearch** | 独立服务，混合搜索，CJK 原生好 | 好 | **托管档默认**；给工作台的即时搜索（⌘K）也顺手 |
| pgvector + ParadeDB（pg_search BM25） | Postgres 内 | 需配分词 | BYOC / Postgres 档，不想多一个服务时 |
| Qdrant / Typesense | 独立服务 | 一般 / 好 | 备选 |

不推荐：Elasticsearch / Vespa（太重）；自建。

**配套**：embedding 走模型网关（DeepSeek 无 embedding，用 BGE-M3——本地 ONNX 版可完全离线，或经网关调云端）；重排用 bge-reranker 本地或经网关；分块按文档结构（anydoc 的 Markdown 标题层级正好可用）。**权限过滤下推**是硬要求：先按身份过滤候选集再算相似度，不能先取 top-k 再过滤（会漏）。

**定案建议**：本地档 sqlite-vec + FTS5 + simple；托管档 Meilisearch；引擎藏在 #10 契约后，一致性套件里放"越权检索用例集"。

## 3. 文档解析：采用 firecrawl/anydoc

| 事实 | 对我们的含义 |
|---|---|
| Rust 库，Node / Python / WASM 绑定，MIT | Node 绑定进协同服务；WASM 版可在浏览器端本地转换（用户拖进来的文件不用先上传） |
| Word / PowerPoint / Excel / OpenDocument / RTF / EPUB / CSV / 文本型 PDF → GFM Markdown，毫秒级，一致的输出模型 | 事实卡管线的第一步；标题层级直接用于分块 |
| 文档模型带嵌入资产（图片字节 + 媒体类型） | 图片进素材库（内容寻址），Markdown 里留引用 |
| 扫描件不做 OCR，`--ocr hosted` 走 Firecrawl Parse（整份文件离开本机） | **做成工作区策略开关**，默认关；开了也只对 `NeedsOcr` 的文件走；后续加本地 OCR provider（PaddleOCR 类）作替代 |
| 自带 Agent Skill | 我们的 DevKit 技能包可以直接依赖它 |
| 出处粒度 | 事实卡要"文件 + 页码 / 章节"；PDF 页码是否保留在文档模型里**要核实**；至少有标题路径可作出处 |

落位：知识 #10 的"解析器 provider"默认实现 = anydoc；HTML 邮件与网页仍走我们入站层的清洗 + fencing。

## 4. 策略引擎与脱敏、凭据不经模型

### 4.1 策略引擎：Casbin（定案）

职责定义（05 schema 的 scopes）编译成 Casbin 策略；数据层每次查询先过它；一致性套件里放越权用例集（"售后客服不能读成本价""撤销职责后 1 秒内不可读"）。

### 4.2 输出侧脱敏（定案）

投递前统一过一遍：字段分级（05）决定"接收方能看哪级"，Presidio 类 provider 识别自由文本里的 PII / 卡号 / 联系方式；命中即替换并记事件。Agent 可持更高权限代办，但输出按接收方清权，防"请告知成本价以便审批"式套取。

### 4.3 密码类敏感信息不经模型

原则：**凭据永远不进对话、不进模型、不进日志。** 三道措施：

| 措施 | 做法 |
|---|---|
| Agent 只能"请求"凭据，不能"接收" | Agent 有 `credentials.request({ name, kind, fields })` 工具，返回的只是"已配置 / 未配置"；值由用户在安全表单里填。这沿用 dsh `ctx.credentials` 只存名不存值的模式 |
| 自动拉起安全表单 | 请求一发出，工作台 / 浏览器里弹出一个**不经模型的原生表单**（OAuth 的直接跳授权页；API key / 密码类给一个字段表单；扫码类给二维码）。表单直接写进 OpenConnector 凭据库（加密），Agent 收到的是连接名。飞书 / 企微场景下推一条卡片，点开也是这个表单 |
| 对话输入拦截 | 输入框和入站层做秘密检测（API key 形态、卡号、"密码是……"等模式）：命中就**不送模型**，改弹安全表单并把原文从事件日志里抹掉（Model-visible ⟺ logged 反过来保证：没进模型就不该留在日志）；已发出的消息里检测到则脱敏后再入日志 |

用户体验："帮我接上 Klaviyo" → Agent："需要 Klaviyo 的 API key，我打开了填写窗口" → 用户在窗口里粘贴 → 窗口关闭 → Agent："已连接，账户是 ××"。全程 Agent 没见过 key。

## 5. 桌面壳改为"浏览器打开 + 极小启动器"

你的判断对：UI 走浏览器，兼容性和可串联性都更好——KOLAgents 的浏览器插件和工作台在同一个浏览器里，插件能直接调本地 / 托管工作区的 API、共用登录态；托管档和本地档是同一套 UI。dsh 自己就是这么做的（本地 Node 服务 + 浏览器打开 + 32 字节 token 换 HttpOnly cookie 的浏览器会话鉴权）。

但浏览器不能替用户启动和维护三个常驻进程（协同服务、dsh、OpenConnector）。所以还需要一个**极小的启动器**，只做五件事，没有任何界面逻辑：

| 启动器做什么 | 说明 |
|---|---|
| 一键安装 | 安装包（macOS pkg / Windows msi）装好三个 sidecar 与启动器；注册为开机自启的用户级服务 |
| 进程监督 | 起、停、崩溃重启、健康检查、端口分配、日志 |
| 托盘图标 | 打开工作台（就是打开浏览器到 `http://localhost:<port>`）、暂停、更新、退出 |
| 自动更新 | 按顺序更新三个 sidecar，更新前跑一次冒烟；失败回滚 |
| 浏览器会话 | 首次打开带一次性 token，换 HttpOnly cookie（照 dsh 的做法）；不监听 0.0.0.0 |

**启动器用 Electron 实现（09-08 定，取代 Tauri）**：托盘常驻；"打开工作台"默认开一个 Electron 窗口加载本地 URL，也可在系统浏览器打开（见下）。选 Electron 的理由不在界面，在运行时：三个 sidecar 全是 Node 程序，Electron 自带 Node，一个安装包把运行时带齐；electron-updater、托盘、开机自启现成；生态里的 dsh-desktop 也是 Electron。代价是体积与空闲内存（一两百 MB），对常驻服务可接受。注意 Electron 内置 Node 版本须满足 OpenConnector 的 Node 22 要求，不够则 sidecar 用独立打包的 Node。三档部署的形态：

| 档 | 形态 |
|---|---|
| 个人电脑 | Electron 常驻托盘；三个 sidecar 随它启动；默认应用内窗口打开工作台，可选浏览器打开 |
| 公司常开机器 / NAS | 无启动器；Docker Compose 跑同样三个服务；成员浏览器访问 |
| 我们托管 | 同一套 UI 从云端提供 |

**应用内打开还是浏览器打开（09-08 定）：默认应用内，保留浏览器入口。** Electron 窗口加载的就是同一个本地 URL，UI 只有一份。选应用内为默认的理由：非技术用户"打开 agentsws"最省解释；Dock / Cmd+Tab / 原生通知 / 深链 / 拖文件现成；避开浏览器扩展与拦截插件的干扰；本地端口不暴露给用户浏览器里的任意站点。浏览器入口必须一直可用，因为托管档、公司 Docker 档、手机远程访问都走它。

**纪律**：UI 必须在普通浏览器里完整可用，Electron 只是外壳；业务界面不调用任何 Electron 专有 API，原生增强（通知、托盘、拖拽、深链）经一个很小的桥接层，做特性检测，浏览器里自动退化。三档部署一套 UI。

**浏览器插件的串联**不依赖工作台在浏览器里：插件与平台靠 API + 配对 token（应用里点"配对插件"），不靠共用页面 cookie。

**浏览器插件的串联**：插件通过配对 API key 调工作区 API（20 §3；不共用页面 cookie），或在托管档调云端工作区；插件在红人主页采到的数据直接进共享数据层的红人表，走的是同一套权限。插件本身作为市场里的"连接"类应用登记（11 §2.1）。

**代价**：浏览器通知不如原生（用 IM 投递补）；标签页关了服务仍在跑（无状态运行本来就不依赖页面）；手机访问本地档要组网（启动器内置向导）。
