worktree `../agentsws-wt/wp219-content-updates` · 分支 `wp/219-content-updates`（从 main 新起）。先读 `_common.md`、`docs/42`（上游评估与升级）、`docs/24`（技能三层：基础层 / 公司层 / 职责层，用户与学习回路的改动在上层）、`upstreams.yml` + `scripts/check-upstreams.mjs` + `.github/workflows/upstream-watch.yml`（每周上游例程）、`packages/skills`（bundled、THIRD-PARTY-NOTICES、WP209 frontmatter）、`packages/roles`（职责 yml）、WP216（Shopify 官方技能，按建站平台启用；分支 `wp/216-shopify-skills` 可能尚未合并）、WP218（electron-updater、更新源 dl.agentsws.com 主 / GitHub Releases 镜像；分支 `wp/218-desktop` 可能尚未合并）、卡片流（`packages/txn`、ApprovalKind 只加）、docs/36（少字、状态图标）。

## 背景（Luoye 10-05 同意的思路）
问题：用了 Shopify 官方技能这类第三方组件，上游更新了用户怎么更新？以后还会有很多第三方技能和组件。定的原则：**进到用户电脑里的第三方内容，要么我们审过，要么用户自己点头。** 按「谁装的」分两类：
- **第一类：我们随软件带的**（bundled 第三方技能、职责里引用的第三方内容…）：我们这边每周上游例程发现 → Fable 照 docs/42 审（许可证没变、新内容没有可疑指令、我们的旁注仍对得上、测试与模拟全过）→ 发到**内容更新通道**（不等软件发版）→ 用户端出卡「X 有新版（官方某日更新，已审）」，可设「已审的自动更新」或每次自己点，随时一键退回。**改到程序本身的才跟软件版本走（左下角更新按钮）。**
- **第二类：用户自己装的**（以后从技能市场 / 网址装的）：用户端自己探测上游、出卡写清改了什么与风险提示，用户点头才更新，可锁版本、可退回。**本单只写进规范，不实现**（等技能市场）。
- **两类共同**：用户 / 学习回路对技能的修改（上层）不被官方更新冲掉——新版基础层与用户改动合并，真冲突出卡让人选。

## 要做
1. **规范** `docs/90-第三方内容更新-v1.md`：把上面写成规范——两类的定义、发现 / 审核 / 分发 / 应用 / 退回全流程、内容包格式、签名与校验、卡片样式与设置项、与软件版本更新的分界线（什么算内容、什么必须随程序）、与 WP216「按建站平台启用」的关系（内容更新只落到启用了它的品牌）、第二类的预留接口。
2. **内容包与签名**：
   - 内容包 = 若干条目（技能目录 / 职责 yml / 其它声明式内容）+ 清单 `content-manifest.json`（条目 id、版本、来源上游与提交、sha256、审核记录摘要、最低软件版本）；
   - 清单用 **ed25519** 签名；**公钥**内置在应用里；**私钥只在发版流水线里**（GitHub Actions secret 名 `CONTENT_SIGNING_KEY`，只写名字，值由 Luoye 填；本单测试用临时生成的测试密钥对，不入库）；
   - 客户端只接受签名对得上、最低软件版本满足的包；任一条目哈希不对整包拒收。
3. **分发**：内容包放在下载站（`dl.agentsws.com/content/<channel>/`，与 WP218 同一个 R2 桶 `agentsws-downloads`），GitHub Releases 同步一份；**本单不上传、不发布**，只做好打包脚本与 `release.yml` 里的一步（推 tag 或手动触发时打包、签名、上传）——工作流不触发。
4. **客户端**：
   - 本机服务每隔几小时（及启动时）查清单；有新的已审内容 → 出一张卡（新 ApprovalKind 只加，如 `content_update`）：写「X 有新版 · 官方某日更新 · 已审」、一句改了什么、「更新 / 稍后 / 查看改动」；设置 → 通用加「已审的内容更新：自动 / 每次问我」（默认「每次问我」）；
   - 应用：原子替换基础层、保留旧版一份、可一键退回；与用户 / 学习回路改动做三方合并，冲突出卡选「用新版 / 保留我的 / 看对比」；
   - 只落到启用了该内容的品牌（如 Shopify 技能只落到建站平台是 Shopify 的品牌）；多品牌按 WP215 各自处理；
   - 状态用图标（docs/36 第四档）；失败给人话。
5. **我们这边的流程**：上游例程发现新版后，生成「待审升级」提案（diff + 许可证对比 + 可疑指令扫描结果），审过合进主干后由发版流水线打内容包——把这条写进 docs/42 升级流程并给脚本。可疑指令扫描：对技能文本做规则检查（外发数据、绕过审批、要凭据、隐藏身份推广等），命中就标红、不自动通过。
6. 测试：签名对 / 不对、哈希不对、最低版本不够、自动 / 每次问我、合并无冲突 / 有冲突、退回、只落启用品牌、可疑指令扫描命中；全用本地替身更新源。
