# WP234 报告：岗位弹性化——负责人不当岗位、第 ③ 步「说说你要做什么」、AI 建议合并 / 拆分、自定义岗位

分支 `wp/234-positions`（worktree `agentsws-wt/wp234-positions`），Claude 子代理。

## 0. 一句话

岗位从「模板直出」变成「按人拼的职责组合」。关键是数据层多了一张**安放表**（一条分配归哪个岗位），
一条职责同时出现在模板岗位和自建岗位里时，界面、岗位层上下文与记忆都分得清它算哪个岗位；
安放不带任何权限，老分配没有安放行就照老规则算，老工作区一个岗位都不变（只是「负责人」从左栏消失）。
第 ③ 步改成「说说你要做什么 → 推荐（一条不预勾）→ 你的岗位（可拖动 / 移到 / 改名 / 新建 / 删空）」，
交给服务端的是岗位清单；公司页岗位卡能合并 / 拆出 / 移动职责，事项与岗位层记忆跟着走。

## 1. 数据层怎么设计的（docs/54 §6）

| 东西 | 怎么存 | 规则 |
|---|---|---|
| 类别（岗位模板） | 出厂的 `SEED_POSITIONS`（`org.catalog()`），不随公司改 | 只当第 ③ 步的目录；不含「负责人」与 `common.*` |
| 岗位 | 原来的 `org_positions` 行（`bundled` / `custom`） | 一个岗位可装来自不同模板的职责 |
| **安放**（新） | `org.sqlite` 的 `org_placements(assignment_id → position_id)` | 有安放 → 只属于那一个岗位；没有 → 老规则（职责清单里有它的岗位都算）。不带权限；撤销分配即失效 |

由安放推出：「我的岗位」、持有人、起 Run 时的岗位层（`positionOf(role, assignment?)`：分配已安放就是它；
否则老规则，再加「这条职责所有分配都安放在同一个岗位」）。`common.member` / `common.owner` 不算任何岗位的活；
「负责人」那一行（`owner`）是身份，不进「我的岗位」。

**合并 / 移动 / 拆出时上下文与记忆怎么走**：

| | 职责清单 | 安放 | 事项 `position_template_id` | 岗位层记忆 | 职责层记忆、卡 |
|---|---|---|---|---|---|
| 合并 A → B | B ∪= A | A 的全改到 B | A → B | 并进 B：没有的搬、一样的留一份、**不一样的两版都留**（A 那版标「（原「A」）」） | 不动（按职责 / 分配挂，本来就跟着走） |
| 移动 R：A → B | B += R，A −= R | A 下 R 的改到 B | A 下走 R 的改到 B | 留在 A | 不动 |
| 拆出（A 的几条 → 新 N） | 建 N + 逐条移动 | 同移动 | 同移动 | 留在 A，N 从空开始 | 不动 |

事项只改 `position_template_id`，`position_id`（用哪条分配在做）不动——分配没变，权限也就没变。
合并后的 A：自建的删掉，随软件带的留着当目录（没人安放在它上面就不出现）。审计 `position.merged` /
`position.duty_moved` / `position.split` / `owner.transferred`，payload 只有 id 与条数。

## 3. 自主做的决定（白话）

1. **安放单独一张表，不往分配上加字段**。分配是权限的载体，安放只管「算哪个岗位」，放一起容易被误读成权限；
   单独一张表撤销分配时自然失效，契约 `Assignment` 一个字没动。
2. **类别目录用出厂模板**，不读公司改过的岗位行——不然公司合并 / 改名之后，向导里的目录也跟着变形。
3. **复用模板的条件**：一行带 `template_id` 且职责全在那个模板里就复用它（名字不同走 WP196 改名）；否则建自建岗位。
   这样客服、网站运营这些常见岗位仍然带着图标、角色定位、平台 CLI 入口。
4. **已经持有、还没安放的老分配**：用户在第 ③ 步（或「分给同事」按岗位分）明说了它归哪个岗位，就按他说的安放；
   已经安放过的不挪（挪走那条路是「移动职责」，事项会一起带过去）。不这样做，老用户重走向导会在左栏看到两份。
5. **拆出时岗位层记忆留在原岗位**、新岗位从空开始（不复制，避免两份以后各改各的）。
6. **合并时打架的记忆两版都留**，不替人二选一（24 §1）。
7. **转交不收回自己那条**：本机装配时的负责人是审批默认收件人与 `brandAnchor`（第一个品牌固定是它）的那一个，
   收回会让系统卡没处去。所以转交 = 多一位负责人；要卸下去成员页撤，**最后一位负责人撤不掉**（新加的防呆）。
8. **「负责人」那一行无论下面挂什么都不进左栏**（演示包里它下面挂着「经营数据」）。真仓库里那一行只有
   `common.owner`（`dtc.analytics` 没装），所以真用户不受影响。
9. **AI 推荐失败照派工单退回只手选**，不拿关键词匹配兜底冒充 AI；演示 / 模拟世界用按词对的替身，界面明说。
10. **同渠道并岗的条件收紧**：只有各类别都只选了这一个渠道才并（INMO 只做 Reddit → 「Reddit 运营」）；
    选了 YouTube + Instagram 的红人营销不会被拆成按渠道的碎岗位。
11. **公司页的「移动职责」用两个下拉**（哪条 → 去哪），没做拖动；拖动只在第 ③ 步（那里同时有「移到…」下拉，键盘可用）。
12. 第 ③ 步顶上原来的「这次主要想让它干什么（红人 / 客服 / B2B）」整个去掉——输入框问得更准，两样并存是同一件事问两遍。

## 6. 偏离

- 公司页「删空岗位」沿用原来的「删掉」按钮（删前照旧要求没人在做）；移动 / 拆出后变空的岗位**不自动删**（它可能还有岗位层记忆）。
- 公司页岗位清单里不再列「负责人」那一行（它在页顶身份卡里）；WP196 的改名入口因此不在岗位清单里了——身份卡标题用的仍是那一行的名字。
- 合并进随软件带的岗位时，它的来源会变成「自建」（05 §2「改了职责 = 改模板」那条老规则）。

## 7. 未完成

- 成员页、人员页、同事 profile 的岗位徽章仍按「第一个含这条职责的岗位」归堆（WP70 `groupDutiesByPosition`），没按安放——
  只是展示，权限不受影响；要按安放得在 `AssignmentView` 上带岗位 id，建议下一单。
- 真模型推荐只用替身测过（解析、校验、引用对不上就去掉、划分不合格换算法），没对真模型跑过。
