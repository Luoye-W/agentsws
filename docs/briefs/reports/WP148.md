# WP148 报告：服务端带浏览器的运行改走 dsh 运行时 + 安装包第三方许可证说明

分支 `wp/148-browser-dsh`（worktree `../agentsws-wt/wp148-browser-dsh`）。Claude 子代理实现，待 Fable 审。

**一句话**：服务端的运行只要带浏览器（职责填了 `browser_scope`、设置页选了一种浏览器、`forRun()` 给了），就和带电脑操控的运行一样改走 dsh 运行时。这样浏览器工具才真的挂得上，截图也能进模型。其余运行仍走 direct，事件序列和改之前逐字相同，由改之前录下的金样钉住。桌面安装包的 `<resources>/licenses/` 里放了第三方许可证说明，托盘新增「开源软件许可」一项可以打开它。

**性能实测**（本机 arm64，`node scripts/bench-browser-dsh.mjs 7`。替身模型第一句就收工，不调工具，所以量到的几乎全是装配加拆除的时间；单位毫秒）：

| 档位 | 冷启动 | 中位数 | 最小 | 最大 |
|---|---|---|---|---|
| direct（不开浏览器，服务端平时就走这条） | 16 | 1 | 0 | 1 |
| dsh 进程内，不挂浏览器 | 29 | 7 | 6 | 11 |
| dsh 进程内，挂浏览器 | 608 | 580 | 574 | 621 |
| dsh 子进程，不挂浏览器 | 331 | 327 | 316 | 395 |

## 2. 自主决定（白话）

1. **分流条件和 WP144 写成一处。** 只要有浏览器或电脑操控之一就走 dsh，不另起一个适配器，这样两样同时在场时自然是同一棵树。
2. **stub 档（没配模型）不改。** 没有模型就没人驱动浏览器，和 WP144 一样只在有模型时建 dsh 适配器。
3. **新增 `dshMode` 选项。** 服务进程不传，仍是 auto：编译过的机器上走子进程，否则进程内。测试需要钉成进程内，才能把 Playwright 那个进程换成假的，而且结果不会随「dsh-adapter 编没编过」而变。子进程档另外用真提供方测了一条。
4. **「一个字节不变」用金样证明。** 我先在旧代码上录下事件序列并单独提交，再改分流。改完以后测试照样逐字对得上。
5. **许可证清单宁多勿少。** `pnpm licenses list` 给的是声明过的生产依赖，比安装包里实际带的多一些（比如一批 dsh 界面包）。多列不违规，少列才违规。「真带着的原生二进制」那一段则是从打包后的目录里实扫出来的。
6. **LGPL 全文只给了官方地址，没有放进安装包。** 本机依赖里找不到一份 LGPL / GPL 全文，凭记忆写又怕不准，所以没放；要不要下载一份放进去，列在第 3 节。
7. **托盘里的「开源软件许可」只在安装包里真有那份文件时才出现。** 这是仓库一贯的做法：不摆点了打不开的菜单项。连公司服务器那一档也照常出现，因为许可证说明的是这台电脑上装的这个安装包。

## 3. 需要 Luoye 定的事

1. **带浏览器的运行，工具调用上限要不要放宽？** 现在仍是 12 次。电脑操控批过授权时放到 40。浏览器干活也是「打开、看一眼、点一下、再看一眼」，12 次可能不够一个小任务。我没改。
2. **每次带浏览器的运行多约 0.9 秒装配时间，能接受吗？** 不能接受的话，按第 1 节的 (a) 或 (b) 单独立项。
3. **LGPL-3.0 / GPL-3.0 的全文要不要随安装包带一份？** 现在只给了 gnu.org 的地址。随包带全文更稳妥，做法是从 gnu.org 下载一次放进仓库。
4. **捆绑的 Node 的 LICENSE 现在也只给了地址。** 可以让 `fetch-node.mjs` 从已经校验过 sha256 的 tar 包里顺手多解出 `LICENSE`（Windows 下载的是单个 `.exe`，没有这个文件）。要不要做？
5. **树里有几种不常见的许可证，请过目。** `@deepseek-ai/libreoffice-kit` 是 MPL-2.0（文件级 copyleft，不改它就只需附声明、给出源码地址）。另外还有 `(MIT OR EUPL-1.1+)`、`Python-2.0`、`BlueOak-1.0.0`、`Unlicense`。**没有 GPL。**
6. **打包必须经 pnpm 调用。** 我拿 `npx electron-builder --dir` 直接跑的那一次，electron-builder 没收 `@img/sharp-*` 这些平台包，安装包里就没有 libvips。经 `pnpm -F @agentsws/desktop package` 跑时是在的。CI 与 `release.sh` 如果都经 pnpm 就没事，建议审核方顺手核一下。

## 5. 偏离

1. **报告位置按调度方说的来**：写在 `docs/briefs/reports/WP148.md` 并提交，不是 `_common.md` 里说的 worktree 根目录下不提交的 `REPORT.md`。
2. **派工单没写、但我做了的**：
   - 托盘加「开源软件许可」一项。派工单要求「关于 / 许可证能看到的位置」，这个应用只有托盘。
   - 加了 `afterExtract` 钩子。不加的话，mac 安装包里就没有 Chromium 的许可证。
   - 加了「带原生二进制却不在清单里就打包失败」这道闸。
   - 提交了量时间的脚本，方便以后重跑。
3. **打包验证用了本机的临时替身，没有下载。** `vendor/node/darwin-arm64/bin/node` 是一个转给本机 `/opt/homebrew/bin/node` 的两行 shell 脚本；`vendor/natives/...` 里放的是仓库 `node_modules` 里现成的 `better_sqlite3.node`。Electron 的 zip 用的是本机缓存，缓存文件的时间戳没变，说明没有重新下载。这些只为让 `package --dir` 走完，验完已经把 `apps/desktop/vendor/` 和 `apps/desktop/release/` 删掉了，两个目录都是我这一单建的，本来就在 gitignore 里。所以这次打出来的包里，捆绑的「Node」**不是真的 Node 22**；冒烟 `probe ok` 只证明依赖补得齐，不证明 ABI 127 对得上，这一点照旧要靠发版时的 `fetch-node`。
4. **打包跑了三次，派工单说「可以跑一次」。** 第 1 次发现 mac 上找不到 Electron 的许可证；第 2 次（`npx electron-builder --dir`）是为了确认 `afterExtract` 那一刻文件还在；第 3 次是最终验证。
5. **子进程档那条测试会起一个真的 `@playwright/mcp` 进程。** 它不开浏览器、不联网：attach 的端口没人监听，那次导航在门禁就被拦下，工具体根本不跑。
