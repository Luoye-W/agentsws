## 2. 我自主做的决定（白话）

1. **profile 层多关了四行**（docs/42 红线 7：默认开着的出网 / 上报，一律在我们这一层关死并加测试）：
   - `web-search-deepseek`（官方的网页搜索）：这一版起，用 DeepSeek 账号的会话**不需要 API Key 就能直接拿账号令牌上网搜索**。
     派工单要求这条默认必须关、不许绕开我们自己的数据接口。它没有单独关"账号令牌"的开关，所以**整行关**——
     原来那条用 API Key 搜的路一起关了（同样绕开我们的路由）。
   - `otel`：官方新塞进默认组合的"上报通道工厂"。单独挂着不发东西，但它存在的唯一用途就是上报；关掉它，以后上游往默认组合里加什么埋点都起不来。
   - `session-telemetry-otel`（**存量补锁**）：用户在官方界面点"反馈"，就把**整条会话记录**（客户原文、工具参数与结果、系统提示…）发到 DeepSeek 的收集端。
     它至少从 0.1.7-rc.1 起就在默认组合里，前两次升级都因为它"不是新增的"而没锁；这一版它换了发送通道和收件地址，在对比里露出来了。
   - `plugin-package-inventory-deepseek`（**存量补锁**）：每次走官方 DeepSeek API 的请求都附上"当前装了哪些插件包"的清单。
     这是我照上一条的教训，把组合里所有没关死的 85 行逐行过了一遍"会不会出网 / 上报"查出来的。
   这四个包在我们实际跑的两档运行时里**一次都没加载过**（模块图实测 0 命中），所以没有任何数据真的出去过；关死管的是"哪天真起了完整 profile"那条路。
2. **给升级流程补了一条规矩**（docs/42）：每次升级不只看"上游这次改了什么"，还要把组合里所有没关死、会出网的行整体对一遍锁定表。理由就是上面那两行存量。
3. **官方"一次改写删掉全部失效图片映射"没跟**：它改的是官方落盘索引的加锁方式；我们的索引是同进程的同步表，逐条删的结果和它一模一样，只是可选的落盘模式多写几次盘。
4. **"升级前"的基线另存了一份**（`0.1.7-rc.2-wp177.json`）：这几周我们自己加了场景、改了行为，旧的那份已经对不上现在的代码，不另存就会把我们自己的改动算到上游头上。
5. **提示词、模块图、组合清单在升级前就先导好存下**：比 WP149 那样"装回旧版再导一次"省一轮安装，结果一样可比。
6. **桌面安装包没打**：这个新 worktree 里没有捆绑的 Node，打包要先从 Node 官网下载——派工单说这种情况停在这一步，照办（§6）。

## 3. 需要 Luoye / Fable 定的事

1. **要不要给"用 DeepSeek 账号的用户"开免 key 网页搜索**：官方那条路我们关了。如果要这个能力，正确的做法是在**我们自己的数据接口**里加一个
   "DeepSeek 原生搜索"后端、用账号令牌当上游凭据，计费 / 缓存 / 审计仍在我们那一层（M，约 2–4 天）。注意官方这种搜索**一次 = 一次完整的模型回合**（慢、费 token）。
2. **两行存量补锁请确认**（`session-telemetry-otel`、`plugin-package-inventory-deepseek`）：按红线 7 应该锁，但属于"以前判过、这次改判"，请过目。要撤就是 profile 文件里删两行 + 测试表删两行。
3. **网页抓取工具 `web-fetch-http` / `tool-web` 没锁**：它们是模型按需抓网页的工具（和沙箱里的 bash 同一类"模型动手"，不是后台上报），我们的两档不挂。
   如果你认为"完整 profile 里模型抓网页也必须走我们的数据接口"，就再锁两行（S）。
