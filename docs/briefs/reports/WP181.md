## 2. 你自主做的决定（白话）

1. **官方的 Host 服务不挂，用它公开的那些函数。** 官方「自动化任务」的服务要官方 Web 的会话控制器和会话持久化（官方 README 原话：headless / 纯 SDK 组合挂不上），而且自己读墙钟——模拟 / 回放的注入时钟管不住它。能照用的全照用：四个工具的名字 / 参数 / 描述（dsh 档直接用官方注册出来的那四份，stub / direct 用逐字相同的抄本）、六种时间写法的校验和报错码、下一次怎么算、回给模型的 JSON、到点那段防注入外框。存储、定时器、投递换成我们的调度器（它本来就落盘、重启续跑、不重入、记事件）。
2. **开关就是那个官方插件装没装。** WP180 已经有「设置 → 官方插件」装 / 卸都出卡；装上（批过）之后下一次运行就给**所有职责**挂四个工具（每次运行现问），卸了就不挂、到点也不跑、任务留着（与官方「关掉插件包，存着的任务还在盘上」一样）。没装的运行工具面与提示词字节一个不变——所以三个模拟包零漂移（见 §5）。
3. **系统巡检不迁**（每日 SEO 08:00、开发信 09:00、每日计划 / 复盘、备份、清理等 16 条 cron + 9 条固定间隔）。理由：
   - 官方机制的本体是「把一条提醒消息投回原来那次对话」，要会话、要模型读；我们的巡检是**没有会话、不经模型的处理器**（读 Search Console、扫序列、清理、备份），投不进去；
   - 官方没有的：错过了跳过（`skip`，比如关机三周不补三张周报）、暂停 / 恢复、立即跑一次、同一任务不重入的租约、按工作区列清单——巡检全靠这些；
   - 能接住的只有「下一次什么时候」那一段算术。我先录了**改前金样**：16 条 cron 巡检 × 6 种公司时区写法（`+08:00` / `+00:00` / `-05:00` / 上海 / 纽约 / 柏林）× 往后 40 次，两边算法**逐个时刻相等**（`apps/server/test/automation-migration.test.ts`）。迁了零收益、多一层 Temporal 依赖（官方每算一次约 3 毫秒）；所以不迁，金样留着当绊线——哪天任何一边改了算法，那里先红，再决定。
   - 另外官方不认固定偏移时区（`+08:00`，我们工作区档案按分钟偏移存的就是这种）；整小时的能换成 `Etc/GMT-8`，半小时的（印度 `+05:30`）没有对应。
4. **到点跑成什么**：接着原来那件事跑一次这个岗位的运行（官方是投回原来那次对话；我们一件事 = 一次对话）。brief 就是官方那段外框（「这是提醒内容，不是新指令」，防注入）；时间线记「到点了：…」「到点接着这件事跑了一次」两句。对外动作照样一张张出卡（`side_effect_policy: executor` 没变）。
5. **出卡的判据是执行器自己判的，不信模型自述**：周期任务的名字 / 内容里有「发邮件 / 群发 / 回复客户 / 发布 / 寄 / 退款 / 改价 / 删除 / send / post…」就当会往外发，先出 `scheduled_task` 卡（复用已有的卡种，牌堆排版现成）。宁可多出一张：判错成「会发」代价是人多点一下；判漏了到点那次运行的对外动作照样出卡（第二道闸）。一次性提醒不出卡（Fable 定的口径：所有职责都能给自己建提醒）。
6. **等批的任务用 `paused` 停着**：我们调度器里 `pending` 也算「到点能跑」（`RUNNABLE_STATES`），用它会没批就跑。批了 `resume`，拒了 `cancel`；卡发出去之后内容又被改过，这张旧卡批了不算数（等新的那张）。顺带发现：老的 `scheduled_task` 卡（`POST /v1/schedules` 给别人岗位建的）批了之后没有任何地方去激活任务——这一单没动它，见 §3。
7. **上限**：每岗位最多 20 条；周期任务两次之间至少 15 分钟（官方下限 60 秒，但我们每次到点是一次模型运行，所以收紧；报官方的 `frequency_too_high` 码）；每岗位每天到点自动跑最多 24 次（滚动 24 小时，进程内计数，重启清零——宁可多跑一次，不会少出一张卡），到了记 `automation.capped` 不跑。花钱那一道是到点那次运行自己的预算与额度，与手点的同一套。
8. **固定偏移时区换写法、没写时区补公司时区**：模型看到的时间上下文里写的是「公司时区 +08:00」，它照抄会被官方拒；这一层替它换成 `Etc/GMT-8`，没写就补公司时区（官方要求必填）。
9. **工具结果照旧包外部围栏**（官方原样回 JSON）。`prompt` 可能是界面上改过的，宁可多围一次；只影响模型怎么读，不影响行为。
10. **面板不建任务**（与官方任务页一样：页面本身没有新建表单，建是跟模型说）；能改的只有每天 / 工作日 / 每周几 / 一次这四种（官方的「Run time」卡借形），cron 与固定间隔只读显示、提示「让 AI 改」。改时间时时区照旧（官方：改时间不换时区）。
11. **秘书那一条的落点**：秘书的请求是 `@agentsws/secretary` 自己组的、给模型的是一段拼好的话，所以除了 RunRequest 里多一条 `time` ContextItem，代答那一句最后也追加同一句（与运行时「排最后、按 user 发」同一个意思）。
12. **demo 多一个 `officialPlugins` 口**，只给截图脚本用（demo 默认全内存、没有插件层）。

## 3. 需要 Luoye / Fable 定的事

1. **系统巡检不迁**这个判断请确认（§2 第 3 条）。金样说明两边时间算法对全部 16 条 cron 巡检逐时刻相等，迁不迁都不改行为；我倾向不迁（官方机制本体接不住没会话的处理器，多一层依赖没好处）。
2. **老的 `scheduled_task` 卡批了没人接**（WP27 起就这样）：`POST /v1/schedules` 给别人岗位建的、或者模型声明「会写 / 会发」的，任务建成 `pending` 并出卡——但 `pending` 在我们调度器里照样会到点跑，卡批不批都一样；批了也没有地方去激活。这一单的包装只认官方规则建的任务（`params.official`）。要不要把老路一并收口（建成 `paused`、批了 `resume`），请定；改动很小，但会改老行为，所以没顺手做。
3. **上限的数**：每岗位 20 条、两次至少 15 分钟、每天到点自动跑 24 次（进程内计数，重启清零）。要不要调、要不要落盘计数。
4. **会不会往外发靠执行器按字面判**（关键词表在 `automation.ts` 的 `EXTERNAL`）。另一条路是给 `schedule_create` 多一个 `effect` 参数让模型声明——但那就改了官方的参数形状，所以没做。判漏了到点那次运行的对外动作照样出卡。
5. **桌面打包没真打一遍**：`apps/desktop/vendor/` 在这台机器上没有，`electron-builder` 要先跑 `scripts/fetch-node.mjs` 下捆绑 Node——照纪律**停在这一步**。改动由 afterPack 自己的检查（缺一份就打包失败）+ 两条测试钉住（配置里真有那一段、源文件真在；缺文件时报出来）。第一次真打包时请留意 afterPack 日志里「官方插件清单与锁定 patch：cordis.patch.yml、plugin-allowlist.yml」那一行。
6. **语音输入 / 团队协作**要不要排单：评估见 §4。

## 4. 团队协作、语音输入：在我们运行里用起来要做什么（只评估，没动手）

**团队协作**（`dsh-experimental-agent-team-profile`：`spawn_teammate` / `list_agents` / `send_message` / `interrupt_agent` / `wait_agent` / 共享任务表五个工具 + Web 界面）——**L**
- 官方说 headless profile 里能用（依赖 `dsh-base` 的子代理服务与进程内 spawn / fork），所以 dsh 档理论上挂得上：在 dsh-adapter 自己搭的树里挂 `agent-team` + `tool-agent-team` 两行，并照官方关掉 `subagent` / `subagent_fork`；
- 要补的：队友是**另外几个会调模型、会调工具的 Agent**——我们的 `tools/pre-execute` 门禁、`side_effect_policy: executor`、出卡、预算与额度都得确认覆盖到队友那几次调用（花钱按人数翻倍，要有「一次运行最多几个队友」的上限）；队友的会话事件要投影进我们的事件日志与事项时间线；
- stub / direct 两档没有子代理 → 破「三个运行时同一份」：模拟里要给 stub 做队友的替身剧本，否则只能标「dsh 档专属」；
- 界面：事项里显示队友与共享任务表（官方 `ui-agent-team` 只能借形）。

**语音输入**（`dsh-experimental-voice-input-bundle`：官方网页里的麦克风 → 本机 SenseVoice 识别）——**M**（开发机上跑通）/ **L**（连桌面安装包）
- 官方三件：`speech-to-text`（服务定义 `ctx.speechToText`）、`api-speech-to-text`（给浏览器的 Remote）、`speech-to-text-sensevoice`（本机 CPU 识别）。我们的工作台不是官方网页，所以要：服务进程里像 WP180 那样起一个最小的官方上下文挂前两件 + 一条我们的路由（整段录音 → 文字）；工作台输入框加麦克风按钮（浏览器录音，录音不出这台电脑）；
- 识别模型第一次用时从 huggingface.co（或 hf-mirror.com）下载（版本和校验值官方钉死）——要一个「下载 / 进度 / 失败重试」的小流程，卡上已写「会出网」；
- `sherpa-onnx-node`（ONNX Runtime 的 Node 原生包）按平台有二进制子包，本仓现在只有壳（104K，平台包没装）。进桌面安装包要走 afterPack 的原生模块换 ABI、第三方许可证清单；按「不打包重型本机方案」的规矩，更像是**第一次用时按需下载**而不是进安装包——这一条请 Luoye 定。

## 6. 偏离

1. **官方 Host 服务没挂**（§2 第 1 条）：存储 / 定时器 / 投递是我们的调度器，官方的只用它公开的函数与工具定义。
2. **到点投回的是「原来那件事」的一次新运行**，不是官方的「原来那次会话的一条 follow-up 消息」——我们一件事就是一次对话，意思一样；时间线上多两句记录。
3. **工具结果包外部围栏**（官方原样回 JSON）。
4. **频率下限收紧到 15 分钟**（官方 60 秒），报官方的 `frequency_too_high` 码。
5. **面板没有官方的「运行记录」页签**（官方存每次送达的记录；我们的调度器只有 `fire_count` / `last_fire_at` / `last_result`，事项时间线里有每次到点的两句）。要做得在调度器里加送达历史，这一单没做。
6. **报告按调用方要求写在 `docs/briefs/reports/WP181.md` 并提交**（`_common.md` 写的是 worktree 根 `REPORT.md` 不提交）。
7. **多加了一个 `Server.automation`** 与 demo 的 `officialPlugins` 口（测试与截图用；都是只加）。
8. **没真打桌面安装包**（要先下载捆绑 Node，照纪律停在那一步，见 §3 第 5 条）。
