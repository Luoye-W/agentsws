# WP261 报告：独立站运营工具——经 Shopify CLI `store auth` + `store execute` 管商品 / 合集 / 页面 / 菜单 / 折扣（决策 175 第 1 步）

分支 `wp/261-ops`（worktree `agentsws-wt/wp261-ops`），Claude 子代理。未推送、未合并。

## 0. 一句话

岗位页（店铺管理 / 整站搭建 / 网页模板所在的岗位）多一行「授权管理商品和页面」：点一下，服务端替用户起 `shopify store auth`，浏览器里打开**店铺后台自己的授权页**，人点批准就好——不建开发者应用、不开终端、不填任何技术参数。授权好了记「已授权 + 能做哪几件事 + 到几点 / 会自动续期」；过期、被收回、缺权限时那一行回到「重新授权」并说清缺哪项。AI 侧多了 **17 个固定的运营工具**（9 个只读 + 8 个改动），不给任意 GraphQL；**改动一律只出审批卡**，人批了服务端才带 `--allow-mutations` 去改，并**读回确认**。底层是 `ShopifyAdmin` 接口，这一单实现「CLI store execute」版；决策 146 的自家应用版以后只是另一种实现。

## 1. CLI 行为摸底（`npm pack @shopify/cli@4.8.5` 到临时目录读发行包，没装、没联 Shopify）

### 1.1 `store auth`

| 问题 | 结论（源码出处：`dist/index.js` 的 `nt()` / `rn()` / `an()`，`chunk-GBYDMHZ3.js` 的会话存取） |
|---|---|
| 授权方式 | **浏览器 PKCE 授权，不是设备码**。用的是 Shopify CLI 自己的公开应用（client_id `7e9cb568…`）。授权页是 `https://<店>/admin/oauth/authorize?client_id=…&scope=…&redirect_uri=http://127.0.0.1:13387/auth/callback&state=…&code_challenge=…`，人在**店铺后台**里批准（要在浏览器里登着这家店的后台）。**没有确认码**——WP245 那种「核对确认码」这里没有，卡上只显示「在浏览器里批准授权就行」 |
| 回调 | CLI 在本机 **`127.0.0.1:13387` 写死端口**起一个小服务等回调，**5 分钟**等不到就报 `Timed out waiting for OAuth callback.`；端口被占报 `Port 13387 is already in use.` → **整台电脑同一时间只能有一个授权**（我们的授权跑法是进程级一份，第二个品牌点会被告知「另一个品牌正在授权」） |
| 浏览器谁开 | CLI 自己开（`open` 包；只有 Codespaces / Gitpod / Cloud Shell 才不开）；开不了打 `Browser did not open automatically. Open this URL manually:` + 网址（stderr）——我们抓这一行，由工作台开一次、卡上给「没弹出来？点这里打开」 |
| 非交互要什么 | **什么都不要**：没有 TTY 检查（`store auth` 没有 `nonTTYFlagRequirements`），`CI` 不影响；**不需要先 `shopify auth login`**（账号登录与店铺授权是两套） |
| 权限 | `--scopes` 逗号分隔；CLI 会先查店里这个应用**已有的权限**（`currentAppInstallation.accessScopes`）并进请求；Shopify 少给了就失败：`Shopify granted fewer scopes than were requested. Missing scopes: a, b.`（在线令牌跟着**操作人员工账号的权限**走，员工账号权限不够会撞上）；人点了拒绝：`Shopify returned an OAuth error: access_denied`；`write_x` 隐含 `read_x` |
| `--json` 输出 | stdout 一段 `{ store, userId, scopes, acquiredAt, expiresAt?, refreshTokenExpiresAt?, hasRefreshToken, associatedUser{id,email,…} }`；提示行全走 stderr |
| 令牌存哪 | `conf` 的 **`shopify-cli-store`** 那一份配置（路径同 WP253 的 env-paths：mac `$HOME/Library/Preferences/shopify-cli-store-nodejs/config.json`、Windows `%APPDATA%\shopify-cli-store-nodejs\Config\config.json`），键 `7e9cb568…::<店>`，里面有 `accessToken / refreshToken? / expiresAt? / scopes`。我们替用户跑时把 HOME / APPDATA / XDG_* 指到 **`<数据目录>/tools/shopify-cli-store-sessions/<品牌>/`**——**与 `auth login` 那一份分开**（重新登录 Shopify 账号时那一份会被整个挪走重建，不能把店铺授权一起挪掉）。**我们不读这个文件**，只记 CLI `--json` 打出来的那几样（没有令牌） |

### 1.2 令牌有效期（重点）

- 存的是**在线令牌**（online access token，跟操作人员工账号绑定）。有效期 = Shopify 回的 `expires_in`；Shopify 的在线令牌惯例是 **86399 秒 ≈ 24 小时**。
- CLI 每次 `store execute` 前看：离过期不到 **4 分钟**就用 `refresh_token` 续（`POST https://<店>/admin/oauth/access_token`，`grant_type: refresh_token`），续好写回配置——**前提是当初 Shopify 回了 `refresh_token`**。没回就报 `No refresh token stored for <店>.` 要重新 `store auth`；续的时候 HTTP 出错也删掉会话、要重新授权。执行时撞上 401 / 404：删掉本地会话、报 `Stored app authentication for <店> is no longer valid.`
- **源码里看不出 Shopify 对 CLI 这个公开应用回不回 `refresh_token`**——这只能真机第一次授权看 `--json` 里的 `hasRefreshToken` 与 `expiresAt`。我们两样都记下：岗位页显示「到 X 月 X 日 HH:mm」或「会自动续期」，事件 `shop_admin.auth_finished` 带 `refreshable` 与 `expires_in_minutes`（Fable 首测第 4 步）。
- **如果真机是「24 小时、不续期」**：每天要点一次「重新授权」（浏览器里批准一下，几秒钟）。这正是决策 146 第 2 步（自家公开应用、长期离线令牌）要解决的，见 §4 第 4 条。

### 1.3 `store execute`

- 文档必须**正好一个操作**；是 mutation 又没带 `--allow-mutations` → 发请求**之前**就报 `Mutations are disabled by default for shopify store execute.`；`--allow-mutations` 只是放行 mutation，没有别的范围限制（所以「只读」靠我们不带它 + 我们自己的文档白名单）。
- `--version` 不给：先多查一次 `publicApiVersions` 取最新 supported；给了不在列表里：`Invalid API version: X` + 列出可用的。
- `--query-file` / `--variable-file` / `--output-file` 都认（我们**全走文件**：Windows 命令行转不准 `"` / `%`、还有 8191 字上限；结果从文件读，不混 CLI 提示行）。
- 结果：`data` 那一层 JSON（`userErrors` 在里面照常回）；GraphQL 顶层 `errors` → `GraphQL operation failed.` + errors JSON（退出 1）；缺权限就是这里的 `Access denied for X field. Required access: \`write_x\` access scope.`；店铺冻结 402 → `currently unavailable`。

### 1.4 本机图片怎么传

`store execute` 只跑 GraphQL，不传文件。走 Shopify 官方的 staged upload：`stagedUploadsCreate`（拿临时地址 + 表单参数）→ **我们的服务进程**按它给的参数把文件 POST 到那个地址（签名地址，不带任何令牌）→ 拿 `resourceUrl` 当 `originalSource` 用 `productUpdate(media:)` 挂到商品上。三步都在**批过的卡**执行时才做。网址图片直接当 `originalSource`。

## 3. 自主做的决定（白话）

1. **改店卡一律 L1（人批了才改）**，不管职责 yml 给 `listing_edit` / `price_change` 等开到了 L2（额内自动）。派工单写「写操作一律先出审批卡，人批了才执行」，L2 在这套系统里是「自动批 + 抽检」，等于没人点就改店——所以第 1 步全按 L1。以后要不要放开见 §4 第 1 条。
2. **店铺授权的会话目录与登录的会话目录分开**（`shopify-cli-store-sessions` vs `shopify-cli-sessions`）：WP253 的重新登录会把那一份整个挪走重建；放一起的话，换个 Shopify 账号登录就把店铺授权顺手清掉了。`store auth` 本来也不需要账号登录。
3. **账本那道老门的修**（§2 ⑪）：`record_read` 是给没接 provenance 的老路径留的自报字段，经 `ledger.stage` 提卡时永远是空 → 所有改文案的卡都 blocked（WP63 起就这样，只是之前没有真路径走到）。现在 provenance 证明读过才记 ok；没读过照旧被 guardrail 拦（同一张 `RECORD_READ_KINDS`）。加了一个 txn 单测钉住两边。
4. **权限按岗位要、不按品牌全要**：岗位上这几条职责的并集 ∪ 以前给过的（CLI 自己也会把店里已有的并进来）。网页模板岗位只要「读商品」，店铺管理岗位再点一次授权时补上写权限。
5. **店铺地址自动拿**：与网页模板同一份；都没有时用品牌分析从官网读到的 `xxx.myshopify.com`（WP258 已有）——大多数 Shopify 店首页都带它，用户不用填；真没有才出一格让填。
6. **API 版本钉 `2026-07`**（Shopify 季度版本），CLI 说不认了就退回 CLI 默认的最新稳定版（这一进程以后都不带 `--version`）。不钉的话每次多查一次版本列表、字段还可能悄悄变。
7. **订单只给只读的最近订单**（`shop_recent_orders`，不带顾客信息），与连接器那一路的 `get_order` / `list_orders` 不重名、不替换。
8. **上架 = 状态改成 ACTIVE + 挂到「Online Store」渠道**（新建的商品默认不在任何渠道上，只改状态顾客还是看不到）；挂渠道要 `write_publications`，挂不上不算失败，卡的执行结果里说一句。
9. **建商品不传 handle**（Shopify 按标题生成）；新建卡的目标 id 是 `new:…`，在 provenance 里记成「读过」（新东西没有原文可读）。
10. **同一张卡执行过就记下**（`<品牌>/shop-ops.json`，留最近 500 张）：执行器重试时不在店里建第二件商品 / 第二个折扣码。
11. **工具面每次运行现问授权**（不缓存）：授权过期了下一次运行工具就没了，岗位页那一行同时变「重新授权」。

## 4. 要 Luoye 定的事（逐条，附建议）

1. **改店卡要不要按职责 yml 放开 L2（额内自动）**：现在一律 L1，每一张都要人点（§3 第 1 条）。**建议**：第 1 步保持全 L1，在 Rollout 跑顺两周、看采纳率后，先只放开「改文案」（`listing_edit`）到 L2，改价 / 上下架 / 折扣继续人批。
2. **权限里含「上架到网店」（`write_publications`）**：新建商品要挂到网店渠道顾客才看得到，没有它「上架」只改状态。风险：如果 Shopify 不给 CLI 这个公开应用这一项，**整次授权会失败**（CLI 要求一项不少）。**建议**：首测验证（Fable 步骤第 3 步）；真失败就从登记表去掉它，上架改成「改状态 + 提示去后台点一下销售渠道」。
3. **店铺管理岗位顶上那条「还缺必需的连接：店铺后台」**：职责 yml 里店铺连接是必需的（订单 / 客服那一路还靠它）。店铺授权好了之后这条黄条仍在（截图 2–4），用户会以为还没弄好。**建议**：下一单把「店铺授权（CLI）已授权」算作 `kind: shop` 的一种满足方式（只对运营这几样；订单详情那一路仍提示连店），或者至少把黄条文案改成「订单与客服还要连店」。
4. **令牌有效期**：在线令牌，若真机证实「24 小时、不续期」，每天要点一次「重新授权」（浏览器里批准一下）。**建议**：先接受（一行一键，几秒钟）；把真机看到的 `refreshable` / 有效时长回报后，决定是否立刻启动决策 146 第 2 步（自家公开应用、长期离线令牌）——工具与卡片已经按 `ShopifyAdmin` 接口写好，第 2 步只换底层。
5. **订单**：新加的 `shop_recent_orders`（只读、无顾客信息）与连接器那一路 `get_order` / `list_orders` 并存。Shopify 对没审批「受保护客户数据」的应用可能把订单查成空或拒绝（docs/43 附录真店实测过一次）。**建议**：先并存；首测看能不能读到订单，读不到就从店铺管理的权限里去掉 `read_orders`（订单仍走连接器）。
6. **删除类不做**（派工单原话），要「删」时只给下架 / 归档。**建议**：保持。
7. **本机图片只许本品牌文件夹里的**（`<数据目录>/brands/<品牌>/`）。用户拖进聊天的图片 / 设计岗的素材目前不在里面。**建议**：下一单把设计岗素材库与聊天附件目录加进白名单。
8. **整站搭建能改页面与菜单（`store_setup`，L1），但不能改商品 / 合集**：照 yml 原意（结构归建站、内容归运营）。**建议**：保持。

## 6. 给 Fable 的真机首测步骤（Windows，Rollout `6suegp-md.myshopify.com`，和 Luoye 一起做）

前提：装的是含 WP261 的包；Rollout 品牌平台是 Shopify；「网站运营」岗位里有「店铺管理」（或建站岗位有整站搭建 / 网页模板）；**浏览器里登着 6suegp-md 的店铺后台**（店主账号最好——在线令牌跟着这个员工账号的权限走）；接好模型。

1. 打开 Rollout 有「店铺管理」的岗位页：应出「让 AI 管商品、页面、菜单和折扣，要先授权」+「授权管理商品和页面」。（CLI 没装就先是「一键安装」；店铺地址 Rollout 已有手填的那一个，不会再问。）
2. 点「授权管理商品和页面」：那一行变转圈「在浏览器里批准授权就行」；浏览器应自己打开 `https://6suegp-md.myshopify.com/admin/oauth/authorize?client_id=7e9cb568…`（没弹出来点「没弹出来？点这里打开」）。
3. 浏览器里看授权页列的权限（商品、库存、内容、导航、折扣、订单、**销售渠道 / 发布**），点批准 → 页面显示 `Authentication succeeded` → 回工作台那一行变淡色「已授权管理商品和页面 · 到 X 月 X 日 HH:mm」或「会自动续期」。
   - 如果失败、那一行红字是「Shopify 没给这几项：上架到网店」→ 回报，按 §4 第 2 条去掉这一项；「刚才在浏览器里没批准」/「5 分钟没等到」/「另一个授权窗口还开着」各是各的原因。
4. **记下令牌有效期**：事件日志里 `shop_admin.auth_finished` 的 `refreshable` 与 `expires_in_minutes`（这就是 §1.2 要的结论）；`%AGENTSWS_DB_DIR%\tools\shopify-cli-store-sessions\ws_19cxxs7l\AppData\Roaming\shopify-cli-store-nodejs\Config\config.json` 存在（**不要打开发出来，里面有令牌**），用户自己 `%APPDATA%\shopify-cli-store-nodejs` 下没有新增。
5. 在店铺管理里说「列一下店里的商品」→ 时间线里有「店里的商品列表」，回话里有真实商品；再说「看看最近的订单」→ 若读不到 / 说没权限，按 §4 第 5 条回报。
6. 说「把 <某商品> 的标题改成 <新标题>」→ 只出一张卡「改商品「…」：标题」（改之前 / 改之后两格、没有 id 之类的技术字），**后台没变** → 点「批准」→ 过撤回窗口 → 后台标题变了；事件 `shop_ops.applied` 的 `verified: true`。
7. 各试一张：改价（卡上原价 → 新价、幅度）、新建一件草稿商品（带两个规格）、给商品加一张网址图片、建折扣码（限 100 次）、改「关于我们」页面正文、改主菜单（建站岗位）。每张批后看后台，回报任何「Shopify 没接受：…」或「GraphQL 错误」的原话——GraphQL 全在 `apps/server/src/shop-graphql.ts` 一个文件，按原话改。
8. 在后台手动改一下某商品标题，再批一张之前出的「改这个商品标题」的卡 → 应该不改、卡上说「在卡出来之后被改过」。
9. 建站岗位（网页模板）：授权后「搭首页」的运行里工具面多出读商品 / 合集；可以试「首页主推放『首页精选』合集」，看它是否查了真实合集 id 写进模板设置。
10. 24 小时后再看那一行：若变「店铺授权过期了」→ 确认无续期（§4 第 4 条）；点「重新授权」应该几秒内恢复（浏览器里已授权过，批准一下就好）。
11. 出问题看：那一行的人话；事件 `shop_admin.*` / `shop_ops.*`（只有码、个数、change_id，没有令牌、没有店铺数据）。

## 7. 偏离 / 未完成

- **GraphQL 没对真 schema 校验过**：纪律是不碰 Shopify，所以 `shop-graphql.ts` 里的文档按 2025-xx 以来稳定的字段写（`productSet` / `productUpdate(product:, media:)` / `productVariantsBulkUpdate` / `stagedUploadsCreate` / `pageCreate` / `menuUpdate` / `discountCodeBasicCreate(context: {all: ALL})` 等），真机首测逐条验证（§6 第 7 步）。字段改名只改这一个文件。
- **没有「重新授权前提醒」**：只在过期后那一行变黄。要不要提前一小时提醒等真机有效期结论再说。
- 「缺权限」截图是改写 `GET /v1/shop-admin` 回包造的（demo 替身一次给全了权限）；缺权限的真实路径由单测钉住。截图里商品卡是在 demo 里先驳回了两张自带的演示商品卡拍的（同类卡在「要你处理」里会叠成一组）。
- 授权失败时没存 CLI 的输出原文（只存分类码与缺的权限名），避免把可能带网址参数的行写进日志；真机若遇到「failed」这一类拿不准，可以临时在本机命令行跑一次同样的 `store auth` 看原文。
- 模拟世界（`packages/simulation`）没接运营工具：模拟请求不带 `shopTools`，三包场景与基线不变。
