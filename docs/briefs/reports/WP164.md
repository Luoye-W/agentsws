## 2 我自主做的决定（白话）

- **契约文件名**：`packages/contracts/cloud-openapi.json`（派工单建议的那个）。真源 `packages/contracts/src/cloud-api.ts`。
- **怎么从类型生成**：没引 `ts-json-schema-generator` 之类，自己用 TypeScript 编译器 API 写了一段（约 450 行，含注释）。理由：① 不加依赖，锁文件不和并行的 WP165 打架；`gen-ontology.mjs` 本来就是这么读契约的；② 契约里用到的写法就那几样，出来的 schema 形状我们自己说了算。路由表本身也是一个 TS 类型（不是字符串清单），改名 / 删类型编译就红。
- **原 `apps/cloud/openapi.json` 留着不动**：它含运营后台，是云端内部那一份，随云端一起搬走。新契约是另一个文件、另一个脚本。
- **三种响应外形照实写，不"统一"**：账号层 `{data, trace_id}`；钱包、红人、转发、托管 `{data}`；AI、搜索数据、值守直接是正文。错误也分三种：账号层带 `trace_id`、入口层 `{code, message, details?}`、转发器访客面 `{error: {code, message?}}`。统一它们是改行为，不是本单的事。
- **严格校验只在测试里**：契约本身不写 `additionalProperties: false`（给客户端留余地，以后加字段不破坏老客户端）；一致性测试按严格档核——真实现多一个契约没登记的字段就红，逼着类型跟上行为。
- **校验器自己写的一小段**（不引 ajv）：契约只会用到 `$ref / type / const / enum / anyOf / properties / required / additionalProperties / items / prefixItems`。校验器有自测（多字段 / 类型错 / 缺必填 / 枚举外都判不过）。
- **值守单独测、放在 `packages/standby`**：Workers 形态没挂值守，Node 形态要真起子进程；用该包现成的替身起真的路由包 + 服务。它 import 了 `apps/cloud-worker/test/contract/conformance.ts`（跨目录相对路径），两边都在第 3 步一起搬进私有仓，路径不会断。
- **协议 / 托管 / 红人回包类型"挪"进契约，原包原名重导出**：开源侧与私有云只认一份；原包的公共名字一个没改。
- **不进契约的**：`/v1/admin/*`（私有）、`/v1/admin/topup`、Stripe webhook（Stripe 调的，不是客户端）、值守公网反代 `/w/{workspace_id}/*`（原样转给子进程，即 `apps/server` 自己的 API）。契约 `info.description` 写明了。
- **WebSocket 的 101**：普通 Node 的 `Response` 不收 101，转发器替身回 200（`chat-relay-do.ts` 原有的兜底）；测试里用 `rec.mark(…, 101)` 记一笔，帧逐个过 `x-websocket` 的 schema。
- **AI 口上游拒了的状态码不列**：原样透传（通常是 OpenAI 的 `{error: {message}}`），在描述里写明；列出的只有我们自己出的 400 / 401 / 402 / 403 / 422 / 500 / 502。

## 3 需要 Luoye / Fable 定的事

1. **`/v1/pricing` 没收进来**：WP165 在我收尾合并 main 时还没合并。它合并后，在 `cloud-api.ts` 加一条（引用它的类型）、重出 JSON 即可——**留给 Fable**。
2. **修了一个行为 bug（不是悄悄改）**：转发器 owner 面三条 `POST /v1/chat/relay/pairing`、`GET /v1/chat/relay/status`、`POST /v1/chat/relay/offline-messages` 从公网入口进来**一律 400「路径里缺工作区号」**——入口 Worker 的映射表里写了内部路径却没改写（与 WP128 修过的 `/v1/support/subscription` 同一个坑；WP124 的测试直接打 DO，没走这一跳）。也就是说官方托管转发器的配对、状态、拉留言从没从公网走通过。我照 WP128 的修法改写了路径（`apps/cloud-worker/src/worker.ts` 的 `handleRelayOwner`），一致性测试钉住。要是 Fable 认为这该另开一单，回退这 8 行即可，测试会红给你看。
3. **一处疑似问题，没动**：公共红人库入口判"带没带工作区令牌"用的是 `Authorization` 里**包含** `wst_`（`worker.ts` 的 `handleKolPublic`）。插件令牌 `plg_…` 是 base64url 随机串，理论上可能恰好含 `wst_`，那一把插件令牌上报会被当成工作区令牌验、回 401。概率很低，建议改成 `startsWith('Bearer wst_')`；这是改行为，没在本单做。
4. **契约与实现形态上的几处不齐，只记录、没统一**（统一就是改行为，影响客户端）：错误信封三种（见 §2）；成功信封三种；值守回包没有 `data` 信封。私有仓那边要不要在某个大版本统一，由 Fable 定。
5. `peer_kind` 在转发器状态里可能缺席（没对端时 `undefined` 被 JSON 丢掉），契约照实写成可选。

## 5 偏离

- 派工单说「不许手写一份和类型两张皮的 JSON」——做到了；但**路由表本身是手写的 TS 类型**（哪条路径、什么鉴权、回什么类型），它和实现之间靠一致性测试的覆盖检查兜住（契约里每条都必须真打到一次成功；实现里有而契约里没有的路由，测试打不到就发现不了——这一半靠审阅）。
- 账号层请求体在 `apps/cloud` 里是 zod 写的，契约里另有一份 TS 请求类型（`MagicLinkRequest` 等）。两者之间没有自动比对，一致性测试按契约类型构造请求、真实现接受，算间接核对。
- 报告按主会话要求写在 `docs/briefs/reports/WP164.md` 并提交（`_common.md` 原说写 worktree 根的 `REPORT.md` 不提交）。
