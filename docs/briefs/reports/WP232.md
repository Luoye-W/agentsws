# WP232 报告：起草出不了卡 + 无关的「订阅费退款口径」卡 + 过程话用了英文

分支 `wp/232-draftcard`（worktree `agentsws-wt/wp232-draftcard`），Claude 子代理。

## 0. 一句话

三处根因都和 Fable 的猜测不太一样：① 不是「同步审批 / 没人在线」，是**服务端找不到收件人就丢草稿**，dsh 把它报成「未获批准（fail-closed）」，模型据此编出了「答案位没人应答」；② 不是政策缺口探测，是**三个运行时收尾时只看「管退款的边界答没答过」、不看这件事跟退款有没有关系**，而 Fable 的 dev 工作区是虚拟产品，管退款的那条恰好是「订阅退款口径」；③ 回复语言那句话把「跟来信语言」放在前面、「对内用中文」放在最后半句，且没点到过程话。

## 1. 三处根因与修法

### ① 起草回复出不了卡（fail-closed）

**查到的事实**（只读查 `events.db`，run `run_89g8h2`）：runtime 是 dsh；`draft_reply` 的入参只有 `subject` / `body`；同一毫秒回了 `draft_reply 未获批准（fail-closed）`。

**根因**：「审批闸 / 答案位」是 dsh 的 `approval/request` seam，而它的应答者就是我们的门禁自己（`dsh-adapter/src/gate.ts`），在同一个调用里同步建卡——**从来不等人**。建不成只有一个原因：服务端 `createDraft`（`apps/server/src/runtime.ts`）要先解析出收件人：

- 这件事是人在工作台打字开的，事项上没钉来信人（`pinned` 里没有 contact）；
- 任务说明那一段注入时 `participants: []`，dsh 拿它当收件人兜底 → `to = []`；
- `createDraft` 见 `payload.to[0] === undefined` 就 `return undefined` → 应答者回 `rejected` → 工具抛「未获批准（fail-closed）」。

草稿就这样被丢了。direct 那一档更早一步就拒（`to` 是必填，模型不知道地址 → `draft_needs_to_and_body`）；stub 走同一个 `createDraft`，同样丢。

**修法**：

| 处 | 改了什么 |
|---|---|
| `apps/server/src/runtime.ts` `createDraft` | 收件人解析不出、或这次运行没读过 → 出一张**「收件人待定」的回信卡**（`outbound_draft`，`payload.manual_send: true`、没有 `to`；标题「回复草稿（收件人待定）：主题」，摘要一句「没有能替你发的收件地址：批了也不会自动发出，复制正文自己发。」）。卡挂在线程 / 订单上，都没有就挂在这件事上。不再 `return undefined`。有钉住的来信人时照旧回给来信人（顺带修了：以前模型没给地址、事项钉着来信人时也会丢草稿）。 |
| `packages/txn/src/precheck.ts` | `isManualSendDraft`（`manual_send === true` 且**没有** `to`）：不过收件人门禁（没有收件人就不会发错人），其余预检（围栏、密钥 / 卡号扫描、脱敏）照旧。带了 `to` 的卡标记不生效，绕不过门。 |
| `packages/txn/src/executor.ts` | 这种卡批了**一个渠道都不碰**：直接记 `applied`，`outcome_ref = { type: 'manual_send' }`。 |
| `packages/deck` + 工作台 | 卡上多一格 `manual_send`；按钮是「我来发 / 不用」，不写「发送」（批了不会发出去，写「发送」是骗人）。 |
| `packages/dsh-adapter/src/tools.ts`、`runtime-direct` | 没建成卡时给模型的那句改成照实说「没出成卡……没有任何卡在等人批」（`@agentsws/stand-ins` 的 `DRAFT_NOT_CREATED` / `STAGE_NOT_CREATED`，三档同一份），不再出现「未获批准」「fail-closed」。direct 的 `draft_reply` 收件人改成可不填，先用线程来信人、再交宿主。起草工具的描述三档同一句：「当场建卡，不用有人在线；没有收件地址时卡上写明、人自己发」。 |

### ② 每次都冒一张「订阅费的退款口径是什么？」

**查到的事实**：`approval.created`（policy_change，`ws_1yfovch2:policy_change:policy.subscription_refund`）三次：09-30 `run_e7krpk1`（kol.instagram，一封钓鱼邮件）rev 1、10-05 `run_19ov4g51` rev 2、`run_89g8h2` rev 3，全都在 `turn.ended` 之后、`run.completed` 之前；proposer 一直是 09-30 那个 assignment。只读查 `onboarding.sqlite`：这个工作区 `vertical = digital`。

**根因**：

1. **谁出的**：不是政策缺口探测，也不是规则脑——是三个运行时收尾那一段「边界选择题」（36 §2.2）。`boundaryGate` 的 `missing` 只回答「管着**退款**这类变更的边界答没答过」，三个运行时都是「`missing` 非空就问」，**不看这件事是不是在要退款**（`wantsChange`）。
2. **为什么固定是这个主题**：虚拟产品包里管退款的那条边界就是 `policy.subscription_refund`（「订阅费的退款口径是什么？」），这个工作区从来没答过 → 每次运行都非空。
3. **为什么挂到别的 run 上、revision 一直涨**：服务端把它交给审批总线，总线按去重键「更新原项」——revision +1、`subject.matter_id` 改成这一次的事项；运行时再把它当成这次的 `proposal` 产出。

**修法**：

| 处 | 改了什么 |
|---|---|
| `packages/stand-ins/src/runtime/support.ts` | 新增 `boundariesToAsk(gate)`：只有 `wantsChange`（来信意图落在那条边界的触发面上）才问。stub / direct / dsh 收尾都用它。dsh 里「模型自己去提退款、被门禁拦下」那条路照旧问（那时显然跟退款有关）。 |
| `apps/server/src/runtime.ts` `createPolicyQuestion` | 新的可选口 `activeApproval(dedupe_key, kind)`：同一缺口已有一张在等人答（pending / in_review / deferred）就**指给它**，不交给总线——不 bump、不改挂。`server.ts` 用 txn 存储接上。 |
| `apps/server/src/runtime.ts` direct 档 | 补接 `createPolicyQuestion`。以前服务端 direct 这一档压根没接（从 a892f4c7 起就没有），所以 direct 下从来不问；现在三档一致。 |

Fable 本机那张 rev 3 的旧卡还在（我只读，没动）：修好之后无关的运行不会再碰它；要清掉就在工作台上答掉或驳回。

### ③ 过程话用了英文

**根因**：`replyLanguageSection` 的中文那句是「对外的回复……用对方来信的语言写：对方写英文就回英文，哪怕上面的说明是中文……对内的东西（给用户看的卡片、摘要、说明）用中文」——先强调「回英文」，最后半句才说对内，而「说明」没点到"边做边说的那几句"；工具结果（技能手册、搜索结果）又多是英文，模型就顺着英文说了。

**修法**：

- 规则改成**先说对内、点名过程话**：「你对用户说的每一句话都用中文：边做边说的过程话（比如"我先查一下……"）、给用户的回复、摘要和卡片，哪怕来信、资料、工具结果是英文。只有要发出去的那份稿子（起草工具里的正文和主题……）用对方来信的语言……」英文版同构。位置不动（order 22）。
- 起草工具的 `body` / `subject` 参数说明里单独写同一句（模型填参数那一刻读它）：「正文跟被回复那封信的语言；只有这份外发稿跟，对用户说的话保持界面语言」。dsh 与 direct 同一份字节。
- `docs/69` §3.3 同步了规则原文与改动理由。
- 替身测试钉住文本与先后；**真模型复测交 Fable**（替身模型不读提示，测不出管不管用）。

## 2. 自主做的决定（白话）

1. **找不到收件人时出「收件人待定、系统不发」的卡，而不是让人在卡上填地址再由系统发**。31 §3.3 收件人门禁是硬规矩（只发给这次读过的来信人 / 已验证联系方式）；让人临时填一个地址就由系统发，等于在门上开个口，这得 Luoye 定（见 §3）。现在这样：草稿一定进待批，人看到就能复制去发，系统绝不替人猜收件人。
2. **按钮写「我来发 / 不用」**，不写「发送」。批了只记「人自己发」（`applied`、`manual_send`），没有任何外发。
3. **事项钉着来信人、模型没给地址时，回给来信人**（以前直接丢草稿）。这是同一处判断顺手修的，收件人仍是钉住的那一位，门禁照旧。
4. **服务端 direct 补接边界选择题**：查下来是一开始就漏接，不是故意的；三档一致是工单要求。direct 的 `stage`（提退款）服务端也没接——那是另一件事，没动，列在 §3。
5. **「同一缺口不反复 bump」放在服务端，不改审批总线的去重语义**：总线「同键更新原项」对别的卡是对的（改了内容要换版本）；只是边界问题本身没变，再问一遍只是噪声。模拟世界自己的 `createPolicyQuestion` 也是交给总线（会 bump），模拟里不影响判分，没动。
6. 回复语言规则**没挪位置**（仍是 order 22），只改措辞 + 工具参数说明。WP226 留的备选「挪到提示最末」等真模型复测再说。

## 3. 需要 Luoye 定的事

1. **收件人待定的卡，要不要允许人在卡上填收件地址、由系统替他发？** 现在是「系统不发、人复制去发」。要系统发，就得在 31 §3.3 收件人门禁上开一条「人工填写的地址」的口（人填的地址算不算「已验证联系方式」、要不要二次确认），我没擅自开。
2. **服务端 direct 这一档没接 `stage`（提退款 / 补偿）**：直连模型时服务端的运行提不出退款卡（stub 与 dsh 能）。是有意还是漏接？本单没动。
