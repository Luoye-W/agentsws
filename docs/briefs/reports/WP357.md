# WP357 报告：DeepSeek 账号那条的模型下拉，改成从账号的模型清单取

分支 `wp/357-account-models`（从 main `f26b86d2` 起，只推分支、不合 main，决策 381）。决策 919 的后半条（Luoye 10-16：「另开小单跟官方，取不到退回写死的两个」）。

**依赖说明**：做法照的是官方 dsh **0.2.1-alpha.4** 的 `@deepseek-ai/dsh-llm-deepseek-account`（README 与 `lib/index.js`）。这一单**没有**依赖 WP354 先合：移植的代码自己就能跑，main 上装的还是 alpha.2 也照样工作。唯一跟版本有关的是"当前版本号"（见第 3 节 A），它读的是装着的那一版 dsh 账号模块的版本号——WP354 合进来后自动变成 alpha.4，不用再改这里。

## 1. 做了什么（白话）

以前：设置页「用我的 DeepSeek 账号登录」那条，模型下拉永远是写死的两个（`deepseek-flash`、`deepseek-v4-pro`），旁边还挂一句黄字「账号登录这一路不去拉清单」。

现在：照官方新做法，**登录之后去问 DeepSeek「我这个账号能用哪些模型」**（`GET https://api.deepseek.com/models`），下拉就是那几个。具体跟官方一样的地方：

- **令牌怎么用**：每次现找官方账号模块要（`resolveToken`），只放进请求头 `x-dsh-auth-token`，不跟重定向；不进日志、不进事件、不进错误信息、不落盘。
- **什么时候去问**：登上之后存这一条时问一次（最多等 5 秒）；之后用记住的那份，超过 10 分钟没更新，下次打开设置页 / 跑模型时在后台再问一次，问到了下拉自己换。换了账号就重新问。
- **问不到怎么办**（决策 919 的要求）：没登录、断网、超时、DeepSeek 回错、回的东西看不懂——**一律退回原来写死的两个**，黄字改成「这次没取到你账号的模型清单，下面是 DeepSeek 官方组件自带的两个……」。之前问到过一份、这次没问到，就继续用上一份。
- **要更新版的模型藏起来**：清单里写了「至少要哪一版」的模型，我们这一版不够就不进下拉；清单里没写版本要求、我们又不认识的新模型，也不进下拉（官方同款，防止拿到一个我们不会用的模型）。如果有人存过的模型后来变成"要更新版"，跑之前就停下说一句人话（「要更新版的工坊才能用……先换一个模型」），一个字节都不发给 DeepSeek。
- **单个模型的参数调整**：官方的 `modelOverrides`（只能调单个模型的名字 / 看不看图 / 输出上限，不能加模型、不能把被藏的放出来）一并移植了，代码里能用，但**没有界面入口**（见第 3 节 B）。
- 另外顺手跟上：清单里写了单次输出上限的，发请求时取它和我们默认 8192 里小的那个。

## 2. 改了哪些文件

- `packages/model-gateway/src/providers/deepseek-account-models.ts`（新）：移植的主体——清单解码、版本门槛、按令牌分开的缓存、退回逻辑。文件头写明出处：`@deepseek-ai/dsh-llm-deepseek-account@0.2.1-alpha.4`（MIT），以及和官方的几处差别。
- `packages/model-gateway/src/providers/deepseek-account.ts`：账号推理口能带上这份目录（列模型照清单、跑之前先过门槛、输出上限取小）。
- `packages/model-gateway/package.json` + `pnpm-lock.yaml`：加 `semver`（仓里 kernel 本来就在用，同一个版本；锁文件只多 7 行）。版本比较照官方用 semver 库，不自己写。
- `apps/server/src/models.ts`：一个品牌一份目录；拉清单那条走账号清单；新清单到了自动换下拉；存账号那条时每次重取。
- `apps/server/src/server.ts`、`apps/server/src/deepseek-account.ts`、`packages/dsh-adapter/src/deepseek-account.ts`：把"装着的 dsh 账号模块版本号"传过去；测试用的清单替身注入口；不安静模式下打 `[llm-deepseek-account]` 诊断日志（只有地址、条数、原因）。
- `upstreams.yml`：登记这次移植（升 dsh 时要对照的那一条）和对应测试。

## 3. 要 Luoye 定的事

| | 事 | 我的建议 |
|---|---|---|
| **A** | 官方拿 dsh 自己的版本号比「至少要哪一版」。我们不是 dsh 本体，我拿的是**我们装着的那一版 dsh 账号模块的版本号**（main 上是 0.2.1-alpha.2，合 WP354 后是 alpha.4；跟我们登录时报给 DeepSeek 的 `x-client-version` 是同一个号）。效果：DeepSeek 标「要 alpha.3 以上」的模型，main 上看不到，合了 WP354 就看得到 | 同意这样。我们的推理口本来就是照着装着的那版 dsh 移植的，用它的号最诚实 |
| **B** | `modelOverrides`（单个模型调参）移植了但没有入口：官方是改配置文件，我们没有这一层 | 先不做入口。真有人要调，按「能力不是功能」，以后让工坊几句话配，不做成固定设置项 |
| **C** | 内置两条的显示名：alpha.4 官方把 `deepseek-flash` 的名字改成「DeepSeek-V4.1-Flash」，我们写死的是「DeepSeek-V41-Flash」。这次按要求"退回现在写死的两个"没动。界面下拉显示的是模型 id，这个名字目前用户看不到 | 合 WP354 时顺手改成官方新名字（一行） |

## 4. 我自己拿主意的地方

1. **测试 / demo 不出网**：注入了推理替身却没给清单替身时，不建目录、直接用写死的两个（和 Files 复用那条同一条规矩），这样现有测试和 demo 一个包都不会因为这单跑到真网络上。
2. 清单问到了，但里面**全是**要更新版的模型（官方这时下拉是空的）：我们下拉保留原来那些，黄字说「你账号里现在开放的模型都要更新版的工坊才能用」。
3. 清单里没提到的模型照样放行（官方同款）——比如用户之前存的 `deepseek-flash` 某天不在清单里了，照常能跑，不会被拦。
4. 目录按品牌一份（每个品牌各问各的，10 分钟一次），没有做成整台机器共用一份——多一个品牌只是多一次很小的请求，换来不用跨品牌通知下拉更新。
5. 清单那边回 401 不清登录（官方同款）；登录有没有失效仍只看推理口 401 和账号模块自己的判断。
6. 诊断日志的"失败原因"只写错误码和我们自己拼的那句话，不把底层错误对象原样打出来（避免哪天底层错误带出请求头）。
