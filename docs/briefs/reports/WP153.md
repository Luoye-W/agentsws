## 2. 我自主做的决定（白话）

1. **人话表用名词，不用动词**：模型写的是「我用 `search_policies` 查了三轮」，换成名词读得通（「我用「规矩与政策库」查了三轮」）；换成动词「查政策」就成了「我用查政策查了三轮」。所以新表是名词口径，WP142 那张动作表（「找人」「查政策」）不动，各管各的。
2. **表外的工具名也不露**：这次运行摆给模型的工具里，表里没有的（比如自定义 MCP 服务器的工具）一律说「一个工具」。宁可少说一点，也不把内部名字上屏。
3. **兜底只改屏幕、不改事件日志**：时间线那一条换成人话；事件日志里 `run.completed.outputs` 还是模型的原话——回放、审计要的是原样。
4. **摘要：有回复就用回复第一句，哪怕这次也起草了 / 挂了变更**：派工单原话是「优先用回复第一句，没有回复才退回做了什么」。失败、中断、预算耗尽仍然先说（那是人得先知道的）。客服那条 stub 路径本来不出回复，摘要不变；模拟包里要回复的场景没有，所以基线一个数没动。
5. **红人 stub 的摘要没改**：红人 stub 的回话第一句是「YouTube 这条渠道上，我按你说的做了这几件事：」，当摘要反而比现在的「找人；找到 12 个候选；查了红人库」差。direct / dsh 下红人职责走的是新规则（回复第一句）。
6. **店主岗位上的路由**：派工单的验收是在 demo 里问一次那句话。我在 demo 上试了：店主岗位 = 「工作区所有者 + 独立站运营」，而通用职责向来不参赛，于是这句话被交给了**独立站运营**——它手里只有客服那四个默认工具，只能去翻规矩库，这和冒烟看到的「查了退货政策」对得上。所以加了一条很窄的规则：本人持有「工作区所有者」、问的又是岗位 / 职责 / 连接 / 授权 / 额度 / 分配 / 谁在做，才交给它。
7. **「最该先处理的三件事」怎么排**：出错的连接 → 缺的必需连接（最多占两件）→ 没人在岗的岗位（并成一件）→ 在岗但没划范围的人（并成一件）→ 剩下的必需连接 → 可选连接。「最多占两件」是因为 demo 里缺 5 条必需连接，三件事会全是「把 X 连上」，看不到别的挡路的事。
8. **回话减字**：职责名单、「谁要它」名单只列三个再说「等 N 条」；二十条可选连接并成一行；每个岗位都挂着的「工作区成员」不列（只有它一条的「普通成员」岗位才列）。
9. **只由店主 / 普通成员组成的岗位，在岗的人没划范围算正常**（说「整个工作区」），不当成要处理的事——这两条职责本来就管整个工作区。
10. **公共段只进服务端的运行**（每条职责、每个运行时都带）；模拟层自己拼请求，没加这一句——加了会动三个运行时的 token 基线，而模拟里的回复不给人看。
11. **站外链接**：WP142 当时定的是回话里只认站内链接；这次派工单写明「链接只许 http(s) 并加 rel=noopener」，按新的来——`ReplyMarkdown` 认 http(s)（新窗口 + noopener），`LinkedText` 本身不动（别处还在用）。

## 3. 需要 Luoye 定的事
