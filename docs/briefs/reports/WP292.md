## 1. 实现清单

1. **`release.yml`（publish 作业）**
   - 「收拢」一步多写一份 `release-meta.json`（tag、版本、渠道、是不是 dry-run、官网渠道 `SITE_DOWNLOAD_CHANNEL`、桶 `R2_BUCKET`、run id）。
   - 收拢后的整套产物（`artifacts/` 里的安装包、blockmap、zip、`latest.yml`、合并后的 `latest-mac.yml`，加上 `downloads.json` 与 `release-meta.json`）**真发版也留成 artifact**：真发版叫 `release-bundle`，dry-run 仍叫 `release-dry-run`；都留 14 天。
   - 「检查 R2 凭据」改成三态（只看有没有，不打印值）：**三个都没填** → 不报错，跳过「上传到 R2」与「更新官网 downloads.json」两步，照常建 GitHub Release，摘要里写一句「R2 交给本机 `scripts/release-upload-r2.mjs`」并给出带这次 run id 的两行命令；**三个都填了** → 行为不变；**只填了一部分** → 照旧红（配错了）。
2. **`scripts/release-upload-r2.mjs`**（新）：`--run <run_id> | --dir <目录> [--channel beta|stable] [--dry-run] [--upload] [--bucket] [--base] [--repo] [--keep]`
   - `--run`：`gh run download <id> -n release-bundle` 取到自建的临时目录（跑完删，`--keep` 留）；`--dir`：读本地目录（release-bundle 的形状，或者全摊在一个目录里都行）。
   - 先核对：以 `latest.yml` 的版本为准，复用 `release-manifest.mjs` 的产物自检（缺 Windows 包 / blockmap / 哪个 mac 包、yml 版本不对、两份 mac 没合并都拒），再对 `downloads.json`、`release-meta.json`、`--channel`，对不上就一个都不传。
   - 顺序与 release.yml 原来的 R2 两步一样：`<渠道>/*.exe → *.dmg → *.blockmap → *.zip`（`public, max-age=31536000, immutable`）→ `<渠道>/latest-mac.yml → <渠道>/latest.yml → <渠道>/downloads.json`（`no-cache, max-age=0`）→ 根目录 `downloads.json`（stable，或渠道 = 官网渠道时；与 CI 原条件一致）。content-type 也照抄原来的。
   - 每个对象：`wrangler r2 object put <桶>/<key> --file … --cache-control … --content-type … --remote`，环境一律 `CI=true WRANGLER_SEND_METRICS=false`、去掉 `CLOUDFLARE_API_TOKEN`（顺手也去掉老名字 `CF_API_TOKEN`），只走 `wrangler login` 的 OAuth。wrangler 用仓库里 `apps/cloud-worker` 那份（4.134，`pnpm install` 后就有）。
   - 中途哪个传挂了就停：排在后面的不动，`latest*.yml` 最后才换，客户端看不到半截版本。
   - 传完用 `curl` 取 `<base>/<渠道>/latest.yml`、`latest-mac.yml`（带查询串躲缓存）核版本；根目录 `downloads.json` 传了也核。不对就退出码 1。
   - 开传前查大小：任何一个对象超过 wrangler 单对象上限 300 MiB，一个都不传（dry-run 也报）。
3. **内容包也一样（追加，coordinator 10-10 要求）**
   - `release.yml` 的 `content` 作业：三个 `R2_*` secret 都没填 → 跳过「传到下载站」，**GitHub 镜像（`content-<渠道>` Release）照传**，摘要写本机命令；只填一部分照旧红；都填了不变。artifact `content-pack` 里多一份 `release-meta.json`（渠道、这趟打不打算发 `upload`、桶、run id）。
   - 脚本加 `--content`：`--run <id>` 取那次运行的 `content-pack`（或 `--dir` 给 `out/content` 或 `r2/<渠道>` 那一层）。**先跑 `node scripts/content-pack.mjs verify --dir r2/<渠道> --builtin`（应用里内置的公钥），验不过一个都不传**（dry-run 也先验）；渠道以清单为准，与目录名 / `--channel` 对不上就拒；那次只打包自检（`upload: false`）的只能看计划。
   - 顺序与缓存头照原 content 作业：`content/<渠道>/blobs/*`（`application/octet-stream`，一年 immutable）→ `content-manifest.json.sig`（`text/plain`，no-cache）→ `content-manifest.json`（`application/json`，no-cache）。传完取回远端清单核序号、取回签名与本地逐字比对。
   - 验签要 `packages/skills/dist` 与 `packages/contracts/dist`，本机先 `pnpm exec tsc -b packages/skills`。
4. **自测** `scripts/release-upload-r2.test.mjs`（安装包 12 条 + 内容包 7 条，共 19 条，不出网）：参数；计划的目录 / 顺序 / cache-control / content-type；根目录 downloads.json 的条件；wrangler 命令行与环境（没有令牌、CI=true、不发统计）；各种对不上就拒；端到端用临时目录里的**假 gh / 假 wrangler / 假 curl**（假 wrangler 把对象「传」进一个临时目录，假 curl 从那里取，校验看到的就是刚传的东西）：默认 dry-run 一次 wrangler / curl 都不调、`--upload` 顺序全对、中途挂了 `latest.yml` 没动、远端版本不对就红、超 300 MiB 一个不传（稀疏文件）、dry-run 产物能演练不能真传。
   内容包 7 条：目录 / 顺序 / 缓存头 / 类型；直接给 `r2/<渠道>` 也认；渠道对不上就拒；默认 dry-run 只取产物与验签、不调 wrangler / curl；`--upload` 验签在 wrangler 之前、顺序全对、取回清单与签名都对；验签替身失败时 dry-run 与 `--upload` 都一个不传；`upload: false` 只能看计划；**再用真的 `content-pack.mjs verify --builtin` 验一份假签名的包，必须拒、一个不传**（需要 dist，没编过就跳过；本机编过，跑了）。

## 2. 我自主做的决定（白话）

1. **默认只打印计划，真传要多加 `--upload`。** 派工单里「默认 dry-run；`--run` 才传」和「`--run <run_id>` 是取产物」两处说法打架，我按更安全的读法：`--run` 只管从哪取，传不传另由 `--upload` 决定；`--dry-run` 也认（与 `--upload` 同时给按 dry-run）。所以第一次跑不会误传。
2. **`--channel` 只作核对，不当改写。** 渠道写在 `downloads.json` 的链接与客户端读的目录里，硬改成别的渠道会让链接 404，所以和版本号推出来的渠道不一致就拒。
3. **CI 多留一份 `release-meta.json`。** 本机脚本靠它知道官网放哪个渠道、桶叫什么、是不是 dry-run，不用 Fable 再手敲。
4. **只看计划时也认 dry-run 那次的产物**（`release-dry-run`），方便第一次真发版前先手动触发一次 dry-run 演练整套计划；真传只认真发版的 `release-bundle`。
5. **只填了一部分 R2 secret 仍然红**：那种情况多半是填错了，悄悄跳过反而会让人以为 CI 传了。

## 6. 未完成 / 已知限制

- **单个对象上限 300 MiB**（wrangler 的 `r2 object put`）。仓库里没记过真实安装包多大；如果哪天某个 dmg / exe / zip 超了，脚本会在开传前拒掉，那时要换分片上传（得用 S3 兼容口，也就要令牌了）——到时候再议。
- 没有真 R2 环境的端到端；第一次真发版就是它的第一次实跑，见下面的顺序。
- OAuth 身份如果能看到不止一个 Cloudflare 账号，wrangler 在 `CI=true` 下不会问，会直接报「有多个账号」：那就在那条命令前加 `CLOUDFLARE_ACCOUNT_ID=<账号 id>`（不是机密，脚本原样透传）。

## 7. Fable 第一次真发版的顺序（安装包 + 内容包）

1. 本机仓库根 `pnpm install`（拿到 `apps/cloud-worker/node_modules/.bin/wrangler`）、`pnpm exec tsc -b packages/skills`（内容包验签要用 dist）；确认登录身份：`CI=true WRANGLER_SEND_METRICS=false env -u CLOUDFLARE_API_TOKEN apps/cloud-worker/node_modules/.bin/wrangler whoami`。
2. `gh secret list` 确认 `R2_ACCESS_KEY_ID / R2_SECRET_ACCESS_KEY / R2_ACCOUNT_ID` 三个**都没有**（只看名字）。
3. （建议）演练：`gh workflow run release.yml -f tag=v0.2.0-beta.1`（dry_run 默认勾着，不传任何东西）→ 绿了以后 `node scripts/release-upload-r2.mjs --run <那次 run id>` 看计划（会标明「dry-run 产物，只能看计划」）；顺便看一眼各文件大小都在 300 MiB 以内。
4. 推 tag（Luoye 定的那个，WP218 建议 `v0.2.0-beta.1`）：`git tag v0.2.0-beta.1 && git push origin v0.2.0-beta.1`。
5. 等 `release.yml` 绿（GitHub Release 已建、摘要里有两行命令）；`gh run list --workflow release.yml -L 1` 拿 run id。
6. `node scripts/release-upload-r2.mjs --run <run_id>` 看计划，对一下版本、渠道、对象数。
7. `node scripts/release-upload-r2.mjs --run <run_id> --upload` 真传；最后一行 `✓ https://dl.agentsws.com/beta/latest.yml 已是 0.2.0-beta.1` 才算完。
7b. 内容包（同一次运行里 `content` 作业绿、摘要里有「内容包的 R2 交给本机」才需要；没有审过可打的内容就没有这一节、跳过）：`node scripts/release-upload-r2.mjs --content --run <run_id>`（先用内置公钥验、看计划）→ 加 `--upload` 真传；最后一行 `✓ …/content/beta/content-manifest.json 已是序号 N` 才算完。
8. 抽查缓存头：`curl -sI https://dl.agentsws.com/beta/latest.yml | grep -i cache-control` 应是 `no-cache, max-age=0`；安装包应是一年 immutable（确认 Cloudflare 缓存规则没盖掉）。
9. 照 WP218 清单：重新构建部署一次官网（构建时才取 `downloads.json`）。
