## 1 一句话

IM 里问「Reddit 运营今天有没有什么需要我处理的」，现在回的是**那个岗位今天的情况**（「「社媒运营」今天：2 张卡等你定，1 个待办，1 件在做。最近：…」+「去工作台处理：…/positions/social-media」），不再是秘书那句「这是专业问题，去问岗位」。交代一件事（「帮我回一下那条评论」）在那个岗位建任务，聊天里回「已记成「社媒运营」的任务，在工作台确认。」+ 事项链接。闲聊 / 日程 / 问同事仍走秘书。钉钉、企业微信补上了判死重连、`im.disconnected` / `im.reconnected`、「收到，我查一下」。事件里的飞书 open_id、钉钉 / 企微 userid、会话 id 只剩加盐哈希。

## 3 自主做的决定（白话）

- **问谁不调模型**：用规则判（点名 → 岗位；工作词 → 主要岗位；闲聊 / 个人的事 → 秘书）。IM 里每句话多等 4 秒判断不划算，判错的代价也小（问错了换个说法再问）。
- **问状况不起模型**：「今天有什么要我处理的」这类，答案就是岗位页上那几个数，直接算出来更快更准、不花钱；别的工作问题才起一次当场问答。
- **交代型建完任务就开始跑**（与岗位页上一样），要出卡也是在工作台定，聊天里一个字都不往外发。
- **企业微信的「收到」用流式回复**：普通回复一条消息只能回一次，流式回复同一个 req_id 可以先开后刷——答案出来会把「收到，我查一下」那句换掉，群里不多一条。
- **企业微信被顶掉就停**：同一个机器人只能有一条连接，两台电脑都开着会互相踢；停下、卡上说清楚，比来回抢强。
- **哈希字段换了名**：`actor_external_id` → `actor_hash`（不是同名换值），以后看事件一眼知道这是哈希；老事件不动。
- **会话 id 也哈希**：派工单只说账号 id，但个人微信的会话 id 里就拼着对方的 id，钉钉 / 企微的兜底去重键也拼着，一并换掉更省心。
