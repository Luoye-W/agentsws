# WP355 报告：指定的模型用它自带的联网搜索（第一版只有 ChatGPT 订阅）

分支 `wp/355-nativesearch`（worktree `agentsws-wt/wp355-nativesearch`），Claude 子代理。没合 main、没打 tag、没发版。真账号没跑，实测脚本写好了，交给主会话或 Luoye 跑（第六节）。

## 一、一句话

工坊里有一张名单，写在代码里，用户没有开关。名单里的模型来源，AI 要上网搜索时先用这家模型自带的搜索；第一版名单里只有「用 ChatGPT 订阅登录」一家。其余来源（DeepSeek、工坊积分、各家 API key、Claude 订阅）照旧走 WP353 那条链：内置浏览器 Google → Bing → 云端 Google → 公开搜索服务。自带搜索搜不成，就自动退回那条链，结果里照实写这次的结果来自哪一路。

**有一件事要先说清楚（决策 938）**：现在产品里还没有任何一次运行会用 ChatGPT 订阅当模型。WP90 当时留了一个尾巴：订阅模型只能在设置卡里选，进不了「默认模型」下拉。所以这一单做完以后，自带搜索在产品里暂时触发不了。等订阅模型能被选来跑活，这条路会自动生效，不用再改搜索这一层。

## 二、现在怎么搜（白话）

1. **先判名单**：看这次运行用的是哪个模型来源（就是运行请求里模型那一格的 provider 名）。随便聊、助理、品牌分析、出卡前查这几处，用的是品牌默认模型那一条。名单只认 `openai-codex`，也就是 ChatGPT 订阅登录。
2. **先查 7 天缓存**：和 WP353 是同一份缓存。同一句话、同一市场语言，7 天内搜过就直接用上次的结果，不管上次是哪一路搜到的（决策 940）。
3. **名单里的来源，先问 ChatGPT 自带搜索**：
   - 用**这个人自己**的 ChatGPT 订阅。订阅账号按人分开，不借别人的。
   - 请求发到 ChatGPT 订阅本来就用的那个地址（`chatgpt.com/backend-api/codex/responses`），在请求里加上 OpenAI 官方的 `web_search` 服务端工具（Codex CLI 自己用的就是这个），然后请模型把搜到的页面一行一条列出来。
   - 来源只认 ChatGPT 真搜到的那几块：搜索记录块和引用标注。模型在正文里自己写出来的网址一概不收。摘要取引用所在的那一行。
   - 搜索语言照决策 922 办：按品牌主市场把语言和市场写进这一问，比如德国品牌写「语言 de、市场 DE」；中文查询写 zh-CN，不带市场。
   - 结果照旧按「网址 / 标题 / 摘要」交回。官方 `web_search` / `web_fetch` 两个工具的样子一个字没改。
4. **搜不成就退回 WP353 的链**：没登录、出错、超过 40 秒、这一小时已经搜了 60 次、模型没真的去搜、搜到的都不在 `site:` 指定的站上，这些情况都只记一句，接着走内置浏览器那条链，不让这一次失败。结果开头会写成这样：「这次的结果来自公开搜索服务。前面没用上的：ChatGPT 自带搜索 这次没搜成（还没用 ChatGPT 订阅登录）。」
5. **节流在我们这一层**：自带搜索全进程同一时刻只搜一次，每小时最多 60 次。这和内置浏览器那条队是分开的两条。
6. **审计与用量**：`web.searched` 审计照旧，只记查询串。自带搜索花的是订阅额度，不扣工坊积分，所以照 WP179 的口径补记一笔 `model.usage`（用途 `web_search`，记 token，花费 0），用量页能看到。
7. **公司档 / 托管档**：不用个人订阅，直接走 WP353 的链。

## 三、令牌怎么管（没碰）

- 这一单**没有一行代码读或打印令牌**。请求走官方 `pi-ai` 的 `openai-codex`，和订阅运行用的是同一个、同一版 1.1.0。令牌由 pi-ai 自己从本机加密库那条 `llm-pi-ai/openai-codex` 记录里取；快过期时它自己刷新，再经凭据层写回。
- 我们只用了 pi-ai 公开的两个口：一个往请求体里加 `web_search` 工具，另一个只读地收结果块。
- 测试里查过：结果、请求体里都找不到令牌，令牌只在 pi-ai 自己加的请求头里。

## 六、实测：脚本写好了，没跑真账号

脚本：`scripts/live-codex-search.mjs`。它不起服务进程，不碰 4317，不碰别的连接，只打 ChatGPT 订阅那一个地址，花的是订阅额度，不花钱。脚本不读令牌、不打印令牌；输出前还会再过一遍脱敏，像令牌的长串一律换成 `***`。先跑一次 `npx tsc -b`。

查询：`site:reddit.com smart glasses`、`INMO Air3 review reddit`、`site:linkedin.com INMO`（这三条按美国市场）、`smarte Brille Test`（德国）、`INMO 智能眼镜 国内 竞品`（中文、不带市场）。

两种跑法：

1. **用 dev-real 里已登录的那一份**（密钥只经环境变量进来，脚本不打印）：
   ```bash
   ( set -a; . "$HOME/Library/Application Support/agentsws-dev/.env.local"; set +a; \
     node scripts/live-codex-search.mjs --data-dir "$HOME/Library/Application Support/agentsws-dev" \
       --variants --out docs/assets/web-search/codex-native-2026-10-16.json )
   ```
   这一份的前提是已经在 dev-real 工作台「设置 → 模型」用 ChatGPT 订阅登录过。脚本只看「哪个人登录过」，看的是记录名，不是值。库里登录过不止一个人时，用 `--person <id>` 挑一个。
2. **临时登录一次**：桌面安装版的密钥在钥匙串里，脚本拿不到，就用这一种。临时目录加临时密钥，跑完整个删掉：
   ```bash
   node scripts/live-codex-search.mjs --login --variants --out docs/assets/web-search/codex-native-2026-10-16.json
   ```
   屏幕上会出一个网址和一串码，用手机打开、输入、确认即可。

`--variants` 会让第一条查询再用三种写法各试一次：不写 `external_web_access`、加 `include: web_search_call.action.sources`、加 `user_location`。目的是看 Codex 后端认哪种写法。现在默认用的是 Codex CLI 的写法（`{type: "web_search", external_web_access: true}`），后端认不认要靠这次实测。屏幕上每条一行：多少条、几条有摘要、用了多久、来自哪些站。完整结果写进 `--out` 那个 JSON，跑完把它附进这份报告即可。

**如果默认写法被后端拒了**（报 400 之类）：先看 `--variants` 里哪一种过了，改 `native-search.ts` 里 `withCodexWebSearch` 的缺省值，一行就够。如果几种都不行，就走决策 939 的备选。

## 七、我自己做的决定（白话）

- **用 Responses 的 `web_search` 工具，没用 `/alpha/search` 口**：派工单点的就是前者；它是 OpenAI 公开的工具，Codex CLI 自己也在用。请求走官方 pi-ai，令牌、刷新、请求头都不经我们的手。`/alpha/search` 是 Codex 没公开的内部 alpha 口，要我们自己拿令牌拼请求头，不合「不碰令牌」，留作决策 939 的备选。
- **结果解析借社区插件，不自己写**：`dsh-web-search-diy` 的 `mapResponsesResponse` 已经在好几家实测过，「模型没真的去搜、凭记忆答」也会被它判出来，判出来就退回 WP353 的链。我们只在外面补两样：摘要（取引用所在那一行）和去掉 OpenAI 给网址挂的 `utm_source=openai`（不然同一页会按两个网址算两条）。
- **名单放在服务端搜索那一层**（`apps/server/src/web-browser/native.ts`），不放在 dsh 适配层：判名单、退回、缓存、节流、审计都在服务端这一层，名单和它们放在一起，以后加一家改一处就够。
- **「模型来源」就是运行请求里模型那一格的 provider 名**：dsh 那一层也是按这个名字（`openai-codex`）决定挂不挂订阅适配器，两边认的是同一个东西。
- **用这个人自己的订阅**：订阅登录本来就按人分开存（WP90），不借别人的。没登录就连那棵登录树都不起（不必为一次搜索装一遍 dsh）。
- **问自带搜索用同一个模型**：运行用什么模型就用什么，目录里没有就退回 `gpt-5.5`（设置页默认那个）。推理力度设成低，省额度、快一点。
- **自带搜索单独一条节流队**：同一时刻一次，每小时 60 次，不另加随机间隔，因为它不开网页，不会被搜索引擎拦。它和内置浏览器那条队分开，互不占名额。
- **40 秒不回就放弃，走 WP353 的链**：官方工具给一次搜索 60 秒，这里留出 20 秒给后面那条链。
- **7 天缓存不分是哪一路搜到的**（决策 940）：订阅用户问同一句话，7 天内不再花订阅额度重搜。
- **花的订阅额度照记一笔用量**：照 WP179 的口径，`model.usage` 用途 `web_search`，记 token，花费 0。用量页能看到 ChatGPT 订阅被搜索用掉了多少。
- **系统提示「网页」那一段没改**：那里写的是「每一次都会在工坊的内置浏览器里打开一次搜索页」。对 ChatGPT 订阅的运行来说这句不准，但它的用意是「别重复搜」，意思还在。要改得动契约（`RunWeb` 加一格），模拟基线也会跟着变；等订阅模型真能跑活（决策 938）时一起改。

## 八、要 Luoye 定的事（938–940）

- **938　订阅模型现在还不能被选来跑活，要不要接着做？** WP90 留了一个尾巴：ChatGPT / Claude 订阅登录以后，只能在那张卡里选模型，进不了「默认模型」和按用途的下拉。所以岗位运行、随便聊、助理现在都不会用订阅跑，这一单的自带搜索在产品里也暂时触发不了。代码已经接好，那一步一通，这条路就自动生效。
  **建议**：开一小单，让 ChatGPT 订阅进「默认模型」下拉。要做的是网关那一跳（订阅不走 OpenAI 兼容客户端，走 dsh 的官方订阅适配器）和设置页一行；做完用第六节的脚本加一次真跑验收。
- **939　如果实测发现 Codex 后端不认 `web_search` 工具，要不要改用 Codex 内部的 `/alpha/search` 口？** 社区插件 `dsh-codex-subscription`（MIT）用的就是这个口，回来的结果直接带网址、标题、摘要。代价有三条：它是没公开的 alpha 口，随时可能改；要我们自己拿令牌拼请求头，和这次「不碰令牌」的做法不一样；会不会更容易被 OpenAI 限流，我判断不了。
  **建议**：先看第六节实测。`web_search` 工具能用就不碰 `/alpha/search`；不能用再开一小单接它，令牌照旧只在服务进程内存里，用完就丢，不落日志。
- **940　自带搜索的额度规矩**：现在是每小时最多 60 次；7 天缓存不分是哪一路搜到的，订阅用户问同一句不再重搜；用和运行同一个模型问（默认 `gpt-5.5`），推理力度设低。这几样都花用户的 ChatGPT 订阅额度。
  **建议**：先照这样。等有真实用户的用量（用量页里 `web_search` 那一栏）再调。
