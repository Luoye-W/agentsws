## 1. 实现清单

**交付 1：插件采到的内容数据进云端公共库**

- **契约**（`packages/contracts/src/kol-public.ts`，只加）：新类型 `PublicContentObservation` 和白名单 `PUBLIC_CONTENT_OBSERVATION_FIELDS`。白名单只有 15 格：渠道、作者 handle、内容 id、类型、标题、发布时间、时长、横竖、播放、点赞、评论**数**、分享、`paid_promotion`（含付费推广标识）、`shoppable`（带货入口）、观测时间。**没有**评论文本、页面地址、封面地址、作者名，也没有用户备注。`PublicContentSample` 加两个可选标识。`ContributionEvent.kind` 加 `content`。
- **库**（`packages/kol-public/src/store.ts`）：
  - 新增伴生口 `KolContentStore`，内存和 sqlite 两份都实现，用 `isContentStore` 判断。
  - 带货 / 广告标识放进旁表 `kol_content_flags`，不 ALTER 主表：NULL = 没采到，0 = 看过、没有，1 = 有。
  - `contentMetricOnDay` 按 UTC 日查同一条内容有没有记过。
  - 删一个人时，旁表的行一起删；要求移除过的人，内容也不收。
- **服务**（`service.ts` 的 `contributeContent` / `contributeContentAs`）：
  - 幂等键 = 渠道 + external_id + observed_at 的 UTC 日。同一天重复报只刷新卡上的数：不多记指标行，也不算奖励。
  - 离线补传的旧观测不会盖掉新数，但会补上库里空着的格子。
  - 日配额和红人观测合算，贡献返额度的口径也一样（每 100 条有效观测 1 积分，`granted` 类，每天封顶）。
  - 任意一条不合格，整批拒。
- **路由**（`routes.ts`）：
  - `POST /v1/data/kol/content-observations`：用工作区令牌，本机转发走这条。
  - `POST /v1/data/kol/plugins/content-observations`：用插件令牌。
  - 两条都不收费，也不在入口预扣表里。
- **KolPublicDO**（`apps/cloud-worker/src/kol-public-do.ts`）：
  - 不加 binding，`wrangler.toml` 没动。新表都是 `CREATE TABLE IF NOT EXISTS`，DO 唤醒时自己建。
  - 加了只读标记 `contentReady`，头注释写明内容路怎么走。
  - 返额度那一笔照旧由录音机记下，带回 `WalletDO`。
- **本机**：
  - `apps/server/src/extension-service.ts`：`contentObservation` 先落本机，登录了云账号就转发。规则和红人观测一样：没登录不送，没有第二个开关。回执加一格可选的 `forwarded_to_public_library`。
  - `apps/server/src/extension-contribute.ts`：加可选的 `contributeContent`，逐键写出窄行（不用 spread）。
  - `packages/api`：`ExtensionContentObservation` 加两个可选布尔（schema 仍是 `.strict()`）。本机 `content_observation` 行多记时长、发布时间和两个标识。
  - SDK 重新生成；ontology 只变了摘要。

**交付 2：体检报告样本不够不收钱**

- `service.ts` 的 `audit` / `deepAudit` 合进同一个 `chargedAudit`：先出报告，再判断收不收。
- `insufficient_samples` 时，报告照出，`credits` 为 0，`note` 末尾接一句「样本不够，这次不收。」（常量 `AUDIT_NOT_CHARGED_NOTE`）。界面显示的就是 `note`，本机 `kol-public-client` 把它放在 `findings[0]`，所以哪个界面都看得到这句话。

**文档**：`docs/75` §2 记了体检的口径，也写明两条内容路不收费、照样返贡献额度；`docs/76` §10 删掉「云端只收红人观测」，换成内容上云的完整说明（送哪几格、不送哪几格、幂等键、回执新字段）。

## 2. 自主做的决定（白话）

- **幂等的桶按 UTC 自然日**，和本机 `content_observation` 的「同一天只记一行」一个口径。
- **同一天有人报过的内容，再报不算奖励**。不分是谁报的：一条事实只奖一次。否则同一条视频刷新十遍就能刷积分。红人观测是「同一个贡献者 24 小时」，这里故意更严。
- **本机当天去重了，照样转发**：云端是幂等的，重复送只刷新数字；上次云连不上没送成的，这次就补上。代价是同一条视频当天多几次请求。
- **不送页面地址、封面地址、作者名和粉丝数**：地址里带平台的一次性参数（分享 id、签名封面）；作者信息走红人那条路。标题照送，它是创作者给自己作品起的名字，公共库原本就存。
- **认不出作者 handle 就不送**：YouTube 上只有 `UC…` 频道 id 的，送上去会在公共库凭空多出一个叫 `uc…` 的人。页面上「3 天前」这种不是时间戳的发布时间，那一格不送，否则云端会整批拒。
- **广告 / 带货标识名叫 `paid_promotion` / `shoppable`，是可选布尔**。现在的插件还不采这两格（私有仓库里查过）。契约先留好口子，WP130 或之后的插件单接上就行。
- **标识进旁表，不改 `kol_contents`**：沿用这个库「旁表，不 ALTER 主表」的惯例，DO 上不需要迁移。
- **内存档也实现了内容写路**：这组方法是逐行读写，不是聚合，插件这条路在测试和 `bin/dev.mjs` 里也要能走通。服务端只在库完全没有这组方法时回 501。
- **经工作区令牌报上来的内容，来源记成 `plugin`**：这条路唯一的调用方就是本机转发插件的数据。红人观测那条路记的是 `manual`，两边不一致，请审核时看一眼。
- **「样本不够」只认 `insufficient_samples`**。样本够、只是同量级可比的人不到 k（分位缺）的，照价收：粉丝真实度是完整结论，报告里已经说清缺的是和别人比。
- **不收钱的体检不记计量事件**，和「0 条不收钱」「基准桶不够 k」的现有写法一致。
