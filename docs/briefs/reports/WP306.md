# WP306 报告：飞书绑定后问话没有任何回复

分支 `wp/306-feishu`（worktree `../agentsws-wt/wp306-feishu`），从 main `60327195` 起。没推送、没合并、没打 tag、没发版；没连真飞书、没碰 4317、没读 .env。

## 1 根因（真机已对上）

**一条代码路径上叠了三个洞，任何一个都会让它一声不吭；真机上是第一个先撞上。**

1. **名册没刷新就问秘书 → 抛「这个人不存在」。** 服务端 `askAgent` 直接调秘书**内核**的 `secretary.ask`。内核只认一份名册（`dir.members`），而这份名册只在秘书**端口**的方法里刷新（`port.ask` / `myProfile` / `people` …，也就是有人打开过人员 / 日程 / 个人资料页时）。服务进程起来之后没人打开过那几页，名册就是空的，第一句检查 `isMember(person_id)` 就抛 `SecretaryError(not_found)`。抛在 `#run` 之前，所以连 `run.*` 都没有。
2. **名册刷新了也会抛：秘书的事件不带 trace_id。** 秘书内核发事件时 `correlation.trace_id` 是 `''`，HTTP 请求里由网关的 trace 作用域补上；IM 这一路不经过网关，空 trace_id 被事件日志拒收（`KernelError: event requires a non-empty correlation.trace_id`）。修完第 1 个、本机复现时撞出来的——只修第 1 个，Luoye 那句照样没回。
3. **抛出来的异常被「重试队列」吞掉，而且一条事件都不记。** `answerInbound` 故意不 catch（注释写的是「抛 = 管线退避重试 ≤ 5 次、耗尽进死信」）。可 IM 那几条管线的重试队列**没有人推**：`pump()` 只在收信那一轮对**邮件**管线调。所以失败的那一条就停在队列里，重试一次都不会发生，也进不了死信；管线在「第一次尝试失败」这一步不记任何事件。结果就是 Luoye 看到的：不回话、没有 `im.answered`、没有报错、没有 `run.*`。
   - 顺带发现的连带问题：邮件管线和 IM 管线**共用一张队列**，邮件管线 `pump()` 时会把 IM 的那条也领走、拿**邮件的** `onEvent` 去处理（可能把一句飞书问话当成客服信开事项）。Luoye 那台机器没连邮箱所以没撞上。

**真机证据**（Fable 10-13 远程查 events.db）：`inbound.received`（channel=feishu，p2p，text）有四条：13:35:58Z、13:37:42Z（绑定那句）、**13:38:13Z（问 Reddit 运营那句）**、**13:52:56Z（「你好」）**，之后没有 `im.answered`、没有错误、没有 `run.*`——消息到了我们、在问秘书那一步丢的，和上面第 1 + 3 条完全对得上。本机用真服务进程 + 假飞书长连接按同样步骤（绑定 → 问话）复现：一模一样，回复只有「绑好了」，事件库只有两条 `inbound.received`。

**长连接这次是好的，但同样有一个会静默的洞（按 Fable 的线索查实，一并修了）**：官方 SDK `@larksuiteoapi/node-sdk` 1.74 的 `WSClient` 每隔 `PingInterval`（飞书服务端下发，常见 120 秒）发 ping，但**默认不判 pong 没回**（`wsConfig.pingTimeout` 不给 = 不判，SDK 源码原文）。走代理（Luoye 机器上 Clash 的 fake-ip，远端 198.18.0.5）时上游断了、本地那一头不 close，SDK 就一直以为连着：不重连、`onReconnecting` 不触发、卡片一直绿勾，之后的消息全丢。本机用**真 SDK** 对一个「收下连接后一帧都不回」的本地长连接做了对照：老配置 3 秒里一直报「连上」，新配置 1 秒判死、自己重连、状态跟着变。

## 3 自主做的决定（白话）

- **不再「抛给管线重试」**：IM 问话失败直接回一句人话、让人重问，而不是排进队列等重试。理由：IM 那条队列本来就没人推；就算有人推，一分钟后突然冒出一句旧答案也让人摸不着头脑。超时那种「答案晚到」例外——晚到了补发，并标明是刚才那个问题。
- **「收到，我查一下」只在 1.5 秒内没答出来时才发**：答得快就只回答案，不多一条消息（决策 446）。
- **没有「最近用的品牌」可用**：系统里没记这个，所以同名岗位跨品牌时按「机器人所在品牌优先」挑，并在答案里说一句（决策 448）。
- **共用队列的 `pump` 修了**：顺手修，免得 Luoye 机器上卡在队列里的那两句，将来连了邮箱后被邮件管线当客服信处理。那两句会一直留在队列里不动（不会再答，也不会误处理）。
- **判死只做了飞书**：钉钉 / 企业微信的长连接是我们自己写的，有没有同样的洞没查（决策 451）。

## 4 要 Luoye 定的事

- **446「收到，我查一下」什么时候发。** 现在：1.5 秒内答不出来才发，答得快就只回答案。另一种是每句都先回「收到」。**建议保持现在这样**（少一条消息）。
- **447 IM 里问岗位的工作问题，答得还不像样。** 修好之后「Reddit 运营今天有没有什么需要我处理的」会回秘书的规则版：「这是社群管理的专业问题，秘书不答——去问社群管理岗位的 Agent。」——有回话了，但没回答他想知道的。原因：IM 一直接的是秘书（41 §1，替人答「他在忙什么、什么时候有空」），不是岗位 Agent；点名路由现在只是把「用哪条分配去问」挑对了。**建议另开一单**：IM 里点名岗位的问题直接问那个岗位的 Agent（起一次只读运行，读这个岗位今天的卡 / 待办 / 进度，答一句 + 深链），秘书只答「人」的问题。
- **448 同名岗位在好几个品牌时怎么挑。** 现在：问题里带了品牌名按品牌名；否则机器人所在品牌优先，答案后补一句「这次按哪个品牌答的」。另一种是回一句让他选。**建议保持现在这样**（不打断他；补的那句告诉他怎么换）。
- **449 问代理最多等多久。** 现在 90 秒，过了先回一句 + 工作台链接，答案晚到再补发。**建议保持**。
- **450 长连接判死的快慢。** 现在 ping 后 30 秒没回判死（最坏约两分半发现断了）。更快要更频繁地 ping（飞书服务端下发间隔，我们改不了），或者把 30 秒改小（网络抖一下就重连）。**建议保持 30 秒**。
- **451 钉钉 / 企业微信要不要同样补「判死 + 断线事件 + 收到」。** 这一单「永不静默」与诊断事件三条渠道都有，但判死、`im.disconnected` / `im.reconnected`、「收到，我查一下」只做了飞书。**建议下一单补**（钉钉 / 企业微信的长连接是我们自己写的，要先查有没有同样的假活）。
- **452 断着的时候发来的消息补不补。** 飞书文档只写了「3 秒内没处理完会重推」，**没写**长连接断开期间推不到的事件重连后会不会补推（未核实）；我们自己补收要申请读历史消息的权限。**建议不补**：卡片如实显示「断了，在重连」，帮助文档写「连上后再问一次」（已写）。
- **453 `inbound.received` 里带着飞书 open_id。** WP211 说「聊天账号 id 不进事件」，但管线那条 `inbound.received` 一直带着 `actor_external_id`（飞书 open_id，应用内的假名 id）。本单新加的事件都没带。**建议改成只记哈希**（另开小单，动的是所有渠道共用的管线）。

## 5 偏离

- 派工单「问谁」说点不出时用「启动品牌（或他最近用的品牌）里的主要岗位」：没有「最近用的品牌」这份记录，用的是**机器人所在的品牌**（每个品牌一套飞书凭据，机器人在哪个品牌，那就是他这次问的品牌）。
- 「正在输入」：飞书机器人没有这个接口；表情回应（reaction）要多开一项权限，没用，改成回一句「收到，我查一下」。
- 跨品牌只在**同一家公司、已装载**的品牌里找（`brandsOfThisOrg` + `background.isBrand`），停掉的品牌不找。
