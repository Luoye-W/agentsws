## 2. 自主做的决定（白话）

- **签的是清单原始字节，文件不单独签。** 清单里有每个文件的 sha256，签了清单就等于签了全部文件；用户端先验签再解析，不存在「解析后再序列化对不上」。
- **公钥表现在是空的，空 = 通道关着（fail-closed）。** 我不能替 Luoye 生成正式钥匙（私钥要由他保管），所以内置公钥留空；设置里照实写「这个版本还没装验签钥匙，内容更新先关着」。钥匙生成脚本给好了。表允许同时放几把，换钥按「先加新公钥随版本发 → 再换私钥 → 再删旧公钥」走。
- **防回放：清单带只增序号**（流水线缺省用当前秒数），用户端记住见过的最大值，更小的当旧包。
- **文件按 sha256 存（`blobs/<sha256>`），不打压缩包。** 不用引入解压依赖、天然去重、旧版本永远在（退回不用再下）；GitHub Release 里不能有目录，所以镜像那边平铺成 `blob-<sha256>`。
- **分界线做成机器规则**：内容包里只许说明文字类文件（`.md .json .txt .yml .yaml` + LICENSE / NOTICE / COPYING），`scripts/` `hooks/` 一律不许。打包时不打，用户端看见就整包拒收。
- **「签出去的就是审过的那一份」做成硬规矩**：登记表 `content-reviews.json` 的每条审核记录带条目摘要；打包时目录摘要对不上最新那条就不打。没审过 / 审完又改过 / 扫描命中没逐条放行的条目只是不打（列进作业摘要），不让整个发版红。
- **上传前用应用里内置的公钥再验一遍**（`verify --builtin`）：secret 里的私钥要是和发出去的应用对不上，用户一份都不会收，那就别传。
- **上传顺序：文件 → 签名 → 清单。** 签名与清单是两个文件，换的那一瞬间有个小窗口（用户端会判「签名对不上」、6 小时后自然好）；写进了 docs/90 §5.3，v2 可以合成一个文件。
- **按品牌各管各的**：设置、当前版、保留的上一版、卡、冲突都按品牌存；技能库里包基础层多一份「只属于这个品牌」的记录（`source.package = 'content-update'`），别的品牌查不到。为此 `MemorySkillRegistry` 的包层查找带上了工作区（没有品牌自己那份时退回全局那份，老行为不变——技能包 269 条测试全过）。
- **自动模式也有闸**：审核记录里有扫描命中、或本机重扫有命中的条目，选了「自动」也照样出卡。
- **退回后不再自动提同一版**（记 `skipped_version`），更高的新版照常提；设置里还能手动再更新。
- **冲突的处理**：没选之前你的那一段照旧生效（新版其余部分已经换上）；「用新版」= 去掉你那处改动；上层只是照抄了旧版那一段（没真改）的，直接跟新版走、不问人。
- **卡片细节**：内容更新卡用「改动」排版（版本前后两格 + 一句改了什么），不用「策略」排版（那个会多一句「批了才落到在岗同事身上」，对这张卡是错话）；每条内容各成一个合并族，不和别的条目合成一张（否则「合并 2 张」只露一个标题、一下更新两条）；冲突卡的选项同时写进 payload（卡片投影读那里），选的那一项按 deck 的规矩从 `edited_payload` 读。
- **开关只给桌面版**：服务进程 `AGENTSWS_CONTENT_UPDATES=on` 才查，桌面壳启动服务时给（外面显式 `off` 才关）；测试、模拟、demo 一律不查、不出网。
- **`role` / `declarative` 条目只定格式不落地**：职责 yml 是全局的一份（`roles.roles`），按品牌替换要动职责库的装配，超出这一单；规范里写死「职责条目只许改挂哪些技能，别的字段有一处不同整包拒收」，打包脚本现在不打这两类，用户端遇到跳过那一条。
- **截图用真流程**：demo 加了一个只给截图脚本用的注入点（内存里的替身更新源 + 现生成的钥匙），卡是服务端真出的、冲突是真合并出来的、退回是真点的。

## 3. 需要 Luoye 定的事

1. **生成正式签名钥匙并放好**（只有你能做）：`node scripts/content-keygen.mjs --out <仓库外路径>` → `gh secret set CONTENT_SIGNING_KEY < 那个文件` → 公钥那一行填进 `CONTENT_SIGNING_PUBLIC_KEYS` → 私钥文件备份后删。私钥放哪备份（密码管理器 / 离线）你定。
2. **内容更新的默认档**：现在是「每次问我」（照工单）。要不要在首次设置里问一次？我没加。
3. **自动模式的范围**：现在「自动」对所有审过、扫描干净的条目生效。要不要只对小版本（例如 1.2.x → 1.2.y）自动、大版本仍问？
4. **Shopify 官方技能永远不会「自动」更新**：它的官方正文本身就在讲那几个上报脚本，可疑指令扫描命中 9 处（全是禁止或说明，旁注已禁）。现在的规矩是「审核记录里有命中 → 选了自动也照样出卡」。要不要改成「审核人逐条放行过的命中不挡自动」？我倾向保持现状（Shopify 这种平台官方技能更新频率低，每次点一下不算麻烦）。
5. **哪些条目进通道**：登记表里先放了 7 份 marketingskills 改写技能 + Shopify 官方技能。open-seo 只贡献了 seo-judgment 里的三段（已随 seo-judgment 那条走）；其余自带技能（客服、B2B、品牌话术等）是我们自己写的，没进登记表——它们改了跟软件版本走。要不要也让「我们自己写的技能」走这条通道（那就不只是第三方内容了）？
6. **镜像 Release 的形态**：每个渠道一条滚动 Release（`content-beta` / `content-stable`，第一次发包时由流水线建 tag）。可以接受这两个常驻 tag 吗？
7. **截图里的英文 / 暗色**：只拍了中文浅色。
