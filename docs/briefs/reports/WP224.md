## 2. 怎么做的（白话）

- **毛利率**：公司页「品牌」那一栏多一张卡，填整个品牌的毛利率，可以按品类 / SKU 再填几格（小的盖大的）。填的东西就是知识库里的一张事实卡，Agent 检索事实卡时就能找到它。没填就是没填：投放面板那一格空着，表下面一行「没填毛利率 · 去填」，点了回到这张卡。
- **盈亏线并排**：投放的 campaign 表和日报上，ROAS 旁边多一格「盈亏线 ROAS」（1 ÷ 毛利率）。ROAS 高于现在的止损线（1）、低于盈亏线的那条后面有个小三角，鼠标停上去说「按毛利算在亏（只提示，不自动停）」。止损卡上判据旁边也并排一颗「盈亏线 ROAS 2.5（毛利率 40%）」。自动止损照旧按 ROAS < 1。
- **两周对照**：每天 23:30 给每条有数的 campaign 记一行：按现在的线会不会停、按盈亏线会不会停。老板面板上那块「两条止损线对照」按 campaign 汇总，「只有盈亏线会停」那一列就是「一直在亏钱那段不报警」的天数；满 14 天表尾写「够两周了，可以定止损线」。接口 `GET /v1/economics/line-compare` 拿得到整张表。
- **一页纸**：每周一 08:00（设置里可改），每个品牌各推一张给老板：情况 / 发现 / 影响 / 建议 / 下一步，每条发现带一个数，数上停一下看出处。数字是跑各岗位面板上那几个查询得来的（店铺销售额与订单、广告两口径、盈亏线那一列、内容按页收入、社媒近 30 天、红人归因、客服待回复），取不到的写「没接」和为什么（没人担 / 没连 / 还没出过数），不估。影响与建议只由数推出，推不出就不写。

## 3. 自主做的决定

1. **毛利率存成知识库事实卡，不另建表**。负责人填 = 他本人提一张卡并激活（同 WP159 违规宣称规则的做法），改一格旧卡退役，清一格就是退役，留痕不删。敏感度定 `internal`——投放、店铺的 Agent 才检索得到；代价是有知识读权限的职责都看得到毛利率。
2. **投放面板的盈亏线用品牌那一格**。campaign 现在没有「卖的是哪个品类 / SKU」这一格，按品类 / SKU 覆盖只在技能（改价、折扣算式）里用得上；以后 campaign 能对上品类再细化。
3. **提示图标判的是「≥ 现在那条止损线、< 盈亏线」**，止损线取这个品牌投放职责的生效额度（不是写死 1）。日报那张表按**订单口径**判（钱是订单里来的），订单口径没有才看平台口径。
4. **日报那张表原来是空的**：服务端一直没把归因两列递给面板（WP75 留的缝），真环境里「日报」永远是空表，盈亏线无处并排。照 `ads-core` 的 `attributeAds`（与模拟世界同一份判据）补上：平台口径取 campaign 表现，订单口径取今天（工作区时区）下的、带广告 UTM 的单；归不上的不分摊。
5. **「只读动作」做成快捷入口 + 报表卡**：职责 yml 的 `actions` 只收写动作，所以「本周经营一页纸」在 `common.owner` 上是一个 `kind: review` 的快捷入口（点一下让 Agent 照 `weekly-review` 技能讲给你听）+ 秘书每周推的那张 `weekly_review` 报表卡；`common.owner` 的写动作一个没加（测试钉住）。
6. **一页纸的数由服务端拼，不经模型手**（`composeWeeklyReview` 纯函数）；技能 `weekly-review` 管的是老板在对话里问「这周怎么样」时怎么讲。
7. **一页纸在老板岗位页上整张摊开**：它不属于任何事项，原来报表块的「→」只会回到岗位页本身，于是这一张直接摊开五段，不再是一行摘要。
8. **「秘书推」**落成：卡的提议人是 `agent_secretary`，发给老板；同一周再推一次是同一张卡出新一版（没归档时）或取代上一张（已归档时），不会一周两张。
9. **推送时间可改**：右栏定时面板的「改时间」只认官方规则建的任务，系统任务改不了，所以在「设置 → 通用」加了一行「经营一页纸：每 [周一] [08:00]」，只改当前品牌那一条。
10. 顺手：campaign 表与止损记录的 ROAS 列原来没写 `format`，被念成 `US$0.60`——改成倍数。

## 4. 要 Luoye 定的事

1. **两周后定止损线**：对照表从合并那天起记（老板面板「两条止损线对照」/ `GET /v1/economics/line-compare`）。满 14 天后看「只有盈亏线会停」那一列定：维持 ROAS < 1，还是改成按盈亏线（自动暂停的范围会变大）。
2. 毛利率的敏感度：现在 `internal`（投放、店铺 Agent 能检索到）。要不要收紧成只有老板与店铺看得到（那样投放 Agent 就只能看面板上那一格，检索不到原卡）。
3. campaign 要不要加「卖的是哪个品类 / SKU」一格，让投放面板按品类用各自的盈亏线。
4. 一页纸里的「影响」只写两条规则：销售比前 7 天少到门槛以上（门槛在 `common.owner` 的公司层阈值 `weekly_sales_drop_pct`，默认 20，没配就不写这条）、有 campaign 落在两条线之间。默认 20 合不合适。

## 6. 偏离

- 「只读动作」不是职责 yml 里的一条 `action`（schema 只收写动作），是快捷入口 + 报表卡（第 3 节第 5 条）。
- 补了日报那张表的数据（第 3 节第 4 条）——单子没点名，但不补的话「日报上并排两线」在真环境里看不见。
- 工具箱的「疑似重复」会把 `policy-review` 与 `weekly-review` 判成一对（名字共用 review、摘要都是「公司在用的技能」，词袋相似度过线）。名字是工作单定的没改；`catalog.test.ts` 那条用例改成只看定时任务那几对，技能那一类的误报留给后面（见第 8 节）。
- WP220 / WP222 并行：`ads/*.yml` 我只在 `skills:` 里加了一行 `unit-economics`；`THIRD-PARTY-NOTICES` / `upstreams.yml` / `bundled.test.ts` 合 main 时与 WP216（Shopify 官方技能）两边都留了。若 WP220 也登记 agency-agents，`upstreams.yml` 的 `agency-agents` 一条要合并成一条（id 唯一）。

## 7. 未完成 / 剩余限制

- 模拟世界没加盈亏线与一页纸的场景（判据都在 `ads-core` / `deck` 的纯函数里，有单测；模拟门禁无漂移）。
- 一页纸的「客服量」用的是客服面板的「待回复」那块（近 7 天的回信草稿数 + 现在还压着几封）——客服岗位没有「来信量」这一块面板。
- 对照账只在本机后台开着时记（关机那几天没有行；汇总按「记了几天」算，不补）。
