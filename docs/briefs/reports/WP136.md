## 2. 我自主做的决定（白话）

1. **谁来起 dsh：服务进程，不是桌面壳。** 服务进程本来就跑在捆绑的 Node 上，所以它用自己的 `process.execPath` 就是「用捆绑的 Node」；dsh 从 dsh-adapter 的依赖里找。这样工作台（浏览器里也行）和托盘走同一条路，桌面壳只管把网址交给系统浏览器。
2. **打开在系统浏览器里，不开桌面壳新窗口。** 桌面壳窗口的 CSP / 导航规则只放行我们自己的源，dsh 网页是另一个端口；系统浏览器最省事、地址栏看得见。
3. **Agents 工坊这个场景就是工作台本身**，不是 `$DSH_HOME/profiles/agentsws`。我们的运行时是 dsh-adapter 自己搭的最小组合，从来不走 `dsh --profile`；为了不让人混，`agentsws` 定为保留名，`$DSH_HOME` 里即使有同名目录也不列。
4. **只有网页场景能在这里打开**；`headless` / `sdk` / `sdk-minimal` / `acp` 只列名字（给程序用的，点开也没有界面），新建时可以选它们当底子。
5. **新建不启动**：用 `--from-default-profile … --dump-default-config` 让 dsh 自己建目录然后退出，不自己拼 `package.json`。
6. **名字规则比 dsh 严**：小写字母开头、字母数字短横线、≤32 字；保留 `agentsws` / `desktop` / `node_modules` / 五个模板名。中文名不行（要当目录名）。
7. **`DSH_HOME` 与 `data/` 平级而不是在里面**：备份 / 导出会整个打包数据目录，dsh 的凭据库和插件不该进去。
8. **环境变量白名单**：系统必需 + 代理（`HTTP(S)_PROXY`，国内用户常要）+ 用户自己设的 `DSH_TELEMETRY_DISABLED`；名字像密钥的再挡一遍。宿主的 `DEEPSEEK_API_KEY` 也不传（官方网页里自己在设置页配）。
9. **默认工作目录 `~/dsh-workspace`**，并且规定它既不能在也不能包含我们的数据目录 / 应用目录 / DSH_HOME，否则整个功能不装配。
10. **权限跟浏览器设置同档**（读 `store_config.read`、改 `policy.stage`，只有所有者）；不是所有者 / 这台部署不能切（托管、Docker、连公司服务器、全内存档）时，左栏那一行和托盘那一项**都不出现**，不摆一个点开是空的入口。
11. **网址里的 token**：只在 open / restart 的响应里出现一次，服务端日志只记抹掉 token 的版本；浏览器里在点击那一刻预开空标签页（等接口回来再开会被弹窗拦截），并把 `opener` 清掉。

## 3. 需要 Luoye 定的事

2. 默认工作目录 `~/dsh-workspace` 的名字 / 位置（非技术用户可能更习惯放「文稿」下面）。
3. 「Agents 工坊官方积分接口作为其他场景的模型来源」做不做（评估见 docs/79 §5：云端要一个 Messages 兼容端点，约 3–5 人日；要用单独一把可吊销、封顶的令牌）。

## 5. 偏离

1. 接口放在 `packages/api` 的路由 + `GatewayDeps.dshScenes`（仓库惯例），不是只写在 `apps/server` 里；因此多动了 `packages/api`、`packages/contracts`、`packages/sdk`、`packages/ontology`（生成物）。
2. 桌面壳「新窗口」那条没做，一律交系统浏览器（理由见决定 2）。
3. 服务进程的 `DSH_HOME` 由桌面壳设（`serverSpawnRequest`），`apps/server` 的 `main()` 不改 `process.env`；非桌面壳跑服务进程时 `DSH_HOME` 取决于宿主环境——只影响将来 WP134 的凭据库位置，场景目录本身不受影响（走 `AGENTSWS_DSH_HOME` / 数据目录旁边）。
4. `gen-sdk.mjs --check` 在这个仓库里本来就恒报「不一致」（它拿未格式化的产物比格式化后的文件），我用「重出后 `git status` 干净」代替。
5. 桌面壳 `test:coverage` 的 100% 门槛本来就没过（`api-client.ts` 里 `connections` / `setBrowserEndpoint` 两段早就没覆盖）；我新加的 `scenes` / `openScene` / 子菜单都有用例覆盖，没去补老的缺口。

## 6. 未完成

1. **进程孤儿**：服务进程被强杀（不是正常关）时，它起的 dsh 网页不会跟着退（子进程被系统收养，占着一个随机端口）；下次启动也不认领它。正常退出 / 重启服务都会先停场景。要彻底解决得记 pid 文件并在启动时核对进程身份，跨平台不好做，留给后面。
2. 托盘菜单只有模型测试，没有 Electron 真机点一遍（e2e 没加用例）；包内实测走的是服务进程 API。
3. Windows / Intel mac 没实测（捆绑 Node 只取了当前平台）；`web` 场景的起法与平台无关，但 SIGTERM 在 Windows 上等于直接结束进程（dsh 来不及优雅关机）。
4. 积分接口作为其他场景模型来源：只评估，未实现（单子要求）。

## 安装包体积差值

实测方法：`pnpm -F @agentsws/desktop package --dir`（macOS arm64）后，在 `agentsws.app/Contents/Resources/app/node_modules`（平铺）上按 `dependencies` + 非 optional `peerDependencies` + 在盘上的 `optionalDependencies` 建依赖图，从 app 的 `dependencies` 出发算可达集；把 `@deepseek-ai/dsh-web-app` 这个节点摘掉再算一遍，差集就是「只为官方 web 场景而在」的包。

| | 大小 |
|---|---|
| 只为 web 场景而在的包 | **78 个，未压缩 24.8 MB，gzip 约 7.6 MB** |
| 其中最大 | `dsh-client-ui-sidebar-documentpreview` 13.8 MB、`dsh-web-frontend` 4.6 MB、`dsh-client-ui-sidebar-terminal` 0.7 MB、`dsh-session-log-export` 0.7 MB |
| 对照：整个 `app/node_modules` | 203.5 MB（`app/` 263 MB，捆绑 Node 112 MB，整个 `.app` 678 MB） |

**差值 < 50 MB → 留在安装包里，不做「首次打开时下载」。** 而且这 78 个包 **WP111 起就在安装包里**：`@deepseek-ai/dsh` 的 `dependencies` 本来就含 `dsh-web-app`，after-pack 的依赖补齐会把整棵带进来；WP136 没改任何 `package.json`，给安装包增加的只有我们自己几个源文件（KB 级）。换句话说，这一单是把已经付过的 24.8 MB 用起来。
