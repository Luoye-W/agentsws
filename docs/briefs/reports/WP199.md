# WP199 报告：审批卡升级给上级后施行失败（修 bug）

分支 `wp/199-escalation`（worktree `../agentsws-wt/wp199-escalation`），已合并一次 main（含 WP200）。

## 根因（一句话）

升级（`ApprovalBus.escalate`）把新的一级（比如老板）**加进了 `routing.recipients`，但执行快照没动**；施行前执行器按**当前**名单重算快照，`recipients` 那一格多了一个人，和批准时绑定的对不上 → `snapshot_mismatch` → 施行失败。谁点的头都一样：只要升级往名单里加过人，这张卡就施行不了。

先写的复现测试（`packages/txn/test/escalation-apply.test.ts` 前两条）在修之前红：staged_change 报 `snapshot_mismatch`，outbound_draft 抛「执行快照已变化」。

## 2 顺查结果（同类路径）

| 路径 | 有没有同样的问题 | 结论 / 测试 |
|---|---|---|
| **转交**（decide 里的 redirect） | 没有：它本来就 revision + 1、重算快照、废旧 token、重新投递 | 升级过再转交 → 新人批 → 施行成功；旧升级步留痕（挂旧 revision）不再算数 |
| **审批人离职交接**（`reroute`，org.ts 上级离职改派老板） | 快照没问题（整份名单重新绑定）；但**有一个缝**：只改派以上级身份收到的卡，被升级送到卡上的人离职时卡不改派——按 Fable 定，这一单一起修了（§1 第 6b 条） | 升级进来的经理离职 → 交给接手的人、链上追加交接一步 → 接手的人批 → 施行成功；离职的人拿旧 token 再点被拒、拿接手人的 token 冒名也被拒；交接之后再升到老板那一级，链不断，老板批 → 施行成功；伪造的交接步（不是从当前持有者交出）不认；**先改派、后升级**：新 revision 上的升级步照样核对得上；服务进程真装配一条：共同负责人被升级送到卡上 → 移出工作区 → 改派老板、链上交接一步 → 老板批 → 施行成功，他再点被拒 |
| **同键重提**（内容更新，revision + 1） | 没有 | 升级后重提 → 老板批新版 → 施行成功 |
| **撤回后重开** | 没有：撤回是终态，重提是新卡（supersedes 旧卡），新卡自己的升级链 | 撤回 → 同一笔重提 → 升级 → 老板批 → 施行成功 |
| **代批（秘书代答）** | 审批总线里**没有代批这条路**。秘书的约时间卡走 `decideMeet`（只认 `proposal.to` 本人，不经执行快照）；秘书路由出的认领卡走普通 `decide`，与上面同一套 | 没有要修的；另一条「一个人替多张卡拍板」的入口是**批量决定**，已补测试：老板在两张升级来的卡上一次批 → 都施行成功 |
| **施行失败后重试**（retryApply） | 修之前同样会挂（重算的还是那份名单）；修后跟着好 | 升级来的批准人批 → 第一次后端失败 → 重试成功 |
| **重启**（SQLite 落盘、换进程） | 修法不依赖进程密钥，关库重开照样核对得上 | 升级后关库重开 → 老板批 → 施行成功 |
| **升级到本来就在名单里的人**（3 人公司里经理 = 老板 = 店主） | 以前不出错（名单没变）；现在记 `added: false` | 照样能批能施行 |
| **升级后改着批**（approve_edited 会重算快照） | 修法里它也用同一个函数，不含升级追加者 | 施行对得上 |

**越权批准照样拒**（五条测试）：不在名单里的人点不动；升级链送到了但没有这条职责批准权的人点不动（`canApprove` 照旧管，15 人场景里李默就是这样）；名单被塞进一个「升级来的」人而链上没有这一步 → 快照对不上；链被改过（换了人、指纹没重算）→ 那一步不认；补一步不在这张卡链里的级别 / 同一级升两次 → 不认；批准人被改成名单外的人 → `authorization_check_failed`。

## 3 自主做的决定（白话）

1. **不走「升级就重签」那条路。** 另一种修法是升级时像改派一样 revision + 1、重算快照、给所有人换新 token。那样原来那个人手里的卡（包括已经推到飞书 / 企业微信的卡）会突然「内容已更新，请重新审阅」，可内容一个字没变——违反 14 §7「升级不撤销原 recipients」。所以选了工作单说的「按升级事件链核对」。
2. **指纹用普通 sha256，不用密钥签名。** 服务进程的 txn 密钥是每次启动随机生成的（`TxnRuntime.secret`，没落盘），用它签的话重启之后所有升级步都核对不上、卡又施行不了。执行快照本身也是不带密钥的哈希，两者防的是同一类事：代码里某条路悄悄改了名单。能直接改数据库的人两样都能伪造——这一点和改之前一样，没变弱也没变强（见 §4 第 2 条）。
3. **施行前多加一道「拍板的人在不在名单里」。** 决定那一刻已经查过，施行前再查一次，两处都说；正常路径下不会触发。
4. **模拟场景用 LinkedIn 而不是 Facebook。** 模拟执行器对 Facebook / Instagram 的发帖还没有施行口（报「未实现 kind」），批了也施行不了；LinkedIn 批了之后开待办，这就是它的「施行成功」。为此给 15 人 pack 的冯萱加挂了 `social.linkedin`（15 人 pack 是手工维护的）。
5. **旧卡不迁移（Fable 定）。** 修这一版之前就升过级的卡没有留痕，施行会被拦下：**这类卡改派一下，或者重新提一张。**
6. **交接步的规矩。** 离职交接不另起一个「交接链」，而是在同一条升级链上追加一步，标 `handover_from`；只认「从这一级当前那个人手上交出去」的交接，所以不能凭空插一个人进来。接手的人记成 `via: 'escalation'`，这样他之后要是也离职，同一条规矩还能接着交。
7. **离职时以上级身份收到的卡，他不是任何岗位的上级也照样交接。** 以前这一步只在「他是某岗位的上级」时才跑；现在离职 / 移出时一律把两种卡交给老板（上级中途换过人时，旧卡原先会留在走了的人手上）。
