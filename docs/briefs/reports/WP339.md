# WP339 报告：Windows 上界面不随窗口宽高调整

分支 `wp/339-layout`（worktree `../agentsws-wt/wp339-layout`），从 main `41f28247` 起。推了本分支跑 Windows CI；没合 main、没打 tag、没发版。没读 `.env*`、没碰 key / token、没碰 4317、没跑批量清理（只删了自己建的临时目录）、没用 pkill。Windows 测试机只读：只看了 `desktop.log`、`Preferences`、显示器 / 显卡清单、显示缩放的注册表值和系统事件日志，没改任何东西、没动应用数据。没碰 WP337 的更新流程（`main.ts` 只在主窗口创建处加了两行）。决策号 828–832。

## 1 结论（先说）

**在当前 main 上复现不了；我们自己的代码里没有能造成这个现象的东西，beta.4/5 → beta.6 之间也没有改过窗口或布局相关的代码。好了是因为「重启并更新」把进程连同窗口一起换了新的，不是哪个改动修好的。**

最可能的根因：**Electron / Chromium 在 Windows 上的窗口尺寸同步毛病**——显示器睡眠 / 被远程桌面唤醒、两块缩放不同的屏、再加两个远程软件的虚拟显示器，这一串显示器变化之后，网页那一层的尺寸和窗口脱节，之后怎么拖都不跟，只有重开窗口能好。可信度：中。证据是旁证（下面 §2），本机和 Windows CI 都复现不出来；这次加了一段「尺寸体检」日志，下次再出现就能一锤定音。

## 2 证据

**截图本身（两张原图对比）**

- 两张截图被缩放到同一宽度 2000，但窗口右上角三个按钮的间距一张约 125 像素、一张约 110 像素——两张图的放大倍数差约 1.14 倍。按这个倍数折算回去，**界面在两张图里是一样大的**（左栏宽、右侧图标栏位置、底边位置都对得上）。
- 也就是说：界面不是「按比例缩小」，而是**停在一个固定大小上不动**；窗口变小时右边被切掉（30 号图右侧图标栏被截断），窗口变大时右边和下边空出一条（31 号图）。左栏 `h-screen`（= 网页视口高）没到窗口底边，说明**网页以为自己的视口只有窗口的约 88%**——是网页视口没跟上窗口，不是 CSS 排版的问题。

- `git diff v0.2.0-beta.4 v0.2.0-beta.6`：Electron 版本没变（都是 44.3.0）、主窗口创建没变（1280×840、无缩放、无命令行开关、无硬件加速设置、无窗口尺寸记忆）、外壳布局只多了一个「记住了」小提醒。WP327 改的是安装目录与更新，和画面无关。

## 5 要 Luoye 定的事

- **828 要不要在「对不上」时自动纠正**：建议**先不做**，等体检日志在真机上抓到一次再定做法。可选做法是轻的（把窗口尺寸抖 1 像素再还原）或重的（悄悄重开一个同样大小、同一页面的窗口，等于自动「重启窗口」，页面里没发出去的字会丢）。上游 #54627 说抖尺寸不管用，所以真要做多半是重开窗口，先拿证据再动。
- **829 要不要为这个升 Electron**：建议**不为它专门升**。44.4–44.7.2 的发布说明里没有修这一类的条目；照常跟版本就行。
- **830 窄窗口（宽不到 768）左栏整个消失、没有展开按钮**（只能 ⌘K 跳转）：这是现有的响应式规则，不是这次的毛病。建议**给主窗口设最小尺寸 800×560**（最省事，桌面版本来就不该被拖得那么窄）；要不要另加「☰」展开左栏，等以后真有人用小屏再说。
