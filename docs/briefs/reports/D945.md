# 决策 945：NAS 版登录安全洞（WP358 范围外发现）交付报告

- 分支：`wp/945-nas-login`（从 main `a8865b2c` 拉出；不合 main、不打 tag、不发版）
- 起因：WP358 报告第五节决策 945。NAS 版按说明书开给同事以后，局域网里任何人打开登录页，用预填的主人邮箱一按就以主人身份进去。
- 方式：主人用「印在日志里的一次性设置码」，同事只走邀请链接（Luoye 10-16 确认）；桌面版行为一点不变。

## 一、一句话

服务只要**不是只给本机用**，登录页就不再把一次性进门链接交给页面、也不再公开主人邮箱。主人第一次进门用**印在服务日志里的一次性设置码**，同事只能走**邀请链接**（点开直接进）。桌面版只听本机，一切照旧。

## 二、怎么判断「只给本机用」

| 情况 | 算哪一档 | 为什么 |
|---|---|---|
| 桌面版 / `agentsws serve`（服务只听 127.0.0.1 或 ::1） | **本机档**，行为不变 | 别的电脑根本打不开这一页 |
| Docker / NAS（镜像里服务听 0.0.0.0），不管宿主端口映射到哪 | **局域网档** | 容器里看不出宿主那一侧开给了谁；说明书还推荐「NAS 反向代理 → localhost:4317」开给外面，那时宿主映射的确只有 127.0.0.1，能访问的人却是整个局域网甚至公网。看不清就按「开给别人了」处理 |
| 环境变量 `AGENTSWS_LOGIN_MODE=shared` | **局域网档** | 给「本机前面挂了反向代理」这种情况手动收紧用 |

没有往宽里放的开关：`AGENTSWS_LOGIN_MODE` 只认 `shared` / `auto`，写 `local` 或乱写服务起不来，免得有人照着网上的帖子把门又打开。

请求来源是不是回环地址**不拿来判断**：Docker 里请求永远来自 Docker 网关地址；本机挂反向代理时所有请求又都像来自本机——两头都会判错。

## 四、我自己定的（白话）

1. **Docker 一律算「开给别人」**，哪怕宿主端口只映射到 127.0.0.1。代价：NAS 主人哪怕只在 NAS 本机上用，第一次也要去日志里找一次码。换来的是不会因为反向代理、端口转发看不见而又漏出去。
2. **主人登录过期以后也用设置码**（日志里永远有最新的一个）。NAS 没有邮件通道，这是不依赖 943（工坊账号认人）的最简单办法。
3. **同事登录过期 = 负责人再发一条邀请**。已经是成员的人再收邀请不会重复加人（测试钉了）。这和 WP358 登录页上「是同事？请负责人发邀请链接」那句话一致。
4. 设置码**印在服务日志里**（这是派单要求的）。能看日志的人本来就握着 `.env` 里的全部密钥，等于没多开一扇门；码用一次就废、连错 5 次就换。
5. 托管实例（Cloudflare 容器里那一份）也听 0.0.0.0，所以同样进局域网档；它没有人从网页登录，所以**不印码**——码不该落进第三方的日志。
6. 局域网档里按邮箱要链接的那条路由还在，只是不再把 token 回给页面（和原来「托管档」同一个开关）。它回的话还是「已发到邮箱」，但 NAS 其实没有邮件——页面上已经不出这个入口，所以不影响人，只是接口文案不准，列在未完成里。
