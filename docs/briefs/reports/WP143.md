# WP143 报告：DeepSeek 图片走 Files API 复用 + 推理内容回传

分支 `wp/143-ds-files` · worktree `agentsws-wt/wp143-ds-files` · 照官方 `@deepseek-ai/dsh-llm-deepseek@0.1.7-rc.1`（MIT）移植。

## 1. 实现清单

1. **Files API 复用**（`packages/model-gateway/src/providers/deepseek-files.ts`，新文件，文件头写了出处：包名 + 版本 + 官方 `lib/index.js` 里对应的 `lib/types/{messages-api,files-api,upload-index,file-store,request-files}.js` 几段）
   - 图先 `POST <根>/v1/files`（multipart，`expires_after[anchor]=created_at` + `expires_after[seconds]`），请求里发 `{type:'image', source:{type:'file', file_id}}`；Files 请求和带 file id 的模型请求都带 `anthropic-beta: files-api-2025-04-14`；全部 `redirect: 'error'`。
   - 同一张图按字节算 sha256（再加上图片类型）得到一个键，同一个 scope（`sha256(接口根 \0 凭据)`，照官方写法，不存凭据本身）下只传一次；并发请求同一张图也只传一次（singleflight）。
   - 复用期：上传时要求远端保留 7 天，剩不到 1 小时就换新 id（都是官方默认值）。
   - **任何一张解析失败或超时（默认 60 秒）→ 整份请求退回内联 base64，一次请求绝不混用**；模型口报「file id 不认了」（照官方的判定正则）→ 作废点名的那条映射（没点名就作废这次用过的全部）→ 重传 → **只重试一次**。
   - 映射存放：默认在内存；`apps/server` 里一个品牌共用一份，落 `<品牌目录>/deepseek-files.json`（0600，里面只有哈希、file id 和时间；备份的 `RAW_FILES` 名单里没有它，不上云）。
   - `deepseek-account.ts`：新增 `deepseekMessagesProvider`（凭据二选一：账号令牌走 `x-dsh-auth-token`，API key 走 `x-api-key`）；`deepseekAccountProvider` 签名没改，改成转调它。`toMessagesRequest` 多了一个可选参数（图片来源、目标模型）。
2. **推理内容回传**
   - 契约只加：`ReasoningReplay { kind: 'deepseek-messages', model, blocks: {thinking, signature?}[] }`，`ChatMessage` 和 `Completion` 各加一格可选 `reasoning_replay`。
   - provider：回复里的 thinking 块连签名原样留下；下一轮放在那条 assistant 内容的最前面原样发回。换了模型只回传思考原文、去掉签名（官方：签名换模型不能用）；只有 `reasoning` 原文、没有回放记录（比如历史来自别家）时发一块不带签名的思考（官方的做法是「省略签名，不丢弃文本」）。
   - 这条路上三处接上：网关透传（`gateway.ts`）、`runtime-direct` 接回历史、`dsh-adapter/llm.ts` 按 tool-call id 接回（和 WP87 的 `reasoning` 同一种做法；`toChatMessages` 加了第三个可选参数）。
3. **API key 那一路改走 Messages**：评估后**做了，但默认不开**（原因见 §2 第 3 条）。`apps/server/src/models.ts` 加了 `AGENTSWS_DEEPSEEK_MESSAGES=1` 开关和 `deepseekUsesMessages()`：只对 `kind: 'deepseek'`、只认官方地址 `https://api.deepseek.com`（也认 `/v1` 结尾）；打开后走 `https://api.deepseek.com/anthropic/v1/messages`，也会用上 Files 复用和推理回传，三步验证照常跑。改过地址的（代理 / 中转）、百炼等别家都不动。
4. **用量 / 计费**：Messages 的 `input_tokens` 不含缓存读 / 写，我们记账的口径（`costOf`）是含在里面的，所以把缓存读 / 写加回 `input_tokens`（以前命中缓存的部分会少算）。Files 上传不经过网关，不记账，也不扣积分（有测试：两次带图的调用只记两笔）。
5. **上游哨兵**：`upstreams.yml` 里 dsh 的 `we_depend_on` 加两行（Files 复用 / 推理回传，标「移植」），`covered_by` 加两份新测试；docs/42 第 ④ 步加一段「dsh-llm-deepseek 的 Files 行为变了要同步」，写清升级时要 diff 哪两节 README、哪几份 `.d.ts`。

### token 省了多少（估算）

- **模型这一侧的 token：基本不省。** DeepSeek 看图的 token 按像素算（官方的格子规则：14 px patch、3:1 降采样，单张最多 1024 token），不管图是 base64 还是 file id，模型看到的都是同一张图，计的 token 一样。前缀缓存那边：两种写法在多轮之间都是稳定的，命中率差不多；只有 file id 刷新（最多 7 天一次）或者退回内联那一次会让缓存从那张图开始失效。
- **省下来的是每轮重复上传的图片字节**（请求体大小、上行带宽、延迟）。测试里拿一张约 200 KB 的图对比「同一张图第二次引用」：内联那次请求体约 273 KB（base64 会多出 1/3），file id 那次请求体不到 1 KB。换成真实用法：一张 300 KB 的商品图在 10 轮对话里每轮都带着，内联要上传约 4 MB，Files 是 300 KB 传一次再加 10 次几十字节的 id。
- 积分：Files 上传不另收。

## 2. 自主决定（白话）

1. **不搬官方的「配额满了先删最老的一批文件再传」**：那会删用户 DeepSeek 账号里的远端文件。我们配额满了就算这次上传失败，整份退回内联，照样能用。
2. **图片前面不加官方那段「附件 id + 请求尺寸」说明文字**：那是官方附件服务的东西，我们没有；图片也不像官方那样先压缩成固定尺寸，原样字节上传。
3. **API key 那一路做成开关、默认关**：官方 0.1.7 起确实只用 Messages，API key 也能用。但有几件事离线核不了：用户从 `/models` 列表里选的模型名在 Messages 口认不认、看图在那个口能不能过、真实计费口径。现有 demo / 截图 / 服务端测试的替身也都是按 `/chat/completions` 写的。派工单说「拿不准就不改」，所以折中：代码和测试都写好，开关默认关，Luoye 用真 key 试一次就能拍板。
4. **注入了 fetch 替身、又没给文件缓存时，Files 关掉**：这样测试 / demo 里的替身不会顺手把上传发到真网络上。demo 和现有测试的行为一个字节没变。
5. **上传的文件名前缀用 `agentsws-`，不用官方的 `dsh-`**：官方配额清理会删 `dsh-` 开头的文件，用自己的前缀，归属清楚。
6. **缓存用量加回 `input_tokens`**：按官方的分桶理解（input 是没命中缓存的那部分）。改了 WP134 一条测试的期望值（12 → 15）。
7. **思考块统一放在 assistant 内容最前面**，不按官方那样逐块对齐原位置。我们的消息结构把文字压成了一段，拿不到原顺序；而 Messages 的回复本来就是思考在前。
