# WP235 报告：公司页岗位真实持有人、「你们的岗位 / 可以加的岗位」、合并不碰模板

分支 `wp/235-orgpos`（worktree `agentsws-wt/wp235-orgpos`），Claude 子代理。

## 0. 一句话

公司页上「还没人做这个岗位」是因为持有人还按老的「凑齐默认包」算（左栏早就按「持有一条就算」了）。
现在两边同一条规则；公司页「岗位」分成「你们的岗位」与折叠的「可以加的岗位（模板）」；合并 / 移动 / 拆出
只作用在有人在做的那几条职责上，目标是模板时另建一个自建岗位，模板一个字不改。
Luoye 的场景：「公共关系（只做 pr.reddit）」合并到「社媒运营（只做 social.reddit）」→ 一个「Reddit 运营」，左栏只剩它。

## 1. holders 为空的根因

`apps/server/src/position-placements.ts` 的 `holdersByPlacement`：分配有安放行就算；**没有安放行的老分配**，要
**凑齐这个岗位的全部默认职责**才算持有人（05 §2 的老规矩）。

- 公共关系的默认包是 4 条（新闻稿、Reddit、论坛、舆情），Luoye 只有 `pr.reddit`。
- 社媒运营的默认包是 FB / IG / TikTok / YouTube 四条，Luoye 只有 `social.reddit`（它本身不是默认勾的）。
- 「负责人」默认包只有 `common.owner`，所以只有它有持有人。

左栏用的是另一条规则 `belongsTo`（职责在这个岗位的清单里就算），WP234 改了左栏、没改持有人，两边就对不上了。
公司页卡片（`org.ts` 的 `holdersOf`）和岗位页（`positions.ts` 的 `instance`）读的都是 `holdersByPlacement`。

**修法**：没安放的分配里有**一条干活的职责**在这个岗位的清单里，就算持有人（底座职责 `common.*` 不算）。
「普通成员」（只有底座职责）与「负责人」那一行仍按默认包算（它们是身份）。另外每位持有人多带 `role_ids`：
他在这个岗位里手上的那几条。

## 3. 桌面壳检查更新：查不到源不再打 ERROR 堆栈

- **根因**：electron-updater 的 `AppUpdater` 构造时自己挂了 `on('error', e => logger.error(e.stack))`。
  `main.ts` 把它的 logger 直接接到我们的 `logger.error`，查失败时先出一段 ERROR 堆栈；状态机又记两条 warn。
- **判断「源还不存在」**（`update-controller.ts` 的 `sourceMissing`）：只认四种——域名解析不到（`ENOTFOUND`、
  `ERR_NAME_NOT_RESOLVED`）、连接被拒、HTTP 404（含 `ERR_UPDATER_CHANNEL_FILE_NOT_FOUND`）、
  GitHub 一个发布都没有（`ERR_UPDATER_NO_PUBLISHED_VERSIONS`）。超时、断网、5xx、证书错、解析坏了照旧按原级别记。
- **这一轮查过的源全都「不存在」**：只记一行 INFO「还没有可用的更新源，暂无新版本」，带每个源的短原因
  （如 `primary=dns github=no-releases`），不带堆栈；状态回 idle，左下角按钮不出现（= 已是最新）。
  交给 electron-updater 的 logger（`electronUpdaterLogger`）在「正在查」时丢掉这一类 error；
  下载、安装阶段的 error 照旧记。
- 桌面壳没有单独的「检查更新」按钮文案，i18n 没动。

## 4. 自主做的决定（白话）

1. **持有人「有一条就算」只对干活的岗位**；「普通成员」和「负责人」仍按默认包，不然所有人都会因为底座职责被算进去。
2. **合并到模板时另建一个自建岗位**，而不是像 WP234 那样把模板改成自建：派工单说模板本身不变。
   在模板里做的**所有人**一起搬过去（不只是点合并的那个人），因为「你们的岗位」那张卡代表的是这摊活整体。
3. **移动职责到模板也另建同名自建岗位**（同一个理由）。界面上看不出差别：原来的卡换成同名的自建岗位，模板落到下面那块。
4. ~~从模板合并出去，模板的岗位层记忆也搬走~~ → Fable 10-06 代定改为**复制**：新自建岗位拿一份（标「（复制自「模板名」）」），模板留一份；自建岗位之间合并照旧并过去。
5. **没人做的模板不能当「被合并的那一个」**（400：「还没人在做，没有可以并过去的职责」）；空的自建岗位仍能合并（为了把它的记忆带过去再删掉）。
6. **合并对话框的名字必填、预填建议名**；目标是自建岗位时预填它原来的名字，改了就是顺手改名。
7. **新岗位不抄模板的角色定位（persona）**：「社媒运营」的定位里可能写着「Reddit 公关不归你」，抄到「Reddit 运营」上反而打架。
8. 模板那块里的卡保留「分给同事 / 加减职责 / 删掉」，不出合并 / 移动 / 拆出。

## 7. 要 Luoye 定的事（Fable 10-06 已代定，见 §9）

1. **从模板合并出去，模板那一层岗位记忆是「搬走」还是「复制」**？现在是搬走（模板里已经没人了）。以后有人再从模板领这个岗位，就从空的记忆开始。
2. **卡上的「N 条职责」**：模板卡上数的是模板整份（公共关系「5 条职责」还把「工作区成员」算进去了，WP234 前就这样），
   持有人那一枚后面写的才是他真在做的。要不要把「你们的岗位」上的计数改成「在做 1 / 共 4」？
3. **更新源判定的一处边界**（桌面）：主源 404 时按 WP218 规则不退 GitHub（GitHub 开关关着时也一样），这一轮只查了主源，
   现在也算「暂无更新源」记 INFO。要严格「两个源都查不到」才算，或让 404 也退 GitHub，说一声。
4. 桌面壳每查一个源，electron-updater 还会记一行它自己的 INFO「Checking for update」，留着方便排查；要不要也压掉？
