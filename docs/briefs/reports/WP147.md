# WP147 报告：截图给 AI 看，电脑操控与浏览器的截图都送进模型

分支 `wp/147-screenshots`（worktree `../agentsws-wt/wp147-screenshots`，从 main `60911ecf` 起；收尾时 `git merge main`，main 没有新提交，结果是 Already up to date）。实现方是 Claude 子代理，2026-09-24。没有 push、没有部署、没有打 tag，没有读任何 `.env*`。**这台电脑上没有启动 cua-driver，没有操作桌面，也没有截真屏**：测试里的驱动和 Playwright 服务器都是假的，只回固定内容；截图只拍了工作台页面。

**一句话**：照官方的条件把截图接进模型。有浏览器或电脑操控的运行，会挂上官方附件库，位置是这次运行自己的临时目录，运行一结束就删掉。只有三步验证通过的模型才向官方声明「能收图」。符合这两条时，官方 MCP 桥会把截图放进工具结果，适配器再按官方规则缩放后发给模型，一次请求最多带 8 张，超出的旧图由官方插件换成占位文字。模型不能看图时，截图位置换成官方的诊断文字，和以前一样一张图都不发。三处告知都加了同一句话：截图会发给你选的 AI 模型，不会存进 Agents 工坊的记录。

## 2. 自主决定（白话）

1. **附件库放在这次运行自己的临时目录，跑完整个删掉。** 官方附件库默认放在 `~/.dsh`，而且「永不自动删除」。派工单要求不落我们的库、不进日志、不上云，所以我把它的根目录指向系统临时目录下一个一次性的目录，运行结束就删。删的只是这次运行自己刚建的那一个目录。
2. **只有「有浏览器」或「电脑操控批过」的运行才挂附件库。** 别的运行一个字节都不变，fast 模拟的基线也没动（见 §4）。
3. **模型能不能看图，只认三步验证的结论，而且验证的必须正是这次运行用的模型。** 与 WP127「换了模型名，上一次的结论作废」是同一条规矩。没验证过就不声明。WP127 的网关对没验证过的模型照常放行带图请求，这里比它严一档，因为这回发出去的是用户的屏幕截图。
4. **每张图缩到多大，用官方 pi-ai 的通用规则**：总像素不超过 2048×2048，编码后目标 1 MiB。没有用 DeepSeek 专用的 1024 token 网格，因为我们的网关后面接的是多家模型。
5. **一次请求最多带 8 张。** 第 9 张来的时候，最旧的 4 张一起换成官方占位文字（`countQuantum: 4`）。这样换掉的那一批之后几轮都不再变，前缀缓存比较稳。字节上限用 pi-ai 的默认值 20 MiB（按 base64 长度算）。8 张的量级大约 11 MiB，平时先碰到的会是张数上限。
6. **超预算时走官方的路，不自己删图。** 适配器报 `IMAGE_OFFLOAD_REQUIRED`，由官方插件在会话里记一条 `image/offload` 再重试。这一步报错不算一次模型步数，也不会被记成「模型挂了」。
7. **门禁对带图的结果按 content 接受**（原因见 §1 第 5 项）。只有带图的结果改了路，其余结果照旧按值接受。
8. **WP144 的脱敏函数和常量仍然导出**，只是不再调用，这是为了遵守「已有公共签名不改」。
9. **图片前面加一段官方句柄文字**（「Image sha256:…; request preview 1280x800px…」），与官方两个适配器一致，模型能据此知道图被缩到了多大。
10. **测试里把 Playwright 那个进程换成假 MCP 服务器**（`vi.mock` 替换官方提供方那层不到 30 行的薄壳，原样调用官方的 `mountSessionMcp`）。原因是真的 `browser_take_screenshot` 必须有一个真浏览器。官方浏览器 seam、官方 MCP 桥、图片准入、我们的门禁、附件库和适配器，在测试里都是真的。

## 3. 需要 Luoye 定的事

1. **服务端上，只开浏览器的运行现在看不到截图。** 服务端平时走 direct 运行时，那一档根本没有浏览器工具（WP86 起就是这样，WP144 只把带电脑操控的运行改走了 dsh）。所以截图进模型在服务端上目前只发生在电脑操控的那次运行里；同一次运行如果也开着浏览器，浏览器截图一样会进。CLI、模拟、桌面里凡是走 dsh 运行时的，两条腿都受益。要不要让只开浏览器的运行也改走 dsh 运行时，是一个单独的改动，我没有做。
2. **一次请求最多 8 张、超了换掉最旧 4 张，这个数合适吗？** 数越大，模型看到的历史越多，但每一轮都更贵、更慢。
3. **安装包里会多出 `sharp` 和 libvips。** libvips 是 **LGPL-3.0** 的动态库，需要你确认可以接受。另外，`@img/sharp-<平台>` 这些预编译包只装了打包机那个平台的。如果在 arm64 的 Mac 上打 x64 的包，x64 那份可能缺，到时截图会退回官方诊断文字（「durable image storage rejected the result」），功能能用但看不到图，不会崩。`after-pack` 的冒烟目前只查 better-sqlite3，没有查 sharp。
4. **截图发给第三方模型，要不要在授权卡上单独问一句？** WP144 报告里提过这个选项。现在的做法是按派工单只加一句告知，授权卡上没有单独的勾选项。浏览器截图也没有逐次授权：模型验证过能看图，就会发。
5. **换过模型的运行不会声明能看图。** 现在只判断「默认模型」验证过没有。职责如果以后各自选模型，需要把验证结论记到每个模型上。

## 5. 偏离

1. **没有挂官方 `dsh-spill-policy`（`maxInlineTokens`）。** 派工单写的是「沿用官方 spill-policy / 图片 token 预算」。我读了它的实现：结果超预算时，它要 spill 后端（`ctx.spillStore`）把整段结果写进文件，还要 `fs` 服务把附件路径映射出来，并叫模型用 `read` / `read_image` 去读。我们的最小树这三样都没有，挂上去只会一直「记一条警告、原样保留」，等于没挂。所以体积交给另外两道官方的关：每张图按官方规则缩放和压缩，一次请求按官方 `LlmImageRequestBudget` 限张数，超了由官方 `image/offload` 换占位。
2. **缩放用官方 pi-ai 的通用规则，没用 DeepSeek 的 1024 token 网格**，原因见 §2 第 4 条。
3. **服务端上只开浏览器的运行没有受益**，原因见 §3 第 1 条。派工单写的是「浏览器两条腿都受益」，这在 dsh 运行时上成立，服务端的 direct 档本来就没有浏览器工具。
4. **契约只改了注释。** `ChatContentPart` 原本就允许数组出现在任何角色上，不需要加新类型。
5. **offload 占位用的是官方原文。** 因为我们没挂 `fs`，占位后半句是「No local normalized image path is available; ask the user to attach it again if needed.」，对截图这个场景来说有点别扭。这是官方文案，我没改。
6. **报告写在 `docs/briefs/reports/WP147.md` 并提交了**（派工人要求的），没有按 _common 写到 worktree 根的 `REPORT.md`。
7. **demo 牌堆那张授权卡的文案也同步了。** 派工单只点了服务端那张卡，但截图拍的是 demo。
