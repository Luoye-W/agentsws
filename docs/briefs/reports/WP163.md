# WP163 报告：客服收信只把「判成客服的信」挪进 KefuAgents（照老产品 KefuAgent）

分支 `wp/163-support-archive`（worktree `../agentsws-wt/wp163-support-archive`），实现方 Claude Opus 子代理。

## 1 实现清单

1. **共用的判断顺序**：`packages/channels/src/email/support-mailbox.ts`（新）。老产品
   `moveCustomerServiceMessageToAiFolder` 的四个开关与顺序做成一个纯流程
   `applySupportMailboxActions`：影子模式 → 接管开关 → 标已读（失败不挡挪信）→ 挪信
   （已在目标文件夹里不挪）。每一步回一条动作记录（`observe` / `mark_read` / `move`，
   `completed` / `skipped` / `failed` + 原因码）。永不抛。两条收信路都用它。
2. **渠道那一路**（`EmailChannelAdapter`）：`poll` 的 handler 可以回 `{ support, skip? }`；
   只有 `support: true` 的信才标已读 / 挪，其余原地不动、不标已读、不记账。新增可选
   `support_mailbox`（影子模式 / 挪信）与 `on_mailbox_action`。`MailSource` 加可选
   `markRead`（标已读与挪信分成两个动作），`ImapMailSource` 实现了它。handler 不回结论 = 老行为。
3. **消息同步那一路**（`MailboxSync`）：判成 `support` 且那一侧接了 → 走同一套开关
   （默认先标已读再挪，库里 `flags.read` 与文件夹跟着改）；那一侧没接记「跳过 handoff_refused」；
   **已在岗位文件夹里的信不再自动挪**；影子模式对红人那只也生效。新增可选
   `support_mailbox()`（每封现查）与 `on_mailbox_action`。
4. **挪信归谁**（`apps/server`）：`ChannelsOptions.mailbox_moves`（`'channel'` 缺省 /
   `'message_sync'`）；服务进程装配传 `'message_sync'`，渠道那一路不拿归档文件夹 = 一下都不动邮箱。
   只装渠道时由渠道挪，口径 = 进了客服路由（`dtc.support` / `amz.support` …，
   `isSupportRoute`）+ 工作模型里有钉着这条线程的事项 + `supportEnabled()`（可选，缺省当开着）；
   去重命中的、解析炸了的一律不动。
5. **分拣 ① 只认后续来信**（`apps/server/src/messages.ts`）：线程归并那一层只对带
   In-Reply-To / References 的信生效。见「自主决定」第 2 条——不改这一处，第 4 条在服务进程里不起作用。
6. **事件与界面**：`apps/server/src/mailbox-actions.ts`（新）——每个动作一条
   `inbound.mailbox_action`（契约 `KnownEventType` 加一格；payload 只有原因码、文件夹、uid，
   地址遮掉，失败原因截到 160 字且遮地址）；每只邮箱记住最近一次失败（同一种动作后来成功就抹掉）。
   `MessageAccountView.last_mailbox_failure`（可选字段）；「消息」页左栏底部一行短字 + 问号
   （哪只邮箱、什么时候、原因人话）。`maskAddress` 实现挪进这个文件，`messages.ts` 原样再导出。
7. **docs/63 §D** 改写：流程图 ① 加注；新增「挪信归谁」「客服信在邮箱里怎么动」两节（开关对照表、
   原因码、事件与界面）。docs/35 记一笔。ontology.json 随契约重出（只有 digest 变）。

## 2 我自主做的决定（白话）

1. **挪信只归消息同步**。两条路里只有消息同步有分拣、知道客服岗位开没开、认得文件夹真名；
   渠道那一路本来就把每封信都当客服信。所以服务进程里让渠道那一路彻底不碰邮箱，最省事也最不会打架。
   调度顺序（先渠道、后消息同步）不用动。
2. **分拣第 ① 层只认后续来信**。写集成测试时撞出来的：渠道那一路同一拍里先跑，给 INBOX 里
   **每一封**新信都开一条钉着自己线程的事项；消息同步随后分拣，第 ① 层拿这封信**自己的**线程 id
   去对，于是连群发信都"命中客服已有线程"、被挪进 `KefuAgents`。只改挪信归属的话，
   线上症状一点不变。63 §D 原话就是「In-Reply-To / References 命中」，所以按原话收紧。
3. **已在 `KefuAgents` / `KOLAgents` 里的信不自动挪**。否则老产品或旧版本挪进去的信会被下一轮分拣
   挪到另一只，形成来回。改归属只走人按的「移到…」。
4. **影子模式对红人那只也生效**：老产品的影子模式是整只邮箱的开关，说的是"别动邮箱"。
   另外三个开关只管客服信。
5. **挪信开关关着时也记一笔「跳过 move_disabled」**：老产品这一步不记，工单要求「挪 / 跳过 / 失败」
   都写事件，就补上了。
6. **非客服信不记事件**：和老产品一样（它根本不调那个函数）；否则每封订阅信都多一条噪声。
7. **「最近一次失败」只放内存**：重启清零，下一次失败再记上。持久化要么动消息库表、要么查事件日志，
   都比这一单大。
8. **界面那一行是可见的短字**（错误与状态必须一眼看见，36 §7），细节放问号里。

## 3 需要 Luoye / Fable 定的事

1. **渠道那一路仍给 INBOX 每封新信开事项、起 Run、过一遍客服判断层**（WP55 的设计：它把这只邮箱
   当成专用客服邮箱）。现在挪信不会错了，但订阅 / 通知信照样会在工作台里变成一条"与 xx 的往来"事项
   并起一次 Run；消息同步判成客服的信还会**再**递一次判断层（`onSupportMail`）。建议另开一单：
   服务进程里渠道那一路只收「消息同步判成客服」的信，或干脆让消息同步接管落事项这一步。
2. **四个开关现在没有界面**，服务进程按老产品默认值跑（影子关、接管 / 挪信 / 标已读全开）。
   要不要在连接页那只邮箱上放这几个开关（尤其影子模式：上线前拿真邮箱对照用）？
3. 消息同步现在默认会把挪进 `KefuAgents` 的客服信**标成已读**（老产品默认就这样，渠道那一路原来也这样；
   但 WP113 的消息同步之前只挪不标）。如果 Luoye 更想让客服文件夹里保持未读，把默认值改成关即可。
