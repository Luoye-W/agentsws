## 1 实现清单

1. **收信一个入口**（`apps/server/src/channels.ts`）
   - 新选项 `inbox_intake: 'channel' | 'message_sync'`。服务进程传 `'message_sync'`：渠道适配器**不再自己轮询 INBOX**，
     `poll()` 只推重试队列。缺省 `'channel'` = 只装渠道的老调用方，老行为一个字没改（有测试）。
   - 新方法 `intakeSupportMail({ account, raw, message_id?, by })`：把一封原始 MIME 递进**这只邮箱原有的那条入站管线**
     （`ChannelInboundPipeline.ingest` → 适配器 `toInbound`：Amazon 子渠道判定、线程台账；管线：去重、脱敏、路由、
     落事项、客服判断层、起 Run）。不另写一份。
   - **同一封信只进一次**：`supportIntakeKey` 按 Message-ID（不分邮箱、不分大小写），没有才按「邮箱 × 文件夹 × UID」；
     台账不过期（`channels.sqlite` 迁移 v5 新表 `support_intake`，内存档 `MemorySupportIntakeLedger`）。每次递交写一条
     `inbound.support_intake`（只有钥匙哈希、谁判的、是不是重复、事项 id）。
2. **消息同步那一侧**（`apps/server/src/messages.ts`、`packages/channels/src/messages/sync.ts`）
   - `MailboxSync.handoff` 多给第三个参数（原始 MIME）；`support_mailbox` 多给邮箱地址（开关按邮箱各一份）。老调用方不受影响。
   - 新选项 `intakeSupport`（服务进程接 `channels.intakeSupportMail`）。给了它，判成客服的信递进管线；不给 = 老行为
     （只开事项 + `onSupportMail` 信号）。服务进程不再接 `onSupportMail`（判断层在管线里跑，避免同一封信过两次判断层）。
   - 交接炸了不让信变毒消息：它已经落进消息库，记一笔 `support_intake_failed`，信不动。
   - **已经在岗位文件夹里的信**第一次被扫到：不开事项、不起 Run，有钉着这条线程的事项就挂上（见第 2 节第 2 条）。
3. **待确认**
   - 契约只加：`MessageListQuery.pending_route`、`MessageThreadSummary.suggested_route / pending_message_id`、
     `MessageConfirmRouteInput / Result`。纯函数 `pendingRouteOf`（内存 / SQLite 两档共用 `query.ts`）。
   - 路由 `POST /v1/messages/:id/confirm-route`（写类元组，不是 outbound）。「这是客服」= 人工分拣：原信从受控原始材料区取回
     递进管线，再按这只邮箱的开关标已读 / 挪信；写 `messages.route_confirmed`（谁、判成什么、交没交出去；无正文、地址遮掉）。

   - 工作台：消息页左栏一格「待确认」（有信时一个点）+ 问号；那一栏每行底下「这是客服 / 不是」。

## 2 我自主做的决定（白话）

1. **「接管」不另存**：派工单说「接管就是这只邮箱开没开客服，已有的就复用」。现有的只有「这个品牌开没开客服岗位」
   （`activeRoles`），没有按邮箱的开关——所以卡上把它画成只读小标，问号里说"到岗位页去开"。
2. **已经在 KefuAgents / KOLAgents 里的信不开事项、不起 Run**：老产品的 `KefuAgents` 里是它处理过的信；第一次连上时
   消息同步回溯 30 天，要是照客服信交一遍，会给一个月前的信起草回复、花一堆模型钱。代价：用户在邮件软件里建了
   「直接进 KefuAgents」的过滤规则，那些新信不会自动开事项（以前渠道那一路只扫 INBOX，本来也不管它们）。
3. **去重钥匙不带邮箱地址**：同一封信抄送到两只已连的邮箱，只开一条事项（与入站管线的去重同一条纪律）。
4. **台账不过期**：入站管线自带的去重表是 24h 窗口，挡不住"人在手机上把信挪回收件箱""人在待确认里又点一下"。
5. **「待确认」也收红人**：判不准的红人信（`suggested_route: 'kol'`）同样进这一栏，按钮叫「这是红人」。
6. **人工确认时原信从受控原始材料区取回**（消息同步落库时就存了，加密、随主体删除）；取不回就交不出去，照实说。
7. **开关写在消息那一侧**（挪信归消息同步），连接面只是按连接 id 转过去。PUT 走连接面的写类元组（改的是"Agent 能不能动你的邮箱"）。
8. **影子模式开着时另两个开关照样能拨**（字变灰），不禁用——方便上线前先配好。
9. **同步里客服交接不再抛异常**（原来会让那封信进毒消息隔离、游标卡住）：信已落库，只是没交出去，记一笔。

## 3 需要 Luoye / Fable 定的事

1. **过滤规则直接进 KefuAgents 的信要不要也开事项？**（见第 2 节第 2 条）现在不开。要开的话，得先定"首次回溯时
   岗位文件夹里的老信怎么办"（比如只交连上之后新到的）。
2. **按邮箱的「接管」要不要真做成开关？** 现在是品牌级（客服岗位开没开）。一个品牌接两只邮箱、只想让其中一只进客服时才需要。
3. **升级时的一拍重叠**：老版本渠道那一路已经给 INBOX 里的信开过事项；升级后消息同步第一次跑，同一封信若还在入站去重表的
   24h 窗口里会被认出来（不重复起 Run），超过 24h 的老信则可能再交一次（开到同一条事项上，但会再起一次 Run）。
   消息同步的游标通常早已推过这些信，实际很难撞上；要不要在升级时把"已有事项钉着的线程"预先写进台账，请定。

## 5 偏离

- 派工单要"复用渠道适配器的处理管线：…游标、毒消息隔离"：游标与毒消息隔离用的是消息同步自己那一套（同一份 `cursors.ts`，
  WP55 的原样），渠道适配器的 INBOX 游标在服务进程里不再推进；Amazon 子渠道判定、线程归并、去重、判断层、起 Run 走的是渠道管线。
- 模拟世界里没有真的起 Run（世界的 `mail.inbound` 本来就只做分拣），"开事项 / 起 Run"是按服务进程同一个 `intakeOf` 算出来的
  结论落在事件上；服务进程里真的开事项、起 Run 由 `apps/server/test/mail-intake.test.ts` 钉着。这样已有场景的指标一格不变。
- 截图里连接页那条邮箱连接与开关响应是**浏览器侧替身**（demo 没有邮箱、不许连真邮箱）；「待确认」那封是 demo 种进消息库的真数据、走真路由。
- 多了一个截图脚本 `scripts/e2e-mail-intake-shots.mjs`（照 WP144 的先例，可重跑）。
