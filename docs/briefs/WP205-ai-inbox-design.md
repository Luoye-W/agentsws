# WP205 以 AI 为核心的消息中心：调研 + 设计稿（先出设计，不写实现）

worktree `../agentsws-wt/wp205-inbox-design` · 分支 `wp/205-inbox-design`（从 main 新起）。先读 `_common.md`、`docs/36`（界面原则、少字、卡片）、`docs/63`（消息与邮箱全量接入）、`docs/54`（岗位是任务主入口 / 路由）、`docs/56`（社媒与社群、客服社群管理）、分拣相关实现与记录（docs/35 里 WP163 / WP167：分拣三层、单一入口、BtoBAgents 文件夹等；`packages/support-core`、`apps/server` 里 triage / intake）、`apps/workstation/src/pages/messages.tsx` 与 `components/messages/*`、在线聊天窗（docs/74）、WhatsApp 入口（WP182）、品牌 token 与动态标记（`packages/brand`）。

## 背景（Luoye 09-30）
「我们能不能做一些创新的消息展示方式，这种传统的布局信息显示很局促。现在只接了一个邮箱，后面如果接多个邮箱，以及在线聊天渠道该怎么办。消息进来，应该有『标签』或者什么的判断吧，就是我们也要把这个工具改造得以 AI 为核心。」

## 要做（这一单只出调研与设计，不写实现代码）
1. **调研**（写进 `docs/88-AI消息中心-v1.md`）：AI 优先的收件箱 / 客服台怎么组织信息——例如 Shortwave、Superhuman、HEY、Front、Missive、Intercom（Fin / Inbox）、Gorgias、Zendesk AI、Linear Asks 等（以实际查到的为准，只看公开页面与文档，不注册登录）；每个写清它的核心想法（按「要你做什么」而不是按时间排、自动分组 / 摘要 / 建议回复 / 批处理 / 线程合并…）、哪些适合我们、哪些不适合。
2. **我们的设计**（docs/88 正文）：
   - **统一入口**：多个邮箱、在线聊天窗、WhatsApp、各社媒私信 / 评论，进来是同一条流；每条带来源渠道与账号，但默认不按渠道分，按「这件事是什么、要谁处理、急不急」组织。
   - **AI 判断**：每条进来先经分拣（接现有分拣三层），打上**类型标签**（客户问题 / 售后 / 询盘 / 红人回复 / 合作 / 媒体 / 账单与系统通知 / 垃圾与营销…，可扩展）、**归哪个岗位**（接 54 路由）、**要不要人**（Agent 已处理 / 已起草等你批 / 需要你亲自看 / 仅供知悉）、**紧急度**，并给一行 AI 摘要；判断可纠正、纠正会被学习（接学习回路）。
   - **展示方式**：给至少**两个方向**，都要比三栏宽敞、信息密度高而不挤。比如：A「今日简报 / 分组卡片流」（按「要你做的 / Agent 在处理 / 只需知悉」分区，线程折成一张卡，展开看全文与 AI 建议）；B「对话为中心」（左窄栏按岗位 / 标签分组，右边整宽的对话视图，AI 摘要与下一步置顶，原文可折叠）。也可以提出更好的。
   - **与出卡审批的关系**：Agent 起草的回复在消息里直接以卡片出现（批 / 改 / 驳回），不再跳到别处。
   - **多账号与渠道**：账号 / 渠道筛选、各账号颜色标识、同一客户跨渠道合并成一个人（身份合并规则与隐私边界）。
   - **动作**：归档、删除、稍后提醒、转岗位、标签纠正、批量处理；遵守「客信怎么动邮箱」开关。
   - 少字、明暗两套、手机可用。
3. **设计稿**：`docs/design/inbox/` 下静态 HTML（单文件、内联、不引外部脚本；字体用本地或系统字体），两个方向各一张桌面 1440（明 / 暗）+ 手机 390，用合成的真实感数据（多邮箱 + 聊天窗 + WhatsApp + IG 私信混在一起，含询盘、售后、红人回复、系统通知、垃圾）；截图放 `docs/design/inbox/shots/`。
4. 结论段：推荐方向、分几步落地（每步能独立上线）、要 Luoye 定的事。
