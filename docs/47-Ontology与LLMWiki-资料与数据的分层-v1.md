## 0. 一句话

**这个分层我们已经做了一大半，只是没叫这个名字。** 那张图右边的六个格子（客户、订单、实时状态、业务关系、权限、动作）在 agentsws 里分别对应：契约里的对象类型、连接器的读动作 + 活数据源、事件日志、范围与职责、连接器 Action 与变更账本。缺的不是"一个 Ontology 产品"，而是**把这些散在 19 份契约里的东西登记成一张对象 / 关系 / 动作的总表**，让知识层（Wiki）里的每一句话都能指到一个真实对象，让 Agent 调用时先查总表再动手。建议做一个薄的"本体登记表"，不引入 Palantir 那种重型平台。

## 1. 两个词到底指什么

| | LLM Wiki（知识层） | Ontology（操作层） |
|---|---|---|
| 存什么 | 文档、会议纪要、政策、历史案例、FAQ——**文字**，回答"是什么 / 为什么 / 以前怎么办" | 客户、订单、商品、店铺、岗位、变更——**对象**，回答"现在是什么状态 / 谁能对它做什么" |
| 真源 | 文件与人写的内容；会过时 | 平台 API 与我们自己的账本；实时 |
| 变化 | 慢，靠人更新、靠学习回路沉淀 | 快，每分钟都在变 |
| 查法 | 检索（语义 + 关键词）→ 摘要 | 按 id / 关系查 → 结构化 |
| 出错的代价 | 答错一句话 | 改错一笔钱 |
| 业界代表 | 个人研究、文档问答工具 | Palantir Foundry 的 Ontology（对象 / 属性 / 链接 / 动作 / 权限一套） |

那张图的结论"只做个人研究和文档问答 → Wiki 就够；做公司业务 → 要 Ontology"，对我们成立：**我们是公司导向、工作导向的**（46 的定位），所以两层都要，而且要分清楚。

## 2. 我们现在的样子（对着六个格子逐个看）

| 图上的格子 | agentsws 里对应什么 | 状态 |
|---|---|---|
| 客户 | `ObjectType: customer / contact / company`，客服共享包的对象 | ✅ 有类型、有 `ObjectRef`；但**没有一张"客户对象长什么样"的总表**，各包各定义 |
| 订单 | `OrderRow`（deck）、连接器 `list_orders` / `get_order`、活数据源缓存 | ✅ 真店端到端已通（09-11）；只在内存，没有"订单对象"的正式登记 |
| 实时状态 | 事件日志（21，hash 链）+ 审批项状态机（14）+ 变更账本（15） | ✅ 这是我们最强的一块 |
| 业务关系 | 岗位 = 人 × 职责 × 范围（05 / 44）；品牌 ⊃ 店铺 ⊃ 产品线；客户 ↔ 订单 ↔ 事项（37） | ✅ 关系存在，但**散在四个包里**，没有统一的"链接"概念 |
| 权限 | scopes（05）+ 范围过滤下推（19 §3）+ guardrail（15）| ✅ 已经是"按对象判权限"，比多数 Wiki 方案强 |
| 动作 | 连接器 Action（18，`action-side-effects.yml` 读 / 写标注）+ `ChangeKind`（15）+ staged change → 审批 → apply | ✅ 有，且写动作永远经账本 |

知识层这边：19 的 FactCard（带 `subject: ObjectRef`、来源、有效期、敏感级）、MemoryFact、KnowledgeSource，三层权限，检索带身份过滤下推——**这就是我们的 LLM Wiki**，而且它已经要求"每张事实卡指向一个对象"。

所以真正的缺口只有三个：
1. **没有登记表**：Agent 拿到一个 `ObjectRef` 不知道它有哪些属性、能连到什么、能对它做什么，只能靠各包的代码；
2. **知识层与操作层的边界没写死**：模型有时会把 Wiki 里的"上个月退款政策"当成实时状态，或者把订单表里的数字写进知识；
3. **调用顺序没规定**：问"这个客户的订单为什么还没发"时，应该先查对象（订单状态）再查知识（物流政策），现在靠提示词碰运气。

## 3. 建议：做一个薄的本体登记表，不做平台

### J1 本体登记表（Ontology Registry）= 契约的索引，不是新的存储

- 新包 `packages/ontology`：一张**只读**的登记表，登记三样东西：
  - **对象类型**：`customer / order / product / shop / matter / approval / change / person / assignment / range_group / product_line …`——每种：主键格式、属性（含敏感级）、真源在哪（平台 API / 本地账本 / 连接器）、新鲜度（实时 / 缓存 5 分钟 / 人写的）
  - **链接**：`order → customer`、`order → product[]`、`assignment → person / role / range[]`、`product_line → parent range`、`matter → customer / order`、`fact_card → subject`——每条：方向、基数、从哪查
  - **动作**：对某类对象能做什么，直接指向 18 的 Action id 与 15 的 `ChangeKind`，带风险级与"要不要审批"
- **登记表从契约生成**，不手写第二份：`packages/contracts` 的类型 + `action-side-effects.yml` + roles 的 scopes 是输入，`scripts/gen-ontology.mjs` 生成 `ontology.json`，CI 检查零漂移（同 SDK 的做法）。
- 给模型的形态：一份紧凑的"你能查什么、能做什么"说明，按岗位裁剪（只列他有权限的对象和动作），进 dsh 的系统提示 / 工具面；给人的形态：设置页一张"数据地图"。

### J2 知识层与操作层的边界，写进规范并在代码里拦

- **知识层只存文字与判断，不存状态**：FactCard 可以说"退款政策是 30 天"，不能说"订单 #1001 还没发货"——后者是操作层的实时状态，Wiki 里出现就是过时的。19 §4 进入管道加一条：带订单号 / 金额 / 库存数的句子进 Wiki 时降级为"历史案例"并打上"当时"的时间戳，不当事实。
- **操作层只经动作改**：任何对象的写都走连接器 Action + 账本，模型不能"记住"一个状态然后当真——这条已经是 15 的规矩，登记表只是让它可见。
- 模型回答里引用对象时带 `ObjectRef`（界面上渲染成可点的卡），引用知识时带 FactCard id——两种引用长得不一样，人一眼能分。

### J3 调用顺序：先对象，后知识，再动作

- 运行时（17）给 Agent 的工具面按"查对象（只读，按范围过滤）→ 查知识（带身份）→ 提议动作（staged change）"三组排列，登记表决定每组里有什么。
- 提示里固定一段："回答关于某个客户 / 订单的问题，先查它的当前状态，再查相关政策；两者矛盾以当前状态为准，并把矛盾报出来。"这段话从登记表生成，不手写。
- 模拟里加一条场景：Wiki 里有一条过时的"该订单已退款"，操作层显示未退款 → Agent 必须以操作层为准并出一张"知识过时"卡（24 的学习回路吃这张卡）。

### J4 不做什么

- 不引入 Palantir / 图数据库 / 单独的本体建模工具：我们的对象与关系已经在契约里，再建一份就是第二真源（40 §1 的大忌）。
- 不把 Wiki 换成知识图谱：文档问答用检索就够，把文档拆成三元组既贵又丢上下文。
- 不让用户"建本体"：对象类型由我们定义、随版本走；用户能建的是品牌 / 产品线 / 自定义岗位这类**实例**，不是类型。

## 4. 落点（估）

| 层 | 改什么 | 量 |
|---|---|---|
| 新包 `packages/ontology` | 登记表类型 + 从契约 / 副作用表 / roles 生成 `ontology.json` + 按岗位裁剪 + 零漂移检查 | 中 |
| 运行时（`runtime-direct` / `dsh-adapter`） | 工具面按三组排列；系统提示里的"能查什么能做什么"从登记表生成 | 小 |
| 知识（`packages/knowledge`） | 进入管道：带状态类数字的句子降级为历史案例；回答里对象引用与知识引用分开渲染 | 小 |
| 工作台 | 设置页"数据地图"（只读）；回答里 `ObjectRef` 渲染成可点卡 | 小 |
| 模拟 | 一条"知识过时 vs 实时状态"场景 | 小 |
| 文档 | 19 加边界条款；17 加调用顺序；ARCHITECTURE 加分层图 | 小 |

- J3 调用顺序先对象后知识再动作，提示与工具面从登记表生成，加一条模拟
