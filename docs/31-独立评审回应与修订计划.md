## 3. 安全机制修订（进规范）

### 3.1 权限：完整元组，不逐维并集（改 05 §4）
- EffectiveConfig 不再合并 scopes；**每次运行绑定一个 Assignment**，其 scopes 原样生效；一个人多职责 = 多个 Assignment，工作项决定用哪个
- 数据层过滤同时按 (domain, ops, range, sensitivity) 四元组判定，任一维不满足即拒
- 空 range 的 Assignment：token 拒签、查询返回空、界面标"未分配范围"

### 3.2 批准绑定执行快照（改 14 §4 §5 §7、15 §5）
- 创建审批项时生成 `execution_snapshot = hash(workspace, connection_id, target ObjectRef + record_version, recipients, final_payload, attachments hashes, executor_version, mandate_hash)`
- `decision_token` 绑定 `(item_id, revision, execution_snapshot)`；revision 变化 → 旧 token 失效、旧卡片刷新为"内容已更新，请重新审阅"
- apply 前重算快照，任一分量变化 → `failed{snapshot_mismatch}`；可幂等 kind 也不例外
- 额度**预占**：stage 时在 (assignment, kind, day) 计数器上预占，apply 成功转实、失败 / 过期释放；同目标同 kind 的 apply 串行（单一施行者队列）
- apply 结果三态：`applied / failed / unknown`；unknown → 查询确认（按 execution_id / 平台对象）→ 人工对账项；备份恢复后先跑对账再放开出站
- 父子顺序：含退款的回信，回信必须在退款 `applied` 之后发出；批准后有取消窗口（默认 2 分钟）
- `staged_action` v1 关闭；所有写只经已建模 kind

### 3.3 关系授权门禁（新增 15 §6.1、18 §2）
- provenance 只证明"读过"；对 refund / reship / address_change 增加 `authorization_check`：请求者（邮件发件人 / 会话对象）必须与目标订单的客户身份匹配（邮箱一致或经验证的关联），否则 block 并转人工核验
- 信息释放规则：Agent 不再持有高于 actor 的读权限（撤销"Agent 知道但不告诉人"作为 v1 原则）；输出通道清单（text、answer、summary、工具 URL、日志）统一过一遍脱敏
- 收件人门禁：outbound 的收件人必须是线程原有参与者或经验证的客户联系方式，不接受"模型从内容里解析出的新收件人"

### 3.4 自动化授权（改 05 §1.4、14 §9）
- 采纳率 = 体验指标，不解锁任何自动执行
- 每个 ChangeKind 有 `risk_class: low | medium | high`；v1：low（查单回复类）可 L2；medium / high（退款、补发、发布、配置、资金）**永远人审**
- 未来解锁条件：风险等级 + 真实结果核验（客户未投诉 / 无重开 / 无回滚）+ 代表性样本（按店铺 / 市场 / 模型 / skill 版本指纹分层）+ 损失上限；任一指纹变化 → 重新评估
- 样本量：单侧 95% 置信下界 ≥ 目标值，而非固定 30

### 3.5 隔离
- 公司端 v1：无第三方代码；个人端插件不得持有共享工作区 token（08 §2.5 删除该路径）
- 安装器默认开启 OpenConnector 鉴权与静态加密；未开启不启动
