## 1. SaaS 与开源中台的有机融合：共享代码，不合并用户

原则一句话：**同一份职责包代码，两种交付形态。** SaaS 是"托管 + 自带界面"的形态，开源中台是"本地 + 统一队列"的形态；用户选形态，不选功能。

### 1.1 三层结构

```
                 ┌──────────────────────────────────────────┐
                 │  共享包（开源，monorepo 里的 packages/*）   │
                 │  客服职责包 · 红人职责包：skills · Backend  │
                 │  契约实现 · 知识管道 · 围栏 · 账本 · evals  │
                 └───────────┬──────────────────┬───────────┘
                             │                  │
            ┌────────────────▼───────┐   ┌──────▼─────────────────────┐
            │ KefuAgents / KOLAgents │   │ agentsws 开源中台           │
            │ 托管 SaaS · 自带 UI     │   │ 本地 · 统一队列 · 多职责     │
            │ 自己的账号与计费        │   │ 自带账号 · 自带模型 key      │
            │ 远程 MCP（给 Codex 等） │   │                             │
            └────────────────────────┘   └────────────────────────────┘
```

- 上面那层是今天要搬的"能力"：KefuAgent 的邮箱接管、分类、起草、知识引导；KOLAgents 的插件采集、红人库、建联。搬 = 抽成共享包，SaaS 改为依赖这些包，而不是复制一份
- 两个下层各自活着：SaaS 继续给"只想用一个客服工具"或"用 Codex 接 MCP"的人；中台给"要一条队列管多个职责"的公司
- 修一个 bug、加一条话术规则，两边同时受益——这就是"有机"

### 1.2 用户层面的四个连接点（都不强迫迁移）

| 连接点 | 做法 | 谁受益 |
|---|---|---|
| 账号关联 | agentsws 账号可关联 SaaS 账号（反之亦然）；不合并计费、不合并数据 | 两边都用的人 |
| 能力互通 | SaaS 的远程 MCP / 无头 API 在中台里作为该职责包的**可选远程 Backend**（08 §7.2 的形态）：中台用户想用 KOLAgents 的公共红人库，点一下连接 | 中台用户得到托管数据；SaaS 得到入口 |
| 双向搬家 | SaaS 用户"导出到本地中台"；中台用户"升级到托管" | 用户随需求换形态，不换产品 |
| 一份知识 | SaaS 工作区的知识库与中台工作区的知识库同一格式（19 文档 + markdown 导出），可以互导 | 不锁定 |

### 1.3 不做的事

- 不把 SaaS 改成中台的前端；不停 SaaS 的 IMAP、不迁邮箱控制权（撤回 03 §7.2 那条"外部接入模式"的强制）
- 不做统一钱包（12 §4 的混合计费延后；两边各自收费）
- 不要求 SaaS 用户装中台

### 1.4 对第一阶段的影响

- 钩子 A 的客服职责包**先从 KefuAgent 里抽共享包**（分类、起草、知识引导、customer-care skill），再接进中台的审批与账本——比从零写快，且 SaaS 立刻能用上中台做好的围栏 / provenance / 关系授权门禁
- KOLAgents 的插件不动；中台侧只登记为"连接"类应用（钩子 B 时再接）

## 2. 许可证：区别、风险、建议

### 2.1 先分三大类

| 类 | 代表 | 别人拿了你的代码能做什么 | 必须回馈什么 |
|---|---|---|---|
| **宽松（permissive）** | MIT、Apache-2.0、BSD | 随便用：改、闭源、卖、做成云服务都行 | 只需保留版权声明（Apache 还要求标注改动、附带 NOTICE） |
| **强 copyleft** | GPL-3.0 | 可以用、改、卖，但**分发**给别人时必须连源码一起开，且衍生作品也得用 GPL | 分发即开源 |
| **网络 copyleft** | **AGPL-3.0** | 同 GPL，且**通过网络提供服务**也算分发：谁把它做成 SaaS 给别人用，就得开自己的改动 | 提供服务即开源 |

还有两类常被误当开源的：

| 类 | 代表 | 本质 |
|---|---|---|
| 弱 copyleft | MPL-2.0、LGPL | 改了我的文件要开，你自己新写的文件可以不开；折中 |
| **源码可见但不是开源** | BSL 1.1（HashiCorp、Sentry）、SSPL（MongoDB）、Elastic License | 禁止拿去做竞争性的云服务；**不被 OSI 认定为开源**，社区一般不买账，GitHub 上会被指出"这不是开源" |

### 2.2 几个只有做了才知道的点

- **专利条款**：Apache-2.0 自带专利授权（贡献者不能回头用专利告用户），MIT 没有。企业法务更放心 Apache
- **上游兼容**：我们依赖 dsh（MIT）、OpenConnector（Apache-2.0）、Commerce Agents 移植代码（Apache-2.0）、Cordis（MIT）。宽松许可证之间随便混；如果我们选 AGPL，仍可以用这些 MIT / Apache 依赖（它们允许被更严格的许可证包含），反过来不行
- **改许可证的方向**：宽松 → 严格（HashiCorp 2023 年 MPL → BSL）会引发社区分裂（OpenTofu 分叉）；严格 → 宽松没人反对。所以**一开始宽松，以后想收紧很难；一开始严格，以后放开容易**——这是唯一要提前想的
- **许可证管不了名字**：任何许可证都不阻止别人 fork 后改名发布；阻止别人用"agentsws"这个名字靠**商标政策**，是另一份文件
- **贡献者协议**：接受外部 PR 前要定 DCO（贡献者在提交里签一行"我有权贡献"，轻）还是 CLA（签协议，可含版权转让，重）。想保留将来改许可证或双许可的能力，需要 CLA；只想安全接受贡献，DCO 够
- **数据与模型不在许可证里**：合成数据集、职责模板、skill 文本可以用 CC-BY-4.0 之类的内容许可证，或干脆同 Apache-2.0

### 2.3 对我们的取舍

| 目标 | 指向 |
|---|---|
| "别处收费我们免费开源"、撬动最多人用、社群贡献职责包 | **宽松**。AGPL 会让很多公司法务直接拒绝内网部署，也让代运营 / 服务商不敢基于它做生意 |
| 怕大厂或服务商把它做成托管服务和我们竞争 | 这是 AGPL / BSL 的用武之地。但我们的护城河按 07 / 32 的定义是社群、职责包生态、上游位置、内容，不是代码本身；而且我们自己的托管档一样要开源版全功能——用 AGPL 防别人托管，等于承认托管是我们唯一收入，与"开源撬动人"矛盾 |
| 三个 SaaS 依赖共享包 | 宽松许可证下 SaaS 闭源部分（计费、托管运维）不受影响；AGPL 下共享包的改动也要开（我们本来就开，无所谓） |
| 上游贡献（dsh-channels、OpenConnector provider） | 贡献回去的部分必须按对方许可证（MIT / Apache）；我们自己 Apache 最顺 |

**建议**：

| 对象 | 许可证 |
|---|---|
| 中台内核、契约、适配层、连接器、职责包、skill、模拟回路、DevKit 规范 | **Apache-2.0** |
| 合成数据集、模板文本 | Apache-2.0（省事）或 CC-BY-4.0 |
| 名字与 logo | 商标政策（README 里一段：可以 fork，不能叫 agentsws） |
| 贡献 | DCO（`Signed-off-by`），暂不要 CLA |
| 将来的托管专有部分（Connect 代持应用、运维面板） | 不开源即可，不需要给开源版加限制 |

一句话：**Apache-2.0 + 商标政策 + DCO。** 这与你"开源、有吸引力、别处收费我们免费"的路线一致，也与全部上游兼容。如果以后真的出现"别人托管我们的东西赚钱而社群没得到回馈"的情况，再考虑对**新版本**收紧——那时你已经有社群和话语权。
