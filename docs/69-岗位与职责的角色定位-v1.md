## 0. 一句话

每个岗位、每条职责都有一段**角色定位**（persona）：你是谁、你负责什么、**你不负责什么、遇到了转给哪个岗位**、怎么做、什么口气、哪些事必须出卡。它进系统提示，排在技能与工具前面。公司可以在右栏改写（另存一层，包里的原文随时还原）。

66 #1 那条记录查下来的结论是：**路由没错**。「在油管上找 20 个频道」确实落到了 `kol.youtube`。错在落下去之后——那次运行的系统提示里从头到尾没有一句「你是谁」，于是模型照着手边唯一一份像样的剧本（客服）答了一句退货窗口。

`packages/contracts/src/roles.ts` 里 `persona?: string` 这个格子从 WP5 就在，四十多条职责**一条都没填**，也**没有任何代码读它**。这一单把它填上、接进三个运行时、给用户一个能改的地方，并且钉住「不许再串岗」。

## 1. 两层 persona

```
Position.persona   岗位那一段：这个岗位在公司里是干什么的、什么活不归它
RoleDefinition.persona   职责那一段：这个岗位里的这一条活该怎么干
```

两段都写，因为**串岗有两种**：

| | 例子 | 谁拦住 |
|---|---|---|
| 岗位之间串 | 红人营销岗位去答客户的退款窗口 | 岗位 persona 的「你不负责」 |
| 岗位内部串 | 红人岗位里 YouTube 那条去管 TikTok | 职责 persona 的「你不负责」 |

只写职责那一层，第一种串岗照样发生——一个岗位下五条职责各说一遍"我不管退款"，不如岗位那一层说一遍。

**只手写中文**（WP226 起，见 §1.1）。格子仍是 `{ zh, en }`，老的纯字符串写法也认（契约只加不删）；`en` 由脚本从中文翻出来，不再是手写的真源。

要的那一份是空的就**回落另一份**：空白的 persona 比语言不对糟得多（前者让 Agent 退回"我是谁都不知道"，后者至少还知道自己是谁）。

### 1.1 为什么只写一份中文（WP226，Luoye 10-05）

WP120 那一版是中英各手写一份，理由是「英文界面下送中文 persona，模型会拿中文回英文客户」。Luoye 10-05 问：这不是多此一举吗？查下来两份手工维护的代价已经出来了——**14 条英文 persona 混着中文**（docs/91 §3.3：模板拼名字时把中文名塞进了「Who you are」），另有几条英文悄悄多说了中文里没有的话。两份字要说同一件事，靠人对是对不齐的。

而当初那条理由也站不住：真正管"用什么语言回"的不是 persona 用哪种语言写，是**有没有一句话明说**。所以现在：

| | 怎么做 |
|---|---|
| 真源 | 岗位 / 职责 yml 里只写 `persona.zh`。老的 `{ zh, en }` 照样读得进 |
| 进系统提示 | **一律送中文 persona**，后面紧跟一条固定的**回复语言规则**（§3.3）。模型读中文说明、照规则用对方的语言回，比送一份机翻英文更稳 |
| 英文从哪来 | `node scripts/gen-persona-en.mjs` 调模型翻译（开发者本机跑，key 只从环境变量来、脚本不读 `.env*`），产物 `packages/roles/persona-en.generated.json` 签进仓库，**每条带来源中文的哈希** |
| 英文给谁用 | 英文界面里**看**与**改**的地方：右栏「角色」面板（公司覆盖、职责详情） |
| 中文改了没重出 | 读职责时哈希对不上就**不用**那份旧英文——英文界面显示中文 + 「未翻译」。`gen-persona-en.mjs --check` 只比哈希、不调模型，CI 里打警告、不卡合并 |

生成脚本自己守两条：**没有汉字与全角标点**、**六个英文小标题都在**（串岗测试按 `Not yours` 找那一段）；翻三次不合格就不写。没有 key 时可以 `--export` 导出中文、换个工具翻好再 `--import` 导回，导回同样逐条校验。

**岗位反查不出唯一那一个时，岗位那一段整段不出**（54 §3「不猜一个」）：一条职责挂在两个岗位里、或一个都不挂（`common.owner` / `common.member`），猜错等于把别的岗位的规矩喂给这次运行。

## 2. 固定骨架：六段，一段都不许省

每段 persona 照这六个小标题写，**小标题逐字出现在正文里**（机器就按这六个词查，不做自然语言判断——那种判断会在半年后悄悄变松）：

| # | 中文小标题 | 英文小标题 | 写什么 |
|---|---|---|---|
| 1 | `你是谁` | `Who you are` | 一句话。这个岗位 / 这条职责在公司里是哪一位 |
| 2 | `你负责` | `You handle` | 3–5 条，名词短语，不写形容词 |
| 3 | **`你不负责`** | **`Not yours`** | **哪几件事不归你、各自转给哪个岗位**（防串岗的唯一一句） |
| 4 | `怎么做` | `How you work` | 做事顺序与判断口径；查不到就说查不到 |
| 5 | `口气` | `Tone` | 对外说话的样子（短句 / 先结论 / 不许诺……） |
| 6 | `必须出卡` | `Always ask` | 哪些动作永远要人拍板——**与 guardrail 一致，不另起一套** |

顺序就是读的顺序：先知道自己是谁，才谈得上负责什么；「你不负责」紧跟在「你负责」后面，因为这两段要对着读才看得出边界在哪。

**长度**：目标是每段 ≤ 200 字的中文正文。机器上限留出六个小标题本身（约 30 字）的开销：**中文 260**。

WP226 起**英文不再卡字数**，`checkPersona` 对英文只查一样：**没有汉字**（含全角标点）。英文是从中文翻出来的，长短跟着中文走；再卡一遍英文，只会逼着翻译删掉一件中文里写了的事。`MAX_PERSONA_CHARS.en` 这个数留着（导出只加不删），没有代码再读它。六个英文小标题在不在，由生成脚本查（`checkGeneratedPersonaEn`）。

**覆盖纪律**：全部四十多条职责与全部岗位模板都要写，**一条都不许空**。两刀分工：

| 谁 | 查什么 | 为什么在这一层 |
|---|---|---|
| yml schema（`checkRoleExtras` / `checkPositionExtras` → `checkPersona`） | 中文：六段缺一段、超长；英文（填了才查）：混汉字 | 管「填了就得填对」——读一条查一条 |
| `node scripts/gen-ontology.mjs --check` | **为空** | 管「一条都不许空」——那是**整包**的纪律，而这个脚本正是唯一一个把四十多条职责与十个岗位一次全读进来的地方 |

空这一刀为什么不塞进 schema：schema 看不见"别的文件都填了、就这一条没填"，而漏写的后果不是编译错，是 69 §0 那条亲测记录重演一遍——新加一条职责、忘了写 persona，那条职责的 Agent 就又没有"你是谁"了，没有人会在半年后想起来去数一遍。

第 6 段「必须出卡」抄的是 guardrail 已有的口径（14 §1 的 L1/L2/L3、15 §5 的"通过 ≠ 施行"）。**不许在 persona 里新发明一条审批规矩**：提示里说"这个要问人"而门禁放行，模型就会照门禁走；反过来提示不说而门禁拦，用户看到的是一张没有来由的卡。两边不一致时以 guardrail 为准，改 persona。

## 3. 装配：这几段排在系统提示的哪里

17 §1 的装配顺序里，persona 是**静态前缀的第一节**。完整次序：

```
品牌（70 §3 的四个槽位，取不到就整节不出）
  → 岗位 persona（order 10）
  → 职责 persona（order 20）
  → 回复语言规则（order 22，WP226，§3.3）
  → 说话规矩（order 25，WP153：不提工具名）
  → 技能索引行（六层叠完的那一份，24 §1）
  → 47 J3「你能查什么、能做什么」（本体登记表生成）
  → 工具定义
  → 策略层 / 工作项上下文 / app_events / 用户消息
```

读下来是从大到小：这家公司 → 这个岗位 → 这条活 → 它会什么 → 它能碰什么。

**三节都在 `PromptSection[]` 里，一个函数出**（`personaSections()`，`packages/roles/src/persona.ts`）。三个运行时不各拼一份：

| 运行时 | persona 从哪进提示 |
|---|---|
| `stub` | `assemblePrompt()`（`packages/stand-ins`）——17 §1 的铁律：装配定义只有一处 |
| `direct` | 同上（`assembleDirect` 就是在 `assemblePrompt` 之上加两个产出工具定义） |
| `dsh` | `installGate` 把它写进 `agentsws:persona` 那**一个** `complete` 段 |

dsh 那一栏要单独说一句：16 §2 的公司端 preset 白名单里 **`complete` 段是唯一有效段**，我们自己注册的这一段会把 dsh 自带的 `deployment:persona-prefix` / `-suffix` 整段遮掉。所以"persona 进没进提示"在 dsh 这儿不是"多加一段"的问题，而是"**那唯一一段里有没有它**"——浏览器（55 §3）、终端（WP89）与 47 J3 那一段也都只能写进这一段，理由逐字相同。

**品牌那一节一格都不许编**：`brand_name` 取不到就整句不写，而不是写"你们公司"。模型读到一句编出来的品牌定位，会把它当事实用进开发信里。四个槽位（品牌名 / 一句话定位 / 主要市场 / 口吻样例）加 WP122 预留的「视觉气质」，每一格都是"取不到就不写那一句"。

### 3.1 公司改写完，下一次运行就生效

运行时装提示时**现查**覆盖表（`personaSections` 是 `RuntimeOptions` 上的一个晚绑定回调，与 `vertical` / `browser` 同一条理由）。改了 persona 不用重启进程——它进系统提示，用户在右栏按下保存，下一件事就该是新的那一份。

### 3.2 stub 改成认职责

WP117 给红人开了第一个岔口（`kolBranch`），但**剩下三十多条职责仍然往下掉进客服那条路**——于是投放岗位在演示里也会去问一句退货窗口。那与 69 §0 是同一个毛病，只是还没有人去点它。

现在 stub 按职责选剧本（`packages/stand-ins/src/runtime/playbook.ts`）：

| 判据 | 剧本 |
|---|---|
| `role.domain === 'kol'` | 红人（WP117 那一套） |
| `role.domain === 'amz'` | 客服 |
| `dtc.support` / `dtc.live-chat` / `dtc.community-support` | 客服 |
| **其余一律** | **没有剧本** |

`dtc` 故意**不**整域映射到客服：它是唯一一个"一个域里两种活"的域（客服三条 + 运营四条），整域映射等于让店铺管理去问退货窗口。

没有剧本时回一句人话——说清是哪条职责、说清这是**演示的限制**（接上真模型照常工作）、并且**不调工具、不 stage、不起草、不出一张卡**。最后那半句是重点：出一张"请批准"的卡去问一件桩根本没做的事，比什么都不做糟得多。

判据只有 `role_id`，**不看意图词**。一件事被岗位路由落到这条职责上之后，它就是这条职责的活；看意图词的后果是一句带"退款"两个字的话又会把投放岗位拽回客服那条路。

真运行时（direct / dsh）不经这个文件——那边由模型自己读 persona 决定怎么做。

## 4. 用户可见可改：右栏「角色」面板

第三栏「记忆 / 技能 / 知识 / 额度」后面加一格**「角色」**（`registerPanelType` + `registerPanelBody`，registry 接口一个字没动，36 §9）。

为什么在第三栏而不在设置页：persona 是"当前这个岗位 / 这条职责"的一部分，与那四个面板是同一类东西——人是在**干这条活的时候**想起"它怎么会这么说话"的，不是在设置页里。

面板上看得见的：

| 作用域 | 看到什么 |
|---|---|
| 岗位（`scope.tier === 'position'`） | 这个岗位的定位 + 它下面每条职责的清单（点一条跳到那条职责自己的定位） |
| 职责（`scope.tier === 'role'`） | 这条职责的定位 + 它属于哪个岗位（反查不出唯一那一个就说清为什么没有岗位段） |

三条硬规矩：

1. **包里的原文永远看得见**。改写是另存的一层，面板上同时有"现在生效的"与"包里的原文"，「还原」按钮拿后者比——与技能的六层覆盖同一条规矩（24 §1）。改过的那一份标出来，没改过就没有「还原」。
2. **能不能改由服务端说**（同 `memory-panel` 的 `can_edit`）。界面上不做第二遍判断：非 owner 点「改写」拿到的是 403 与一句人话，不是一个静默失败的输入框。
3. **改的是一段话，不是一张表**（36 §13.2）。这一栏没有"新增一行 / 删除一行 / 拖动排序"——persona 是内容，内容归数据；这里给的是「预览 + 改一段」。

### 4.1 覆盖层的三条纪律

| 纪律 | 为什么 |
|---|---|
| **包里的原文一个字不动** | 覆盖是另存的一层，所以「还原」永远做得到 |
| **只有公司层，没有个人层** | 个人改 persona = 每个人手里的 Agent 说不同的话，而 persona 是公司对外的口径。要个性化的东西在个人技能层里（24 §1 的 `personal`），不在这儿 |
| **只有 owner 改得动** | 它进系统提示，改了它等于改了 Agent 对外说什么 |
| **每改一次记一条审计** | `persona.overridden` / `persona.reverted`，都带着改了谁（`subject_kind` + `subject_id`） |

**两道门，不是重复**：路由那一关要 `policy.stage`（tuple authz），端口里再判一次"是不是 owner"。tuple authz 答不出后一个问题。

**公司只改中文**（WP226）。改写框里永远是中文那一份（英文界面下也是，框上一行字说明"改的是 Agent 读的那一份"）。改完之后英文怎么办，二选一选了**不在保存时调翻译**：

| | 做法 |
|---|---|
| 覆盖后的中文与包里一样 | 英文照用包里生成的那份 |
| 覆盖后的中文变了 | 英文那一格**留空** = 未翻译。英文界面显示中文原文 + 一个「未翻译」标记（`PersonaView.untranslated`）；Agent 读的本来就是中文，不受影响 |

为什么不在保存时调一次翻译：保存是 owner 在右栏点一下的事，挂一次模型调用就多了花钱、要 key、会失败、会慢四样，换来的只是英文界面上那一段的显示；机翻失败时还只能二选一——为了一段显示挡住真正进提示的中文，或者存一份没校验过的英文。显示中文 + 标记是诚实的，也不挡人。

也不再"另一边从现在生效的那一份补齐"：那样补进去的是包里按旧中文翻的英文，与公司刚写的中文说的不是同一件事。老的覆盖里两边都填了的（WP226 之前存下的）照原样认。英文那一格写了中文的覆盖直接 400。

### 4.2 覆盖存哪儿

一个 JSON 文件（`<数据目录>/personas.json`），不开 sqlite 表。这份数据一共几十行、几乎不变，而且要能被人直接看见——"公司把红人那条改成什么了"是排障时第一个要看的东西。文件坏了不让进程起不来：当成"没有覆盖"，包里的原文照常生效。

**一份，不按品牌分**。69 §4 定的是「公司层覆盖」，而岗位模板与职责定义本来就是制度层的东西（跨品牌共用一份，同 `org.positions`）。按品牌各存一份的后果是同一条职责在两个品牌里说两套话，而没有人记得去同步第二份。

### 4.3 岗位 persona 的原文以包里的 yml 为准

`org.positions()` 存下来的那一行管的是"这家公司有哪些岗位、各挂哪几条职责"——它种下去的那一刻就**没有** `persona` 字段。所以取岗位原文是两步：先用存下来的那一行确认公司确实有这个岗位，再去 `packages/roles/positions/<id>.yml` 取原文。

不把 persona 抄进存下来的那一行：抄进去等于把原文**冻在首次设置那天**，之后包里改好的措辞一个都到不了老工作区，而「还原」还原的也会是那份旧快照。

公司自己建的岗位包里没有 → 没有原文 → 整段不出（54 §3「不猜一个」）。

## 5. 怎么钉住它：串岗测试与"别编"

persona 是一段文字，删掉半句不会有编译错、不会有场景变红——只会在半年后的某次真模型运行里，红人岗位又开始答退款窗口。所以它必须有一条**机器读得懂的护栏**。四层，各钉一件事：

| 层 | 文件 | 钉什么 |
|---|---|---|
| 内容 | `packages/roles/test/persona-crosswalk.test.ts` | 包里**真的那几段**：红人五条的「你不负责」里写死了"客户退款物流→客服""自己账号发帖→社媒运营"；客服四条写死了"写开发信→红人营销"；投放四条写死了"商品价与促销→网站运营"；社媒九条一律"客户问题转客服，哪怕在评论区 / 群里"；同一个平台名两个岗位（`social.x` ⇄ `kol.x`）互相点名 |
| 装配 | `packages/runtime-direct/test/persona-sections.test.ts`、`packages/dsh-adapter/test/persona-sections.test.ts` | 那几段**真的进了送模型的文本**：岗位名、职责名、「你不负责」都在；岗位在前职责在后；dsh 那边它在**唯一有效**的 complete 段里 |
| 路由 | `packs/dtc-3c-3p/scenarios/org/positions-stay-in-lane.yml` | 五个岗位各发一句典型的活，落到对的那条职责上；同一个人挂五个岗位（路由必须在**同一个人**的多条分配之间分得清，才证明分开它们的是职责定义而不是"他只有这一条职责"） |
| 服务 | `apps/server/test/personas.test.ts` | 看 / 改 / 还原 / 审计 / 两道门 / 改写完下一次运行就是新的那一份 |

**为什么五个岗位都发一句，而不是只发红人那一句**：串岗不是红人独有的毛病。只修出问题的那一条，等于等着下一个岗位再犯一次同样的错。

### 5.1 别编

persona 里出现的每一个事实都必须有出处。两条具体的：

- **品牌那一节**：四个槽位取不到就整句不写，不写"你们公司"。模型读到一句编出来的品牌定位，会把它当事实用进开发信里。
- **数字与日期**：「怎么做」那一段只说"先查真实记录、查不到就说查不到、不猜日期不猜金额"，**不**把任何一个具体窗口天数写进 persona。窗口在事实卡里（19），写死在 persona 里的后果是它过期了还在被引用。

### 5.2 与技能六层的关系

技能是 `package → company → department → position → role → personal` 六层叠加（24 §1）。persona **只有两层**（岗位 / 职责）加一层公司覆盖，不是六层：

| | 技能 | persona |
|---|---|---|
| 层数 | 六层 | 岗位 + 职责两层，各自可被公司层覆盖 |
| 个人层 | 有（`personal`） | **没有**——公司对外的口径不该一人一份 |
| 部门层 | 有 | 没有——部门不是用户面对的单位（54：用户面对的是岗位） |
| 叠在哪 | `effectiveConfig` 之后、装提示之前 | 同位置（`personaSections()`） |

两者的**覆盖纪律相同**：上游的东西不被下游改写，包里的原文永远留着、随时还原。

### 3.3 语言：送中文 persona + 一条回复语言规则（WP226）

（这一节原来写的是"运行时没传 `lang`、一律送中文那份，是一处已知的留尾"。WP226 把它从留尾改成了定规。）

三个运行时送进模型的一律是**中文** persona（§1.1：中文是唯一手写的真源）。紧跟在职责那一节后面是一条固定规则（`replyLanguageSection`，`packages/roles/src/persona.ts`）：

> 你对用户说的每一句话都用中文：边做边说的过程话（比如"我先查一下……"）、给用户的回复、摘要和卡片，哪怕来信、资料、工具结果是英文。只有要发出去的那份稿子（起草工具里的正文和主题，给客户、红人、媒体、平台上的人）用对方来信的语言：对方写英文就写英文；没有来信可对照时（主动开发信、发帖），用目标市场的语言。

（WP232 改的措辞：10-05 真模型实测草稿跟来信写成英文是对的，可过程话也跟着成了英文。旧句子先讲"对方写英文就回英文"、最后半句才说对内，且"说明"没点到过程话。现在先说对内、点名过程话，再把"跟来信语言"收窄到外发稿；起草工具的 `body` / `subject` 参数说明里另有同一句——`@agentsws/stand-ins` 的 `DRAFT_BODY_DESCRIPTION`，dsh 与 direct 同一份。若真模型复测仍冒英文过程话，下一步是把这一节挪到提示最末。）

这一句中英各有一版，按**界面语言**选：它说的"对内用哪种语言"就是界面语言。服务端还没有"工作区界面语言"这一格（界面语言是前端偏好，`RunRequest` 上也没有 locale），所以运行时现在送中文那一版；模拟世界按 pack 的 `locales.operators` 选。哪天工作区有了界面语言，`runtime.ts` 里那一行 `replyLanguageSection('zh')` 换成取工作区的值即可。

三条路拿到同一份字节：stub / direct 走 `assemblePrompt`，dsh 写进唯一那个 `complete` 段（§3 那张表）。钉在 `apps/server/test/reply-words.test.ts`（真 `createRuntime`：排在职责之后、说话规矩之前，系统提示里没有英文 persona）与 `packages/dsh-adapter/test/persona-sections.test.ts`。

**实测与备选**：这条规则管不管用，要真模型跑英文客户来信才看得出（fast 档的替身模型不读提示）。如果实测发现英文客户下回成中文，备选是英文界面送生成的那份英文 persona——不在这一单里改口径，结果见 `docs/briefs/reports/WP226.md`。
