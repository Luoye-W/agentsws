## 1. RunRequest（协同服务 → 运行时适配器）

```ts
type RunRequest = {
  id: string; schema_version: 1; workspace_id: string
  kind: 'work_item' | 'scheduled' | 'workflow_step' | 'extraction' | 'reflection' | 'dev_task' | 'simulation'
  actor: { person_id: string; assignment_id: string; role_id: string }     // 以谁的身份、哪个职责
  work_item?: { id: string; conversation_id: string; role_id: string }
  trigger: { event_id: string; source: 'inbound' | 'schedule' | 'workflow' | 'approval_result' | 'manual' | 'sentinel' }

  context: ContextItem[]          // §2 注入清单，每项带 source_ref，运行时逐项发 context.injected 事件
  grounding: GroundingRule[]      // 05 §1.8；运行时若不支持 tool_choice 则由宿主预取并作为 ContextItem 注入
  tools: {
    allow: string[]               // 全名 allowlist（tools.restrict）；含 OpenConnector MCP 的发现工具
    connect_token: string         // role-read token（08 §2.2）
    side_effect_policy: 'personal' | 'executor'   // 16 §3：executor 下 write_external 一律 block
  }
  skills: SkillRef[]              // 05 §1.5，含叠加后的解析结果（个人 > 部门 > 公司 > 包）
  persona: { sections: PromptSection[] }          // company.md + 职责 persona；每段有 id，记事件
  budget: { max_tokens: number; max_tool_calls: number; max_seconds: number; max_cost_base: number }
  expectations: { outputs: ('draft' | 'staged_change' | 'proposal' | 'answer' | 'dev_result' | 'none')[]; must_stage_if_change_requested: boolean }
  runtime: { preset: string; profile: string; plugins: string[]; model: ModelRef; seed?: number }   // seed 给模拟
  idempotency_key: string         // 同一 trigger 重复投递不重复跑
}

type ContextItem = {
  id: string; kind: 'customer' | 'thread' | 'order' | 'fact_card' | 'memory' | 'summary' | 'prefetch' | 'app_events' | 'policy'
  source_ref: ObjectRef | string  // 从哪来（记录 id / 事件 id）
  sensitivity: Sensitivity        // 05 §1.1；> actor 可见级的项 Agent 可读但输出侧脱敏
  content: unknown                // 已 fencing（入口统一做）
  bytes: number
}
```

上下文装配顺序（决定 prompt 缓存命中）：静态前缀（persona、skills 索引行、**本体登记表那一段**、工具定义）→ 策略层（constraint 类必注入）→ 工作项上下文（按新近度到 cap）→ `app_events`（"自你上次回复以来发生了什么"）→ 用户消息。静态前缀字节稳定，测试断言重建后逐字节相同。工具定义本身按 §5.1 的三组排列。

## 2. 事件流（运行时 → 协同服务，SSE / WS，全部落事件日志）

| 事件 | 载荷 | 说明 |
|---|---|---|
| `run.started` | request_id, runtime, model | |
| `context.injected` | item_id, kind, bytes, hash | 每个 ContextItem 一条；日志回放可重组 prompt |
| `prompt.assembled` | hash, static_prefix_hash, total_tokens | 缓存与审计 |
| `text.delta` | text | |
| `tool.call` | call_id, tool, input（脱敏） | |
| `tool.result` | call_id, status: ok / error / blocked, reason?, provenance_added[] | blocked = 门禁拒绝 |
| `change.staged` | change_id | 与 15 联动 |
| `proposal.created` | approval_item_id, kind | 14 |
| `ui` / `ui.partial` | component, payload | 积木（服务端 enrichment 后） |
| `progress` | step, note | |
| `budget.warning` / `budget.exhausted` | which, used, cap | 耗尽即中断，close_open_tool_uses |
| `run.completed` | usage{in, out, cached, cost_base}, outputs[], summary | |
| `run.failed` | error{code, retryable} | |

十种核心事件对齐 Commerce Agents；`context.injected` 与 `prompt.assembled` 是我们为铁律加的。

## 4. 运行时适配器契约（任何运行时都实现）

```ts
interface RuntimeAdapter {
  capabilities(): { tool_choice: boolean; streaming: boolean; followup: boolean; seedable: boolean }
  run(req: RunRequest, sink: (e: RunEvent) => void, signal: AbortSignal): Promise<RunResult>
  followup?(session_ref, event: AppEvent): Promise<void>      // 有会话概念的运行时（dsh）可选
  health(): Promise<Health>
}
```

| 实现 | 备注 |
|---|---|
| `dsh-adapter` | SDK 起 headless run；preset = 职责；`pre-execute` 里查 allowlist + provenance + guardrail；`post-execute` 做 fencing + provenance 写入 + 产物登记；`approval answerer` 把 `ctx.approval.request` 转成审批项并等待（或按额度自动答）；`systemPrompt.section/context` 注入 ContextItem 并发事件 |
| `direct-llm` | 不经 dsh，自己跑 turn loop（Commerce Agents 移植），给云端大脑与无 dsh 场景 |
| `replay` | 录制回放：按 request hash 返回记录的事件流（模拟 realistic 档） |
| `stub` | 规则生成草稿（模拟 fast 档） |
| `dev-executor` | 编码 Agent：dsh headless / Claude Code / Codex；输入 DevTask，输出 dev_result |

dsh-adapter 契约测试钉住的 seam：`tools/pre-execute` 返回 allow/deny/ask 语义、`post-execute` 可 replace/enrich/block、answerer waterfall、`section`/`context` 落成持久快照、`tools.restrict` 在 scoped context 生效、SDK `run()`/`subscribe()` 事件形状、preset 挂载与继承。任一红 = 不升级。

## 5. 规则

1. **无状态**：运行不读上一次运行的会话文件；需要历史就放进 `summary` / `thread` ContextItem
2. **fencing 在入口**：ContextItem.content 进 RunRequest 前已围栏；运行时不再信任任何外部文本
3. **预算耗尽**：运行时必须补齐未闭合的工具调用再结束；产物已 stage 的保留，未 stage 的丢弃并记事件
4. **grounding**：命中即先调工具；运行时不支持强制则宿主预取，预取结果作为 `prefetch` ContextItem
5. **app_events**：自上次回复以来的外部事件（客户回信、付款到账、审批结果）以一条 ContextItem 注入，格式固定 `[App events since your last reply: …]`
6. **中断**：AbortSignal 触发 → `run.cancelled`，同"预算耗尽"处理
7. **幂等**：同 `idempotency_key` 的 RunRequest 24h 内返回原 RunResult
8. **调用顺序：先对象、后知识、再动作**（47 J3，WP52）——见 §5.1

### 5.1 调用顺序（47 J3）

工具面按三组排列，**组的先后是纪律，组内按名字**（字节稳定，17 §6.2）：

| 组 | 装的是什么 | 纪律 |
|---|---|---|
| ① 查对象 | 只读 Action 与命名查询（订单、客户、商品…） | 按范围过滤已经在网关那一层做完了 |
| ② 查知识 | `search_policies` 一类的检索 | 带身份（19 §3 过滤下推） |
| ③ 提议动作 | `stage_refund` / `draft_reply` | 只产出待批提案，写永远经账本（15 §5） |

模型是从上往下扫工具表的，顺序本身就是一句提示：把"现在是什么样"摆在"政策怎么说"前面。

静态前缀里还多一段**"你能查什么、能做什么"**，按这次运行的工具面裁剪 47 J1 的本体登记表
生成（`@agentsws/ontology` 的 `runOntologyBrief`，≤ 1500 字），末尾是一句固定话：

> 回答关于某个客户 / 订单的问题，先查它的当前状态，再查相关政策；两者矛盾以当前状态为准，并把矛盾报出来。

**这段话从登记表生成，不手写**：代码里只有一处（`ORDER_RULE`），三个运行时与设置页的
"数据地图"都用它。它是纯函数（输入只有 `actor` 与 `tools.allow`），所以 §6 用例 1 的
回放铁律照旧成立——从事件日志重组 prompt 仍然逐字节一致。

## 6. 一致性用例

1. 回放事件日志重组 prompt，与 `prompt.assembled.hash` 一致（铁律自动校验）
2. 静态前缀两次装配逐字节相同
3. 不在 allow 的工具调用 → `tool.result{blocked}`，不到达工具
4. 预算 max_tool_calls=3，第 4 次调用 → `budget.exhausted`，未闭合调用被补齐
5. grounding 命中 + 运行时无 tool_choice → 第一条 ContextItem 是 prefetch
6. `must_stage_if_change_requested` 且模型未 stage → run.completed 带 `no_stage` 标记（15 §4.4）
7. replay 运行时对同一 RunRequest 返回相同事件序列（seed 固定）
8. sensitivity 高于 actor 的 ContextItem 内容出现在草稿里 → 14 预检脱敏拦下
9. （47 J3）工具面三组排列：读对象的工具排在查知识之前，产出工具永远在最后一组；
   只换顺序不换名字，工具集与 `tools.allow` 逐个对得上
10. （47 J3）问"这一单退了没有"而 Wiki 里有一条过时的"已退款"：第一次工具调用是 `get_order`
    不是 `search_policies`，回答以操作层为准，并出一张"知识过时"卡
    （`packs/dtc-3c-3p/scenarios/knowledge/stale-fact-vs-live-state.yml`，三个运行时都跑）
