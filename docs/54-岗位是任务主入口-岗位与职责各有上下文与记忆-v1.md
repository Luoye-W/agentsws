## 0. 一句话

用户面对的是**岗位**（客服、网站运营、红人营销……），不是职责。开一件事 = 交给一个岗位；岗位里的 Agent 自己判断该走哪条职责、用哪条职责的额度与权限去做（**路由，不是权限并集**——05 §4 的"不做跨 Assignment 并集"不变）。职责入口保留给"我就要它用售后那条规则来做"的人。岗位与职责各有一层记忆：岗位记的是"这个岗位在这家公司怎么做事"，职责记的是"这条活儿的专业教训"。

## 1. 对象（Q1）

```
Position（岗位模板，05 §2，不变）
└─ PositionInstance（岗位实体，新）：一个工作区里"网站运营"这个岗位本身
     ├─ holders：谁在做（算出来的：名下有该岗位默认职责全集的人，05 §2 原则不变）
     ├─ roles：展开的职责 → 各自的 Assignment（已有）
     ├─ memory：岗位记忆（技能层 `position` + 教训池里提升到岗位层的条目）
     └─ matters：`position_id` 挂这个岗位的事项（37 的 Matter 已有 `position_id?`）
Role（职责，05 §1，不变）
     └─ memory：职责记忆（技能层 `role` + 提升到职责层的教训）
```

- `Matter` 加 `entry: 'position' | 'role'`（从哪儿开的）与 `role_id?`（职责入口时指定；岗位入口时由路由填、可换）。
- 技能层从四层变六层：`package → company → department → position → role → personal`（越靠后越具体、越优先；只加不删，现有四层的语义与文件一个不动）。
- 教训（learning）提升目标加 `position` / `role` 两档：一条教训可以从个人层提到"这个岗位"或"这条职责"，同岗位的其他人 / 同职责的其他分配都吃到。

## 2. 入口（Q2）

| 入口 | 谁用 | 做什么 |
|---|---|---|
| **岗位**（主） | 所有人 | 首页岗位卡与岗位页顶部一个按钮"交给这个岗位一件事"：一句话 + 可选附件 / 关联订单 → 开事项（`entry: position`）→ 岗位路由挑职责 → 起 Run（用那条职责的 Assignment、额度、技能）→ 卡片回到事项时间线 |
| 职责（次） | 想指定规则的人 | 岗位页里职责那一层每条职责旁一个小按钮"用这条职责开"（`entry: role`），跳过路由 |
| 秘书路由（41） | 谁都可以丢一句话 | 已经路由到**岗位**；出的认领卡认领后 = 岗位入口 |
| 卡片 / 来信 / 定时 | 系统 | 不变（它们本来就带职责） |

岗位路由 = 41 秘书路由那套判据（职责名 / 描述短语 / grounding 意图词 / 动作 id / 数据域）在**一个岗位的职责集合内**跑一遍；拿不准就问一句（一张选择卡：这件事像 A 也像 B，你定），不猜。路由结果写在事项时间线上，可以手动换职责。

## 3. 上下文与记忆（Q3）

| 层 | 上下文（起 Run 时喂给模型的） | 记忆（跨事项留下来的） |
|---|---|---|
| 岗位 | 岗位面板的数字块与告警（36）、岗位下所有职责的进行中事项摘要、岗位持有人的可用时段 | `position` 技能层（"这家公司的网站运营改价先看竞品"）、提升到岗位层的教训 |
| 职责 | 职责 yml（scopes / 动作 / 额度 / grounding）、职责技能、知识适用范围（19）、该职责的历史事项 | `role` 技能层、提升到职责层的教训 |
| 个人 | 本人 profile、可用时段 | 个人记忆与 `personal` 技能层（不变，21 的敏感级不变） |

组装顺序 = 六层叠加（§1）；岗位入口的 Run 同时带岗位层与被路由到的那条职责层；职责入口的 Run 也带岗位层（它仍属于那个岗位）。记忆写入：事项收尾时的复盘（已有）可以把一条教训**提**到岗位层或职责层，走 learning 的提议 → 批准那条路，不自动写。

> **09-19 加（69，WP120 已实现）**：上表「上下文」那一列的**最前面**还有两段
> **角色定位（persona）**——岗位一段、职责一段，各是六段固定骨架（你是谁 / 你负责 /
> **你不负责、转给哪个岗位** / 怎么做 / 口气 / 必须出卡），中英各一份。
> 它排在技能索引与工具定义前面（17 §1），公司可以在第三栏「角色」面板改写。
>
> 与本文 §3「不猜一个」的关系：**岗位反查不出唯一那一个时，岗位那一段整段不出**
> （一条职责挂在两个岗位里、或一个都不挂，如 `common.owner`）——猜错等于把别的
> 岗位的规矩喂给这次运行。职责那一段照旧出。
>
> 骨架、写法规范、覆盖层与串岗测试见 **69**。

**手改入口（WP71，36 §10）**：除了"复盘提升"这条自动路，每一层的记忆还能**手改**——第三栏的「记忆」面板里，本层的条目可改 / 可删 / 可手动加一条，也可以"提到上一层"。三条规矩分得很清：

| 动作 | 走哪条路 | 为什么 |
|---|---|---|
| 改 / 删 / 手动加**本层**的一条 | `POST` / `PATCH` / `DELETE /v1/memory` —— **当场写** | 本层就是本人自己干活的那一层，没有第二个人要为它点头 |
| **提到上一层** | `POST /v1/skills/:name/promote` → 一张待审卡 | 上一层是别人也要吃的东西（24 §3 不批不生效） |
| 复盘提升 | 同上（已有） | 不变 |

改得动哪一层看**你在哪一层干活**：职责层要本人持有该职责，岗位层要本人在这个岗位下至少持有一条职责，公司 / 部门层要 owner，包层与个人层这条路不开。判据在服务端一份（`canEditMemory`），`GET /v1/memory` 回一格 `can_edit` 给界面，界面不自己判第二遍。手动加的那一条落在**本层自己的技能记录**里（不是 overlay），所以它会被下一次 `resolve` 并进去、真的喂给模型。

### 5.1 阈值与叠加顺序（实现里定的两个数）

**岗位内路由**（`packages/roles/src/route.ts`）。候选分数是**归一后的份额**（这一条的
判据词权重之和 ÷ 参赛各条之和），于是两条阈值都读得懂：

| 线 | 值 | 为什么 |
|---|---|---|
| `MIN_SEPARATION` | 0.15 | 第一名与第二名的份额差。"六四开还算分得开、五五开就别猜了"——`0.575 : 0.425` 正好卡在线上 |
| `MIN_PICKED_SCORE` | 0.3 | 第一名自己的份额。四条职责平分（各 0.25）时谁也不像，这条把"哪条都沾一点"挡在外面 |

岗位下只有一条职责时两条都不看（没得选就是它）；一个判据词都没命中也算拿不准
（空手猜一条比问一句糟）。通用职责（`common.member` / `common.owner`）不参赛。

**六层叠加顺序**（`packages/skills/src/registry.ts` 的 `TIER_ORDER`，唯一一份真源）：

```
package → company → department → position → role → personal
```

越靠后越具体、越优先。职责压在岗位上面：一个岗位里有好几条职责，职责那一层说的话
更贴着这件活。`actor` 上没有 `position_id` / `role_id` 时那一层**自然被跳过**——
一条职责挂在多个岗位里、而分配上没记岗位时就是这种情形，这时候在事项时间线上说一句
（§3 最后一行），不猜一个。

### 5.2 两处与本文不同的地方（实现时定的）

1. **岗位与分配分了两个字段**。`Matter.position_id` 一直是 **Assignment id**（36 §3 的
   "岗位"= 本人持有的那一条），工作台、deck、日历都在读它。所以"这件事属于哪个岗位"
   另立一格 `position_template_id`——一个说"用谁的哪条分配在做"（权限与额度从它来），
   一个说"它属于哪个岗位"（岗位层上下文与记忆从它来）。合成一格就得改掉半个工作台。
2. **`GET /v1/positions/:id` 两种 id 都收**。同一前缀下 `/cards`、`/view`、`/ontology`
   里的 `:id` 是 assignment_id，而岗位实体讲的是岗位模板。为了不让界面被迫先查一次
   模板 id，这条路由两种都认（给的是分配就换算成它所属的岗位）。

## 6. 岗位弹性化（WP234，2026-10-05 Luoye 定）

### 6.0 为什么改

Luoye 在 Windows 真机上走完首次设置后提了两件事：

1. **模板直出不贴人**。以前第 ③ 步勾「社媒运营」= 九条渠道全上；只做 Reddit 的 INMO
   要么被塞进一堆不做的渠道，要么只能去展开里单勾、再起一个叫「我的岗位」的名字。
   中小公司的岗位是**按这个人要做的事拼出来的**，不是按我们的模板切出来的（50 §0
   「职责是积木、岗位是拼法」——这一条早就写了，界面一直没跟上）。
2. **「负责人」不是干活的岗位**。它是身份（公司负责人 / 管理员），放在左栏「岗位」里，
   和「客服」「网站运营」排在一起，用户会以为那是一摊要每天去做的活。

所以：岗位从「模板直出」变成「按人弹性组合」；负责人从左栏挪到「公司」页。**机制不拆**——
`common.owner` 分配、审批默认收件人、WP215 `brandAnchor`、学习卡、系统任务一个字不改，
只改呈现。

### 6.1 三样东西各管什么（只加不删）

| | 以前 | 现在 |
|---|---|---|
| **岗位模板**（随软件带的那几个：客服、网站运营、社媒运营……） | 第 ③ 步直接勾的就是它 | 只当**类别目录**——第 ③ 步「按类别浏览全部职责」用它分组。模板本身一个字不改 |
| **岗位**（工作区里的岗位行，`org_positions`，`bundled` 或 `custom`） | 基本就是模板的一份拷贝 | 一个有名字的**职责组合**：几条职责可以来自不同模板（「Reddit 运营」= `pr.reddit` + `social.reddit`） |
| **安放**（新，`org_placements`：分配 → 岗位） | 没有。05 §2「岗位不落在分配上」，谁在哪个岗位是算出来的 | 一条分配**归哪个岗位**，明确记一行。没有这一行的老分配照老规则算（下表），行为逐字不变 |

为什么要「安放」这一行：一条职责可以同时出现在几个岗位行里（模板「社媒运营」里有
`social.reddit`，自建的「Reddit 运营」里也有）。只看岗位行的职责清单，就分不出这个人的
`social.reddit` 是在哪个岗位里做的——左栏会把同一条活儿列在两个岗位下，起 Run 时岗位层
也只能跳过（§5.1 末段「不猜一个」）。安放把这个歧义在源头消掉。

**安放不带任何权限。** 权限、额度、动作面永远看那一条分配本身（05 §4 路由不是并集，不变）；
安放只回答「这条活儿在界面上、在岗位层上下文与记忆里，算哪个岗位的」。撤销分配，安放那一行
跟着失效（只认未撤销的分配，不另删）。

**归属规则**（一份，`apps/server/src/position-placements.ts` 的 `belongsTo`）：

| 这条分配 | 属于哪个岗位 |
|---|---|
| 有安放行，且那个岗位行还在 | **只**属于那一个 |
| 没有安放行（老数据、制度页手动分配的） | 每一个职责清单里含它的岗位（= WP69 现状） |

由此推出的几样，全部按这一条算：

- **我的岗位**（左栏、首页岗位卡、⌘K）：本人有分配归属于它的岗位。岗位页的职责清单仍是
  岗位行的那几条，`my_assignment_id` 只给归属于**这里**的那一条——同一条职责被安放到别的岗位
  去了，这里就显示成「我不做」。
- **持有人**：有分配安放在这里的人，加上老规则——未安放的分配里**有一条干活的职责**在这个岗位里的人
  （WP235：以前要凑齐默认包，于是老工作区里只做公关一条 `pr.reddit` 的人，左栏有「公共关系」、公司页却写
  「还没人做」；现在与左栏的 `belongsTo` 同一条）。只有底座职责的「普通成员」与「负责人」那一行仍按默认包算。
  公司页每位持有人带 `role_ids`：他在这个岗位里手上的那几条。
- **起 Run 的岗位层**（`positionOf`）：给了分配且已安放 → 那个岗位；否则老规则（只挂在
  一个岗位行里才算），再加一条——这条职责所有未撤销的分配都安放在同一个岗位，就是它。
- **工作区底座职责**：`common.member` 与 `common.owner` 都**不算任何岗位的职责**。一个岗位
  对这个人来说只剩它们，就不进「我的岗位」；「负责人」那一行（id `owner`）本身是身份，**无论下面
  还挂着什么都不进「我的岗位」**（演示包里它下面挂着「经营数据」——要在左栏看到它，用 §6.4 移到
  一个干活的岗位）。于是「负责人」从左栏、首页消失，而 `common.owner` 那条分配原样在（§6.5）。

### 6.2 第 ③ 步的产出：岗位清单

第 ③ 步不再交「勾了哪几个岗位 + 哪几条职责」，交的是**岗位清单**：

```
positions: [{ name, role_ids[], template_id? }]
```

`POST /v1/onboarding/apply` 收到之后：

1. 每一行：带了 `template_id`、而且这几条职责全在那个模板里 → **复用那个岗位行**（名字不同就
   改名，走 WP196 那条不改版本的路）；否则**新建一个自建岗位**，职责 = 这几条。
2. 建分配，每一条新分配写一行安放。已经持有的不重建：它**还没安放**（老分配）就按这一行安放——
   不然它按老规则同时算在模板岗位和这个新岗位里，左栏出两份；**已经安放过的不挪**（挪走那条路是
   §6.4「移动职责」，事项会一起带过去）。制度页「分给同事」按岗位分时同一条规矩。
3. 一条 `onboarding.applied`，带每个岗位的 id 与职责（不带用户那段原话）。

老的 `position_ids / role_ids / custom_position_name` 三格照收（契约只加不删）：
没给 `positions` 时按老算法展开、不写安放——老客户端走向导，结果与以前逐字相同。

### 6.3 划分建议：一份算法，前后端同用

`packages/contracts/src/position-plan.ts` 的 `proposePositions(role_ids, catalog)`——纯函数，
工作台第 ③ 步与服务端校验 AI 结果都调它：

1. **按类别分堆**（类别 = 模板；一条职责挂在几个模板里时归第一个）。
2. **同渠道并成一个岗位**：几条职责是同一个渠道（id 后缀相同：`pr.reddit` / `social.reddit`）、
   来自不同类别，而且**在各自类别里只选了这个渠道** → 并成「Reddit 运营」。
   INMO 只做 Reddit 就是这一条；选了 YouTube + Instagram 的红人营销不会被拆碎。
3. **太多就拆**：一堆超过 `MAX_DUTIES_PER_POSITION`（= 6，可调）就按顺序切成几堆，
   名字「社媒运营 · 1」「社媒运营 · 2」。6 是对着 50 的拆法定的：客服 4 条、网站运营 4 条、
   红人 5 条都在线内，社媒 9 条刚好超——那正是「一个人管九个平台」不现实的那一档。
4. 名字：类别名 / 「渠道名 运营」；AI 给了名字且过了校验就用 AI 的。

**AI 给的划分先过校验**（`checkSuggestedPositions`）：每条职责恰好出现一次、只用推荐里有的职责、
每个岗位不超阈值、名字非空且不超 64 字。过不了就整份换成上面的算法——不半信半疑地拼。

### 6.4 建好之后也能改：合并 / 移动 / 拆出

公司页岗位卡上三个动作，与第 ③ 步是同一套规则（都在 `org` 端口里做、都只有负责人能做、
都记审计）：

| | 职责清单 | 分配的安放 | 事项（`position_template_id`） | 岗位层记忆 | 职责层记忆、卡 |
|---|---|---|---|---|---|
| **合并到…**（A → B） | B ∪= A | 归属于 A 的全部改安放到 B | A → B | **并进 B**（见下） | 不动（按职责 / 分配挂，本来就跟着走） |
| **移动职责**（R：A → B） | B += R，A −= R | 归属于 A 的 R 改安放到 B | A 下面**走 R 的那几件**改到 B；别的留在 A | **留在 A**（那是 A 的做事方式，不跟着一条职责走） | 不动 |
| **拆出…**（A 的几条 → 新岗位 N） | 建 N，再逐条按「移动」 | 同移动 | 同移动 | **复制一份给 N**（Luoye 10-06），两边都留；N 里每段标题带「（复制自「A」）」 | 不动 |

**岗位记忆怎么并**（`mergePositionMemory`）：A 那一层有两种条目——手动加的（A 自己的技能记录里
的段）与提升批下来的（A 那一层 overlay 上的 op）。逐条搬到 B 的同一种里：

- B 没有这一段 → 整段搬过去；
- B 也有这一段、正文一样 → 留一份；
- B 也有、正文不一样 → **B 的不动，A 的那一版作为新的一段加进 B**，标题后面带「（原「A」）」。

一个字都不丢、也不替人二选一（24 §1 不自动合）。搬完 A 那一层清空。

**WP235（Fable 10-06 Windows 真机）：三个动作作用在「你们的岗位」上，不改出厂模板。**

- 公司页「岗位」分两块：上面**你们的岗位**（有人在做的 + 自建的；卡上写谁在做、他手上是哪几条），
  下面折叠的**可以加的岗位（模板）**（没人做的出厂模板）。「负责人」（页顶身份卡）与「普通成员」不列。
  合并 / 移动 / 拆出只出现在「你们的岗位」上，目标也只列这一块。
- 一个岗位**真在做的职责**：模板只算有人做的那几条（Luoye 只做公共关系里的 `pr.reddit`，合并带走的就是这一条，
  不是公关整包）；自建岗位整份都算。
- **目标是模板**（合并到 / 移动到一个 `bundled` 岗位）：不改模板，另建一个自建岗位接住它——职责 = 模板里真在做的
  那几条 + 带过来的，图标与上级照抄，在模板里做的人全部安放过去、事项一起搬；合并时名字可给，
  不给按职责建议（几条都是同一个渠道 → 「Reddit 运营」，否则沿用目标的名字；`mergedPositionName`，前后端同一份），
  移动时同名。回执带 `created`。模板原样留在库里，没人做了就落到「可以加的岗位」。
- **源是模板**（从它合并 / 移动 / 拆出）：只把在里面做的人挪走，模板的清单一条不删。
- **模板的岗位层记忆是复制不是搬**（Fable 10-06 代定）：新的自建岗位拿一份（每段标「（复制自「模板名」）」），
  模板留一份——以后有人再领这个模板，不从空开始。自建岗位之间合并照旧「并过去、A 删掉」。
- 「你们的岗位」卡上的计数是「在做 N / 共 M」：M 是岗位里干活的职责（不算「工作区成员」），N 是其中有人在做的。
- 例：「公共关系（Luoye：`pr.reddit`）」合并到「社媒运营（Luoye：`social.reddit`）」→ 一个自建「Reddit 运营」
  装这两条，左栏只剩它；两个模板一个字不变。

**合并之后的 A**：自建的直接删掉；随软件带的留在库里当类别目录（没人安放在它上面，就不在任何人
的左栏出现）。**移动 / 拆出之后变空的岗位**不自动删——它可能还有岗位层记忆；公司页上它显示
「空岗位」，删之前提示「合并到别的岗位，记忆会跟过去」。

审计：`position.merged`、`position.duty_moved`、`position.split`（payload 只有 id 与条数，
没有记忆正文）。

**展示上的归属**（Luoye 10-06 补）：成员页、人员页、同事 profile 的岗位徽章按安放归——分配视图
（`AssignmentView` / `ProfilePositionView` / `PersonCardView.positions[]`）多带一格 `position: { id, name }`：
安放了就是那个；没安放、职责只挂在一个岗位里（「负责人」那一行不算）就是它；分不清就不给，界面照老办法归堆。

### 6.5 负责人：身份，不是岗位

- 左栏「岗位」与首页岗位卡只放干活的岗位（§6.1 最后一条）。
- **「公司」页顶上一块「负责人」**：谁是负责人、他那里有几张待定的卡、一个入口「公司设置与授权」
  （就是原来左栏那一页，地址不变）、一个「转交给…」。
- **转交** = 把 `common.owner` 分给另一位成员（走现有的分配路，记 `owner.transferred`）。
  第一版**不收回自己那一条**：本机装配时的负责人是审批默认收件人与 `brandAnchor` 的那一个，
  收回会让这台机器上的系统卡没处去。所以转交之后两个人都是负责人，原来那位要卸下，
  在成员页撤掉自己那条分配（那条路本来就有，撤销前会先确认另一位负责人还在）。
- 审批、授权、额度照样归持有 `common.owner` 的人——一行判据都没改。

### 6.6 老工作区

- **不自动合并**已有的岗位（用户自己用 §6.4 合）。
- 老分配没有安放行 → 一律按老规则，界面上的岗位与以前一样；唯一的变化是「负责人」那一行从左栏
  与首页隐去。
- 一旦用了 §6.4 的任何一个动作，被动到的分配就有了安放行，从此按新规则走。

## 7. 岗位页 v2 的「工作」：工作项视图（WP241，2026-10-06 Luoye 定）

设计稿 `docs/design/position/`（WP239 两轮）。Luoye 10-06 定的口径：**卡片流管决定，工作管进度**。
岗位页「工作」页签从上到下：交给它（一行）→ 要你处理（= 首页那副牌钉在这个岗位上，原样）→
**工作**（本节）→ 数据看板。

### 7.1 为什么要服务端出一份

「工作」要把四样本来分在四处的东西排进同一张列表 / 看板 / 日历 / 表格：

| 类别 | 真源 | 以前在哪看 |
|---|---|---|
| 事项（AI 在办的一件事） | 37 `Matter` | 左栏职责下的对话 / 任务、事项页 |
| 待办（人手动加的那一类） | 37 `Todo` | 待办页、日历（不按岗位滤） |
| 定时任务 | 25 `ScheduledTask` | 岗位页「记录」底下一张小表（只取地址栏那一条分配） |
| 社媒排期 | 56 `SocialPost` | 职责页的内容日历 |

前端拼四份会各算一遍「哪些算这个岗位的」，与页头「N 件在办」、卡片流的「N 张」对不上（WP141 吃过这个亏）。
所以服务端出一份视图，归属规则与 `instance()` 同一套。**它是视图不是新对象**：没有一张表存「工作项」，
每项都指回真正那一行，这一层一个写口都没有。

### 7.2 接口与形状

`GET /v1/positions/:id/work`（`getPositionWork`；`:id` 两种都收，同 §5.2 第 2 条）→ `PositionWorkView`
（`packages/contracts/src/position-work.ts`，前后端同一份）：

```
PositionWorkView {
  position_id                      岗位模板 id
  items: PositionWorkItem[]
  counts { doing, queued, waiting, done, cards, todos_today }
  duties [{ role_id, role_name, assignment_id }]   本人在这个岗位做的几条（筛选 / 加待办挂哪条）
  done_window_days = 14
}
PositionWorkItem {
  id = `${kind}:${ref_id}`   kind: matter | todo | schedule | post   ref_id 指回真那一行
  title · role_id? · role_name? · assignment_id?（本人那条）
  group: doing | queued | waiting | done      分组（进行中 / 排着的 / 等别人 / 已完成）
  status                                       原始状态（只当 data 属性，界面不翻）
  due_at?                                      截止（待办）/ 下次时间（定时、排期）
  progress?                                    最近一句进展（≤ 80 字）
  cards · card_ids                             等你的卡
  source: you | agent | schedule | inbound | meeting
  updated_at · matter_id? · movable
}
```

### 7.3 规则（每条都在 `position-work.ts` 里有一个函数）

**哪些算这个岗位的**（`positions.ts` 的 `work`）：

- 事项：`matterInPosition`——与页头「N 件在办」同口径（记了岗位的按岗位；老事项按分配属于这个岗位），
  含同岗位别的持有人开的。归档了还开着的不出（WP207：归档 = 移出默认列表）。
- 待办：**本人**名下、`position_id`（= 分配）是本人在这个岗位的某一条。
- 定时：本人、挂在本人在这个岗位某条分配上的；**系统例行的不进**（每日计划、日 / 周 / 月复盘、巡检——处理器是 `schedule.ts` 的 `HANDLERS`，
  每条分配各一份，是工作台怎么运转、不是这个岗位在做的事），它们在「设置 · 定时任务」里照样能看能停。
- 排期：这个品牌的帖子，渠道 → 职责（`reddit` → `social.reddit`）是本人在这个岗位做的那条；
  没排时间的草稿不算（它只是一段草稿，卡在卡片流里）。

**分组**：

| | 进行中 | 排着的 | 等别人 | 已完成 |
|---|---|---|---|---|
| 事项 | `open` | — | `waiting` | `closed`（近 14 天） |
| 待办 | `open` / `doing` | `open` 且排在以后（`scheduled.start > now`） | `blocked` | `done`（近 14 天）；`dropped` 不出 |
| 定时 | `running` | `active` / `pending` / `paused` / `failed` | — | `done`；`cancelled` 不出 |
| 排期 | `draft`（排了时间、等批） | `scheduled` / `failed` | — | `published`（近 14 天） |

**等你的卡**：本人队列里、这个岗位职责上、还没定、真是卡（与 `pending_cards` 同一个过滤）。事项按卡的
`subject.matter_id` 挂；待办按自己记着的卡 id 挂，**它挂着的那件事项上的卡也算它的**（同一件事别让人找两处）。
所以行尾「N 张卡等你」点过去，卡片流里一定翻得到那张。

**看板拖动**（`canMoveWorkItem`，按现有状态机）：

- **只有待办能拖**：人是承诺人，状态本来就由人改。能在「进行中 / 等别人 / 已完成」之间拖，改成
  `doing` / `blocked` / `done`（走待办自己的 `PUT /v1/todos/:id`）。「排着的」不收拖动——它的意思是
  「排在以后某个时段」，进去要给时间（日历视图里给），光拖一下没有时间可记。
- **事项 / 定时 / 排期不许拖**：它们的状态由运行、调度循环、发帖结果推进，人拖一下改不了「做到哪了」。
  卡片拿着不动，悬停说一句为什么；要停定时去「设置 · 定时任务」，要结束一件事进事项页，要拍板的在卡片流。

**页头三个数**：「N 张等你定」= `instance.pending_cards`（与卡片流同口径）；「N 件在办」= `counts.doing`；
「今天 N 个待办」= `counts.todos_today`（截止 / 排在今天、还没做完的；点过去是「截止：今天」筛选，同一个口径）。

**截断**：已完成只带最近 14 天（再早的去「记录」）；总数封顶 300 条，先保没做完的。
