# 76 · 插件开放接口 v1

| 项 | 值 |
|---|---|
| 日期 | 2026-09-20，WP119b |
| 是什么 | 任何人都可以给 Agents 工坊写采集插件（Chrome / Firefox 扩展、别的工具）的那组**本机 HTTP 接口** |
| 参考实现 | 开源仓库 `apps/extension`（**功能精简**）；官方完整版不开源，内测用户从私有 Release 拿 zip |

## 0. 一句话

插件跑在用户自己的浏览器里，打到**本机**的 Agents 工坊服务（`http://127.0.0.1:<port>`）；用户在工作台生成 6 位配对码，在插件里输入，那个插件从此拿到一把**只绑它**的令牌。装了本机服务才能用；云端只在本机用户登录云账号时才参与（共享公共红人库），**插件自己永远不持有云令牌**。

## 1. 配对（配对时绑定）

1. 用户在工作台「设置 → 连接 → 浏览器插件」点「生成配对码」：`POST /v1/extension/pairings` → `{ code: "482013", expires_at }`。码是 6 位数字（前导零保留）、5 分钟有效、**一次性**；同一工作区再生成一次，上一码当场作废。
2. 插件拿码来换令牌：`POST /v1/extension/pair`，`Origin` 头必须是**扩展自己的 Origin**（`chrome-extension://<id>` / `moz-extension://<uuid>`）。**配对时绑定**：码换令牌的那一刻，插件 id 就与令牌绑死——之后每个请求都要令牌与 Origin 同时对得上，把令牌抄进别的扩展里没用。
3. 换回来的是 `{ token, token_id, workspace_id, scopes, expires_at }`。**明文令牌只在这一跳出现**，本机库里只有它的哈希；令牌 30 天有效，用一次记一次 `last_used_at`。
4. 工作台上列得出每一把令牌（插件自报名字 + 扩展 id + 配对时间 + 最近使用），**逐个可吊销**：`POST /v1/extension/tokens/:id/revoke`。吊销是写 `revoked_at` 不是删行——用户要看得见什么时候撤的。
5. 配对表**落 SQLite**（本机 `extension-pairing.sqlite`）：重启服务不再要用户重新配对（WP119 留尾的那一条）。

**Origin 纪律**：扩展 id 只从 `Origin` 头来，不从请求体里来——请求体是插件说的，`Origin` 是浏览器说的。非扩展 Origin 一律不认；不开通配 CORS 的纪律不变。

## 2. scope

| scope | 允许什么 |
|---|---|
| `kol.observe` | 上报观测（`POST /v1/extension/observations`） |
| `kol.capture` | 预留：经本机服务写联系方式等需用户显式同意的写入 |
| `kol.read` | 读本机红人库里已有红人的脱敏形态 |

scope 由服务端发令牌时定（现在是三个全给），插件**自报不算数**；接口侧每次都查。

## 3. 端点一览

| 方法与路径 | 鉴权 | 干什么 |
|---|---|---|
| `POST /v1/extension/pairings` | bearer（工作台用户） | 生成 6 位配对码 |
| `GET /v1/extension/tokens` | bearer | 本工作区的令牌清单 |
| `POST /v1/extension/tokens/:id/revoke` | bearer | 吊销一把令牌 |
| `POST /v1/extension/pair` | 无（码 + Origin） | 码换令牌（配对时绑定） |
| `GET /v1/extension/hello` | 无 | 版本协商与能力宣告（见 §4） |
| `POST /v1/extension/observations` | 令牌 + Origin，需 `kol.observe` | 上报一批观测 |

错误一律走服务进程统一信封：`{ code, message, trace_id }`，`message` 是给人看的话。

## 4. hello：版本协商

`GET /v1/extension/hello` 不需要令牌。返回：

```json
{
  "workspace_id": "ws_dtc3c",
  "workspace_name": "NordVolt Gear",
  "cloud_linked": true,
  "shares_to_public_library": true,
  "scopes": ["kol.observe", "kol.capture", "kol.read"],
  "server_version": "0.1.0"
}
```

插件用它做三件事：确认本机服务在不在（哪个端口都是它自己配的）；把工作区名字显示给自己的用户；**如实告知**「登录了就共享到公共红人库」——登录云账号即共享公开数据，没有第二个开关（Luoye 09-19）。`cloud_linked: false` 时采集只进本机。

## 5. 观测的数据格式

`POST /v1/extension/observations`，一次最多一批（建议 ≤ 20 条，离线攒的队列分批补传）：

```json
{
  "observations": [
    {
      "kind": "creator",
      "captured_at": "2026-09-20T03:12:00.000Z",
      "url": "https://www.youtube.com/@somechannel",
      "payload": {
        "channel": "youtube",
        "handle": "somechannel",
        "display_name": "Some Channel",
        "followers": 48213,
        "observed_at": "2026-09-20T03:12:00.000Z"
      }
    }
  ]
}
```

- `kind` 区分观测种类（红人 / 内容 / 联系方式…）；`payload` 里放的是**页面公开可见**的字段，契约 `packages/api` 的 `ExtensionObservation` 有逐字段说明，新字段一律进 `extra`（只加不改）。
- 每条观测按 **URL + 观测时间** 幂等：同一个 URL 重复报是"更新观测"，不是新建两个红人。
- **送出去的是窄行**：登录云账号时，公共红人库只会收到公开页面本来就有的那几格（渠道 / handle / 名字 / 粉丝数 / 类目）——联系方式、备注、内部打分**不出本机**（联系方式走单独的 reveal / 贡献计费，见 `docs/68`）。
- 应用没开时插件把观测攒在本地队列，服务回来再补传；补传按同样的幂等键，重复报不会写重。

## 6. 限流与错误码

- 令牌请求按令牌限流（突发 30 / 每秒 5）；超了回 `rate_limited`，插件应该退避重试。
- 常见错误码的人话：`bad_origin`（这不是扩展发来的请求）/ `bad_code`（码得是 6 位数字）/ `expired`（码过期了，重新生成一个）/ `used`（这个码已经用过了）/ `no_pairing`（没这个码，去工作台重新生成）/ `forbidden`（这把令牌没有需要的 scope）/ `rate_limited`（太快了，歇一下再试）。

## 7. 隐私规则

- 采集只针对**用户自己打开的页面**；插件不做后台爬取。
- 只进本机；上云只在上面的窄行范围内。用户没登录云账号，什么都不会离开这台机器。
- 本机服务不把观测转发给任何第三方；模型分析（打分 / 体检）走用户自己配的模型。

## 8. 30 行最小示例（配对 + 上报一条观测）

```js
// 1) 用户在工作台拿到码后，插件里输入它：
const pair = await fetch('http://127.0.0.1:4317/v1/extension/pair', {
  method: 'POST',
  headers: { 'content-type': 'application/json' }, // Origin 由浏览器自动带上
  body: JSON.stringify({ code: '482013' }),
}).then((r) => r.json());
if (!pair.data) throw new Error(pair.message);
const token = pair.data.token;

// 2) 存好令牌（chrome.storage.local），之后每个请求带上：
const hello = await fetch('http://127.0.0.1:4317/v1/extension/hello').then((r) => r.json());

// 3) 上报一条观测：
const res = await fetch('http://127.0.0.1:4317/v1/extension/observations', {
  method: 'POST',
  headers: { authorization: `Bearer ${token}`, 'content-type': 'application/json' },
  body: JSON.stringify({
    observations: [{
      kind: 'creator',
      captured_at: new Date().toISOString(),
      url: location.href,
      payload: { channel: 'youtube', handle: 'somechannel', observed_at: new Date().toISOString() },
    }],
  }),
}).then((r) => r.json());
console.log(res.data.saved);
```

## 9. 与 WP119 的差别（本单改了什么）

- 配对从"只认预注册的扩展 id"改成**配对时绑定**：任何扩展都能配，绑死在配对那一刻。
- 配对表从内存档升级为 **SQLite 档**（`extension-pairing.sqlite`），语义两档逐条一致，一致性有测试钉住。
- 工作台的令牌清单本来就是按"逐个可吊销"做的，本单没动它的行为。
