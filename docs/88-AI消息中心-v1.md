## 0. 一句话

**消息页的主轴从「按时间排的邮件列表」换成「这件事要你做什么」**：所有邮箱、聊天窗、WhatsApp、社媒私信进同一条流；每条进来先过分拣，得到四样判断——**是什么（类型）、归谁（岗位）、要不要你（四档）、急不急（三档）**——外加一行 AI 摘要；判断可以一键改，改过的会记成看得见的规则。Agent 起草的回复直接以卡片出现在消息里，批 / 改 / 不发就在原地。

现在的消息页（`docs/assets/workstation/v2-messages.png`）是四列：左栏导航、文件夹与标签、会话列表、阅读区。一屏里真正给"读和决定"的只有右边那一块，而且每一行都长得一样——Agent 已经处理完的客服信、等你批的补发、平台账单，在列表里是同一种灰。

### 1.2 横着看，最有用的五条

1. **主轴是"AI 做到哪了"，渠道只是筛选。** Intercom 的 Fin 文件夹、Gorgias 的 AI 视图、Gmail AI Inbox 都把"AI 已处理 / 等人 / 转人工"放在最前；渠道和账号退成一枚小色点。我们本来就有岗位与卡片，这一条几乎是现成的。
2. **判断带理由、带把握，逐档放权。** Linear 每条建议附一句白话理由和备选，并能按类别设"只显示 / 自动应用"；Zendesk 每项各有置信度。对应我们：每枚判断胶囊能展开"为什么"，把握不够的不挪不动（63 已有 0.6 线），准了再对某一类自动。
3. **纠正要被学到，而且学到的东西看得见。** Zendesk、Help Scout、Spark 都明说"人改了不训练模型"；HEY / Spark / Outlook 的做法是"改一次，这个发件人以后都这样"；Inbox Zero 把学到的模式列出来可改。我们已有发件人规则（63 §D ②）和学习回路（24），缺的是把它**摆到界面上**："你教过它 · 这周少问你 12 次"。
4. **噪音成捆处理，不一封一封点。** Shortwave / HEY 的 Bundle、Gmail 的订阅管理、Inbox Zero 按打开率批量退订。平台通知、物流、营销对跨境卖家是大头，折成一行、整捆标已读 / 归档。
5. **跨渠道认人：强信号自动、弱信号提示、合了能拆。** Intercom 同邮箱 / 同电话自动合；Zendesk 的 WhatsApp / Instagram 永远新建人（于是同一个客户变三个人）；Chatwoot / Gorgias / Zendesk 合并都不可逆。我们照 `kol-core` 的纪律：弱信号只出建议卡，合并记 `merged_from`，随时拆得开。

另一条侧面的佐证：Notion Mail 关停、HEY 把邮箱开放给 agent，说明"收件箱"正在变成"人审 agent 的工作台"——这正是 Agents 工坊一开始的形状（36：只有要人决定的才是卡）。

## 2. 统一入口：一条流

### 2.1 进来的都是"一件事"

| 来源（`MessageSource`） | 账号是什么 | 现在 |
|---|---|---|
| `email` | 每只邮箱（support@ / sales@ / 个人邮箱…） | 已接，一只 |
| `chat` | 每个站点的聊天窗 | WP124 只落离线留言；要把在线会话也落进来 |
| `whatsapp`（新增成员） | 每个 WhatsApp 业务号 | WP182 只做了入口，服务端还没有收信来源 |
| `instagram` / `facebook` / `tiktok` / …（新增成员） | 每个社媒账号的私信；评论单列一类 | `social-core` 有读口，没进消息库 |

**列表上的一行 = 一件事 = 一段会话**（63 的 `MessageThreadSummary` 口径不变）。多出来的只有一条：同一个人跨渠道的会话在**对话视图**里并成一条时间线（§5），但在列表上仍是各自一行、只在头像旁标「同一个人 · 邮件 2 封」——把两段会话在列表层硬并成一行，会让"这一行到底是哪个渠道、回复会从哪儿发出去"变得说不清。

**默认不按渠道分**，按四样判断组织（§3）；渠道与账号是筛选（顶上一排色点胶囊）和每行头像右下角的一枚小角标。

### 2.2 与现有文件夹的关系

`KefuAgents` / `KOLAgents` / `BtoBAgents` 在服务器上照旧（63 §C，那是用户邮箱的结构，不动），但**不再是消息页的主导航**：岗位那一格判断已经说明了"归谁"。文件夹视图收进「···」里的「按邮箱原样看」，给想对照自己邮件软件的人。

## 3. AI 判断：四格 + 一行摘要

每条进来先过 63 §D 的分拣（① 线程归并 → ② 发件人规则 → ③ 自动信头 → ④ 便宜档模型，收口三道不变），产出从三样变成四样：

| 格 | 取值 | 从哪来 | 界面 |
|---|---|---|---|
| **类型**（这件事是什么） | 客户问题 · 售后 · 询盘 · 红人回复 · 合作 · 媒体 · 账单与系统通知 · 物流 · 垃圾与营销 · 个人与其他（可扩） | 规则层先给（③ 自动信头 → 账单 / 营销 / 物流；② 发件人规则）；给不出才问模型；**单选** | 灰胶囊，带 ✎ |
| **岗位**（要谁处理） | 已开的岗位之一，或「负责人（你）」 | `route` + 54 的岗位内路由（`routeWithinPosition`）挑职责；岗位没开就是你 | 描边胶囊「客服 › 社群管理」 |
| **要不要你**（四档） | 等你批 · 要你看 · Agent 在办 / 已处理 · 只需知悉 | **派生，不让模型猜**（见下表） | 状态胶囊，决定进 A 稿的哪一段 |
| **急不急**（三档） | 客户在等 · 今天（或"3 天内"）· 不急 | `priority` + 渠道时钟（聊天在线、WhatsApp 24 小时窗口、首响线）；名字与 36 §13.4 的 P0「客户在等」同一份 | 红 / 黄胶囊，"不急"不出胶囊 |
| **一行摘要** | ≤ 40 字，写"这件事要你干什么"，不是复述 | 63 已有的 `summary` | 卡片标题行，前面一颗 ✦ |

**"要不要你"为什么派生**：63 §H 已经吃过这个亏的反面——"猜错的代价是人以为 Agent 在忙，其实那条线程停在等他点头"。所以这一格只看事实：

| 档 | 判据（按顺序，命中即停） |
|---|---|
| 等你批 | 这段会话挂着一张未决的卡（出站草稿、补发、合作、报价…） |
| 要你看 | 分拣判不准（`suggested_route`）；或 `route = inbox` 且 `needs_reply`（非岗位信，得你自己回）；或岗位那一侧转了人工（接管卡）；或类型是账号安全 / 平台处罚类且急 |
| Agent 在办 / 已处理 | 归了岗位，事项在办（在办）或已回复、已归线程（已处理） |
| 只需知悉 | 以上都不是（`needs_reply = false`） |

### 3.1 可纠正，而且纠正会被学到

- **每枚胶囊都能点**：点开是一个小的单选层（B 稿截图 `b-desktop-correct-light.png`）——只有预设单选，没有自由输入（36 §13.2）。层顶上写把握与来源（"把握 91% · 模型" / "发件人规则" / "你改过"）。
- 下面一个默认勾着的「记住：这个人以后都按我改的来」→ 写一条 `SenderRule`（63 §D ②，模型之前跑，下次不花钱）。改岗位 = 现有的「移到…」纠错；改到岗位上会按「客信怎么动邮箱」开关动邮箱。
- 不勾"记住"的那种改动进学习回路（24 §3）的 Lesson 池：夜间聚类，同类改动够多了出一张「以后 Instagram 里问物流的都归客服？」的选择卡——**学到的东西先问一句再生效**，不静默改行为。
- **看得见**：A 稿右栏「你教过它」一块：本周少问你几次、最近两条规则、「共 7 条 →」进规则清单（能撤）。这是 Zendesk / Help Scout / Spark 都没做到的那一格。
- **信任逐档放开**（借 Linear）：每个类型各自一档「只显示判断 / 自动照判断走」。第一版全部"只显示"，除了 63 已经自动的那三条路（客服 / 红人 / B2B 岗位信）。

## 4. 展示方式：两个方向

两稿用同一份合成数据：6 个来源（support@ / sales@ / 个人邮箱 / 聊天窗 / WhatsApp / Instagram），当天 56 条，含售后、询盘、红人回复、媒体、平台结算、待确认、物流、营销、可疑。人名、公司、地址全是编的，域名一律 `.example`。

### 4.1 方向 A「今日简报」——分组卡片流

![A 桌面](design/inbox/shots/a-desktop-light.png)

- **顶上一句话**："今天进来 56 条，6 件要你，其余 Agent 在办或只需知悉 · 约 6 分钟"。下面一排来源胶囊（色点 + 数），再是岗位 / 类型两个下拉。
- **三段**，从上到下就是优先级：
  1. **要你做的**：每件一张卡。卡头 = 头像（右下角渠道角标，底色是账号色）+ 人 + 来源 + 时间；标题行 = 一行摘要；再一排胶囊（急不急 → 类型 → 岗位 → 状态 → 同一个人）。卡底一行"最小决定"：草稿第一句 + 主动词（发送 / 批准合作 / 是，交给客服）。
  2. **Agent 在办**：一个岗位一行（"客服：已回复 9 · 在办 2 · 刚答完「欧规插头能不能用」"），点开才看到那几段会话。Agent 在干活时标题旁一颗呼吸点（36 §12.2 呼吸只代表"Agent 在替你干活"）。
  3. **只需知悉**：成捆的卡（账单与系统通知 7、物流 6、营销与订阅 14、可疑 1），整捆「标已读 / 全部归档 / 退订 3 个」。
- **展开**：点一张卡就地展开（不跳页）：左边原文折叠（默认只露最近两条）+ Agent 草稿卡（原文语言 + 中文译文 + 事实芯片 + 按钮），右边一栏"为什么这么判"与"同一个人"的依据。
- **右栏「今天」**：按岗位的条、各账号数（影子模式的邮箱标「只看不动」）、你教过它、稍后回来。
- **手机**：顶部三段变成分段切换「要你做 6 / 在办 20 / 知悉 30」，卡片一列，右栏收起（`a-mobile-light.png`）。

**好在哪**：一眼就知道今天要花几分钟、先做哪件；"已处理的"不再和"要你的"长一个样；大量通知成捆以后，真正要读的只有 6 张卡。**短处**：连续跟一个客户来回聊的时候，卡片流不如一个完整的对话视图顺手——这正好是 B 的长处。

### 4.2 方向 B「对话为中心」

![B 桌面](design/inbox/shots/b-desktop-light.png)

- **左边窄栏（340）**：按「要你做 / 按岗位 / 按类型」三种分组切换（截图是按岗位）；每行 = 头像 + 渠道角标 + 名字 + 一行摘要 + 一两枚状态胶囊；底部「不归岗位 · 31」折成一块。左侧导航收成图标，让出宽度。
- **右边整宽对话**：
  - 头：人 + 各渠道身份胶囊（WhatsApp 号码、邮箱）+「同一个人 · 依据订单 NV-10482 · 拆开」；右上角归档 / 稍后 / 转岗位 / ···。
  - 「AI 判断」一排胶囊，点哪枚改哪枚（`b-desktop-correct-light.png`）。
  - **置顶 AI 摘要**：三句话把前因讲完 + 右边一块「下一步：批准补发并回复（窗口关了就只能发模板消息）」。
  - 时间线：跨渠道按天排，老的原文折成一行（"原文 ▸"），Agent 已自动发的也折着；今天的来信整段 + 译文 + 图。
  - **草稿卡就在时间线里**（与 A 同一张卡）。
  - 底部**只有一个输入框：「教 AI 怎么答…（客户看不到这句话）」**——36 §13.3：岗位对话人只教不直接回。非岗位的信（个人邮箱里的媒体约访）这里换成普通写信框 + 63 §F 的三条建议。
  - 最右一栏是上下文：订单、这个人（第几单、来过的渠道）、引用的事实卡。
- **手机**：只显示对话，顶上「‹ 客服 · 5」返回列表；上下文栏收起（`b-mobile-light.png`）。

**好在哪**：跟一个人来回处理最顺；跨渠道的来龙去脉一屏看完。**短处**：左栏仍是一长列，"今天到底要做几件"要自己数；56 条里 50 条不用你管，它们照样占着列表。

### 4.3 考虑过、没画的第三个：看板

按"等你批 / 要你看 / Agent 在办 / 已处理"四列泳道，卡片拖来拖去。像 Linear 的看板，也像客服台的工单视图。没画的原因：消息的状态**不该由人拖**——"等你批"是因为挂着卡，"已处理"是因为 Agent 回了（§3 的派生表）；一个能拖的看板等于允许人手改一个本该由事实决定的状态。

### 4.4 推荐：A 做消息首页，B 的对话视图做展开页

- **打开「消息」看到的是 A**：它回答的是 Luoye 那句"局促"背后的真问题——不是列宽不够，是**所有东西一样重**。A 按"要你做什么"分三段，天然把 50 条不用管的压下去。这也与 36 的原则 ①「工作找人」、⑤「只有要人决定的才是卡」同一个方向。
- **点卡片右下角的 → 圆钮进 B 的对话视图**（36 §2.2 "→ 圆钮是出口"那条规矩）：要连续跟一个人时用它。B 的左栏在这一页里退成"同组的其他会话"，可折起。
- 顶上保留「简报 / 对话」切换：习惯"一列会话 + 阅读区"的人可以把 B 设成默认（记在本机）。

两稿里的组件是同一套：卡头、胶囊、草稿卡、改判层、身份胶囊。所以"推荐 A + B 展开"不是做两遍，是一套组件两种排法。

## 5. 草稿卡、多账号、同一个人

### 5.1 Agent 起草的回复就在消息里批

- 挂在这段会话上的卡（`DeckCard`，36 §2.3）**原样**画在消息里：A 稿在卡片展开区，B 稿在时间线末尾。不是复制一份——同一个卡 id，首页队列、岗位页、消息页三处看到的是同一张，**在哪批了，三处一起消失**。
- 按钮字照 36 §2.2 按排版走：出站 = **发送 / 改一下 / 不发**；带钱的 = **发送并补发 / 改金额 / 驳回**；合作 = **批准合作 / 改金额**；接管 = **打开浏览器 / 放弃这一步**。快捷行不超过 3 个，剩下的进 `···`。
- 「改一下」= 36 §2.1 的「指导」抽屉（作用域：只这一条 / 同类 / 以后都这样），不是给人一个回复框——岗位对话人只教不回（36 §13.3）。
- **草稿显示两种语言**：客户的语言是会发出去的那份，下面一行淡色中文译文（Intercom 的双向翻译思路）。译文**按需生成**（卡片展开时才译，缓存），不对每封预译——与 63 §F「按需生成」同一条纪律。
- 证据还在右上角「证据 N」（36 §2.2 证据层进右栏），消息里只摆三个外围芯片：对象（订单）→ 额度 → 事实卡。

### 5.1b 邮件助手不在第三栏了（接 WP208）

Luoye 09-30：「为什么邮件助手会放到这个第三栏？应该很自然地集成在消息里。」WP208 先做最小搬家（阅读区里一块可收起的「AI 助手」）。本设计里它的最终落点是：**A 稿卡片展开区**（草稿卡 + 右边"为什么这么判 / 同一个人"）与 **B 稿对话视图**（置顶摘要与下一步、时间线里的草稿卡、最右的上下文栏）。63 §I 与 36 §9.4 那个 `mail-assistant` 右栏面板到这一步退役；设计稿的第三栏图标轨里已经没有它。

### 5.2 多账号与渠道

- **账号色**：一个账号一个颜色，专用一套六色（与状态色分开：状态用 `--ws-good/warn/bad/info`，账号用另一套靛 / 青 / 琥珀 / 紫 / 玫 / 绿，明暗各一份），只出现在两处：筛选胶囊前的色点、头像右下角的渠道角标底色。**颜色只说"哪个账号"，不说"好坏"**。超过六个账号循环，并在筛选里配上账号名。
- **渠道**：角标里的小图形说渠道（信封 / 气泡 / WhatsApp / Instagram…；实现时用 36 §8 的 `<BrandIcon>`，设计稿里用的是自画的通用图形）。
- **筛选**：顶上一排来源胶囊，点一个只看这个账号，再点回全部；岗位、类型各一个下拉。筛选状态记本机。
- **影子模式 / 只看不动的邮箱**在右栏账号清单上标「只看不动」（63 §D 那个开关的琥珀色）。

### 5.3 同一个客户跨渠道：合并规则与隐私边界

"人"是一个新的轻对象（`MessagePerson`，§7），挂着这个人在各渠道的身份（邮箱地址、WhatsApp 号码、IG 账号、聊天窗访客）。

| 信号 | 怎么处理 | 理由 |
|---|---|---|
| 同一个邮箱地址（归一后）出现在我们的多只邮箱里 | **自动挂** | 本来就是一个人 |
| 聊天窗访客留了邮箱（74 "按邮箱续聊"那一份） | **自动挂** | 同上 |
| WhatsApp 号码 / 客户报的订单号，对上**本品牌店铺订单**上的电话或邮箱 | **自动挂**，并把"依据订单 NV-10482"写在人头上 | 订单背书的强信号（Intercom 也按同电话自动合） |
| 同名、IG 显示名像、邮箱只差一点 | **只出建议卡**「这两个像是同一个人：合并 / 不是」，永远不自动 | 照 `kol-core/merge`（48 §5.2）的老规矩 |

四条边界：

1. **只在一个品牌工作区内认人**（52：一个品牌一个工作区）。品牌 A 的客户与品牌 B 的客户即使同一个邮箱也不连。
2. **判断只看归一键**（小写邮箱、E.164 电话、平台账号 id），不送模型、不去外面查人（不做"补全资料"）。
3. **合了能拆**：合并记 `merged_from`，人头上一个「拆开」；拆开后各自的会话回到各自那一个人名下。Chatwoot / Gorgias / Zendesk 的合并都不可逆，那是我们要避开的。
4. **删除与导出按人走**：一个人要求删除时，他挂着的每一个身份的原文都在范围里（63 §J、18 §2.1 的 `subject_ref`）。**红人不是客户**：红人那一侧已有 `creator` 与它自己的同一人合并，两边不混；同事与自己的地址永远不合进客户。

## 8. 结论

### 8.1 推荐

**A「今日简报」做消息页的默认，B 的对话视图做点进去的展开页**（§4.4）。理由三句：

1. Luoye 说的"局促"，根子是所有消息一样重；A 按"要你做什么"分三段，50 条不用管的自动压下去，要你的只剩几张卡。
2. 它是现有体系的延长线，不是另起一套：卡片（36）、岗位路由（54）、分拣三层与发件人规则（63）、学习回路（24）全部原样接上，新增的只有"类型"一格、"要不要你"的派生和"人"这个轻对象。
3. B 的强项（跟一个人连续处理、跨渠道时间线）放在展开页正合适，两稿的组件是同一套，不用做两遍。

少字、明暗、手机三条两稿都守着：卡上可见字只有一行摘要 + 胶囊 + 草稿第一句（36 §7 的 60 字线），"为什么这么判"与同一个人的依据都在展开区或问号里；明暗两套只换令牌；手机 A 是分段 + 一列卡，B 是只显示对话。

### 8.2 分几步落地（每步能单独上线）

| 步 | 做什么 | 上线后用户看到什么 | 依赖 |
|---|---|---|---|
| ① 判断四格 | 分拣多出"类型"（规则层先给，模型兜底）；服务端派生"要不要你"与"急不急"；改判单选层 + 「记住」写发件人规则 | 现在的消息列表每行多两三枚胶囊，点了能改 | 只动消息库与分拣；契约只加 |
| ② 今日简报 | A 稿那一页：三段、成捆、整捆标已读 / 归档、稍后提醒、「你教过它」；旧的三栏收进「按邮箱原样看」 | 打开消息先看到"6 件要你" | ①；**只有邮箱也成立** |
| ③ 卡进消息 | 会话挂卡（按 `thread_id` / 事项 id 关联），卡在消息里原地批；三处同一张 | 不用再跳到首页或岗位页去批回复 | ②；卡片组件不改 |
| ④ 对话视图 | B 稿的展开页：置顶摘要 + 下一步、原文折叠、教一句输入框、上下文栏；草稿译文按需生成 | 点 → 进一个完整的对话 | ③ |
| ⑤ 多渠道 | 聊天窗在线会话全量落库；WhatsApp 收信（接 WP182 的入口）；IG / FB 私信（接 `social-core` 读口）；账号色与来源筛选 | 聊天、WhatsApp、私信和邮件在同一条流里 | ①；各渠道连接 |
| ⑥ 同一个人 | `MessagePerson`、强信号自动挂、弱信号建议卡、拆开、按人删除 | 头像旁「同一个人 · 邮件 2 封」 | ⑤ 才有跨渠道的意义；邮箱之间 ① 之后就能做 |
| ⑦ 手机 | 两稿的窄屏排法 | 手机浏览器能用 | 看远程访问的路（下面第 8 条） |

① ② 两步只靠现有的一只邮箱就能上线、就能看出差别，建议先派这两步。

### 8.3 要 Luoye 定的事

1. **方向**：A 做默认 + B 做展开页（推荐），还是只要其中一个？
2. **类型清单**：§3 那十个（客户问题 · 售后 · 询盘 · 红人回复 · 合作 · 媒体 · 账单与系统通知 · 物流 · 垃圾与营销 · 个人与其他）够不够、要不要增删；现有 11 个标签降为"次要标签"可以吗？
3. **"要不要你"四档的叫法**：等你批 / 要你看 / Agent 在办 / 只需知悉。
4. **同一个人**：订单背书的电话 / 邮箱**自动挂**（推荐），还是一律先出建议卡？
5. **营销与垃圾**：只折起、不动邮箱（推荐，默认），还是提供"自动归档营销"开关（会改用户邮箱）？
6. **批量批准**：同类、低风险、不涉钱的草稿卡要不要允许一次批多张？（推荐第一版不做）
7. **译文**：草稿与来信默认显示中文译文（按需生成，要花一点模型钱），还是默认收起、点了才译？
8. **手机**：工作台现在是本机服务，手机要通过云端托管或局域网访问才用得上——手机排法排在第几步？
9. **旧的三栏**：收进「按邮箱原样看」可以吗，还是保留成「简报 / 对话」之外的第三个切换？

### 8.4 自主决定（第一版按我的判断出，Luoye 可改）

- 渠道不当主轴，只当筛选和角标。
- "要不要你"不让模型猜，只按"有没有卡 / 事项状态 / 分拣判不准 / 要不要回"派生。
- 列表层不把跨渠道会话并成一行，只在对话视图里并时间线。
- 岗位对话里没有回复框，只有"教 AI"（沿用 36 §13.3）；非岗位信照 63 §F 给写信框与建议。
- 类型单选、标签多选；"可疑"是旗不是类型。
- 看板方向不画（§4.3）。
- 设计稿里渠道图形是自画的通用图形，实现时换 `<BrandIcon>`。
