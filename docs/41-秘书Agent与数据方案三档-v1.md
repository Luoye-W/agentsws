## 1. 秘书 Agent：个人信息的管家，不是专家

### 1.1 定位（一句话）

**秘书 = `common.member` 职责下每个人自带的个人 Agent，以本人权限运行，只管三件事：我是谁、我在做什么、我什么时候有空；以及"这件事该谁做"。** 专业的事（回客户、投广告、改价）它不做，它只把事路由给对的岗位 Agent。

### 1.2 四个能力

| 能力 | 做什么 | 边界 |
|---|---|---|
| **代答** | 别人问"李默在做什么 / 负责哪些店 / 擅长什么 / 现在忙不忙"，问他的秘书就能答 | 只答**本人设定的公开级别**内的内容（见 1.3）；每次代答记事件，本人能看到"谁问了什么、秘书答了什么"；秘书从不透露对话正文、私有待办、个人记忆 |
| **日程与会议** | 合并本人的外部日历 + 排期待办 + 定时任务 + 会议；有人约会先查冲突、给可用时段；会前把相关事项摘要成议程；会后接 WP23 的产出（决定 / 待办 → 认领卡） | 只动本人日程；约别人 = 向对方秘书发一张"约时间"卡，对方秘书按对方规则答 |
| **任务路由** | 有人把一件事丢给秘书（对话 / 邮件转发 / 会议纪要），秘书判断该谁做：按 04/05 职责定义的"管什么"+ 40 §3 撞车检测 + 40 §2 工具箱是否已有现成的 → 出认领卡给对的岗位 / 人 | 秘书**不执行**专业动作；路由结果是提议，认领才成立（06 §2、31 I13：本人确认前不形成责任） |
| **个人信息管理** | 维护 profile（岗位、范围、擅长、联系方式、公开级别、可用时段）；个人记忆与个人层技能的"管家"（看、改、导出、删） | 21 的敏感级；管理员对个人数据只有迁移 / 归档 / 销毁（40 E1） |

### 1.3 公开级别（本人设，三档）

| 字段 | 仅本人 | 同事可见（默认） | 全工作区公开 |
|---|---|---|---|
| 岗位与负责范围 | — | ✓ | ✓ |
| 现在在做的事项标题 / 数量 | — | ✓ | ✓ |
| 忙闲（时段级） | — | ✓ | ✓ |
| 日程明细（和谁开会） | ✓ | 可选 | — |
| 擅长与技能层 | — | ✓ | ✓ |
| 私有待办、个人记忆、对话正文 | ✓ | — | — |

代答走 `POST /v1/people/:id/ask`（问方身份 + 问题）→ 对方秘书用对方权限 + 公开级别过滤后回答；越级的问题回"这个要问本人"。跨工作区（20 Join）后置。

### 1.4 秘书与其他 Agent 的关系

```
问："退货窗口外能不能退？"      → 秘书：这是售后岗位的专业问题 → 转给售后 Agent（或建议问李默）
问："李默现在有空吗？"          → 秘书：查日程忙闲（同事可见级）→ 答"下午三点后有空"
说："把这个客户投诉处理一下"    → 秘书：路由 → 售后岗位 → 撞车检测 → 认领卡（不是自己去回）
说："帮我约王岚周四聊定价"      → 秘书：查双方忙闲 → 向王岚秘书发"约时间"卡 → 对方点头后进双方日历
```

秘书用的是 direct-llm / dsh 同一套运行协议（17），只是 persona 与工具面不同：工具只有日历、profile、目录查询、认领卡、撞车检测；没有任何写外部系统的动作。

## 2. 数据方案三档

先说共同底座：**不管数据住哪，都是同一套服务进程 + 同一套契约**，换的只是存储后端。为此要补两个抽象：`DataStore` 方言（SQLite ↔ Postgres，21 已留位）与 `BlobStore`（本地目录 ↔ S3 兼容对象存储，放会议录音、附件、原始材料等大文件）。三档只是这两个开关加部署形态。

### 2.1 第一档：本地自托管（免费，开源版默认）

| 形态 | 适合 | 存储 | 大文件 | 备份 |
|---|---|---|---|---|
| **单机** | 一个人 / 两三人 | 本机 SQLite | 本机目录 | 每日 `export` 到你指定的目录（可指到 iCloud / 网盘同步目录） |
| **公司 NAS / 内网服务器** | 5–50 人，公司已有群晖 / 威联通 / 一台内网机 | NAS 上 Docker（群晖 Container Manager、威联通 Container Station 都能跑 compose）：服务进程 + OpenConnector + SQLite（数据卷在 NAS 共享目录）；人多了换 Postgres 容器 | **就用 NAS**：`BlobStore` 指向 NAS 共享目录，或 NAS 自带的 MinIO（S3 兼容）；录音、附件、导出包都在公司自己的盘上 | NAS 快照 + 每日 `export`；异地备份用 NAS 自带的同步 |

员工电脑装桌面壳，选"连接公司服务器"，登录走邀请链接；电脑上不存真源（40 E3）。一句话卖点：**数据在公司自己的 NAS 上，谁走了都带不走，也不经过任何第三方**。

### 2.2 第二档：第三方云直接接（自带账号，我们不经手）

目标是"用现成的托管数据库 + 对象存储，我们给配置向导，不替用户经手凭据"：

| 云 | 数据库 | 对象存储 | 跑服务进程 |
|---|---|---|---|
| 阿里云 | RDS PostgreSQL（或 PolarDB） | OSS | ECS 一台小机跑 compose，或函数计算 + 容器 |
| AWS | RDS PostgreSQL | S3 | Lightsail / ECS Fargate |
| 腾讯云 | TencentDB PostgreSQL | COS | 轻量应用服务器 |
| 中立托管库 | Supabase / Neon（Postgres）| Cloudflare R2 / Backblaze B2（S3 兼容） | Fly.io / Railway / 自己的 VPS |

做法：连接页新增"数据后端"一节，**原生表单**填 Postgres 连接串 + S3 兼容的 endpoint / bucket / key（凭据进本机加密库，不经模型）；填完点"迁移"= `export` 本地 → `import` 到云端；服务进程本身仍由用户用我们给的 compose 在云主机上起（或先留在本机，只把数据放云上——数据在云、跑在本地也成立）。我们不代持任何云账号。

真正要做的技术活只有两件：Postgres 方言、S3 兼容 BlobStore。云厂商差异全在 endpoint 和区域，不需要为每家写代码。

### 2.3 第三档：我们托管（盈利模式）

**"数据在你家、服务我来跑"与"全托管"两种，都按 12 定的混合计费：钱包充值 + 按量 / 订阅。**

| 产品 | 数据住哪 | 我们跑什么 | 收什么钱 | 适合 |
|---|---|---|---|---|
| **托管控制面（推荐先做）** | **公司自己的 NAS / 云**（第一或第二档） | 只跑无状态的服务进程 + 更新 + 监控 + OpenConnector 的 OAuth 配套（Connect，08）；数据不经我们 | 订阅：按工作区座位 / 月；模型与转写按量从钱包扣 | 不想运维又不肯把数据交出去的公司——国内中小跨境电商大多是这种 |
| **全托管** | 我们的多租户集群（**按租户独立密钥、按租户独立库或 schema**，区域可选：国内 / 海外，21 的数据驻留） | 全部 | 订阅 + 存储与模型按量；随时 `export` 带走，无锁定 | 完全不想碰技术的公司 |
| **企业专属** | 客户指定的云账号（第二档），我们代运维 | 部署 + 运维 + 升级 | 年费 | 有合规要求的 |

三条纪律：① 三档之间**随时搬家**（`export / import` 同一格式，33 双向搬家）；② 全托管也**按租户加密**，我们没有读数据的路径，只有迁移 / 销毁；③ 开源版永远能自托管到第一、二档，托管档不藏功能只卖省心（32 的开源优先）。

### 2.4 一键选与技术入口

连接页"数据后端"三个按钮：**本地（默认）/ 接我的云 / 用 agentsws 托管**。前两个走原生表单与向导；第三个跳到账号页充值开通。底下永远留"高级"：直接改 `AGENTSWS_DATA_DIR` / `DATABASE_URL` / `BLOB_URL` 环境变量，compose 文件公开。

## 4. 自主决定（待 Luoye 审）

- F1 秘书 = 每人自带的个人 Agent，只读工具面、无外部写动作；专业问题一律转岗位 Agent
- F2 代答按本人设的三档公开级别过滤，默认"同事可见"；每次代答本人可见
- F3 数据方案先做第一档（含 NAS）与第二档的技术底座（Postgres 方言 + S3 兼容 BlobStore）；第三档先做"托管控制面"（数据在你家）再做全托管
- F4 三档之间同一格式随时搬家；全托管按租户加密、我们无读路径
- F5 云厂商不逐家写代码，只做 Postgres + S3 兼容两个开关；配置向导用原生表单、不代持云账号
