> 目的：把 31 §3「安全机制修订（进规范）」的每一条，对着代码问三个问题——
> **实现在哪、测试在哪、还差什么**。差的一律写成待办，不含糊过去。

> - ✅ **落地** = 有实现、有专门的用例钉住它、没有已知缺口

> 剩下的 J / K / L / N 各有原因，见待办清单。

## 3.1 权限：完整元组，不逐维并集

### (a) EffectiveConfig 不合并 scopes；每次运行绑定一个 Assignment ✅

- **实现**：`packages/roles/src/effective.ts` 的 `effectiveConfig(assignment_id)`
  ——入参是**一个** Assignment id，不接受人 id，从源头上就没有「把一个人的几个岗位并起来」这条路。
  网关侧由 `packages/api/src/app.ts` 的 `bindAssignment` 中间件兑现：`X-Assignment` 头指定哪一条，
  中间件核对它属于本人本工作区、没被撤销，再把它放进请求上下文；授权判定只看这一条。
- **测试**：`packages/roles/test/effective.test.ts`
  - `two assignments of one person keep their own scopes`
  - `is refused for a revoked assignment (05 §3)`
- **还差什么**：无。

### (b) 数据层按 (domain, ops, range, sensitivity) 四元组整条判定 ✅

- **实现**：`packages/data/src/authz.ts`——每条 grant 编译成一整块 SQL 谓词
  （scope 的 `json_each` 相关子查询 + sensitivity 的 `IN` 列表），多条 grant 之间是
  **整条 OR**，不是逐维并集。
- **测试**：`packages/data/test/authz.test.ts`
  - `several grants OR whole tuples together — never a per-dimension union`（这条就是点名断言）
  - `a domain or op mismatch produces no clause`
  - `workspace grants drop the range predicate but keep the sensitivity ceiling`
- **还差什么**：无。

### (c) 空 range 的 Assignment：token 拒签、查询返回空、界面标「未分配范围」 ✅

- **实现**：
  - 标记：`packages/roles/src/effective.ts` 的 `unassigned_range`（`ranges` 为空且有 `range: 'assigned'` 的 scope）
  - 查询返回空：`packages/roles/src/policy.ts`——`range: assigned` 的 scope 在没有 ranges 时**不产生策略行**，
    于是 SQL 谓词是「永假」，查询自然是空集；`packages/roles/src/store.ts:302` 另有一道显式拒绝
  - 拒签：`packages/connect-adapter/src/adapter.ts:520`——上游 OpenConnector 的空 `allowedConnections`
    语义是**不限制**（WP12 实测），所以适配器必须自己把空范围拒掉，不能原样透传
  - 界面：`apps/workstation/src/components/org/members-tab.tsx:186` 读 `unassigned_range`，
    出一句「没给范围，现在什么都查不到」（英文档 `No scope — they can see nothing`）
- **测试**：
  - 端到端（最贴题）：`apps/server/test/org.test.ts` →
    `空范围拒：范围为空的分配标 unassigned_range，assigned 范围的查询拿不到东西`
  - `packages/roles/test/effective.test.ts` → `marks unassigned_range when ranges are empty but the role needs them`
  - `packages/data/test/authz.test.ts` → `an assigned grant with no ranges produces no clause at all`；
    `packages/data/test/data-store.test.ts` → `an assigned grant with empty ranges yields nothing (no error)`
  - 连接器侧拒签：`packages/connect-adapter/test/connect-conformance.ts` →
    `空 allowed_connections 拒签（上游空列表 = 不限制）` / `空 allowed_actions、未知连接同样拒签`
- **还差什么**：无。**WP34 补上了界面那句话的渲染断言**——
  `apps/workstation/test/org.test.tsx` →
  `空范围的分配标出「没给范围，现在什么都查不到」（31 §3.1 c / 39 待办 M）`
  （fixture 现在有 `unassigned_range: true` 的分支；有范围的那一行不出这句话）。→ 待办 M ✅

## 3.2 批准绑定执行快照

### (a) `execution_snapshot = hash(workspace, connection_id, target+record_version, recipients, final_payload, attachments, executor_version, mandate_hash)` ✅

- **实现**：`packages/core/src/snapshot.ts` 的 `executionSnapshot()` / `snapshotMatches()`；
  分量类型在 `packages/txn/src/types.ts` 的 `SnapshotComponents`。
  创建时算一次（`packages/txn/src/approvals.ts` 的 `snapshotOf`），apply 前用**同一个函数**再算一次
  （`packages/txn/src/executor.ts` 的 `snapshotOf`）——两处算的必须是同一组分量，
  所以分量的来源（`ApprovalExecutionContext`）在 WP31 进了契约（见 3.3 (c)）。
- **测试**：`packages/txn/test/security.test.ts` → `执行快照绑定：批准后连接被换掉 → apply 时 snapshot_mismatch`
- **还差什么**：无。

### (b) `decision_token` 绑定 `(item_id, revision, execution_snapshot)`，revision 变化 → 旧 token 失效 ✅

- **实现**：`packages/txn/src/util.ts` 的 `signToken()`（HMAC 这三样 + nonce）；
  台账在 `TxnStore.putToken / getToken / revokeTokensFor`。
- **测试**：`packages/txn/test/security.test.ts`
  - `旧 decision_token 批新 revision 被拒；新 token 可用`
  - `decision_token 绑定快照：审批项快照被改动后旧 token 失效`
- **还差什么**：卡片刷新成「内容已更新，请重新审阅」这句话在 deck 里有，
  但**卡片是被动刷新的**（下次拉队列才看到）；实时推还等 WebSocket（WP15 遗留）。不算安全缺口。

### (c) apply 前重算快照，任一分量变化 → `failed{snapshot_mismatch}`；可幂等 kind 也不例外 ✅

- **实现**：`packages/txn/src/executor.ts` 的 `applyLocked` 步骤 5.5。
  它排在幂等短路（步骤 0）**之后**、后端调用之前——步骤 0 只对「已经 applied / unknown 的同一条」短路，
  不是「这个 kind 可幂等所以跳过校验」。
- **测试**：同上 `执行快照绑定…`；幂等那条是 `packages/txn/test/ledger.test.ts` → `用例 8：同 id apply 两次 → 第二次返回第一次结果，无二次退款`
- **还差什么**：无。

### (d) 额度预占：stage 时占、apply 成功转实、失败 / 过期释放 ✅

- **实现**：`TxnStore.reserve / commitReservation / releaseReservation / countReserved`
  （`packages/txn/src/store.ts` 与 `sqlite-store.ts` 两档）；
  转实与释放各自和状态跃迁在**同一个事务**里（`executor.ts` 的 `finish` / `fail` 里的 `rt.tx(...)`）。
- **测试**：`packages/txn/test/security.test.ts` → `并发拆单被预占挡住：同日额度只剩一个名额时，第二条 require_review`；
  释放那条是 `packages/txn/test/ledger.test.ts` → `审批项撤回 → 变更 withdrawn 且释放预占`
- **还差什么**：无（WP34）。过期释放挂在审批项过期上，而 `expire()` / `escalate()`
  以前**在服务进程里根本没有被调用**（只有 `packages/simulation/src/runner.ts` 在模拟回路里调）。
  WP34 接了一个调度器消费者：`apps/server/src/housekeeping.ts` 的 `runApprovalHousekeeping`
  （先过期后升级，两步各自 try/catch）+ `schedule.ts` 的 `registerApprovalHousekeeping`
  + 系统任务 `sched_approval_housekeeping`（每分钟，`misfire_policy: run_once_now`）。
  升级链要问的「范围管理者 / owner 是谁」由 `createApprovalDirectory` 回答。
- **测试（WP34）**：`apps/server/test/housekeeping.test.ts`
  - `真机器节奏下一张卡到期会 expired，并释放它挂着的额度预占（15 §3.2 d）`
  - `超时会 escalated 到 scope_manager，再久一点到 owner；原 recipients 不撤`
  - `已经过期的卡不再被升级去打扰下一层（先过期后升级的顺序）`
  - `装配之后有一条一分钟一拍的家务任务，处理器已登记`
  → 待办 A ✅

### (e) apply 结果三态 `applied / failed / unknown`；unknown → 查询确认 → 人工对账项 ✅

- **实现**：`packages/txn/src/executor.ts` 的 `finish()` 三个分支 + `reconcile()`；
  待对账队列是 `TxnStore.pendingReconcile()`，游标 `getCursor / setCursor`（重启接着跑）。
- **测试**：
  - `packages/txn/test/security.test.ts` → `apply 三态：unknown 后不释放预占，reconcile 确认已施行 → applied`
  - `packages/txn/test/sqlite-integration.test.ts` → `15 §5.8：apply 拿到 unknown → 关库重开后仍在对账队列，reconcile 接着处理`
- **还差什么**：无（WP34）。「备份恢复后先跑对账再放开出站」落在
  `apps/server/src/reconcile.ts`：`engage()` 在装配时同步判断（账本里有 `unknown`
  或半路断掉的 `applying` 就把急停 `outbound` 档挂上，不做 IO），`run()` 在 `listen()`
  之前跑真对账；查不出来的留成人工对账项，**出站保持停着**；人自己停的档不替他放开。
  `applying` 这个瞬时状态由新加的 `Executor.recoverInterrupted()` 收拢成 `unknown`
  ——不然它进不了 `pendingReconcile`，没有人管。`GET /v1/health` 多一格
  `reconcile: { state: pending|done, pending: n }`。
- **测试（WP34）**：`apps/server/test/reconcile.test.ts`
  - `造一条 unknown 变更 → 重启 → outbound 停 → 对账完成 → 放开`
  - `半路断掉的 applying 先收拢成 unknown，再进对账队列`
  - `查不出来的留成人工对账项，出站**保持停着**`
  - `人自己停的出站档，对账完了也不替他放开` / `干净的库：出站不停，health 的 reconcile = done / pending 0`
  真机器上跑过一遍（`AGENTSWS_PORT=4410`，往 `txn.sqlite` 塞一条 `unknown` 后重启）：
  `status: halted`、`outbound.on: true`、`reconcile: { state: pending, pending: 1 }`。→ 待办 B ✅

### (f) 同目标同 kind 的 apply 串行（单一施行者队列）✅

- **实现**：两层。进程内一条 Promise 链（`Executor.serial`）+ 存储层的施行锁
  （`TxnStore.acquireApplyLock / releaseApplyLock`，`packages/txn/src/executor.ts` 的 `withApplyLock`）。
  内存档是进程内 Map，SQLite 档是 `apply_locks` 表（`IMMEDIATE` 事务抢写锁）+
  `apply_lock_tokens`（**围栏号只增不减**，锁行删了号也不回头）。
  围栏号原样传给 `backendApply` / `deliverOutbound`（`ApplyCallbackOptions.fencing_token`）——
  锁防的是同时写，围栏号防的是「租约过期后才醒过来、以为自己还持着锁」的迟到写。
- **测试**：
  - 一致性套件两档各跑：`packages/txn/test/store-conformance.ts` 的
    `施行锁与围栏号 · <档名>` 六条（号从 1 起、持锁期间拒、过期接管拿新号、号只增不减、
    错号释放不生效、不同 key 互不干扰）
  - 跨进程：`packages/txn/test/sqlite-integration.test.ts` 的
    `两个进程同时 apply 同一条变更：一个赢，另一个回 conflict，后端只被叫一次` 等三条
  - 进程内：`packages/txn/test/security.test.ts` → `同目标同 kind 的 apply 串行（单一施行者队列，不交叉）`
- **还差什么**：无（WP34）。`apps/server/src/backend.ts` 现在按
  `<target>|<kind>`（与存储层施行锁同一把 key）记下见过的最大号，比它小的一律回
  `failed{retryable:false}`（**不是** `unknown`：这次写确定没发生，不必造一条对账项）；
  被拒的那次不抬号；没传号的老调用方放行。
- **测试（WP34）**：`apps/server/test/backend.test.ts` →
  `号只增不减：3 之后再来 2 就是迟到写，直接拒` / `同号可以再来一次（重试同一把锁），更大的号照收`
  / `不同目标 / 不同 kind 各算各的号，互不干扰` / `没传号的老调用方一律放行` /
  `出站投递同样受围栏号管`。→ 待办 G ✅

### (f-2) 父子顺序：含退款的回信必须在退款 applied 之后 ✅

- **实现**：`packages/txn/src/executor.ts` 的 `deliverLocked()` 开头逐条检查 `item.links.children` 的状态。
- **测试**：`packages/txn/test/security.test.ts` → `父子顺序：含退款子项的回信必须在退款 applied 之后才发`

### (g) 批准后取消窗口（默认 2 分钟）✅

- **测试**：`packages/txn/test/security.test.ts` → `批准后取消窗口：窗口内不施行、可 cancel；窗口过后可施行`

### (h) `staged_action` v1 关闭；所有写只经已建模 kind ✅
