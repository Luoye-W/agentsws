## 1. 职责骨架（R1）

> **WP75 实现**：四条 yml 在 `packages/roles/roles/ads/`（骨架样板写在 `meta.yml` 的
> 文件头，其余三条只写"这个平台特有的那几件事"）+ 岗位模板
> `packages/roles/positions/ads.yml`（**默认勾 Meta / Google**——不是"用得多"，
> 是只有这两条今天真连得上）+ `SEED_POSITIONS` / `BUNDLED_ROLES` 各加四条。
>
> **五个 ChangeKind 沿用仓里那四个名字 + 一个新的**：`create_campaign` /
> `budget_change` / `bid_change` / `pause_ad` 从 15 §2 第一版起就在 `ChangeKind` 里，
> 本文 §1 写的 `campaign_create` / `ad_pause` 是同一件事的另一个写法。同一件事
> **不给第二个名字**——`HARD_L1` 里放着 `create_campaign`，再加一个同义词，
> 那道硬顶就会对一半的提案静悄悄不生效。对照表在
> `packages/contracts/src/ads.ts` 的 `ADS_KIND_ALIASES`。新加的只有 `creative_swap`。
>
> **额度是岗位级的**：`max_daily_spend` 写在四条 yml 的同一个 caps 名下，
> guardrail 按岗位把四个平台的**当日花费加起来**再判（`GuardrailFacts.dailySpendTotal`，
> 由 `AdsStore.spendToday()` 算）。各判各的等于四条职责一起把总闸撑爆而谁都没越线。
>
> **`KIND_ALIAS` 加了两条**（`packages/roles/src/effective.ts`，只加不删）：
> `stage_campaign` → `create_campaign`、`pause_ads` → `pause_ad`。对不上的后果
> 与 WP73 那次逐字相同——`riskClassOf` 兜底 `high`，而 31 §3.4 只让 low 超过 L1，
> 于是**止损永远落在 L1**：广告烧钱的时候 Agent 反而要等人点头才能踩刹车。
>
> 像素只读这件事由 `pixel_event` 这个**新数据域**兑现（职责 scopes 里只有 `read`）——
> 塞进 `ad_account` 的话，"能改广告预算"与"能改网站上的像素代码"就成了同一把钥匙。

四条骨架相同，各自一张连接卡：`ads.meta`（`meta_marketing`：Marketing API，`ads_management` 权限，与 `meta_graph` 分开两张卡但可复用同一次授权）、`ads.google`（`google_ads`：developer token 审核制 + OAuth；Merchant Center 归它）、`ads.x`（`x_ads`：申请制）、`ads.tiktok`（`tiktok_ads`：Business Center 授权）。

| 读 | 写（→ ChangeKind） | 额度默认 | 上限 |
|---|---|---|---|
| 账户 / campaign / 广告组 / 广告列表与表现（花费、展示、点击、转化、ROAS）、预算与出价、素材、像素 / 转化事件状态 | `stage_campaign`（`campaign_create` 新建 / 复制 campaign）、`stage_budget_change`（`budget_change`）、`stage_bid_change`（`bid_change`）、`pause_ads`（`ad_pause` 止损）、`stage_creative_swap`（`creative_swap` 换素材 / 文案） | `max_daily_spend`（岗位级总闸，四平台共用，默认 ¥1000 / 天）、`max_budget_delta_pct` 20、`max_bid_delta_pct` 15、`stop_loss`（ROAS < 1 且花费 > 日预算 30% → 暂停） | **新建 campaign / 提预算超额 / 提日花费总闸永远 L1**；额度内改预算 / 出价 L2；止损暂停 **L3**（自动，回头出一张"已止损"卡）；换素材 L2 |

- 像素 / 转化追踪：只读 + 异常卡（像素掉了 / 转化事件不上报）；改代码那件事归建站，永远 L1。
- 归因：`ads-core/attribution.ts` 读 GA4 / 平台归因 + 订单 UTM（复用 `kol-core` 的 UTM 解析），面板上标"平台口径 vs 订单口径"两列，不合并成一个数。
- 日报：L3 自动出（照店铺日报卡）。

## 2. `ads-core`（R2）

> **WP75 实现**：`packages/ads-core`，五模块 + 四条适配器（Meta / Google 真实现，
> X / TikTok 接口 + 说得清为什么还没接）。全包无 IO、无 `Date.now()`、无 `console`、
> **零真 key**（fetch 注入，测试里塞一个假的对着真 URL 断言）。
>
> 三处刻意的形状：`budget.ts` 每个判定都回一句**可上卡面的 `reason`**
> （回 boolean 的那一版，卡上只能写"超额了"）；止损缺一格回 `unknown` 而不是
> `false`（缺数时按"是止损"自动暂停 = 把 L3 那一档送给一个没人核对过的数）；
> `attribution.ts` 的"平台报了、订单一单没找到"那一行**照样出现在表里**
> （筛掉它 = UTM 没挂对这件事永远不会被发现）。
>
> `spec.ts` 的形状按本节那一行定死（`{ platform, placement, width, height,
> max_duration_s?, max_text_chars?, safe_area? }`）并从包入口导出——**WP76 的
> `design.ads` import 的就是它**，不抄第二份。

`budget.ts`（总闸、delta 判定、止损判定，纯函数）、`variants.ts`（素材 / 文案变体计划：一个 campaign 下 A/B，文案过 `commitment_scan`）、`attribution.ts`、`spec.ts`（各平台素材规格表：尺寸 / 时长 / 文案字数 / 安全区——设计岗 `design.ads` 也读它）、`channels/{meta,google,x,tiktok}.ts` 适配器（**本 WP 只做 Meta 与 Google 真实现**，X / TikTok 接口 + 人话）。

## 3. 面板与卡（R3）

> **WP75 实现**：数据源 `ads`（我们自己算出来那几块）+ 四个平台源
> （`ads_meta` / `ads_google` / `ads_x` / `ads_tiktok`，连上 Meta 不会把 Google
> 的像素那一块点亮）。积木九块在 `packages/deck/src/{blocks,queries}.ts`，
> 三个新芯片（`platform` / `spend_gate` / `stop_loss`）在 `project.ts` + i18n 中英。
>
> **总闸剩余那一格在每一张投放的卡上都有**，不只是提预算那一张：新建一条
> campaign、换一版素材，都发生在"今天还能花多少"这个前提下。人点头之前
> 看得见它，是 04 §5 那条额度纪律唯一真正生效的地方。
>
> 止损卡上那一格放的是**判据**（"ROAS 0.6（线是 1），今天花了 400，占日预算的
> 40%"）不是"止损"两个字——卡上只写结论，点头这件事就没有内容。
>
> **五张卡里前四张是审批项，第五张不是**。像素异常卡（`adsPixelAlerts`，
> `apps/server/src/ads.ts`）是**通知**：14 §1 那句判据（"通过后施行什么"）在它
> 身上答不上来——像素掉了，投放这一侧一行代码都改不动（改追踪代码归建站，
> 而且永远 L1）。点头点不出任何一件会发生的事，那就不是审批项，形状照
> `packages/meetings` 那张系统卡。三件事定死：健康的一条都不出卡（告警区里
> 常年摆着"一切正常"，真出事那天没人会看）；`missing` / `misconfigured` / `stale`
> 是三张不同的卡（去找谁修不一样，并成一句"像素出问题了"等于把这一步判断
> 推回给人）；卡上写的是"转给建站"不是"去改代码"——投放没有那个权限
> （`pixel_event` 域里只有 `read`），写了就是让人去点一个点不动的东西。

数字块：今日花费 / 总闸剩余、ROAS（两口径）、转化数、止损次数；分块：各平台 campaign 表、待审改动（预算 / 出价 / 新建 / 素材各一车道）、止损记录、像素健康、日报卡。卡：新建 campaign 卡（L1，带预算与受众摘要）、预算 / 出价改动卡、已止损通知卡、素材变体卡、像素异常卡。

## 4. 模拟（R4）

> **WP75 实现**：DSL 加四个事件（`ads.campaign` / `ads.budget_change` /
> `ads.pause` / `ads.attribution`）与四条断言（`ads_campaign` / `ads_budget` /
> `ads_stop_loss` / `ads_attribution`）。判据**只有 `ads-core` 那一份**，
> 世界里不写第二份——两份判据必然有一天对不上，而对不上的那天没人会发现
> （模拟绿着，真环境按另一份走）。
>
> `daily-cap-blocks-new-campaign` 那一条故意让 Meta 花 600、Google 花 350：
> **每个平台都没越自己那条线**，加起来 950 已经贴着 1000——各判各的话这一下
> 会顺利通过，那正是 04 §5 要防的事。
>
> `attribution-two-views` 里三张归不上的单各有各的理由，其中一张写的是**红人
> 那条口径**（`utm_medium=kol`）：认了它就等于把红人带来的单算到广告头上，
> 下一次预算按错的数批。

3 人 pack +3（三运行时）：`ads/budget-change-over-cap`（提预算 > 20% → L1）、`ads/stop-loss-auto-pause`（ROAS 跌破 → L3 自动暂停 → 通知卡）、`ads/daily-cap-blocks-new-campaign`（日花费总闸满 → 新建被拦并明说）；15 人 pack +1：`ads/attribution-two-views`（平台口径与订单口径不同 → 面板两列不合并）。
