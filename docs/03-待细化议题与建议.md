## 1. 七个最大的空白（按对后续影响排序）

### 1.1 与现有三条 SaaS 产品线到底是什么关系 —— 最紧要，且是产品决策不是技术决策

现状：KefuAgents 与 KOLAgents **已经是托管 SaaS**——各自有邮箱接管、知识库、审批队列、积分计费（1 积分 = $0.01，Waffo 收款）、用户体系；KOLAgents 还已经有远程 MCP server（M1–M4）。BtoBAgents 是 Next.js + Cloudflare 的独立产品，且 08-08 明确"不与 KefuAgents 做衔接设计"。

而中台路线写的是"付费插件 = 替换职责包的 Backend provider + 高级 skill + 云端大脑 LlmAdapter"。这句话隐含了一个没说出口的前提：**现有 SaaS 要变成无头服务**。它有三种解法，差别很大：

| 方案 | 含义 | 后果 |
|---|---|---|
| A. 插件 = SaaS 的客户端 | 插件把 SaaS 的 API / MCP 当 Backend provider 和云端大脑；中台用户在中台工作台干活；SaaS 自带后台退化为"账户、账单、连接器授权" | 一套队列、一套知识；SaaS 前端逐步瘦身；两边的邮箱接管要定归属 |
| B. 双轨并行 | SaaS 独立卖；插件只共享模型与知识底座，数据不互通 | 两套队列、两套知识，直接违反"一条队列"原则；最省事但自相矛盾 |
| C. 中台托管版 = 新 SaaS | 长期把 SaaS 前端迁进工作台，"我们托管"档就是新的 kefuagents.com | 方向正确但工程量大，要先有 A |

**建议：A 为现在，C 为方向。** 三个直接推论：

1. KOLAgents 的远程 MCP server 天然就是第一个"Backend provider"实现，不用新写；反过来它定义了 Backend provider 的对外形态（无状态 Streamable HTTP + resources + prompts）。
2. **邮箱只能有一个主人。** KefuAgents 现在是"IMAP 里建一个 `AI 客服` 文件夹接管"，中台也要做 email 连接器。同一个邮箱不能被两边同时收。建议：中台连接器拥有邮箱；付费插件不再自己收信，只消费中台给它的线程。这条改动会碰 KefuAgent 的核心路径，要提前排。
3. 计费单位：中台本地永远免费；付费部分沿用积分（云端大脑按用量），席位费只在"我们托管"档出现。不要发明第三种单位。

另外要正面回答一个矛盾：BtoBAgents "不与 KefuAgents 衔接"是 08-08 的决定，而中台的核心卖点之一是"跨职责一条队列、共享上下文"。BtoBAgents 作为中台插件接入，本身就是衔接。要么收回那条决定，要么 BtoBAgents 不进中台。我倾向前者：不衔接的是**产品叙事**（不对外把它们讲成一套），衔接的是**数据层**（同一个客户库、同一个审批队列）。

**待拍板**：A/B/C；邮箱归属；BtoBAgents 是否进中台。

### 1.2 工作项与 dsh 会话怎么映射 —— 架构上最大的未决

所有文档都写"渠道事件最后一跳落 dsh"、"调度器到点起 headless run 或唤醒 session"，但没有说：一封客户邮件、一个红人建联、一条 WhatsApp，对应**哪个** session？

| 模型 | 做法 | 代价 |
|---|---|---|
| 长会话 | 每个客户线程 / 每个红人一个常驻 session，事件 followup 进去 | session 数量随客户数线性增长；compaction 与成本难控；个人端与公司端要同步 session；dsh 会话格式无兼容承诺，长期存活的 session 最先被升级打坏 |
| 无状态运行 | 状态全在共享数据层；每个工作项每次触发起一个 headless run，上下文（客户档案、线程历史、事实卡、职责）由宿主组装注入；run 结束即退出，session 只当审计轨迹 | 每次运行要重组上下文（有 token 成本，但可缓存静态前缀）；长任务要靠 goal driver 或调度器分段 |

**建议：无状态运行。"会话是审计轨迹，不是状态容器。"** 理由：它与 Commerce Agents 的 turn 模型一致（state 在宿主，turn 是纯函数）；webhook 的 fire-and-forget 就够用；同步协议只需同步记录和事件，不需要同步 session；dsh 升级时只影响适配层的"起 run"那一段。

要定义的东西随之清晰：一个**运行请求**（RunRequest）——`{ 职责, 以谁的身份, 工作项 id, 注入上下文清单（每项带来源 id，满足 Model-visible ⟺ logged）, 允许工具集, 预算（token / 工具调用次数 / 时长）, 预期产出类型 }`，以及运行结束回写的**运行结果**。这是协同服务与 dsh-adapter 之间唯一的接口。

**待拍板**：长会话 vs 无状态运行。

### 1.3 执行器在哪——两个入口，一个执行器

"规则进执行器"已定，但执行器有两个调用入口，且它们不在同一个进程里：

- **会话内**：dsh 工具调用 → `tools/pre-execute` 门禁（provenance / guardrail）→ `Backend.stage_*` → staged change 落账本
- **会话外**：人在飞书卡片 / 工作台点"通过" → 审批服务写 `approved_change_ids` → 调 `Backend.apply_change` → apply 时重跑 guardrail

第二条路径里没有 dsh。所以 **Backend 实现必须宿主在审批服务能直接调用的进程里**，而不是宿主在 dsh 插件里。建议的落位：

```
packages/core            契约与纯规则：Backend 接口、gates、fencing、guardrail caps、StagedChange 类型（不 import dsh、不 import 连接器）
packages/connectors      原始 API 客户端：Shopify / IMAP / 飞书 / WhatsApp（无业务语义）
services/executor        Backend host：每个职责的 Backend 实现，组合 connectors；对内提供 stage/apply；持有 provenance 的 seen_* 与 change ledger
packages/mcp-servers     只是 executor 的 MCP 门面（薄），不是独立实现
packages/adapter         dsh 侧：把 executor 的工具接进 dsh，pre/post-execute 里调 core 的 gates
```

这意味着现在 README 里 "mcp-servers：knowledge / shopify / feishu-docs" 要改口——它们是门面，实现只有一份，否则 Claude Code 接 MCP 看到的是一套规则，dsh 里跑的是另一套。

还有一条要写清：provenance 的 `seen_*` 是**每次运行**的状态。无状态运行下它随 RunRequest 产生、随运行结果持久化到共享数据层，apply 时凭运行 id 反查"这个 id 当时确实被读过"。

**待拍板**：executor 作为协同服务的一个模块，还是每个连接器各自一个进程（我倾向前者，v1 单进程）。

### 1.4 模型供给与成本 —— 完全没讨论过

没有任何一份文档回答：**谁付 token 的钱、key 放哪、怎么按人按职责记账。**

建议在协同服务里加一个**公司模型网关**（LLM gateway），v1 就要，因为它一次解决四件事：

1. key 只存在公司实例（加密），个人端与每个 dsh 进程拿到的是网关签发的短期 token——凭据分发与撤销问题顺手解决，dsh 明文 YAML 里不再有真 key
2. 按 职责 × 人 × 工作项 记账；这是 L1→L3 晋级、付费插件用量、"我们托管"档成本核算的共同底座
3. 路由：默认 DeepSeek；付费插件的领域推理路由到云端大脑；同一个网关做 prompt cache 友好的静态前缀纪律（Commerce Agents A11）
4. 数据出境的单一出口：欧洲客户的 PII 走哪家模型、脱敏在网关侧做——GDPR 的答案只能在这里给

**待拍板**：v1 是否含网关；默认模型；欧洲客户数据是否允许进云端大脑（这决定付费插件能不能卖给做欧洲市场的公司）。

### 1.5 "复用飞书通讯录"是一个没验证的假设

所有身份、审批卡片、文档投影都押在飞书上。但 10–50 人的跨境电商公司，用企业微信和钉钉的比例很可能高于飞书；很多小公司干脆只有微信群。押单一 IM 的风险是：第一批种子客户里一半装不了。

**建议**：身份抽象成 provider。v1 基线 = 本地账号（邮箱 + magic link），不依赖任何 IM；飞书 / 企微 / 钉钉作为 SSO + 通讯录同步 + 卡片投递的 provider，飞书先做。审批投递同样抽象：飞书卡片 / 企微 / 邮件兜底。成本很小，收益是不锁死在一个 IM 上。

**待验证**（不是讨论）：找 5 家目标画像的公司问一句"你们内部用什么"。

### 1.6 第一个用户故事与"谁来装"

文档从架构讲到部署三档，但没有一段写"第一天"。10–50 人的公司通常没有 IT；开源本地安装这件事，装的人是谁？老板、某个懂技术的运营、还是我们托管？

建议先写死一个 v1 用户故事，其余都服从它：

> 一家 3 人跨境公司。运营在自己的 Mac 上装 agentsws（或者我们托管）→ 用邮箱登录 → 授权客服邮箱 → 接 Shopify 只读 → 把现有 FAQ 文档拖进知识库 → 10 分钟后第一封客户邮件的回复草稿出现在队列里 → 点"通过"发出。4 周后采纳率 ≥95%，系统建议升 L2。

"完成"的定义：这一条 4 周跑通，中间没有人碰终端。

**楔子选择**：文档里提了两个引流口——① 外部 MCP server 让 Claude Code / Codex 能接（面向开发者）；② 客服 L1 队列（面向运营）。两者用户不同。建议 v1 楔子 = **客服职责包**，理由是 KefuAgents 已经验证了这个需求存在且用户愿意付费；MCP server 顺手做，但不当主楔子。KOL 排第二。

这一条还牵动 `01-开工顺序` 的一处矛盾：01 把"个人端先用起来"排在公司层之前，而侦察报告说"重心在公司工作台"。见 1.7。

**待拍板**：v1 用户故事是否如上；楔子选客服。

### 1.7 个人端在 v1 到底要不要

个人端 dsh 实例存在的唯一硬理由是**个人身份渠道**（个人微信 / WhatsApp / LinkedIn 登录态不出本机）。为它付出的代价是：两层同步协议、按权限的部分复制（PowerSync / Electric 选型）、换机迁移、个人端插件包。这是整个方案里工程量最重、也最晚才能产生用户价值的部分。

| 4、5 | 同意 | 模型网关进 v1；身份基线 = 本地账号，IM 作 provider |
| 6 | 没懂"第一个用户故事" | 它指"我们优先为哪一个具体场景做优化"。第 7 项回答后它自动有了答案：一个运营在自己电脑上装、自己用 |
| 7 | 目标是整个公司切换，但直接说服老板很难；要个人能用 → 部门接入容易 → 原先个人在用的能并进部门 → 公司同理 | 这是 v1 的核心设计约束，见 §7.4 |

### 7.2 现有 SaaS 怎么"保持工作 + 变无头"

不做第三个代码库。原则：**SaaS 的前台一行不动，给它加一个无头面。**

- KOLAgents 已经有远程 MCP server（M1–M4），它已经是半无头的；补齐"外部投喂线程"与"外部审批回写"两个口即可。
- KefuAgent 要加两样：① 把分类 / 知识检索 / 起草回复这些内部函数暴露成带鉴权的 API；② 每个 workspace 一个开关"外部接入模式"——打开后它自己的 IMAP 轮询停掉，线程由中台连接器投喂，回复由中台队列审批后经 SaaS 或中台发出。直接注册的 SaaS 用户开关关着，一切照旧。
- 中台侧：付费插件 = 调这两个 API 的 Backend provider。开源客服职责包在插件不装时用通用模型 + 开源 skill 跑，所以**中台不被 SaaS 改造进度阻塞**。
- 判断"实在不行"的标准：如果 KefuAgent 的起草逻辑与它自己的邮箱接管耦合到无法在两周内拆出 API，就先让开源职责包独立跑，SaaS 改造排到中台 L1 跑通之后；仍不新建第三套。

### 7.3 白话版：§1.2 与 §1.3 到底在问什么

**§1.2 会话映射。** dsh 里一个"会话"就是一个聊天窗口。问题是：一个客户来了一封邮件，我们是（甲）给这个客户开一个永远不关的聊天窗口，以后他每来一封都追加进去；还是（乙）每次来信都新开一个窗口，把这个客户的档案、历史往来、相关知识作为"简报"塞进去，答完就关。甲像给每个客户配一个专人，乙像每次派一个新人但带着完整的交接文件。我建议乙：客户数一多，甲的窗口数失控、成本失控，而且 dsh 升级最先打坏的就是长期存活的窗口；乙的所有状态都在我们自己的数据库里，dsh 换版本只影响"怎么开窗口"那一小段。

**§1.3 执行器位置。** "执行器"就是真正干活的那段代码：查 Shopify 订单、起草邮件、把退款登记成一条待审变更。它会在两个时刻被调用：一是 Agent 思考时（在 dsh 里），二是人在飞书卡片上点"通过"时（这时没有 Agent，也没有 dsh）。所以这段代码不能放在 dsh 插件里，得放在我们自己的服务里，dsh 和飞书卡片都来调它。MCP server 只是给 Claude Code 也能调它开的一个"插座"，不是另一份实现。

### 7.4 生长式设计：一套软件、一个数据模型、三种规模

**原则**：没有"个人版 / 部门版 / 企业版"三套代码。个人 = 只有一个成员的工作区。生长靠一个原语：**加入（Join）**。

三个概念：

| 概念 | 定义 |
|---|---|
| 人（Person） | 全局身份，邮箱登录；不属于任何工作区，可以同时在多个工作区里 |
| 工作区（Workspace） | 共享的单位：成员、职责、队列、客户库、知识库、连接器。个人工作区 = 成员数为 1 |
| 加入（Join） | 把一个工作区并入另一个工作区。个人→部门、部门→公司用的是同一个操作 |

三个阶段：

1. **个人**：本机装。自己给自己分职责，自己审自己的队列（仍是 L1，Agent 起草、我点通过）。连接器：公司邮箱（自己授权）、Shopify、个人渠道。
2. **部门**：第一个决定共享的人（或主管）把自己的工作区"升级为共享"——搬到一台常开机器或我们托管。其他人 Join 进去。Join 之后每个人本机的软件不消失，变成共享工作区的客户端：个人渠道还在本机，其余读写都走共享工作区的 API。**这就是双层架构里的"个人端"**——它不是另做的产品，是 Join 之后自然形成的状态。
3. **公司**：建公司工作区，各部门工作区 Join 进去，成为公司工作区里的一个"范围"（部门）；原主管成为该范围的管理者。老板不需要被说服"切换"，他看到的是部门已经在用，Join 一下就有全公司视图。

**Join 时对每类对象的处理**（要设计死的清单）：

| 对象 | 处理 |
|---|---|
| 身份 | 不变；这个人多了一个工作区 |
| 职责 | 个人自封的职责映射到目标工作区的职责模板，由目标管理者确认 |
| 客户 / 联系人 / 任务 | 并入目标库，按邮箱 / 域名去重；`owner` 保留原创建者；两人共有同一客户 → 双 owner，冲突字段按事实卡双值并存 |
| 知识（事实卡 / 话术 / 规则） | **不直接发布**，全部变成目标工作区审批队列里的提议；策略层规则不带入，由目标工作区的老板定 |
| 连接器 | 公司资产类（公司邮箱、Shopify）所有权转移到共享工作区；个人身份类（个人微信 / WhatsApp / LinkedIn）留在本机 |
| 会话 / 审计轨迹 | 打包上交，追加进目标事件日志 |
| 权限 | 从"自己是老板"降为成员；范围 = 自己原有数据 + 目标分配的 |
| 技能 | 个人技能小仓保留；想共享的走技能晋升审批 |

**第一天就要满足的约束**（否则以后并不进去）：

1. 每条记录出生就带 `workspace_id`、`owner`、`scope`，个人期也不例外
2. 人的 id 全局唯一，不与工作区绑定
3. 权限模型的"范围"维度从第一天支持嵌套（部门），即使个人期只有一个范围
4. 02 文档的导出包就是 Join 的传输格式：Join = export + import + 映射确认。**02 因此不是 v2，是 v1 核心**
5. 共享工作区与个人客户端之间 v1 走在线 API 直连，不做离线副本；同步引擎仍推迟

**退出**：人离开时个人渠道带走，工作区里的客户关系与知识留下。这条在 Join 那一刻就要明示并确认，不能事后才说。

**由此改动的拍板项**：§6 第 9 项作废；§1.6 的用户故事改为"一个运营在自己的 Mac 上装、自己用 4 周"；§5 第 3 次讨论的议题改为 Join 语义。

### 7.5 这个设计带来的新决策

| # | 决策 | 我的建议 |
|---|---|---|
| 10 | 个人期的安装形态：非开发者要能装本地服务 | 打成桌面 App（参考生态里的 dsh-desktop），CLI 只给开发者；如果桌面打包来不及，给个人一个我们托管的免费档 |
