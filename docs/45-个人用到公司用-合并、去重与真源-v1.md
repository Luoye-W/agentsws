## 0. 一句话

**个人用的时候，你就是一家一个人的公司**；进公司不是"把我的东西复制过去"，而是走一遍"对照 → 去重 → 老板批"的合并向导。合并之后**公司那份是真源**，你原来那份变成指向它的别名；以后公司里谁再建同样的东西，建之前就被查重拦住指到已有的那份。

## 1. 现在已经有的（不用重做）

- 个人工作区（`kind: personal`）本来就存在（20 §1），一个人用 = owner 与成员是同一个人，分工限制自动关闭（20 §6 用例 1）。
- 20 §4 已经定了 **Join 向导**：源工作区导出 → 目标工作区导入 → `join_mapping` 审批项逐类对照（人、职责、客户、知识、技能、连接器、定时任务……）→ 完成后源工作区归档只读。
- 40 §2 已经落地了"建之前先查"（五个入口查重）和"往上浮"（个人层的东西被 ≥ 2 岗位采用 → 出卡晋升）。
- 44 / WP47 落地了品牌（范围组）与产品线，但它们**还不在 Join 的对照表里**，也**不在查重入口里**——这就是 Luoye 问题的缺口。

## 2. 三个问题、三个答案

| Luoye 的问题 | 答案 | 落在哪 |
|---|---|---|
| 个人怎么有效并进公司 | 走 Join 向导，**一次对照、按类批准**，不是逐条手搬 | 20 §4 已有骨架，补对象 |
| 个人设的品牌 / 产品线能不能自动复制到公司 | **能，但是"提议"不是"覆盖"**：向导把它们列出来，和公司已有的逐条对照，一样的合并、相似的让 owner 选、没有的新建；owner 一键"全部采纳" | H1、H2 |
| 公司里别人也设了同样的东西 | **建之前先查**（品牌 / 产品线 / 店铺三个新查重入口）；同一把唯一键只允许存在一份，后来的人直接被指到已有那份并看到是谁建的 | H3、H4 |

## 3. 方案

### H1 个人工作区 = 一个人的公司，什么都先在自己这儿建

- 一个人用时，品牌、产品线、店铺范围、连接、技能、知识全部建在他的个人工作区里，`owner: person_id`。没有"个人设置"和"公司设置"两套界面——**同一套界面，只是工作区不同**。
- 好处：进公司那天不用"从个人设置里挑哪些是公司的"，因为个人工作区里的每样东西都有明确的类型和唯一键，向导能自动对照。

### H2 进公司 = Join 向导补三类对象，逐条对照出三种结果

20 §4.2 的对照表加三行（唯一键是关键——没有唯一键就没法自动对照）：

| 对象 | 唯一键 | 一样 | 相似 | 没有 |
|---|---|---|---|---|
| 店铺 / 平台账号范围 | Shopify：`myshopify` 域名；亚马逊：卖家 id + 站点 | 合并：个人那条变别名指向公司那条 | — | 新建进公司（owner 批） |
| 品牌（范围组） | 名字归一化（去空格、大小写、全半角）**或**成员重合 ≥ 50% | 合并成员取并集，记谁带进来的 | 名字不同但成员大半重合 → 出一张对照卡，owner 选"是同一个品牌，用哪个名字"或"两个品牌" | 新建（owner 批） |
| 产品线 | 父范围相同 + 判据平台相同 + 判据集合相同 | 合并 | 父范围相同、判据集合有重叠但不等 → 对照卡，owner 选"合并取并集 / 保留两条 / 以公司那条为准" | 新建（owner 批） |

- 向导一屏列完，按类分组，每类一个"全部采纳"，也能逐条改。批准落一张 `join_mapping` 审批项（14），一次签字，事件全留痕。
- **连接（凭据）不跟着走**：40 §1 定了凭据归属，个人连的店进公司要 `transferConnection`（20 §4.2 已有），并且要本人在向导里明确点"把这条连接交给公司"。

### H3 合并后公司那份是真源，个人那份变别名，改动只改真源

- 合并完成：公司对象是唯一可编辑的那份；个人对象打 `superseded_by: <公司对象 id>`，只读、可回看（同 40 §2.3 往上浮的做法）。
- 本人以后打开自己的品牌 / 产品线，看到的就是公司那份（别名解析），改动走公司规则（owner / scope_manager 才能改，别人只能提议）。
- 退出公司（20 §4.4）：公司对象留下，别名断开；他的个人工作区继续用自己归档的那份（恢复可编辑）。

### H4 公司里两个人建了同样的东西：建之前拦，建之后合

- **建之前**：40 §2 的查重入口从五个变八个——加品牌、产品线、店铺范围。新建表单一填名字 / 域名 / 判据，就查同唯一键或相似的，命中就显示"已有：品牌乙（王岚 建，3 个岗位挂着）→ 直接用它"，用户点一下就是引用，不会产生第二份。
- **建之后**（并发或绕过界面）：夜间任务扫同唯一键，命中出 `policy_change` 卡"这两条是同一个吗"，owner 选合并；合并同 H3。
- **不做**自动改名或自动删除：任何合并都要有人点头，且留 `superseded_by` 可回退。

### H5 反向：公司设好的自动下发，个人只能提议不能改

- 公司里的品牌 / 产品线 / 店铺范围对成员是只读的组织结构；成员想改（比如把某个 SKU 挪到另一条产品线）= 出一张 `policy_change` 提议卡给 owner / scope_manager，不是直接改。
- 原因：44 里范围直接决定"谁能看到什么数据、能改什么"，让成员随手改等于让他自己给自己扩权限。

## 4. 不做什么

- 不做"个人设置面板"与"公司设置面板"两套；不做"同步开关"（同步 = 真源唯一 + 别名，没有第二份就没有同步问题）。
- 不做自动合并"相似"的东西；相似一律出卡让人选。
- 不做跨公司合并（两家公司各自有品牌乙）：那是两个工作区，互不相干。

## 6. 拍板结果（2026-09-11 Luoye 同意，WP50 实现）

- H1 个人工作区 = 一个人的公司，同一套界面不分个人 / 公司设置
- H2 Join 向导补三类对象，按唯一键对照出"一样 / 相似 / 没有"，按类一键采纳，凭据要本人明确交出
- H3 合并后公司那份是真源，个人那份 `superseded_by` 只读，退出公司时恢复
- H4 建之前查重拦、建之后夜间扫 + 出卡合并，任何合并都要人点头
- H5 公司对象对成员只读，改动走提议卡

**落地时补的两条**（实现里发现、写进这里免得下次再想一遍）：

- **别名解析发生在"展开"那一侧，不是 `effectiveConfig` 那一侧**。44 G1 就是这么设计的：
  判权限那一刻读的是**存下来的那份已展开范围**，不再查品牌表。所以别名真正生效还需要
  一次重新展开——Join 落地那一步的 `assignments.update` 就是那一次。
- **他自己那个工作区里的岗位换不了 id**：职责层不许跨工作区挂品牌。那种情况原样存回去，
  靠展开时解析别名——结果一样（他的范围变成公司那条的成员），留痕也一样。
