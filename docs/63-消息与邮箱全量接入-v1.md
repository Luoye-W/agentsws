## A. 导航：左栏那一格换成「消息」

左栏原来是 首页 / 待办 / 日历 / 目标。现在是 **首页 / 消息 / 待办 / 日历**。

为什么换掉的是「目标」：一只邮箱是人**每天**真正会去的地方，目标是**每周**看一次的
东西。左栏那几格是"去哪儿"，不是"什么重要"——按去的频次排，目标就该让位。

**目标模型不删**（37 的 `daily_plan` / `review` 都依赖它）：

- `/goals` 路由保留，老书签点得开；
- 入口收进「待办」页的一个 tab（`/todos?tab=goals`）——待办与目标本来就是同一件事的
  两端（37 §2.3 的"长期待办挂目标"），人看完"这周还剩什么"顺手想看"这个月定的数走到哪了"，
  中间不该隔一次导航；
- ⌘K 里仍然搜得到；
- 首页那一行"目标 2 项 · 1 项落后 →"照旧跳 `/goals`。

「消息」那一格右边是一个**点**，不是一个数字。未读 132 时一个红色的 "132" 会让整块左栏
看起来像在报警，而它要说的只有"那边有没读的"。数字留给点进去之后的文件夹。

## B. 消息 = 统一收件处

v1 只有邮箱一种来源，但**数据模型按"来源可扩"建**：

```ts
type MessageSource = 'email'   // 以后：'im' | 'dm' | 'whatsapp' | …
```

每条记录都带 `source`，界面与查询一律按它分流，**不许按"有没有 Message-ID"之类的间接
特征判**。写死成邮件的那一版，第二种来源来的那天就得重做；而多带一个字段今天只值
一行代码。

## C. 收信：全量同步

对每只**已连接**的邮箱（复用现有连接与本机加密凭据，**不新增任何凭据入口**）同步：

`INBOX` + 已发 + 草稿 + 垃圾箱 + 垃圾邮件 + `KefuAgents` + `KOLAgents`。

**先列文件夹再扫**（WP161）：每只邮箱先问服务器要一份文件夹清单，已发 / 草稿这类按语义认
真名（`[Gmail]/Sent Mail`），服务器上没有的那种不扫；岗位文件夹按下面「文件夹名」一节认。
清单每只邮箱各列各的、各缓存各的（10 分钟重列一次）；列不到就按缺省名单试，下一轮再列。

### 文件夹名：与老产品同名（WP161，Luoye 09-27）

岗位文件夹的**规范名**与 Luoye 的老产品逐字相同：

| 岗位 | 规范名 | 老产品 | 消息页显示名 |
|---|---|---|---|
| 客服 | `KefuAgents` | KefuAgent 建的就是它 | 客服在处理 |
| 红人营销 | `KOLAgents` | KOLAgents 建的就是它 | 红人合作 |
| B2B（预留） | `BtoBAgents` | —— | B2B 往来 |

**为什么非得同名**：很多 IMAP 服务器的文件夹名区分大小写。v1 写成了全小写
`kefuagents` / `kolagents`——用过老产品的人接进来，邮箱里就会出现两只名字相近的文件夹，
信分在两处，而且他在邮件客户端里按老名字建的过滤规则对新那只不起作用。

**认已有文件夹不分大小写**，每只邮箱单独判断：

1. 服务器上有规范名那只 → 用它；
2. 没有规范名、但有任何大小写变体（`kefuagents` / `KEFUAGENTS`）→ **沿用已有的那个真名**，不另建；
3. 都没有 → 第一次挪信时按规范名新建。

多个变体同时存在时优先规范名，其余变体**照常扫描**——那里面的信不挪、不删、不改名。
那是用户邮箱里的结构，我们没有资格替他合并。显示名走 i18n，界面上不露真名。

B2B 只是预留：`MessageRoute` / `folder_kind` 多了 `b2b` 这个可选值，**分拣器现在不产出它**
（`allowRoute` 把它降回 `inbox`），`BtoBAgents` 也不在缺省扫描清单里；消息页上没有
B2B 那只文件夹的信时不显示「B2B 往来」。等 B2B 岗位那张单接上分拣再放开。

四条纪律，前三条直接沿用 WP55（48 §4 L3 #5）那一套，**不另起炉灶**：

1. **每文件夹一个 UID 游标**。IMAP 的 UID 只在一个文件夹内唯一，这不是可选项。
2. **`UIDVALIDITY` 变了就从 0 重来**（服务器重建过邮箱）。宁可重拉一遍，不要静默漏信。
3. **毒消息隔离**：一封解析就抛的信记一笔、跳过、继续；连续到阈值永久越过并留记录。
4. **扫描租约**，但 key 是 `msg:<地址>` 而不是 `<地址>`——**故意错开**：只装了渠道的老装配里
   邮件适配器（`EmailChannelAdapter`）自己也在扫这只邮箱的 INBOX，两边抢同一把租约的话谁也扫不动。
   服务进程里（WP167 起）适配器已经不自己扫了，收信只有消息同步这一个入口（见 §D「收信一个入口」）。

**首次只回溯最近 30 天 / 最多 2000 封**，可「再往前取」。一只用了五年的邮箱有几万封信，
第一次打开消息页不该等十分钟。

**原文 MIME 进受控原始材料区**（加密、按发件人为 `subject_ref`、随主体删除，18 §2.1 原样），
库里只存**解析后的**：头（只留分拣要看的那六个）、纯文本、净化后的 HTML、附件元数据；
附件字节走现有 blob。

**身份按 `Message-ID` 算**，不按「账号|文件夹|uid」：一封信被挪到另一个文件夹之后 UID 会
换号，用位置当身份的话同一封信会变成两条。

### 数据模型（`packages/contracts/src/messages.ts`）

```
MessageRecord   一封信：来源 / 账号 / 文件夹（真名 + 语义）/ uid / 会话 / 头 / 正文 /
                净化后的 HTML / 附件元数据 / 旗标 / 标签 / 路由 / 分拣结论 / 原文引用
MessageThreadSummary  列表上的一行 = 一段**会话**（不是一封信）
MessageFolder   文件夹：真名 + 语义 + 未读数（各家名字不一样，界面按语义画）
MessageLabel    标签（内置十一个 + 用户自建）
SenderRule      "以后这个发件人都这样"
MessageDraft    草稿
ReplySuggestion 回复建议（短 / 详 / 婉拒）
MessageTriage   一次分拣的结论
```

存储：**自己一张库一张 `_migrations`**（35 §2），内存与 SQLite 两个实现共用
`query.ts` 的纯函数做细筛与会话聚合——搜索结果最怕两边不一致。

## D. 分拣（triage）

每封新来信过一次，产出
`{ route, labels[], needs_reply, priority, summary(≤40 字), confidence }`。

### 路由三条

- `route = 'support'`：**仅当**这个品牌启用了客服岗位 → 交给客服那一路（开事项、过判断层、起 Run，
  见下面「收信一个入口」），并把信 IMAP MOVE 到 `KefuAgents`（或这只邮箱上已有的大小写变体，
  见 §C「文件夹名」；怎么动照这只邮箱卡上的开关）；
- `route = 'kol'`：**仅当**启用了红人营销岗位 → 归并到红人合作线程，MOVE 到 `KOLAgents`；
- 其余 `route = 'inbox'`：**留在 INBOX 不挪**，只打标签——**不开事项、不起 Run**，只在「消息」页里。

"岗位没开就不挪信"这条**不许绕过**，而且岗位开没开是**每次现查**、不缓存——
岗位是会变的，缓存了就会出现"昨天开了今天关了，信还在往 `KefuAgents` 里挪"。

### 流程（文字版流程图）

```
一封新信
  │
  ├─①  In-Reply-To / References 命中客服或红人已有线程？
  │       是 → 直接归那边（confidence 1，by=rule）   ← 不花模型
  │       （WP163：只认带这两个头的**后续来信**；全新的一封不拿自己的线程 id 去对。
  │        WP167 之前渠道那一路同一拍里先给每封新信开事项，拿自己去对就会人人"命中"；
  │        现在不会了，但这条口径留着——它本来就是 63 的原话）
  │
  ├─②  命中用户教过的发件人规则？（整地址比整域更具体，具体的赢）
  │       是 → 按规则走（confidence 1，by=rule）     ← 不花模型
  │
  ├─③  自动信头？（List-Unsubscribe / List-Id / Auto-Submitted /
  │     Precedence: bulk / noreply@ 发件人——WP167 修了 noreply 这一条从没命中过的 bug）
  │       是 → 订阅·通知类，打标签，needs_reply=false（by=rule）  ← 不花模型
  │
  ├─④  halt.model 开着？
  │       是 → 标「未分拣」（by=halted），route=inbox            ← 不花模型
  │
  └─④' 走模型网关的**便宜档**（purpose=extraction）
          只送 头 + 正文前 2000 字，**不送附件**
          allowed_routes 里只有已启用的岗位 → 模型选不出一条这台机器上不存在的路
          │
          └─ 收口三道：
               ① 岗位没开的路降回 inbox
               ② confidence < 0.6 的 support / kol **不挪、不开事项**，
                  route 留 inbox，suggested_route 挂上去，
                  进「消息」页的「待确认」一栏（人点「这是客服」才交出去）
               ③ 摘要裁到 40 字、标签只留认得的
          │
          └─ 模型抛异常 / 不可用 → 落兜底（route=inbox，界面显示"未分拣"），
             **不让这封信进不来**
```

> **一个已经踩过的坑**：头要从 `headerLines`（原始行）里取，不能用
> `parsed.headers.get('list-unsubscribe')`——mailparser 会把它结构化进一个叫 `list`
> 的键，照 `headers.get()` 读的话第 ③ 层**一次都不会命中**，每封群发都白花一次模型。
> 这条有用例钉着。

### 归档文件夹按岗位

现有 `archive_folder` 的默认值从 `agentsws` 改为**按岗位**：客服 `KefuAgents`、
红人 `KOLAgents`（WP161 起与老产品同名；服务器上已有大小写变体就沿用那只，每只邮箱各认各的）。
旧配置显式写了别的名字的照旧，`null` = 关掉归档。MOVE 失败**只 log**，信仍在消息里可见
（WP55 的纪律）。对账判「这封是在归档文件夹里搜到的」也不分大小写，老默认 `agentsws` 照认。

### 收信一个入口（WP167，Fable 09-27 定）

**收信只走一个入口：消息同步。** 它先分拣，再按分拣结果交给各自那一路：

```
消息同步（MailboxSync，每只邮箱每个文件夹一个游标）
  │  落消息库（每一封都看得见）
  ├─ 分拣
  │    ├─ support            → 交给客服那一路：开事项、过判断层、起 Run；再按开关标已读 / 挪进 KefuAgents
  │    ├─ kol                → 交给红人那一路（照现在的规矩：归并到合作线程的事项上）
  │    ├─ inbox + 挂了 suggested_route（判不准）
  │    │                     → 「消息」页的「待确认」一栏：不开事项、不挪；人点「这是客服」才交出去
  │    └─ inbox              → 只在「消息」页：不开事项、不起 Run、不花模型钱
```

**"交给客服那一路"复用渠道的入站管线，不另写一份**（`channels.intakeSupportMail`）：
Amazon 子渠道判定、线程台账（收件人门禁的依据）、去重、落事项、客服判断层（WP125）、起 Run，
全在那一条里。服务进程装配时给渠道传 `inbox_intake: 'message_sync'`，渠道适配器就**不再自己轮询 INBOX**
（重试队列照推）；只装了渠道、没装消息同步的老装配（缺省 `'channel'`）保留老行为——适配器自己扫
INBOX、每封新信开事项（有测试钉着，别当成 bug 修掉）。

一张图说清以前与现在：

| | 以前（WP55 + WP113 两条路） | 现在（WP167） |
|---|---|---|
| 订阅 / 通知 / 供应商信 | 渠道那一路开一条事项、起一次 Run、过一遍判断层 | 只进「消息」页 |
| 客服信 | 渠道那一路开事项、起 Run；消息同步再递一次判断层 | 消息同步分拣后交一次，开事项、起 Run、过一次判断层 |
| 判不准的 | 渠道那一路照样开事项 | 「待确认」，人点了才交 |
| 谁扫 INBOX | 两边都扫（租约错开） | 只有消息同步 |

**同一封信只进一次客服管线**：按 Message-ID 记一张不过期的台账（没有 Message-ID 的按
「邮箱 × 文件夹 × UID」）——同步了两拍、信被挪走换了 UID、人在手机上又挪回收件箱、人在「待确认」里
又点了一下，都不会再开一次 Run。入站管线自己那张去重表是 24h 窗口，挡不住这些。

**升级那一拍**（WP167 终审追加）：老版本的渠道那一路已经给 INBOX 里每封信开过事项、起过 Run。换成新代码之后，
消息同步第一次扫到这些信时**一律当"已处理"**——只进「消息」页，不再开事项、不再起 Run、不再起草回复。认法两条：

1. **事项钉着的**：第一次同步之前（只做一次，台账里写一个标记 `meta:wp167_legacy_seed_v1`；写到一半断了下次整批重来），
   把工作模型里每条会话事项钉着的线程 id（= 那条线程第一封信的 Message-ID）和消息库里这些线程下的每一封信预写进台账；
2. **适配器游标之前的**：渠道适配器原先那条 INBOX 游标停在"老版本处理到哪儿"（收信归消息同步之后它不再推），
   INBOX 里 UID 不超过它的信都当已处理；`UIDVALIDITY` 变了这条游标作废。后续来信（Message-ID 不是线程 id）靠的就是这一条。

游标之后到的新信照常：客服信开一条事项、起一次 Run。

**已经在岗位文件夹里的信**（老产品或人自己在邮件软件里建的过滤规则挪过去的）第一次被扫到时，
**不开事项、不起 Run**：有钉着这条线程的事项就挂上，算"那一侧早就接了"，信不动。理由：老产品的
`KefuAgents` 里是已经处理过的信，回溯 30 天把它们全交一遍会给一个月前的信起草回复。过滤规则直接放进
`KefuAgents` 的新信同样不开事项（Fable 09-27 定）。「接管」保持品牌级：就是这个品牌开没开客服岗位。

**「待确认」**：人点「这是客服」= 人工分拣（事件 `messages.route_confirmed`：谁点的、判成什么、交没交出去；
没有正文、地址遮掉），原信从受控原始材料区取回递进管线，再按这只邮箱的开关动邮箱；客服岗位没开就
交不出去，什么都不改，界面照实说。点「不是」只记人的判断，信从这一栏消失。

**挪信 / 标已读只归消息同步**（WP163）——它有分拣，知道哪封是客服信、岗位开没开。服务进程装配时给渠道传
`mailbox_moves: 'message_sync'`，渠道那一路一下都不动邮箱。只装渠道的老装配才由渠道那一路挪，而且也只挪
**判成客服**的信（进了客服路由、建了客服线程、客服岗位开着）。

另外两条防"挪来挪去"：

- **已经在岗位文件夹里的信不再自动挪**（`KefuAgents` ↔ `KOLAgents` 不会被两轮分拣来回挪）；
  要改归属走「纠错」那条路（人按的「移到…」）。
- 分拣第 ① 层只认后续来信（见上面流程图 ①）。

### 客服信在邮箱里怎么动（WP163，照老产品 KefuAgent）

语义照搬 KefuAgent `src/lib/support/service.ts` 的 `moveCustomerServiceMessageToAiFolder`，
实现在 `packages/channels/src/email/support-mailbox.ts`，两条路共用。判成客服之后按顺序：

| # | 开关（老产品字段） | agentsws 里 | 默认 | 做什么 |
|---|---|---|---|---|
| 1 | 影子模式（`shadowMode`） | `support_mailbox.shadow_mode`（新增，可选） | 关 | 开着 = 整条流程照跑，**邮箱一下都不动**，只记一笔「跳过」 |
| 2 | 客服文件夹接管（`aiSupportFolderEnabled`） | 复用 `archive_folder`（`null` = 关）；消息同步里是 `folder_enabled` | 开 | 关着 = 不动，记「跳过」 |
| 3 | 标已读（`aiSupportMarkRead`） | 复用 `archive_mark_read`；消息同步里是 `mark_read` | 开 | 先在原文件夹里标已读；失败记一笔，**不挡挪信** |
| 4 | 挪信（`aiSupportMoveEmails`） | `support_mailbox.move`（新增，可选） | 开 | 信不在目标文件夹里才挪；关着记「跳过」 |

影子模式说的是"这只邮箱"，所以对红人那只（`KOLAgents`）也生效；另外三个开关只管客服信。
开关**每封现查**、**按邮箱各一份**。

**界面（WP167）**：连接页那只邮箱卡上三个开关——影子模式 / 挪进 KefuAgents / 标已读——外加一个只读的
「接管」小标（接管 = 这个品牌开了客服岗位，岗位页的事，不另存一份）。卡上只有开关与一句话，解释进问号；
影子模式开着时卡上醒目标「只看不动」。改一次写一条 `mailbox.switches_changed`（谁、哪只邮箱（遮过）、
改了哪几个），**立刻生效**——下一封就按新的走。存在品牌数据目录的 `mailbox-switches.json`；
路由 `GET` / `PUT /v1/connections/:id/mailbox-switches`（读 / 写两档元组，与连接面同档）。

每一步写一条 `inbound.mailbox_action` 事件：`action`（`observe` / `mark_read` / `move`）、
`status`（`completed` / `skipped` / `failed`）、原因码（`shadow_mode` / `folder_disabled` /
`move_disabled` / `handoff_refused` / `unsupported` / `server_refused` / `error`）、文件夹与 uid。
**不含正文**，邮箱地址遮掉（`a***@b.com`），失败的技术原因截到 160 字、里面的地址也遮掉。
「消息」页左栏底部显示**最近一次没动成**的那一条（一行短字 + 问号里说哪只邮箱、什么时候、为什么）；
同一种动作后来成功过就不再挂着。这份"最近一次"只在进程内，重启清零。

### 纠错

任何一封信都可以「移到客服 / 移到红人 / 移回收件箱」，同时问一句
**"以后这个发件人都这样？"** → 勾了就写一条发件人规则。规则跑在模型**之前**（第 ② 层），
所以教过一次之后同一个发件人的下一封直达，不再花模型——这既省钱，也让"我教过它"这件事
**看得见**。人挪过的那一封，分拣结论记 `by: 'user'`、`confidence: 1`，下一轮不会被改回去。

## E. 标签

内置十一个（中英）：订单与物流、供应商、平台通知、账单与发票、合作邀约、营销订阅、
招聘与人事、法务与合规、账号安全、个人、可疑。用户可**自建、改名、改色、合并**；
内置的删不掉（只能改名改色），自建的删掉会从所有信上摘干净。

标签**存 agentsws 本地**。服务器支持 IMAP keyword（`PERMANENTFLAGS` 含 `\*`）时顺手同步成
keyword（前缀 `agentsws_`），不支持就**只在本地**——**不要为了标签去挪信**：那会改变
用户邮箱里的结构。

「可疑」**只提示不删信**。我们不替用户判"这封是诈骗"，只把它标出来。

## F. 回复建议

`needs_reply = true` 的信，**打开时**在右侧给 1–3 条建议（短 / 详 / 婉拒，**有差别**，
不是同义改写）。点了**进编辑框成草稿**，人改完自己点发送。

五条纪律：

1. **非岗位信件永不自动发**。这条路的终点是一个装着建议正文的写信框，没有第二个出口。
2. **按需生成**：只有右栏那一格挂载（= 人打开了那封信）才生成，并缓存 30 分钟。
   对全量来信预生成是最贵的错法——一只邮箱两千封信，九成没人会打开。
3. 语气与签名取**个人层**技能 / 记忆（54 的六层）；知识库能引用时**标出处**。
4. 发送走现有 **outbox 七态 + 对账**，`Idempotency-Key` 齐（按"收件人 + 主题 + 正文 + 会话"
   算，于是"网络抖了一下人又按了一次"只会发出一封）。
5. **不出审批卡**。36 那句"只有要人拍板的才是卡"反过来也成立：人自己按下发送的东西不该
   再问他一遍。

> **收件人门禁那一条的边界**（31 §3.3）。Agent 的回信仍然只走
> `channels.deliver`，收件人只从线程台账取，一个字都没放松。人自己写的信走新的
> `channels.sendMail`，收件人**从入参来**——那道门禁挡的是"模型从入站材料里解析出一个新
> 收件人"，它不该也挡住人在写信框里敲的地址。两条路在代码上分得开，调用
> `sendMail` 的只有 `/v1/messages/send`（要 `X-Assignment`、挂 `outbound: true`）。

## G. 作为普通邮箱该有的

列表（**会话聚合**）/ 阅读 / 已读未读 / 星标 / 归档 / **删除 = 移到垃圾箱，绝不永久删除** /
写信 / 回复 / 全部回复 / 转发 / 抄送密送 / 附件收（发在下一版）/ 草稿自动保存 /
搜索（发件人、主题、正文、标签、文件夹）/ 多邮箱切换与「全部邮箱」/
键盘快捷键（`j` `k` `e` `r` `a` `/`，跟主流邮箱一致——肌肉记忆比自创一套值钱）。

**已读、星标、归档、删除都回写 IMAP**，而且是**双向**的（标回未读也要回写）。
理由只有一句：用户回到自己的邮箱软件里看到的必须是同一个状态。做不到这一点的"集成"
比不集成更糟——他得在两个地方各读一遍。回写失败**只 log**：本机状态照改，信照样看得见。

**HTML 正文两层防护**：

1. 服务端净化（白名单标签与属性、扔掉 `script`·`style`·`iframe`·`form` 与一切 `on*`
   事件、`javascript:` 链接）；
2. 前端再套一层 `<iframe sandbox>`（**无脚本、无同源**）。
   WP227（Luoye 10-05）：正文链接点了用系统浏览器 / 新窗口打开——沙箱只多开 `allow-popups
   allow-popups-to-escape-sandbox`，前端再筛一遍链接，只放行 http / https / mailto（其余拿掉 `href`）；
   桌面壳 `setWindowOpenHandler` 按同一份白名单交 `shell.openExternal`。

**远程图片默认不加载**（防追踪像素）。做法不是删掉 `<img>`（那样版式就塌了），是把
`src` 搬到 `data-ws-remote-src`：在人按下「显示图片」之前，浏览器**一个请求都不会发出去**
——追踪像素要的就是那一个请求。每封可「显示图片」、可「总是信任这个发件人」。

> 为什么不装 `sanitize-html`：它自带一串传递依赖，而我们要的只是"白名单 + 去远程图片"
> 这两件事，而且净化结果还要再被 sandbox iframe 兜一次。多一个供应链入口换不到那一层
> 额外保证。自己那份有独立的用例表，改一条规则就能看见后果。

## H. 与岗位的关系

`KefuAgents` / `KOLAgents` 里的信在消息页**照样能看**（文件夹视图），但：

- 顶上一条状态带：**「客服 Agent 在处理 / 等你拍板 / 已回复」**
  （判据取自那条事项的状态，**不猜**——猜错的代价是人以为 Agent 在忙，
  其实那条线程停在等他点头）；
- 右下角一个 **→ 去对应工作线程**（`/matters/<id>`）；
- **这里不给「直接回复」**。人与 Agent 同时回同一个客户，是这套东西最难解释的一种错。
  要亲自回：先点「我来接手」，走现有的 takeover。

## I. 三栏

- **左栏不变**（只换了一格的名字与图标）。
- **中栏** = 文件夹 / 标签条 + 会话列表 + 阅读区（宽屏左右分，窄屏上下切）。

## J. 隐私与驻留

- **信件全部落本机库**。
- 送模型的只有**两处**：D-④ 的分拣（头 + 正文前 2000 字，不送附件）与 F 的回复建议
  （本封 + 这条会话前几封的摘要 + 知识库命中）。两处都走**用户自己配置的模型网关**。
  全仓再没有第三处把信件内容送出这台机器。
- **日志不打正文，也不打完整邮箱地址**（`ann@customer.example` → `a***@customer.example`）。
- 导出包**默认不含信件正文**（开关可选）。

## K. API

`/v1/messages/*`（二十二条；WP167 加了「待确认」那一条 `confirm-route`），鉴权元组照 `work.ts` 那一条
（`approval.read` / `approval.stage`，`range: own`）。理由与 37 一样：一只邮箱是**本人自己
的收件处**，05 的 scopes 是对业务数据域说的（订单、顾客、广告账户），邮箱不是其中之一。

三条边界写在路由表上，看得见：

- **一条硬删信的路由都没有**（删得掉的只有标签、发件人规则、草稿）；
- **只有 `send` 是 `outbound`**（急停出站档拦它，读照常）；
- 全部要 `X-Assignment`，权限沿用现有成员 / 品牌隔离（一个品牌一张消息库，
  品牌 A 的信在 B 的任何路由里都读不到）。

### M.2 接法

- **飞书**：企业自建应用（App ID / App Secret）+ 机器人能力 + 事件订阅选「长连接」+ 事件 `im.message.receive_v1`。
  私聊都收；群里 mentions 里有机器人自己的 open_id 才收（启动时查 `/open-apis/bot/v3/info`；查不到退回「有 @ 就算」——
  只开 @ 权限时飞书本来只推 @ 了机器人的群消息）。回复用 `im.v1.message.reply` 挂在原消息下。
  事件回调立刻返回（飞书 3 秒内要回执），问代理放到管线里。App ID 不合 `cli_` + 16 位时 SDK 会悄悄不连，我们先拦。
- **钉钉**：企业内部应用（Client ID / Client Secret）+ 机器人（消息接收模式 Stream）。一次 HTTP 换 ticket → WebSocket →
  回调**先回执**（60 秒内不回执会重推）→ 管线。群里 `isInAtList=false` 不收。回复经消息自带的 `sessionWebhook`
  （有有效期；只许发往 `https://*.dingtalk.com`），群里顺手 @ 回提问人。
- **认人**：三条团队渠道共用。工作台点「绑定我的账号」拿一个 6 位码（10 分钟、一次性），私聊机器人发「绑定 123456」。
  码只显示给登录了工作台的那个人，所以「谁拿着这个聊天账号」由他本人证明；同一个账号 10 分钟猜错 5 次就不认。
  绑定表放本机加密库（聊天账号 id 也是个人信息）。认不出的人只回一句「先去绑定」，不代答。
- **凭据**：只在工作台原生表单里填，直接进本机加密库；不经 AI、不进日志 / 事件 / 响应体，填完不回显；
  连不上时卡上是一句人话（凭据不对 / 没开长连接 / 连接数超限 / 暂时连不上），原始错误串只进诊断事件。
- 企业微信在 WP85 只做了注入口、服务进程里没接真连接；这一单一并接上（`ws`），并换成同一套绑定。
