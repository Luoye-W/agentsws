## 0. Luoye 09-27 定的

1. 「各种 AI 服务 + 原本要订阅的数据接口」统一汇聚、按次卖的这一层**另建私有项目**。
2. 还没公测，**云端要搬就全搬、彻底**；按最佳架构来，在线聊天转发、红人这类不适合和 AI / 数据接口放一起的，**可以分开**。
3. 底座直接用或参考 **new-api / one-api 这类开源项目**；以后还要封装**类似 Apify 的服务**；Workers 跑不了的上 **Cloudflare Containers**。
4. 要**共享缓存**：别人查过的数据再查，命中照收。
5. **agentsws、KOLAgents、KefuAgents、BtoBAgents 共用一个账号、一个积分余额。**

## 1. 总体：一个私有仓库，三层，各自部署

| 层 | 管什么 | 跑在哪 |
|---|---|---|
| **① 账户与钱包** | 账号、组织、登录、链接令牌；**唯一一本账**（积分钱包、预扣 / 结算 / 退款、计量事件）；充值（Stripe）；运营后台 | Workers + DO（现有 AccountsDO / WalletDO / LedgerDO 与 `apps/cloud`、`packages/metering`、`apps/cloud-admin` 原样搬） |
| **② 能力网关**（卖货） | AI 接口、同步数据接口、异步任务（类 Apify）、公共红人库、共享缓存、服务商条款表 | Workers + DO + Queues / Workflows + R2；new-api 放新加坡一台小服务器（§3） |
| **③ agentsws 产品云** | 红人云（租户同步）、托管实例、在线值守、官方聊天转发实例 | Workers + DO + Containers（现有代码搬） |

- **同一个私有仓库、分开部署**：契约只有一份、一套 CI，小团队最省事；每层是独立的 Worker，互相用 Cloudflare Service Bindings 调，一层出事不拖垮另一层。
- **一本账**：所有收费（AI、数据、任务、红人库、订阅、托管）都走 ① 的钱包。②③ 只通过内部接口「预扣 → 结算 / 退款」，自己不记余额。new-api 自带的额度不当钱包，只用来和上游账单对账。
- **四个产品共用**：KOLAgents / KefuAgents / BtoBAgents 接 ① 的账号与钱包、调 ② 的能力；它们各自的产品云（相当于 ③）以后按需加，不和 agentsws 的混。

## 3. AI 接口

- 前面是我们的薄网关（现有 `/v1/ai/*`：预扣 → 数据驻留 → 转发 → 按 usage 结算），后面接 **原样不改** 的 new-api 做几十家模型汇聚与格式互转。
- **为什么原样不改**：new-api 是 AGPL-3.0，另按第 7 节要求保留署名与原项目链接；改了就要向通过网络使用它的用户公开改动。原样用、且用户不直接和它交互，就没有这个负担。
- **放哪：一台小服务器（Fable 09-27 建议，改掉原先的「先上 Containers」）**。new-api 是常驻的 Go 进程：要一直开着的数据库连接池、后台轮询（异步任务、渠道测活）。Containers 上它会别扭（出处见 §7）：盘是临时的；`sleepAfter` 默认 10 分钟、没有「永不休眠」，休眠后第一个请求要等 1–3 秒冷启动、后台轮询停掉；D1 / Hyperdrive 给不了 Go 容器用，只能靠 Cron 定时唤醒硬撑。一台常开的小服务器正好对上。
  - **地点：新加坡**。Luoye 的 Supabase 项目全在 `ap-southeast-1`（新加坡），new-api 的库也放那里，服务器跟库同城。境外机房不用备案。
  - **规格**：2 vCPU / 2–4 GB 起步够用；Docker Compose 跑 new-api（docs/61 已有配方，去掉 Caddy 与数据库容器）。
  - **库**：Supabase（Luoye 09-27 定）新建一个项目给 new-api 用；Redis 先不上，要时再加。
  - **不开公网口**：服务器上跑 `cloudflared`（Cloudflare Tunnel），只有我们的 Worker 带服务令牌能打到它；new-api 的管理后台走 Cloudflare Access，只放 Luoye 的邮箱。
  - **挂了怎么办**：单台先够用；它不可用时，我们的薄网关退回现在的「直连 DeepSeek」那条路，AI 接口不整个停。
  - 服务器由 Luoye 自己买（付款不经 AI）；系统更新、备份脚本、监控在部署那一单里写好。
- 需要几十家模型之前，也可以先维持 Workers 形态现在的「直连 DeepSeek」，new-api 晚一步接（改 `AGENTSWS_NEWAPI_BASE_URL` 一行）。

## 4. 数据接口与异步任务（类 Apify）

- **同步数据接口**（搜索、AIsa 这类 REST）：留在我们的网关层（Workers），现有三家适配器照用。
- **异步任务**：自己写一个任务服务——每个任务一个 DO（状态、预扣、结算、退款），Queues / Workflows 排队与重试，结果存 R2，按条计费走 ① 的钱包。上游是 Apify 这类托管服务时只做「提交 → 轮询或回调 → 取结果」，Workers 够用；以后自己跑浏览器抓取才上 Containers（或 Browser Rendering）。
- **借 new-api 的形**：new-api 有一套 JS「任务插件」（manifest 里声明 `baseUrl` / `allowedHosts` / 用量单位 `count|second|token|credit`，宿主负责轮询、提交时预扣、完成时按实际用量结算、连续失败或超时退款）。我们的任务服务照这个形状定「一家上游 = 一份插件」的接口，但不把钱放进 new-api（一本账）。
- 第一家上游：Apify（BtoBAgents 已在用，条款没禁止转售输出；上线前书面确认按次向终端用户收费的用法、LinkedIn 数据单独做合规评估）。

## 5. 共享缓存

现在的缓存是每个组织钱包对象内存里的 LRU，别的组织用不上、对象一睡就没了。要重做：

- **放哪**：按「查询键」分片的共享层——热数据放 KV 或按键 hash 分片的 DO，大结果放 R2。
- **缓存键**只用规范化后的请求参数（服务商、接口、查询、地区、语言、日期桶）做 hash，**键和值里都不带组织与用户**。谁查过什么只记在各组织自己的计量事件里；共享层只知道「这个键有结果」。
- **条款表**：每家服务商一行——能不能存、存多久、能不能给别的客户用。表里没写明允许的，**默认不进共享层**，只做本组织短时缓存。
- **不进共享层**：用户自带 key 查的（本来就在本机直连、不经过云）；个人联系方式（走红人库现有的「按次揭示 + 审计」，不当缓存卖）。
- 命中照收，成本记 0；结果上标数据日期，用户可以「重新查」（照常收费）。
- 已经跨租户共享的只有公共红人库（`KolPublicDO`），并入这一层统一管。

## 6. 候选底座对比（摘要）

| 项目 | 许可证 | 适合做什么 |
|---|---|---|
| QuantumNous/new-api | AGPL-3.0 + 署名条款 | **模型汇聚层，原样用**（最全最活跃，48.9k★） |
| Laisky/one-api | MIT | 想私有魔改一套 Go 网关时的备选（个人维护） |
| one-hub / done-hub | Apache-2.0 | 同上；one-hub 半停滞 |
| songquanpeng/one-api | MIT | 2025-02 起停更，不选 |
| Veloera | GPL-3.0 + 附加条款 | 已停止维护，不选 |
| sub2api | LGPL-3.0 | 定位是订阅账号拼车，有上游条款风险，不碰 |
| LiteLLM | MIT（`enterprise/` 商业许可） | 代理基于 FastAPI；pass-through + 按次计价免费，但没有充值 / 钱包 / 售卖后台 |
| FastAPI 自写 | MIT | 等于把约 3.6 万行 TS 用 Python 重写、离开 Workers / DO，不划算 |
| FastGPT | Apache-2.0 + 附加条款 | 知识库平台，禁止拿来做同类多租户 SaaS，无关 |
| Portkey / Bifrost | MIT / Apache-2.0 | 纯路由网关，没有计费，可作参考 |

Luoye 提到的「Fast API」：最可能是 Python FastAPI 框架（或 LiteLLM，它的代理用 FastAPI 写）。两条都不如「现有 TS 网关 + new-api 原样」。

## 8. 拆分步骤（每步一个 WP）

1. 开源仓补齐完整对外 OpenAPI（ai / data / wallet / 红人 / 转发 / 托管），进 CI。
2. 自带 key 适配器拆成开源包；simulation 与 7 个测试里「真起云服务」的部分换成契约替身；`apps/server` 只依赖契约与客户端。
3. 建私有仓，**带历史**搬：`apps/cloud`、`apps/cloud-worker`（按三层拆成三个 Worker）、`apps/cloud-admin`、`packages/{cloud-entry,metering,hosted,kol-cloud,kol-public,standby}`、`deploy/` 的云部分、`scripts/{demo-cloud-admin,import-kol-public}.mjs`。私有仓通过 npm 包或 git 依赖用开源仓的 `contracts`。
4. 开源仓删掉以上目录；README 与 docs/49、61、64、74 写明「官方云是私有服务」。
5. 私有仓：接 new-api（新加坡小服务器 + Cloudflare Tunnel）；做共享缓存层与条款表；做任务服务，Apify 第一家。
6. KOLAgents / KefuAgents / BtoBAgents 接统一账号与钱包（各自单独排）。
