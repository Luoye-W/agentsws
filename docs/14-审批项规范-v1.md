# 审批项规范 v1（契约 #3 审批总线）

| | |
|---|---|
| 日期 | 2026-09-08 |
| 对应 | 03 §2.2；架构总览 §六"一条审批队列"；Commerce Agents A3；06（认领 / 晋升 / lesson）；10（上游升级）；11（应用安装升级）；13（定时确认） |
| 原则 | ① 所有改变 Agent 行为或对外产生影响的事，都以一条审批项进同一条队列 ② 审批状态只由宿主写，永不从聊天文本解析 ③ 通过 ≠ 施行：施行由执行器做，施行时重跑规则 ④ 每条审批项都是学习信号 ⑤ 一个对象同一时刻只有一条待审 |
| 存放 | 审批项在共享数据层；每次状态变化是事件日志里的一条事件（并排版本） |

## 1. 类型（kind）

| kind | 什么 | 提议者 | 通过后施行什么 | 来源文档 |
|---|---|---|---|---|
| `outbound_draft` | 对外草稿：邮件 / WhatsApp / 社媒帖 / 评论回复 | Agent | 经渠道 `send` 发出 | 04、08 §7 |
| `staged_change` | 业务系统写变更（退款 / 改价 / 发布主题 / 合并 PR …），账本里一条 StagedChange | Agent | 执行器 `apply_change` | 05、12 §2 |
| `staged_action` | 长尾写：一个 OpenConnector Action 调用 | Agent | 执行器以 `role-apply` 调 Action | 08 §2.3 |
| `knowledge_update` | 知识提议：事实卡 / 话术 / 策略层的新增、修改、冲突裁决 | Agent / 秘书 / 人 | 写入知识库对应层 | 06 §2 |
| `skill_promotion` | 技能段级修改向上一层提交（个人→部门→公司→市场） | 人 / 每周巩固 | 目标层版本 +1，源层移除已合并段 | 06 §3 |
| `skill_lesson` | 次日学习建议："给你的 X 改一段" | 夜间整理 | 写入个人层 | 06 §5.2 |
| `claim` | 认领项：会议 / 群聊抽出的 action_item / decision / question / data_request | 秘书 / 会议 bot | 变工作项 / 进决策账本 / 进缺口队列 | 06 §2 |
| `policy_change` | 策略层：额度、职责定义、分配、职责分离设置、工作区策略 | 人 / Agent 建议 | 写 WorkspacePolicy / Role / Assignment | 05 §3 |
| `home_suggestion` | 首页调整建议 | 自适应层 | 改个人首页布局 | 06 §1 |
| `scheduled_task` | Agent 创建的定时任务（会写 / 会发的） | Agent | 定时任务激活 | 13 §1.3 |
| `app_install` / `app_upgrade` / `app_uninstall` | 公司工作区的应用安装、升级、卸载 | 人 / 哨兵 | 本地包管理执行 | 11 §3 |
| `upstream_upgrade` | 上游依赖升级 | 上游哨兵 | 合并升级分支、更新 pin | 10 §3 |
| `join_mapping` | Join 时职责映射、客户合并、连接器转移的确认 | Join 流程 | 执行 Join | 03 §7.4 |
| `dev_handoff_result` | 编码 Agent 交回的结果（PR / 主题副本）验收 | 编码执行器 | 转成 `staged_change`（发布） | 12 §2.1 |

新增 kind 的规则：必须能回答"通过后施行什么、由哪个执行器施行、失败怎么回滚"；否则它不是审批项，是通知。

## 2. 公共信封（所有 kind 共有）

```ts
type ApprovalItem = {
  // 身份
  id: string
  schema_version: 1
  workspace_id: string
  kind: Kind
  revision: number                         // 同一 dedupe_key 重复提交时 +1，历史保留

  // 归属（每条有且只有一个职责）
  role_id: string
  range?: RangeRef[]                       // 店铺 / 部门 / 账号
  subject: {                               // 它是关于什么的
    object: ObjectRef                      // { type: 'customer'|'order'|'thread'|'skill'|'fact_card'|'package'|…, id }
    work_item_id?: string
    conversation_id?: string               // 与会话绑定（定时、认领要用）
  }
  dedupe_key: string                       // §5

  // 人话
  title: string                            // ≤ 80 字，队列里的一行
  summary: string                          // ≤ 300 字，为什么要这么做
  payload: KindPayload                     // §3，按 kind 的判别联合

  // 证据（人看什么来决定）
  evidence: {
    run_id?: string                        // 提议它的运行
    source_events: string[]                // 事件日志 id：客户来信、会议片段、上游发布…
    provenance: { seen: ObjectRef[] }      // 本次运行见过的 id（写类必填）
    diff?: Diff                            // before/after 或段级 diff
    precheck: PrecheckResult               // §6
    citations?: { fact_card_id, quote }[]  // 引用的知识
  }

  // 提议者
  proposer: { kind: 'agent' | 'person' | 'sentinel' | 'registry' | 'system'; id: string; assignment_id?: string }

  // 自动化
  automation: {
    level_at_creation: 'L1' | 'L2' | 'L3'
    auto_approved: boolean                 // 宿主按额度自动写入
    mandate_check: { within: boolean; caps_hit: string[] }
    sampling: { selected: boolean; reviewed?: SamplingReview }   // L2 抽检
  }

  // 路由与时限
  routing: {
    recipients: Recipient[]                // 当前可决定的人（可因升级增加）
    assignee?: person_id                   // 认领后
    explicit?: person_id                   // 原文点名 / 规则指定
    rule: 'role_holder' | 'scope_manager' | 'owner' | 'explicit' | 'unclaimed'
    escalation: { after_hours: number; business_hours: boolean; chain: ('scope_manager' | 'owner')[]; escalated_at: string[] }
    separation_of_duties: boolean          // 提议者不得自批
  }
  priority: 'immediate' | 'queue' | 'digest'   // 来自 NotificationRule.mode
  due_at?: string

  // 状态
  state: State                             // §4
  decision?: Decision                      // §4
  apply?: ApplyRecord                      // §4

  // 投递
  deliveries: Delivery[]                   // §7
  // 关系
  links: { parent?: string; children: string[]; supersedes?: string; superseded_by?: string }
  // 时间
  created_at: string; updated_at: string; expires_at?: string
}
```

字段纪律：`title` / `summary` 是模型写的人话，**数字不经模型手**——金额、日期、id 由 payload 与 evidence 提供，界面从结构化字段渲染，与 title 冲突时以结构化为准（Commerce Agents 的 reconciler）。

## 3. 各 kind 的 payload

| kind | payload 必填 | 备注 |
|---|---|---|
| `outbound_draft` | `channel`（email / whatsapp / meta_dm / social_post …）、`to`（收件人 ref，必须在 provenance 里）、`thread_ref?`、`body`（结构化：subject / text / attachments refs）、`language`、`redaction_preview`（按收件人脱敏后的最终文本）、`children`（随信的 staged_change，如退款） | 发出的是 `decision.edited_payload ?? payload` |
| `staged_change` | `change_id`（账本）、`kind`（refund / price / address / publish_theme / merge_pr …）、`target`、`before`、`after`、`guardrail_notes`、`margin_before_pct?`、`margin_after_pct?`、`mandate_result` | 账本是真源，这里是投影 |
| `staged_action` | `action_id`、`connection`、`input`、`agent_md_excerpt`（该 Action 的 schema 与说明摘要） | 永远 L1，除非该 action_id 单独晋级 |
| `knowledge_update` | `layer`（fact / phrasing / policy）、`op`（add / update / resolve_conflict / retire）、`target_id?`、`content`、`provenance`（文件 + 页码 / 会议片段）、`confidence`、`conflict?`（双值） | policy 层只有 owner 可决 |
| `skill_promotion` | `skill`、`from_tier`、`to_tier`、`sections`（段 id + replace/append/remove + 新内容）、`triggering_evidence`（哪些运行 / 纠正）、`eval_result` | eval 红则 precheck 失败不进队列 |
| `skill_lesson` | `skill`、`section`、`proposed_text`、`lessons[]`（run_id、信号、置信度） | 接受写个人层；忽略即负样本 |
| `claim` | `claim_kind`（action_item / decision / question / data_request）、`text`、`quote`、`source`（meeting / group / email）、`route_confidence`、`due?`、`auto_answer?`（data_request 时 Agent 先算出的结果） | 决定动作是 accept / redirect / not_mine / not_a_thing |
| `policy_change` | `target`（mandate / role / assignment / sod / workspace_policy）、`before`、`after`、`affected_assignments[]` | 只有 owner 可决；Agent 只能"建议"不能"提议生效" |
| `home_suggestion` | `layout_before`、`layout_after`、`reason` | 一天最多一条 |
| `scheduled_task` | `task`（13 §1.3 的 ScheduledTask，state=pending） | 通过即 active |
| `app_*` | `package`、`version_from?`、`version_to`、`permissions_diff`、`connectors_needed`、`simulation_report` | 升级带权限变化必重签 |
| `upstream_upgrade` | `upstream_id`、`from`、`to`、`classification`（seam / breaking / security / wishlist）、`test_results`、`sim_metrics_delta`、`recommendation` | 10 §3.3 |
| `join_mapping` | `role_map[]`、`customer_merges[]`、`connector_transfers[]`、`knowledge_proposals_count` | 03 §7.4 |
| `dev_handoff_result` | `dev_task_id`、`result`（PR / theme_id / artifact）、`test_report`、`preview_url`、`screenshots_before_after` | 通过 → 生成 `staged_change{publish}` 子项 |

## 4. 状态机与决定

```
proposed ─precheck失败─▶ blocked（终态，回提议者）
proposed ─额度内─▶ auto_approved ─▶ applying ─▶ applied | apply_failed
proposed ─路由─▶ pending ─认领─▶ in_review
pending / in_review ─▶ approved | approved_edited | rejected | redirected | deferred | withdrawn | expired | superseded
approved / approved_edited ─（有施行的 kind）▶ applying ─▶ applied | apply_failed
apply_failed ─人处理─▶ pending（重开）| withdrawn
redirected ─▶ pending（新 recipients，revision+1）
deferred ─到时─▶ pending
```

```ts
type Decision = {
  action: 'approve' | 'approve_edited' | 'reject' | 'redirect' | 'defer' | 'withdraw'
  by: person_id | 'mandate'                // 'mandate' = 宿主自动
  at: string
  via: 'workstation' | 'im_card' | 'email' | 'api' | 'batch'
  reason?: string                          // reject / redirect 必填；进负样本
  edited_payload?: KindPayload             // approve_edited 时的最终版本
  edit_diff?: Diff                         // 原稿 vs 最终版，学习信号（强）
  redirect_to?: { person_id?: string; role_id?: string }
  defer_until?: string
  decision_token: string                   // 投递时签发；绑定 (item_id, revision, execution_snapshot)；revision 变化即失效（31 §3.2）
}

type ExecutionSnapshot = {                 // 09-08 新增：批准绑定的不可变执行快照
  hash: string                             // hash(workspace, connection_id, target + record_version, recipients, final_payload, attachments hashes, executor_version, mandate_hash)
  components: Record<string, string>
}

type ApplyRecord = {
  attempts: { at, by_executor, idempotency_key, result: 'ok' | 'failed', error?, execution_id? }[]   // execution_id = OpenConnector 的
  guardrail_rerun: { passed: boolean; caps_hit: string[] }   // 施行时重跑
  outcome_ref?: ObjectRef                  // 发出的消息 id / 已发布主题 id / 合并的 PR
}
```

规则：

1. **通过 ≠ 施行**。`approved` 只是写入 `approved_change_ids` 与批准时的 `execution_snapshot`；施行由执行器发起，先重算快照（任一分量变化 → `snapshot_mismatch` 失败），再重跑**硬禁令**（软额度已被人批准的记 `approved_exception` 不再失败），`Idempotency-Key = change_id`；批准后有取消窗口（默认 2 分钟）；含子退款的回信必须在退款 `applied` 之后发出
2. **谁能决定**：`routing.recipients` 里的人，且其 Assignment 对该 role/domain 有 `approve` 操作；`separation_of_duties=true` 时提议者本人不得决定（个人工作区例外：成员数 1 时自动关闭 SoD，但事件里标 `self_approved`）
3. **无人可决**：路由到 owner 的"未认领"车道；SoD 无人可替时升级 owner 并留痕，不硬阻断
4. **过期**：`expires_at` 默认 = 创建 + 7 天（对外草稿 48 小时，认领 14 天）；过期不施行、记 `expired`、进日报
5. **撤回**：提议者（或其运行的所有者）在 pending 时可撤回；已 approved 不可撤，只能由执行器失败或人工反向变更

## 5. 去重与重复提交

`dedupe_key = hash(workspace_id, kind, subject.object, discriminator)`，`discriminator` 按 kind：`staged_change` 为 `(target, field)`；`outbound_draft` 为 `thread_ref`；`knowledge_update` 为 `target_id ?? normalized(content)`；`skill_*` 为 `(skill, section)`；`claim` 为 `(source, quote_hash)`；`app_*` 为 `package`；`upstream_upgrade` 为 `upstream_id`。

规则：同一 `dedupe_key` 在 `pending / in_review / deferred` 时再次创建 → **更新原项**（payload、evidence、`revision+1`，旧版本进历史），**旧 decision_token 全部失效**，已投递的卡片刷新为"内容已更新，请重新审阅"（31 §3.2），不新开。这是 teamai"更新原 PR 而非重复开"的做法。`approved` 之后再来一条同键 → 新项，`links.supersedes` 指向旧项。

## 6. 预检（创建时自动跑，失败即 blocked）

| 检查 | 对哪些 kind | 失败含义 |
|---|---|---|
| provenance | outbound_draft、staged_change、staged_action | 收件人 / 目标 id 不在本次运行见过的集合里 |
| record-read | staged_change（标 `requires_record_read`） | 改前没读过全记录 |
| guardrail / mandate | staged_change、staged_action、outbound_draft 含子变更 | 超额 → 不是失败，是 `L1` 路由；违反 protected_fields → blocked |
| fencing 覆盖 | 所有含外部文本的 | 外部文本未围栏（这是执行器的 bug，不该到这里） |
| 脱敏预览 | outbound_draft、claim（含 auto_answer） | 生成 `redaction_preview`；含机密字段且接收方无权 → blocked 并说明 |
| 语义 diff | knowledge_update、skill_* | 生成人可读的"改了什么"；空 diff → 不建项 |
| 权限 diff | app_*、policy_change | 生成"多了 / 少了哪些权限" |
| eval | skill_promotion | 目标层 eval 不回归；红则 blocked |
| 模拟 | app_install / app_upgrade / upstream_upgrade | fast 档跑通且指标不劣化；红则 blocked |
| 密钥扫描 | 所有 | payload 里出现 key / 卡号形态 → blocked + 触发 13 §4.3 的安全表单 |

预检结果写进 `evidence.precheck`，界面上是一行绿 / 黄 / 红。

## 7. 投递与回调

```ts
type Delivery = {
  channel: 'workstation' | 'feishu_card' | 'wecom_card' | 'dingtalk_card' | 'email'
  to: person_id
  sent_at: string
  external_id?: string                     // 卡片 message id
  view: 'full' | 'redacted'                // 按接收方权限
  decision_token: string                   // 一次性；回调必须带；用后作废
  status: 'sent' | 'delivered' | 'acted' | 'expired' | 'failed'
}
```

规则：工作台队列**永远**投递；IM 卡片 / 邮件按 NotificationRule；卡片内容按接收方脱敏；**回调只做一件事：带 `decision_token` 调 `POST /approvals/{id}/decide`**，不带业务参数（防篡改）；IM 平台重试同一回调 → 幂等（token 已用 → 返回原结果）；一条项被某人决定后，其他人的卡片刷新为"已由 × 处理"。

升级（`escalation`）= 新增 Delivery 给下一层，不撤销原 recipients；工作时间按工作区 tz。

## 8. 批量与队列视图

- 队列 = 一个人所有 kind 的 pending + in_review，按 `priority` → `due_at` → 等待时长排序；按 `role_id` 打标签；可按 kind / 职责 / 范围过滤
- **批量决定**：同 kind 同 role 可多选一次通过 / 驳回；每条仍单独过预检与额度，单独记 Decision（`via: 'batch'`）；`staged_change` 批量通过时逐条 apply，一条失败不影响其他
- "今天队列预计 X 分钟"= Σ(kind 的平均处理时长 × 数量)，由历史决定时长估算

## 9. 学习信号（每条审批项结束时发出）

| 事件 | 强度 | 去哪 |
|---|---|---|
| approve（未编辑） | 采纳 +1 | Assignment.automation_state[action].adoption.accepted |
| approve_edited + edit_diff | 纠正（强） | 06 §3.4 lesson 池；adoption.edited |
| reject + reason | 负样本（强） | lesson 池；adoption.rejected；guardrail_hit 类触发降级检查 |
| redirect | 路由训练 | 06 §2.4 路由器记忆 |
| L2 抽检 reviewed | 抽检结果 | 采纳率；驳回 → 降级触发 |

> 09-08（31 §3.4）：采纳率是体验指标，**不解锁自动执行**；自动执行由 ChangeKind.risk_class + 结果核验 + 版本指纹决定。
| 决定耗时 | 队列健康 | Agent 健康看板 |

采纳率 = accepted / (accepted + edited + rejected)，按 (assignment, action) 窗口统计，晋级规则在 05 §1.4。

## 10. API（经唯一网关）

| 方法 | 路径 | 谁调 |
|---|---|---|
| POST | `/approvals` | 执行器 / 秘书 / 哨兵 / 市场（内部凭据）；人也可（`kind: policy_change` 等） |
| GET | `/approvals?lane=mine\|scope\|unclaimed&kind=&role=&state=` | 队列 |
| GET | `/approvals/{id}`、`/approvals/{id}/history` | 详情、修订与事件 |
| POST | `/approvals/{id}/decide` | 人 / 卡片回调；body: `{ decision_token, action, reason?, edited_payload?, redirect_to?, defer_until? }` |
| POST | `/approvals/{id}/claim`、`/release` | 认领 / 释放 |
| POST | `/approvals/batch/decide` | 批量 |
| POST | `/approvals/{id}/withdraw` | 提议者 |
| POST | `/approvals/{id}/retry-apply` | 施行失败后 |
| WS | `approval.*` 事件流 | 工作台、投递 provider |

事件（事件日志，`schema_version` 并排）：`approval.created`、`.blocked`、`.routed`、`.delivered`、`.claimed`、`.escalated`、`.decided`、`.auto_approved`、`.sampled`、`.applying`、`.applied`、`.apply_failed`、`.expired`、`.withdrawn`、`.superseded`。凡是回到模型的（如"你的草稿被改成了……"）都以事件形式注入下一轮，满足 Model-visible ⟺ logged。

## 11. 一致性用例（任何实现都要过；替身也要过）

1. 同一 dedupe_key 两次创建 → 一条待审，revision=2，旧 payload 在历史里
2. 无 approve 权限的人调 decide → 403；有权限但 SoD 命中 → 403 并说明
3. 卡片回调重放同一 decision_token → 幂等返回原结果，不产生第二个 Decision
4. approved 后执行器 apply 时额度已收紧 → apply_failed，guardrail_rerun.passed=false，人可见原因
5. 额度内 L2 → auto_approved 仍建项，10% 被 `sampling.selected`
6. 24 工作小时未认领 → 新增 scope_manager 投递，原 recipients 不变；48 小时 → owner
7. 提议者撤回 pending 项 → withdrawn；撤回 approved 项 → 409
8. outbound_draft 收件人不在 provenance → blocked，不进队列
9. approve_edited → edit_diff 非空且 lesson 池收到一条纠正信号
10. 过期项不施行；过期后同键新建为新项且 supersedes 指向旧项
11. 批量通过 5 条 staged_change，第 3 条 apply 失败 → 其余 4 条 applied
