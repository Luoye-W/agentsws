# 开源优先路线修正（取代 31 §2 的完成标准）

| | |
|---|---|
| 日期 | 2026-09-08 |
| 起因 | Luoye 对 31 的回应：不认同"先证明付费闭环"；要做成开源且极有吸引力，把别处收费的东西直接免费开源；要打一个非常痛的痛点；这是平台，之后会有很多 Agent 跑在上面；KefuAgent / KOLAgents 都在内测、没有用户和收入数据；靠开源社群提需求慢慢丰富功能；底层架构先全部敲定以免推翻重来；build in public，每个功能都是内容 |
| 结论 | 商业化不是第一阶段的目标，**采用是**。评审里属于架构与安全的部分全部保留；属于"先收钱"的部分撤回。"底层先敲定"我同意，但要加一个条件（§2） |

## 1. 31 里保留什么、撤回什么

| 31 的内容 | 处理 | 理由 |
|---|---|---|
| F2 权限完整元组、禁 MCP 直读敏感域、空范围拒签、公司端无第三方代码、关系授权门禁 | **保留** | 这是底层，正是"先敲定"要敲定的东西；开源项目被人一发提示注入就没人敢用 |
| F3 批准绑定执行快照、额度预占、unknown 对账、staged_action 关闭 | **保留** | 同上；"Agent 提议、人批准"是我们对外最核心的承诺，必须真的成立 |
| F4 采纳率不解锁自动执行、风险分级 | **保留** | 开源用户第一次被自动退款坑了就是一条负面视频 |
| I15 文档矛盾回写、I10 身份与 GDPR 修正、I11 桌面进程清单收缩 | **保留** | 架构层 |
| F5 Connect 事实（Gmail CASA、Amazon 角色、WhatsApp 不必 BSP） | **保留事实，改结论** | 开源版本来就是"自带账号"：用户自己的 Shopify app、自己的邮箱应用密码、自己的 Meta 应用；我们**不代持**。Connect 作为托管服务的事以后再说 |
| 完成标准 = 5 家付费 | **撤回** | 改为采用指标（§3） |
| 收入线重排、单位经济、ARPU | **撤回为背景资料** | 不进第一阶段目标；07 的商业化整体标"延后" |
| "本地免费是否含 L2/L3"的拍板 | **定案：全部免费** | 你的立场：别处收费的我们免费。开源版 = 全功能，无付费墙 |
| Join / 市场 / DevKit / 哨兵 / 秘书 / 学习晋升移出第一阶段 | **改为分层**：设计全部冻结（已写在 14–29），**实现按切片推进**；哪个先做由社群需求和内容节奏定 | 见 §2 |
| 三个 SaaS 的接入 | **降为"把它们的能力搬进开源版"**，而不是"作为付费应用并入" | 它们没有用户；把 KefuAgent 的邮箱接管与 KOLAgents 的插件采集直接做成开源职责包，比维护三条 SaaS 线更省力且更有吸引力 |

## 2. "底层先敲定"的正确做法：接口冻结，实现按切片

推翻重来的真实原因不是"契约没写够"，而是"契约写完没被真实使用验证过"——18 份契约里任何一份第一次接真账号都会改。所以：

| 层 | 状态 | 做法 |
|---|---|---|
| **接口层**（18 份契约的类型、事件、错误码、不变量） | **现在冻结**（14–29 已是 v1，31 的安全修正已并入） | 之后只允许加字段、加 kind，不允许改语义；改语义 = 升 major + 迁移器 |
| **实现层** | 按纵切片推进 | 每个切片只实现它碰到的契约；未碰到的契约有替身实现，让一致性套件一直绿 |
| **验证层** | 模拟回路（不变量）+ 一条真实切片（真账号） | 真切片是契约的"验收"，不是商业验收 |

这样既满足"底层先敲定"（接口不再动），又避免"没真实使用就冻结实现"。

## 3. 第一阶段（开源发布版）的目标与完成标准

**目标**：一个非技术人员 10 分钟装好、当天就用上、愿意发朋友圈的开源本地中台。

**完成标准（采用指标，非收入）**：

| 指标 | 说明 |
|---|---|
| 安装到首个成功工作项 | 中位数 ≤ 15 分钟（真实用户，非我们自己） |
| 7 天留存 | 装了之后第 7 天还在用的工作区比例 |
| 30 天活跃工作区数 | 开源发布后第一个月 |
| 社群提需求数 / 被采纳数 | 需求进入公开 roadmap 的数量 |
| 每周可发布的内容 | build in public 的产出节奏 |
| 安全事故 | 0（提示注入、误发、误退款） |

**"别处收费、我们免费开源"的清单**（写进 README 首屏）：

| 别处 | 我们 |
|---|---|
| 客服 AI 按席位收费（Gorgias / Zendesk / Intercom Fin） | 客服职责包免费，本地跑，自带模型 key |
| 连接器平台按连接数收费（Composio / Pipedream） | OpenConnector 本地 runtime，1000+ provider，自带账号 |
| 红人数据按条收费 | 浏览器插件采集 + 本地红人库免费（KOLAgents 的能力搬过来） |
| 会议 bot / 纪要按分钟收费 | 本地转写 + 提议管道免费（秘书 Agent，晚一点） |
| 审批工作流是企业版功能 | 统一审批队列免费 |
| 公司知识库是企业版功能 | 带权限的知识库免费 |
| 多店铺 / 部门 / SSO 是企业版功能 | 全免费 |

## 4. 痛点：钩子选哪一个

要求：非技术人员一看就懂、每天都碰、现在花钱或花大量时间、能做成 60 秒视频。三个候选：

| 候选 | 痛在哪 | 视频画面 | 风险 |
|---|---|---|---|
| **A · 英文客服邮件全接管** | 每天几十封英文客户邮件，时差，退换货规则记不住，现有工具按席位收费还要上传客户数据 | 客户来信 → 3 秒出草稿（引用店铺政策、订单状态）→ 一键批准 → 发出；退款作为一张待批卡 | 需要真实 Shopify + 邮箱；安全模型要先到位（正好是我们做好的） |
| B · 红人一键建联 | 翻主页、抄数据、找邮箱、贴表格，KOLAgents 已验证是体力活 | 插件在红人主页点一下 → 入库 → 开发信草稿 → 批准发出 | 邮箱找不到时价值骤降；社媒平台 OAuth 审核 |
| C · 会议 / 群聊自动变待办 | 开完会没人记、群里说的事没人接 | 会议结束 → 各人队列里出现认领项 | 隐私与组织政治（评审 I13）；需要会议 bot |

**我的建议：A 为钩子，B 为第二个月的内容，C 放到社群要求时。** 理由：A 最高频、最普适（每家独立站都有）、现有替代品明确收费、演示画面最直观；而且它逼我们把审批队列、变更账本、关系授权门禁这些底层一次做扎实——第一条视频的"Agent 提议退款、人点一下"就是平台理念的完整表达。

## 5.1 实现顺序：先把框架"搭起来"，再用切片把替身换成真实现（09-08 补）

"起点是从 KefuAgent 抽共享包"是表述不当。顺序是：

| 步 | 做什么 | "搭起来"的含义 |
|---|---|---|
| 1a 框架骨架 | 内核（Cordis、事件日志、API、急停）+ **18 份契约的接口与替身实现** + 模拟回路 fast 档 | 一条假的端到端场景在全替身下跑通、不变量全绿——此时框架**在接口层面已全部搭起来** |
| 1b 切片替换 | 按客服切片需要的顺序，把替身逐个换成真实现：交易控制模块 → 运行协议（dsh-adapter、direct-llm）→ 邮件渠道 → Shopify（OpenConnector）→ 知识 → 模型网关 → 工作台最小版 → Electron 壳 | 每换一个，一致性套件与模拟仍绿 |
| 1c 业务载荷 | 客服职责包：从 KefuAgent 抽出分类、起草、知识引导、customer-care skill 成共享包，装进 1b 的框架 | 与 1b 并行，因为它决定契约字段哪些是真的 |
| 1d 真账号验收 | 真实邮箱 + 真实测试店跑通第一封信 | 契约的验收 |

之所以不"先把 18 个契约全部实现完再做功能"：没被真实切片碰过的实现一定会改，那才是推翻重来；接口冻结 + 替身 + 模拟让"框架全部搭起来"在 1a 就成立，而实现的顺序由切片决定。

## 6. build in public 的里程碑（每个都是一条内容）

1. 架构图与 18 份契约开源（"我们怎么设计一个不会推翻重来的 Agent 中台"）
2. 模拟回路：一家虚拟 3 人公司跑完一天，事件日志重组 prompt
3. 第一封客户来信 → 草稿 → 批准 → 发出（真账号）
4. 退款作为待批卡：提示注入攻击演示 + 被门禁拦下
5. 拖一份 FAQ，回复开始引用政策
6. 一键安装包：非技术人员 10 分钟上手
7. 开源发布 + 首个社群需求进 roadmap
8. 红人插件采集 → 建联草稿（钩子 B）
9. 第一个社群贡献的职责包装上就能用
