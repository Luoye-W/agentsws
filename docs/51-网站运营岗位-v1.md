## 0. 一句话

**先在账户设置里选平台，再决定这个岗位能连什么、能做什么。** 网站运营四条职责的"读"全走平台只读动作，"写"全走 staged change → guardrail → 审批 → apply（15 的老规矩）；额度按**动作**分，不按子领域分。Shopify 现在就能做（35 条写动作已在对照表里），WooCommerce 是下一个（连接器里已有 provider），Magento 没有 provider、先灰显。

## 1. 前置：网站平台选择（N0）

| 项 | 做法 |
|---|---|
| 存哪 | 公司档案（46）加 `storefront_platform: 'shopify' \| 'woocommerce' \| 'magento' \| 'other'`，首次设置第 ① 步就问（和"你卖的是"并排），设置页可改 |
| 现在支持 | **只有 Shopify**。其它选项灰显并标"待增加"；选了"other"= 没有店铺连接，网站运营岗位只剩内容与博客里不依赖平台的部分 |
| 它影响什么 | ① 连接页只显示该平台的店铺卡；② 职责模板里的 `connectors[]` 按平台解析（`shopify_admin` / `woocommerce` / …），动作对照表（43 §2）按平台一份；③ 岗位面板的"店铺后台"分块按平台取数；④ 登记表（47）里对象的真源标注按平台 |
| 下一个平台 | WooCommerce：OpenConnector 已有 provider，做一份动作对照表 + 一套读动作映射即可；Magento：连接器没有 provider，要先写 provider，排在后面 |
| 不做 | 一个工作区多平台并存（一家公司同时 Shopify + WooCommerce）——用两个工作区或等 44 的范围模型加"平台"一维时再议 |

## 2. 岗位"网站运营"= 四条职责（N1）

岗位模板默认四条全勾，可去勾；范围（44）挂店铺 / 品牌 / 产品线照旧。旧 `dtc.ops`（15 人 pack）→ `dtc.store` 别名迁移；04 §1 旧的十条职责按下表归并。

### 2.1 店铺管理 `dtc.store`

一条职责、五个能力面，**额度按动作分**：

| 能力面 | 读（只读动作） | 写（staged change → 审批） | 额度 / 自动化上限 |
|---|---|---|---|
| 店铺设置 | 店铺信息、政策页、运费 / 税 / 支付设置、导航、主题列表 | 政策页 / 页面改动 `listing_edit`；主题发布 `publish_theme`（43：走官方 CLI，未发布副本预览） | 页面 L2；主题发布 **永远 L1**；结账 / 支付 / 税这类设置 **不给写动作**（人在后台改） |
| 商品管理 | 商品、变体、库存、集合、元字段 | `listing_edit`（文案 / 图 / SEO）、`price_change`、`publish_product` / `unpublish_product`、集合增删商品、库存 `set` / `adjust` | 文案 L2；改价 ≤ `max_price_delta_pct`（默认 20%）L2、超额 L1；上下架 L1；库存调整 ≤ `max_inventory_adjust`（默认 50 件）L2，直接设定 L1 |
| 促销与折扣 | 折扣码、自动折扣、活动列表 | `discount_code`（营销发码，与客服的安抚发码分账）、`promotion`（自动折扣 / 活动） | 单码 ≤ `max_promo_discount_pct`（默认 30%）且限量 L2；全站活动 / 无上限码 L1 |
| 数据日报 | 销售 / 订单 / 转化 / 流量（Shopify + GA4 + GSC） | 无写；出"日报卡"与"异常卡" | L3 |
| 评价管理 | 评价列表、评分（经评价应用连接器：Judge.me / Loox，**待增加**） | 回复评价（草稿）、邀评 | 回复 L2；差评处理转客服 `dtc.support`；邀评 L2 且合规词表 |

- **guardrail**（15）：`target_in_range`（44）、`price_change` 幅度、`publish_*` 永远人审、活动级促销永远人审；Amazon 那套出站硬闸不适用。
- **面板积木**（36）：数字块：总销售额、订单数、转化率、库存告急数；分块：店铺后台（已有四块）、待审改动（listing / 价 / 上下架 / 促销各一条车道）、库存告急表、差评表、日报卡。
- **卡片**：改价 / 上下架 / 促销 / 主题发布的 staged change 卡（14 四段式已有）、日报卡（L3 自动，看完即归档）、异常卡（销售骤降 / 库存断货 / 转化异常）。

### 2.2 内容与博客 `dtc.content`

| 项 | 内容 |
|---|---|
| 干什么 | 博客文章、独立页面（FAQ / 关于 / 活动页）、页面 SEO 元字段；图片素材向设计岗（待做）下需求单 |
| 读 | 文章 / 页面列表与正文、SEO 字段、知识库（19：内容可以引用事实卡，但不能编数字） |
| 写 | `publish_post`（新建 / 更新草稿 L2；**发布 L1**）、页面 `listing_edit`（L2）、SEO 元字段 `set_metafields`（L2） |
| 额度 | 每日发布上限 `max_posts_per_day`（默认 2）；发布永远人审 |
| 面板 | 草稿队列、待发布、近 30 天发布与流量（GSC） |
| 现有底子 | Shopify `create_page / update_page / create_article / update_article / set_metafields` 已在写动作对照表；`publish_post` 已是 ChangeKind |

| 项 | 内容 |

## 3. 不做什么（N2）

- 不给结账 / 支付 / 税 / 域名这类"改一下就影响收款"的设置写动作，人在平台后台改。
- 不做一个工作区多平台。
- 评价、邮件营销、物流、3PL 的连接器按"待增加"排队，本期只把职责、动作、额度、面板骨架立起来；连接器不在，面板明说"还没连"（36 §3 的老规矩）。

## 4. 模拟（N3）

3 人 pack 加三条、15 人 pack 加两条，三运行时：
- `store/price-change-over-cap`：运营 Agent 改价超 20% → L1 人审 → 批准 → apply 经 mock connect（15 人 pack 已有改价场景，补"超额"分支）
- `store/publish-product-needs-approval`：上架永远人审
- `content/blog-draft-then-publish`：草稿 L2 自动、发布 L1
- `fulfillment/overdue-alert-and-fulfill`：超期未发出异常卡 → 标记发货 L2
- `store/daily-report-card`：日报卡 L3 自动出、看完归档
